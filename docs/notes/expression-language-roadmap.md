# 式言語の表現力 — 段階整理とマイルストーン対応付け（仮説）

## このノートの位置づけ

**意思決定ではなく、仮説・要求整理のレベルのメモ。** 「将来 `.ui` に
書ける式・文をどこまで強化するか」を段階に分け、各段階が既存マイルストーン
（[`_roadmap.md`](../../process/_roadmap.md)）のどこに対応しそうかを **仮説として**
並べる。確定はしない。実際の線引きは、その機能が必要になったマイルストーンが
来た時点で ADR で判断する。

関連する論点は既に別ノートに断片として存在する。本ノートはそれらを
**横断して見渡すための地図**であり、各論の正本ではない:

- 値の持ち方（`TypedValue` 汎用値ユニオン）→
  [`typed-value-evaluator.md`](./typed-value-evaluator.md)
- 演算子を入れる文法拡張（uniform expression grammar extension）→
  [`dsl-grammar.md`](./dsl-grammar.md) Q3 / Q5
- 構造化された要素型（`item.filename` など）→
  [`dsl-grammar.md`](./dsl-grammar.md) Q8

---

## 出発点の問い

将来像として、Slint を参考に `.ui` の式・文を強化するなら **どの程度の
表現力**が要るか。そして、その場合 **仮想マシン（VM）のような処理系**が
あったほうが筋が良いか。

現状（M3 時点）の `.ui` は意図的に「演算子ゼロ」である
（[`dsl_spec.md`](../dsl_spec.md) §4.6）。より正確には、**プロパティ束縛と
`if` 条件の式**はリテラルと変数参照だけで演算子を持たず、**handler の文**は
代入が中心（ただし handler の右辺にはコレクション操作
`append` / `drop-last` / リストリテラルがある）。一方で **構造制御**
（`if` / `for`）と **リアクティブ基盤**（値が変われば画面が自動更新される
仕組み）は既にある。

Slint の表現力は「際限なく自由な言語」ではなく、**範囲を限定した純粋な
リアクティブ式言語 + 限定的な命令文**で止まっている（一般ループなし・
再帰なし・ループは構造の `for` だけ）。この到達範囲を 5 段階に分けて整理する。

---

## 表現力の 5 段階（ユーザ視点で何ができるようになるか）

各段階は「文法全体の能力」であり、どの束縛位置でも同じものが書けるようになる
（spec の「式文法は全位置で一斉に育つ」前提に従う）。いずれの段階も
**一般ループなし・再帰なし**を共通の前提とする。

| 段階 | 平たく言うと | 具体例 | 何が増えるか（内部） |
|---|---|---|---|
| **M-expr1 述語サーフェス** | **条件が書ける** | `if 枚数 > 0`、`if 準備できてない`、`A かつ B` | 比較・論理・否定。結果は真偽だけ。新しい値の持ち方は不要 |
| **M-expr2 計算束縛サーフェス** | **値を計算できる** | `"\{labels[current]}"`、`枚数 + 1`、`幅 = 枚数 × 10px` | 値を生む式（算術・文字列連結・三項・要素アクセス）。**軽い側と重い側の 2 つ（2a / 2b、下記）に分かれる** |
| **M-expr3 構造化データサーフェス** | **データをまとめて持てる** | 「1枚 = 番号 + キャプション + 比率」を1つのまとまりで | struct 型・メンバアクセス。並行配列の解消 |
| **M-expr4 ロジック命名サーフェス** | **処理に名前を付けて再利用** | よく使う計算や、ボタン押下時の複数手順・分岐に名前を付ける | 関数定義・命令文（分岐・呼び出し） |
| **M-expr5 連動・状態・動き** | **双方向同期 / 状態切替 / アニメ** | 入力欄と変数の双方向同期、状態に応じた見た目、アニメ | 式・文ではなく UI の「振る舞いエンジン」 |

### 各段階の境目で何が起きるか

- **M-expr1 は最小で効果が大きい。** 今いちばん不便なのは「`if` の条件に
  真偽の変数 1 個しか置けない」こと。M-expr1 は結果が真偽に閉じるので、
  既存の真偽位置（`if` 条件・`Button.selected`/`enabled`）でそのまま使える。
  **値の持ち方を変えない**ので影響が小さい。
- **M-expr2 で性質が大きく変わる。** ここで束縛が「変数を映す」から
  「値を計算する」に変わる。ただし段階の中に **軽い側（2a）と重い側（2b）**が
  あり、`TypedValue` 汎用値ユニオン（M3 の A9 が明示的に繰延）を導入するのは
  **2b** のほうである。
- **M-expr3 は型システムの仕事。** gallery が今「サムネ番号の配列」と
  「キャプションの配列」を別々に持っている（ズレやすい）のを、1 つの
  まとまりにする。値モデル拡張なので **2b と一体で扱う**。
- **M-expr4 で初めて「処理系/VM」の問いが現実になる**（下記参照）。
- **M-expr5 は式・文の範囲外**で、UI の振る舞い機構の話。

### M-expr2 の内訳:2a（軽量）/ 2b（`TypedValue`）

M-expr2 は「式が値を生む」段階だが、その値が **既存スカラ型に収まるか**で
2 つに分かれる。この区別は対応付け（どこを pre-1.0 必須にするか）で重要になる。

| サブ段階 | 内容 | 結果の型 | `TypedValue` | 例 |
|---|---|---|---|---|
| **M-expr2a 既存スカラ値生成** | 要素アクセス `xs[i]`、既存スカラ同士の算術・連結・三項で、結果が `i32`/`string`/`bool` に収まるもの | 既存スカラに収まる | **導入しない** | `labels[current]`（string）、`index + 1`（i32）、`"S" + label`（string） |
| **M-expr2b 一般計算束縛** | 結果が新しい種類の値（色・寸法など）になる、または式が任意型の値を運ぶ評価モデルの一般化 | 新しい種類の値を含む | **導入する** | `幅 = 枚数 × 10px`（寸法）、計算した色 |

ポイント:

- **2a は評価器に「値を返す式」能力を足すが、値の種類は増やさない。** よって
  `TypedValue` ユニオンを要さず、ABI 表面への影響も小さい。M-expr1 のすぐ上の
  軽い拡張として、独立した新規マイルストーンを立てずに前倒しできる余地がある。
- **2b が `TypedValue` を導入する重い側**で、値モデルが横断的に変わる。
  pre-1.0 必須の議論（下記）は **本来 2b/3 の話**であり、2a までは含まない。
- gallery のユースケース（[`gallery-expression-use-cases.md`](../../process/milestone-3/requirements/gallery-expression-use-cases.md)）
  で言うと、`labels[current]` のラベル切替や並列スカラ配列引きは **2a** で
  表現でき、寸法・色の計算や struct は **2b/3** に上がる。

## 既存マイルストーンへの対応付け（仮説）

確定ではない。「自然に置くならどこか」の **仮説**。

| 段階 | 仮説の対応先 | なぜそこか（必要とする既存要件） |
|---|---|---|
| **M-expr1 述語** | **M4 の早い時期**（または M3 の小さな後続） | M4 の interaction が `enabled: フォームが妥当` のような述語を必要とする。`TypedValue` を入れない（A9 の繰延範囲の内側）ので低リスク。独立マイルストーンにするほどではない |
| **M-expr2a 既存スカラ値生成** | **M-expr1 の近く（M4 周辺の軽い拡張）** | `TypedValue` を入れない（既存スカラに収まる）ので ABI への影響が小さい。独立した新規マイルストーンを立てるほどではない |
| **M-expr2b 一般計算束縛** | **新規 pre-1.0 マイルストーン（M4 と M5 の間が自然）** | `TypedValue` を導入＝値の持ち方が横断的に変わり **ABI に影響しうる**。M6 の ABI freeze 前に置く必要 |
| **M-expr3 構造化データ** | **同上（M-expr2b と同じマイルストーンに同梱）** | データ駆動 UI・並行配列の解消。値モデル拡張なので 2b と一体 |
| **M-expr4 ロジック命名** | **pre-1.0 の末、または post-1.0** | 主に runtime 内部の話で ABI への影響が小さい。showcase が必要とすれば前倒し |
| **M-expr5** | **3 分割** — 双方向束縛→**M4** / states・transitions→**M5** / アニメ→**post-1.0** | TextField（M4）が双方向束縛の典型、theming（M5）が状態切替を必要とする、アニメは roadmap に既存項目（post-1.0 の higher-level animation DSL）がある |

### この対応付けの 2 つの要点

1. **M-expr5 は一塊ではなく、自然に既存マイルストーンへ分かれる。** 双方向束縛は
   M4 の TextField が、状態切替は M5 の theming が、アニメは post-1.0 が
   既に必要としている。新規の置き場所はほぼ要らない。
2. **新規マイルストーンを立てる必要があるのは実質 M-expr2b/3 だけ**（2a は
   軽量で前倒し可）。根拠はプロジェクト自身の前例に沿う:multi-window は
   「ABI への影響が横断的で、freeze 後の append-only サーフェスでは吸収できない
   から **pre-1.0 に前倒し**」とされている（[`_roadmap.md`](../../process/_roadmap.md) M4）。
   `TypedValue` 導入（2b）は同じ性質なので、同じ理屈で **pre-1.0 の独立
   マイルストーン**に置くのが整合的。

## 評価機構（VM）の問いとの関係

出発点の「VM が筋か」への現時点の読み:

- **Slint 級の表現力に VM は要らない。** Slint 自身がバイトコード VM を使わず、
  AOT パスは Rust/C++ コード生成、インタプリタパスは式ツリーの tree-walk。
  リアクティブ UI で重いのは命令の実行速度ではなく依存グラフ管理で、そこは
  Wasamo に既にある（`Signal<T>`）。
- **VM の問いが現実になるのは M-expr4**（呼び出しフレーム・文の逐次実行という
  「コードのモデル」が初めて入る段階）。M-expr1〜3 の範囲では一貫して
  **tree-walk リアクティブ評価器**で足りる。
- VM（バイトコード）は「表現力の手段」ではなく **「IR の符号化形式」の将来
  オプション**として切り離して扱うのが筋。Wasamo の IR は既に
  `wasamoc → runtime`、さらに C/Zig/Rust ホストが消費する **ABI 境界**なので、
  式を安定した命令列で符号化する利点は *serialization の観点* にあって、
  *表現力の前提条件* ではない。
- つまり、評価機構の判断（＝別途検討する「(b)」）を詰める必要が出るのは
  **M-expr4 に着手する判断をした時点**。それ以前の段階では選択肢は tree-walk
  一択。

## 未解決の中心論点

段階ごとの置き場所のうち、M-expr1 / 2a / 4 / 5 は既存マイルストーンに割り当て
られるので、実質の意思決定は 1 点に集約される:

> **`TypedValue` を導入する M-expr2b/3 を、ABI freeze 前のどこに独立
> マイルストーンとして挿すか。**（2a は軽量で、この判断には含めない）

その前提として事前の確認が要る:

> **M-expr2b の `TypedValue` は本当に C ABI 表面に影響するか**
> （ホストが計算済み値を set/get するか）。
> 影響するなら「pre-1.0 必須」で確定。しないなら post-1.0 もあり得て、
> M5 を圧迫しない。`abi_spec.md` で確認してから挿入位置を確定するのが安全。

## 再訪契機

- M4 の interaction 設計で `enabled: <述語>` が必要になった時 → M-expr1 を
  M4 に正式に組み込むか判断する。
- 要素アクセスや既存スカラの算術が具体的なアプリ事例として出た時（結果が
  既存スカラに収まる）→ **M-expr2a** を M-expr1 近くの軽い拡張として検討する。
- 新しい種類の値（色・寸法）・structured item field（`item.filename` 等）が
  具体的なアプリ事例として出た時 → **M-expr2b/3** と `TypedValue` を一体で開く
  （正本は [`typed-value-evaluator.md`](./typed-value-evaluator.md) 再評価トリガ、
  [`dsl-grammar.md`](./dsl-grammar.md) Q8）。
- M4 の TextField で双方向束縛が必要になった時 → M-expr5 の双方向束縛部分を
  M4 で開く。
- 関数定義や分岐付きハンドラ本体が必要になった時 → M-expr4 に着手する判断と
  同時に、評価機構（tree-walk / VM）の検討（(b)）を起こす。
- M-expr2b（`TypedValue`）の ABI への影響の有無が `abi_spec.md` で確定した時 →
  本ノートの「中心論点」を更新し、必要なら挿入位置を ADR 化する。
