M3 target app — wireframe 候補

M3 target app 候補を選定するための exploratory artifact。 Grid / ScrollView / List では済まない layout 要求を出す desktop app の wireframe 4 案を示し、 (i) 各案が必要とする surface とその代替可否を整理し、 (ii) m3-start-framing.md に照らした 5 つの判断軸で候補を比較する。 入力可能な widget は M2 surface（Text, Button）+ 視覚 placeholder のみで成立する範囲に留めている。 本ファイルは合意成果物ではなく、最終的な選定理由・out-of-scope・spec 同期ルールは 候補確定後に起こす target app pre-doc（markdown）で明文化する。 赤丸数字は ui-layoutsystem.md 表のうち各案が要求する surface 概念への参照番号。

案 X — Mail Reader 3-pane viewer

フォルダ｜メッセージ一覧｜本文 preview の 3-pane。Dock chrome（top toolbar / bottom status）+ SplitView × 2 + 多重 List + 本文末尾の WrapPanel タグ列。 desktop メール clientの最も普及した形。

要求される layout surface

  • ① DockPanel 相当（top toolbar / bottom status の edge dock）
  • ② SplitView × 2（folder/list, list/body のリサイズ）
  • ③ List × 2（folder, message。message 側は from / subject / preview / time の 多フィールド item template）
  • ④ ScrollView × 3（folder, list, body の独立 viewport）
  • ⑤ WrapPanel（タグ chip 列、折り返し）
  • Separator / Divider（本文区切り線）

bindings / state

  • selected_folder → message list を filter
  • selected_message → body pane の全フィールドに分配
  • item template が message.from / subject / preview / time を同時参照
  • tag chips は selected_message.tags[] の繰り返し（message list の繰り返しとは並列、ネストではない）

案 Y — Music Player now-playing + queue

左に playlist sidebar、中央上に now-playing（album art 正方形 + コントロール）、 中央下に再生 queue。AspectRatio と ZStack overlay が必然的に登場する。

要求される layout surface

  • ① AspectRatio コンテナ（album art の 1:1 固定）
  • ① ZStack（art 上に再生インジケータを重ねる）
  • ② SplitView（now-playing と queue の縦分割。水平方向）+ sidebar との垂直分割
  • ③ List + ScrollView（queue）
  • Sidebar の List（playlists、selectable）
  • Card 相当のグループ化（now-playing 領域の視覚枠）

bindings / state

  • current_track（i32 index）→ now-playing 各フィールド
  • progress_sec（i32）→ progress bar 幅
  • is_playing → 再生ボタンの表示切替
  • queue items: track.title / artist / duration
  • i32 / String binding のみで成立（M2 surface の延長）

案 Z — Photo Gallery thumbnail grid + lightbox

WrapPanel の thumbnail 配列と、選択時に画面全体にかぶせる lightbox overlay。 WrapPanel と AspectRatio と ZStack を中心要件にできる。

要求される layout surface

  • ① WrapPanel / Flow（thumbnail の auto-wrap、viewport 幅依存の order）
  • ② AspectRatio（thumbnail 正方形、lightbox 写真の比率固定）
  • ③ ZStack（画面全体に dim scrim + 中央 image + ナビ ボタン）
  • ScrollView（thumbnail grid の縦 overflow）
  • 繰り返し生成（thumbnail items）
  • Tabs（top chrome の view 切替）

bindings / state

  • selected_id（i32, -1 で lightbox 非表示）→ overlay 表示制御
  • state 切替で同一画面に 2 つの構造（grid / lightbox）が共存 → ZStack の必然性
  • thumbnails: photo.id / thumb_color / caption
  • conditional rendering（if selected_id >= 0 { lightbox }）の DSL 表現が必要

案 W — File Explorer 2-pane file manager

Toolbar + breadcrumb + sidebar + 多列 detail list + status bar。 List の各 item template の内部が Grid の 3 列揃え（Name | Size | Modified）になっており、 layout primitive の入れ子 が thesis の中心になる。

要求される layout surface

  • ① DockPanel（toolbar / breadcrumb / status bar の edge dock）
  • ② List 内 item template に Grid（3 列）。layout primitive の入れ子が thesis の中心
  • ③ Breadcrumb（HStack + 折り返し / WrapPanel 弱要求）
  • ④ SplitView（sidebar / main）
  • ScrollView（main list の縦 overflow）
  • Sidebar 内 List + section header（Quick access / Drives）
  • view 切替で WrapPanel（icon view）への分岐も視野に入る

bindings / state

  • current_path（String）→ breadcrumb segments、main list の seed
  • selected_id → row 強調
  • item: file.name / size / modified / is_dir（複数フィールド + conditional display）
  • view_mode（i32 or enum 相当）で main 領域の primitive を切替

判断材料 — 必要 surface とその代替可否

本節は候補ごとに「何が必要か」を整理する input レイヤーである。 比較軸は layout primitive（layout-engine が解く問題：配置 / overflow / 重ね / 比率固定 等）。 Sidebar / Tabs / Breadcrumb / Toolbar 等の composed widget（名前付き UI 部品）は本節後半で別途比較する。 候補選定そのもの（thesis / framing に照らした判断）は次節「判断軸 — 候補選定の 5 軸」で扱う。

概念の語彙と機能の批判的検討

比較表に挙げる概念について、語彙の出典 / 機能 / 既存 primitive での代替可否 / M3 AC への含意 を整理する。 「追加検討が必要」と見える surface のいくつかは Grid star sizing や属性化で済むことが、ここでの整理から見えてくる。

Grid
機能: 行と列で 2 次元の格子状にレイアウト。セルサイズは絶対値（px）/ 比率（* / fr）/ 内容依存（auto）から選ぶ。
語彙の出典: 全フレームワーク横断（XAML / WPF, MUI, Compose, Slint, QML, CSS Grid）— 名前のばらつきが最も小さい primitive。
批判的検討: 単一行 / 単一列で使えば実質的に Stack (V/H) を兼ねる。star sizing を持てば後述の Dock / Split / ZStack の多くを代替できる「土台 primitive」。
M3 AC との関係: 既存 AC 候補。star sizing を含むかは spec で明示する論点。
ScrollView
機能: 子要素を viewport にクリップし、超過分をスクロール操作で露出する。
語彙の出典: 全フレームワーク共通（ScrollViewer / ScrollView / ScrollArea）。
批判的検討: 独立性が最も高い。viewport / clipping を扱う唯一の primitive で、他で代替できない。
M3 AC との関係: 既存 AC 候補。
List
機能: 配列データから item template を介して N 個の子を生成し、選択管理と仮想化を伴って表示する。
語彙の出典: List (SwiftUI), ListView (XAML / QML), LazyColumn (Compose)。「item template」は XAML / QML 語彙。
批判的検討: 単なる繰り返しは「要素の繰り返し生成」だけで足りる。List 独自の付加価値は (i) 選択状態管理 (ii) 仮想化の 2 点。ROADMAP 末尾で LazyList が post-1.0 として分離されているので、M3 の List は仮想化を含まない可能性が高い。とすると M3 の "List" は実質「選択管理付き 繰り返し生成 + ScrollView」に縮約され、独立 primitive と呼ぶべきか議論の余地がある。
M3 AC との関係: 既存 AC 候補。仮想化を含むかは spec で明示する論点。
要素の繰り返し生成
(Repeater / ForEach / map / for-in)
機能: コレクションを反復して N 個の子要素を生成する。選択 / 仮想化を持たない汎用反復。
語彙の出典: 各フレームワークで実装方式が異なる：
  • container 型 primitive — Repeater (Qt QML), ItemsControl (XAML / WPF)
  • View ラッパー型 — ForEach (SwiftUI)。View に見えるが Range/Collection を取る構文的ラッパー
  • 言語キーワード / テンプレート構文型 — for in (Slint), {#each} (Svelte), v-for (Vue)
  • ホスト言語 loop — .map() (React / shadcn / MUI)。JSX が JS 式なのでそのまま動く
批判的検討: Wasamo の DSL は自前言語（ホスト言語に埋め込まれていない）ので、設計選択肢は 三択：
  1. 独立 primitive（container 型）として切り出す。QML / XAML 流儀。新 IR ノード + runtime container + spec 章が要る。合成しやすいが primitive 数が増える。
  2. DSL 構文要素（loop + template）として組み込む。Slint for in 流儀。wasamoc の grammar 拡張と IR 上の child-generation 表現が要る。primitive 数は増えないが、DSL 構文が「宣言的木」から「制御フロー含み」へ広がる。M2 で統一した HandlerExpr がここに干渉しうるかも論点。
  3. List の subset として吸収。M3 AC の List 1 つだけで全反復を賄う。最小 primitive 数だが、Grid セル / WrapPanel 子 / breadcrumb segments を「List」と呼ばせる無理が出る。表現力上の歪みが大きい。
ui-layoutsystem 表の分布で見ると、Web 系（React / Vue / Svelte）は何らかの構文型、XAML / QML は container 型、Slint / SwiftUI はその中間（言語側の宣言形）に置かれる。Wasamo はどの流儀でも採れるが、(2) を採ると spec の「文法」と「木構造」の境界が動く 点が M3 DSL spec 公開判断に直接効く。
M3 AC との関係: 既存 AC では List の内訳として暗黙化されている。target app 決定後に上記三択を明示的に選ぶ判断が要る。(3) を取らない限り、何らかの形で AC か spec の射程に入る。
DockPanel
機能: 親要素の上下左右の端に子要素を順次吸着し、最後の子要素が残り中央領域を占める。
語彙の出典: DockPanel (XAML / WPF)。機能的に近いのは Compose の Scaffold（ただし Scaffold は composed widget）。
批判的検討: toolbar / 中央 / statusbar の 3-edge 構造は Grid (auto / * / auto) で素直に表現できる。4-edge（上下左右 + 中央）も Grid の入れ子で書ける。XAML 自身が Grid と DockPanel の両方を持つが、現代の WinUI / WPF コードでも Grid が主流で DockPanel は legacy 寄り。4 案いずれも chrome は Grid star sizing で構成可能。
M3 AC との関係: Grid star sizing で代替可能。独立 primitive として追加するかは target app 決定後の判断。
SplitView (resizable)
機能: 隣接する 2 (以上) の領域の境界をユーザーがドラッグして、領域比率を再分配する。
語彙の出典: SplitView (WinUI / QML), HSplitView/VSplitView (SwiftUI), Resizable (shadcn), GridSplitter (XAML / WPF)。
批判的検討: WPF の GridSplitter が示すように、SplitView = Grid + Splitter widget（ドラッグで Grid の star ratio を mutate するもの）として因数分解できる。container 自体は Grid のままで、Splitter を子要素として追加すれば十分。M3 surface としては「独立 container」か「Grid + Splitter widget」かの 2 通りの捉え方がある。
M3 AC との関係: Splitter widget として組み込む形が筋。ただし widget 追加は drag interaction を伴うので、M3 が drag を扱うかは別議論として残る論点。
WrapPanel / Flow
機能: 子要素を主軸方向に並べ、viewport の主軸サイズを超えたら副軸方向の次行に折り返す。
語彙の出典: WrapPanel (XAML), Flow (Qt QML), FlowRow / FlowColumn (Compose), flex-wrap (CSS)。XAML と QML が独立に同じ名前を持たない点が珍しい primitive。
批判的検討: Grid では代替不可。Grid は列数 / 行数が事前定義されるが、WrapPanel は viewport 幅で動的に列数が決まる。layout-engine に「viewport 幅依存の measure → wrap → arrange」のロジックを新規追加する必要がある。代替不能性の意味で独立 primitive として扱う動機が最も強い。
M3 AC との関係: 既存 AC 外。target app が要求するなら追加候補。
ZStack / Overlay
機能: 子要素を同一座標空間に z 順で重ねる。子要素間で位置を押し合わない。
語彙の出典: ZStack (SwiftUI), Box (Compose), z-index (CSS)。XAML には専用 primitive がなく、Grid の同一セルに複数の child を置くことで実現する。
批判的検討: XAML 流儀では Grid が ZStack を兼ねる。M3 が Grid を持つなら、ZStack 機能は Grid の自然な副作用として得られる。SwiftUI のように独立 primitive にするかは構文の明示性の問題で、機能としては Grid 同一セルで代替可能。
M3 AC との関係: Grid 同一セル overlap で代替可能（spec で z 順を明文化する形）。独立 primitive にするかは構文の明示性で判断する論点。
AspectRatio
機能: 子要素 / 容器のサイズを指定した縦横比に固定する（例: 1:1, 16:9）。
語彙の出典: AspectRatio (shadcn / radix-ui), .aspectRatio() (SwiftUI), aspect-ratio CSS property, Modifier.aspectRatio() (Compose)。XAML の Viewbox は scaling 中心で semantics が異なる。
批判的検討: container ではなく sizing constraint（任意 container に適用できる属性）として捉えるのが現代的。CSS の aspect-ratio property、Compose の Modifier がこの捉え方。container の sizing 属性として layout-engine の measure 段階に組み込めば、独立 primitive を立てずに済む。
M3 AC との関係: sizing 属性として扱う形なら独立 primitive 不要。独立 container にするかは構文の明示性で判断する論点。
Card / GroupBox / Separator / Divider
機能: 視覚的グループ化（背景色 + 角丸 + 境界線 + 影）/ 視覚的区切り（1px ライン）。
語彙の出典: Card (Material / shadcn), GroupBox (XAML), Pane (QML), Separator (shadcn), Divider (Material)。
批判的検討: layout primitive ではなく styling。M5 (Identity & tooling) の theming surface に属する性格。
M3 AC との関係: layout 議論の射程外。M5 で扱うのが筋。

整理のまとめ: 表の「追加検討が必要」5 項目（DockPanel / SplitView / WrapPanel / ZStack / AspectRatio）の代替可否を見ると、 DockPanel と ZStack は Grid (star sizing + 同一セル overlap) で代替可能、AspectRatio は sizing 属性化で代替可能、 SplitView は「Grid + Splitter widget」に因数分解可能、と整理できる。 Grid で代替できないのは WrapPanel のみ。 また「要素の繰り返し生成」は表に追加する余地がある — ただしこれは独立 primitive 化（Repeater 型）/ DSL 構文要素化（for-in 型）/ List 吸収の三択の判断対象。 どれを実際に M3 AC へ含めるか / どの形で扱うかは target app 決定後に別途検討する。

マトリクス上は太字行（DockPanel / SplitView / WrapPanel / ZStack / AspectRatio）が「ROADMAP M3 AC 外の surface」だが、 上の批判的検討に従って読み直すと次のように整理される：

  • DockPanel（X / Y / W で要件）— Grid auto / * / auto sizing で代替。新 primitive 不要。
  • SplitView（X × 2 / Y × 2 / W で要件）— Grid star sizing + Splitter widget に因数分解。M3 で必要なのは Splitter widget のみ。
  • WrapPanel（Z で主役 / X で tags / W で icon view）— Grid では代替不可。M3 で真に新規追加すべき layout primitive。
  • ZStack（Y / Z で要件）— Grid 同一セル overlap で代替。spec で明文化すれば足りる。
  • AspectRatio（Y / Z で要件）— sizing 属性として layout-engine に組み込めば足りる。新 primitive 不要。
  • 要素の繰り返し生成（全案で要件）— 独立 primitive 化（Repeater 型）/ DSL 構文要素化（for-in 型）/ List 吸収のいずれを採るかの三択判断。

上の代替可否を踏まえ、各案について新規追加を検討する余地がある surfaceを並べると次のようになる （Grid star sizing と同一セル overlap は spec 明文化のみで足りる前提）：

  • 案 X (Mail): WrapPanel / Splitter widget / 繰り返し生成
  • 案 Y (Music): Splitter widget / 繰り返し生成 / AspectRatio 属性
  • 案 Z (Gallery): WrapPanel / 繰り返し生成 / AspectRatio 属性
  • 案 W (Explorer): Splitter widget / 繰り返し生成（WrapPanel は icon view を採るなら追加候補）

なお、これらの「新規追加候補」を ROADMAP M3 AC との縮約・拡張の観点で総合判定する整理は、 後続「判断軸 — 候補選定の 5 軸」節の 軸 4（ROADMAP M3 AC の縮約余地） を参照。

composed widget（命名された UI 部品）

Sidebar / Tabs / Breadcrumb / Toolbar / Card は主要フレームワークで 名前付きの合成 widget として提供される（XAML NavigationView、MUI Drawer、Compose TopAppBar 等）。 M3 でこれらを (A) layout primitive の組合せで表現させる か (B) M3 surface に composed widget として加える かは設計判断。 framing F4「M3 を feature breadth milestone に戻さない」の素直な読みでは (A) を取り、navigation 系 widget は M4 以降に置く。 下表は (A) の立場を取った場合に各案で必要な layout 組合せ を示す。組合せで素直に書けない箇所は M3 surface の不足を意味する。

(A) で素直に書けない箇所（赤背景）が composed widget を M3 surface に入れるかどうか の判断点：

  • Tabs の視覚区別（案 Z）— Button の selected 状態を視覚的に表す手段が M2 の style: accent のみ。M3 で selected/normal の styling 切替 surface を持たないと Tabs として読めない。これは theming 議論（M4–M5）と接続するので、案 Z を採るなら M3 で 最低限の selected styling を入れるか、tabs を全く違う UI（例: dropdown）に置き換えるかを決める必要がある。
  • Breadcrumb のクリック可能セグメント（案 W）— セグメントごとに Button を生やすことは繰り返し生成で可能だが、視覚的に「Button らしくない Button」が要る点で Tabs と同じ styling 問題を持つ。
  • Card / GroupBox（案 Y）— 視覚的グループ化（背景色 + 角丸 + 境界線）は VStack + style 属性で書けるが、これは layout primitive ではなく styling DSL の射程。Card を独立 widget として持つかは M5 (Identity & tooling) 寄りの判断。

まとめると、案 X / Y / W は composed widget をすべて (A) layout 組合せで書ける（styling の細部を除く）。 案 Z は Tabs が selected styling を要求する点で M3 surface に圧力をかける。 Toolbar / Sidebar / Status bar / Breadcrumb（表示のみ）は全案で (A) で成立する。

これらの styling 圧力を含む M4–M5 surface への漏出を、4 案横断で 「不可避 / 回避可能 / reservation で十分」のラベル付きで整理した一覧は、 後続「判断軸 — 候補選定の 5 軸」節の 軸 5（M4–M5 surface への漏出） を参照。

判断軸 — 候補選定の 5 軸

本節は前節「判断材料」を input として、 m3-start-framing.md の framing decisions (F1–F7) に照らして 候補を比較する synthesis レイヤーである。 軸は 5 つで、それぞれが framing の特定の決定に接続している。 判断はオーナーが行うものであり、本節は「候補ごとの傾向」を整理するに留める。

各軸の詳細根拠

軸 1 — Phase 単位の出荷可能性

  • 案 X (Mail) — 悪。Grid + SplitView + List + 多フィールド template が同時に揃わないと 3-pane が画面として成立しない。途中段階で意味のある proof が出にくい。
  • 案 Y (Music) — 中。now-playing (AspectRatio + ZStack) と queue (List) は別 phase に切れる。
  • 案 Z (Gallery) — 良。phase 1 = WrapPanel + thumbnails、phase 2 = lightbox (ZStack + 条件レンダリング) と段階化が自然で、各 slice が M2 拡張を観察可能に示せる。
  • 案 W (Explorer) — 中〜良。sidebar List → main detail List (Grid in template) と段階出荷可能。

軸 2 — Public DSL draft の執筆量と novel surface

  • 案 X (Mail) — 中。多フィールド item template の binding scope / name resolution（dsl-grammar.md の open question を直撃）が重い。layout 自体は Grid star sizing で書けるので軽い。
  • 案 Y (Music) — 中。AspectRatio sizing 規則、ZStack の z 順 / hit 規則、bool binding。先例は揃っている。
  • 案 Z (Gallery) — 重。WrapPanel の measure→wrap→arrange を normative に規定（先例は CSS / Compose Flow）+ 条件レンダリング構文（先例まちまち）。public draft 執筆コスト最大。
  • 案 W (Explorer) — 中。nested template scope + 繰り返し生成構文の確定が要る。layout 自体は Grid 入れ子のみ。

軸 3 — Visible proof による M2 拡張の可観測性

  • 案 X (Mail) — 観察対象は多フィールド item template による message list。M2 不可能性 中（M2 でも複数 Text を縦に並べて擬似 list は擬装できるので「拡張」が弱く見える可能性あり）。離散・再現性 高。
  • 案 Y (Music) — 観察対象は AspectRatio で固定された album art + ZStack overlay。M2 不可能性 強。ただし再生 progress は連続・再現性低で proof として劣化、AspectRatio / ZStack に観察を寄せれば離散化できる。
  • 案 Z (Gallery) — 観察対象は WrapPanel の viewport 幅依存 wrap と lightbox overlay。M2 不可能性 強（両方 M2 で表現原理的に不可能）。「拡張」が画面に直撃する最強候補。離散・再現性 高（resize 操作の正確さに依存する点のみ注意）。
  • 案 W (Explorer) — 観察対象は List item template 内の Grid 3 列揃え（Name / Size / Modified）。M2 不可能性 強（M2 は揃えられない）。離散・再現性 高。

軸 4 — ROADMAP M3 AC の縮約余地

  • 案 X (Mail) — 全 4 項目維持。縮約余地なし。
  • 案 Y (Music) — List は queue 用に必要だが小規模、Grid は star sizing で必要、ScrollView 必要。縮約余地小。
  • 案 Z (Gallery) — List 不要（thumbnails は WrapPanel + 繰り返し生成、queue 的選択管理なし）。Grid は ZStack 兼用で任意。WrapPanel が新規追加 AC 候補に。
  • 案 W (Explorer) — 全 4 項目維持 + Splitter widget 追加候補。縮約余地なし。

軸 5 — M4–M5 surface への漏出

  • 案 X (Mail) — 漏出 1: Splitter widget の drag → input model（不可避 if resizable、固定比 Grid に退行すれば回避可能だが mail-like 感が薄まる）
  • 案 Y (Music) — 漏出 1〜3: Splitter（X と同様）、Card / GroupBox の視覚枠 → styling / theming（回避可能 — 視覚枠なし placeholder でも proof は成立）、bool (is_playing) → TypedValue 圧力（回避可能 — i32 の 0/1 で擬装可、ただし擬装感あり）
  • 案 Z (Gallery) — 漏出 0〜2: Tabs の selected styling → theming（不可避 if Tabs 採用、dropdown / 単一 view に退行すれば回避可能）、lightbox scrim opacity → styling（回避可能 — 不透明矩形でも overlay 構造の proof は成立）。Tabs を落とし scrim を不透明矩形にすれば漏出 0 が達成可能。
  • 案 W (Explorer) — 漏出 1〜2: Splitter（不可避 if resizable）、Breadcrumb の「Button-not-Button」styling → theming（現 desc は表示専用なら回避可能）、bool (is_dir) → TypedValue 圧力（icon glyph で表現すれば回避可能）

観察: Splitter widget は X / Y / W に共通して effectively 不可避な漏出。 Z だけが構造的に Splitter を持たない（gallery は single-pane + overlay）。 これは F4 軸では Z の固有の強みになる。

観察 — 候補ごとの傾向

5 軸を並べたときの候補ごとの傾向は次のとおり。判断はオーナー。

  • 案 Z (Gallery) — 軸 1・3・4・5 で強く、軸 2 で重い（WrapPanel の measure-arrange 仕様）。spec を書く覚悟があれば最良候補。Tabs を落とせば軸 5 の漏出も 0 まで落とせる。
  • 案 W (Explorer) — 軸 1・3 で良、軸 2・4・5 で中庸。バランス型だが Splitter 漏出と AC 縮約なしが弱点。
  • 案 X (Mail) — 軸 3 (ii) で「M2 でも擬装可能」のリスク、軸 1 (3-pane 同時成立) で減点。最も「mail らしい」が proof としての切れ味は鈍い。
  • 案 Y (Music) — 軸 3 で再生 progress の連続性が proof としての観察対象を弱める。漏出も多め。

ただしこれは軸を均等加重した場合の素読みで、framing 上の重み付け （spec drafting コスト vs M4–M5 漏出回避、どちらを重く見るか）はオーナー判断。

このファイルの位置づけと将来再構成トリガー

本ファイルは M3 target app 候補を選択するための exploratory artifact である。 最終的な選定理由・必要 surface・out-of-scope・spec 同期ルールは、本ファイルではなく 候補確定後に起こす target app pre-doc（markdown）で明文化する。本 HTML はその pre-doc から 視覚 input として参照される位置づけになる。

現状の単一 HTML 構成（wireframes + 語彙批判的検討 + マトリクス + composed widget 比較）は 候補選択フェーズに最適化されている。以下のいずれかが起きたら、 本 HTML を wireframe のみの構成に縮小し、cross-cutting 分析（特に「概念の語彙と機能の批判的検討」）を 別の markdown note に抽出する再構成を検討する：

  • 語彙批判的検討の中身を M3 DSL spec ドラフトが直接参照する必要が出たとき
  • HTML 内の vocabulary 整理が target app 選択の文脈と切り離されて参照されるようになったとき
  • 別の milestone（M4 以降）で同様の primitive 整理を再利用したくなったとき

上記のいずれも当てはまらないうちは、単一 HTML を維持することを優先する （markdown 抽出は pre-doc 執筆時に再度書き直しになる可能性が高いため、early extraction は割に合わない）。
