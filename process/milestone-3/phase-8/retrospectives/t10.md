  が記録された。

- 3 ホストの rebuild + 起動リハーサルは全て green。T6 で観測された
  sandbox 内 `zig build` の `AccessDenied` は今回再発しなかった

- T9 pre-merge review が指摘した「文書タスクの parallel-doc drift」を
  T10 start gate の trap #2 に明示列挙し、script は引用ベースで書けた。

### 自己分析（どの層が外れたか）

- **計画仮説はおおむね妥当:** plan の T10 骨子(prep / owner run / retro)は
  そのまま成立した。再切りで足したのは証拠形式の明文化・fail-fix 時の
  gate 再選択条件・close 観察・M4 残課題の script 内明記で、いずれも
  「owner が迷わない / 誤記録しない」ための精度向上だった。
- **prep 重視の読みが当たった:** owner 側の環境失敗(DLL 解決・build
  順序)を script とリハーサルで先取りしたため、human gate の一周目が
  そのまま最終結果になった。human gate のコストは owner の時間なので、
  assistant 側で消せる失敗class を先に消すのが正しい配分だった。
- **外れは特になし。ただし一般化しておく:** 「表面が変わっていないことの
  証明」が prep の中で最も安いのに最も強い工程だった。owner-gate 系
  タスクは、過去 evidence を prep material に使う前に git 範囲チェックを
  標準手順にするのがよい。

### 計画仮説・前提の問い直し（オーナーと）

- **「T10 は再撮影すべきか」** — しない。
  表面が T7 から不変であることを git で示せる限り、assistant baseline は
  T7 のままが正しい。撮り直しは表面が変わった時だけ。
- **「owner にスクリーンショット提出を求めるか」** — 求めない。
  G(5) は human-visible gate であり、証拠は live observation の明示
  受け入れ。owner 撮影を要求すると assistant baseline と証拠形式が
  混ざり、ゲートの役割分担が崩れる。
- **「fail observation が出たら T10 内で直すか」** — additive fix に限り
  T10 branch で直す。ただし compiler/runtime/`gallery.ui`/hosts に触れる
  修正は gate selection と review lane を再評価してから(今回この分岐は
  使われなかったが、条件は start gate に記録済み)。

### 反証可能な是正テスト

- Owner-gate 系タスクの prep では、過去 evidence を prep material と
  宣言する前に「evidence 取得 commit → HEAD の対象パス git log が空」を
  記録する(空でなければ再取得へ分岐)。
- Owner-facing script には、pass 基準と同じ粒度で「fail に数えない既知
  事項リスト」を必ず併記する(誤 fail 記録の防止)。
- Surface-coupled な script を再利用する時は、surface-unchanged check の
  記録なしに流用しない(capture scripts と同じ規律)。
