# M3-Phase 8 フレーミング

**状態:** ドラフト（オーナー合意待ち）
**対象フェーズ:** M3-Phase 8（選択中状態 ＋ ギャラリー統合 ＋ DSL 仕様書の
公開ドラフト）— **M3 の最終フェーズ**

開発プロセス（[workflow.md §2](../../../procedures/workflow.md)）に従い、本
ドキュメントは設計判断（ADR）を書く前に **オーナーと方向性を合意する**ための
入力資料です。個々の判断の選択肢・比較・推奨は、ここでは確定しません。ここで
固めるのは、Phase 8 は何を届けるフェーズなのか、どの問いを判断項目（DD）として
予約するのか、どこまでを Phase 8 の担当範囲とし、どこからを「きっかけ（trigger）
が来たら後続フェーズで」と送るのか、そして検証のしかたです。

前フェーズからの制約引き継ぎ（プロセスの §2.1）は
[constraints.md](./constraints.md) で済んでおり、本ドキュメントはその上に
乗ります。先行する M3 各フェーズから受け継ぐ作業規律（仕様同期を 2 回に分ける /
「まとまり（Moment）」はコミット単位ではない / 全マージはオーナー承認を要する /
最終タスクと締めの責務を分ける / 実装ゲート / 陽性対照）はここで再説明せず、
[constraints.md §9](./constraints.md) を参照します。

> **用語の最小限の補足（初出のみ）:**
> - **DD（判断項目）** … このフェーズで決めるべき設計上の問い。1 つの DD が
>   1 つの問いに対応し、後で ADR（決定記録）として書く。
> - **公開ドラフト** … `docs/dsl_spec.md`（DSL の仕様書）を、社外の読者や
>   将来のツール開発が依拠できる「最初の公開版」として出すこと。
> - **配置（placement）** … 「子をこの親の中でどう置くか」（行・列・寄せ方）の
>   情報。前フェーズ 7b で書き方が確定済み。

## Phase 8 受入れ基準

正本（SSOT）は [process/_roadmap.md M3](../../../_roadmap.md#m3-dsl-surface) /
[plan.md §Acceptance criteria](../../plan.md)。Phase 8 は M3 の最終フェーズと
して、次の**既存の受入れ基準**を満たします。

* **A10** — ボタンの選択中状態の書き方。具体的にどう書くか（`selected: bool`
  属性 / 独立部品 `ToggleButton` / テーマ経由）は「それを担当するフェーズで
  確定」と計画に書かれており、**その担当が Phase 8**。DD-M3-P8-001 で確定。
* **A1** — 統合した `examples/gallery/gallery.ui` が M3 の機能をすべて
  「DSL → 中間表現（IR）→ 実行時」の経路で通しで動かす。Phase 8 は各フェーズが
  育てた画面を**統合**し、3 言語すべてで動かす。統合先は
  [gallery-wireframe.html](../../requirements/gallery-wireframe.html) の
  Photo Gallery ターゲットアプリで、[spec.md](../../requirements/spec.md) の
  同期ルールが「各フェーズの画面を通し証明として置き、**最終フェーズで full
  app として閉じる**」と定める。使い捨て検証画面は残さず畳み込む（dashboard
  ではない）。
* **A12** — `docs/dsl_spec.md` を公開ドラフトに昇格。Phase 1〜7 で各フェーズ
  ごとに更新済みなので、Phase 8 の作業は**編集**（ゼロから書くのではない）。
* **A11**（継続的な義務）— `.ui`（DSL）/ 中間表現 / コンパイラ（`wasamoc`）/
  実行時 / 仕様書 / ギャラリー例 が足並みをそろえて閉じる。Phase 8 でも適用。

**新基準が要らない理由（F の根拠）:** Phase 8 の 3 つの成果はいずれも既存の
基準が名指しています。7b では配置の*書き方*をどの基準も名指していなかったため
A13 を新設しましたが、選択中状態は最初から A10 が予約しています。よって
**新基準は不要**の見込み。例外は、DD-M3-P8-002 が「M4 構文の予約」などで
**新しい公開上の約束**を生む場合のみで、そのときだけ基準改訂の例外手続き
（改訂ログ ＋ ロードマップ反映）を踏みます。判断は ADR 確定（Accepted）時点で
固定し、計画の改訂ログに記録します。

**マイルストーン完了基準（Phase 8 ＝ M3 の締めが背負う）:**
[plan.md §Milestone-end criteria](../../plan.md) のとおり、A1〜A13 をすべて
満たす / 3 つの成果（A10・A1・A12）/ 変更履歴（CHANGELOG）/ 各フェーズの仕様
同期が監査可能 / **社外読者チェック**（仕様書だけで M3 の機能を再現できるか）/
**こっそり先送りした M3 機能が無いこと** / 統合後のクリーンビルドが CI で緑。
これらは Phase 8 の締め（§6）とマイルストーンの締め（§7）にまたがります。

## Phase 8 設計方針

方針は、**再検討しない前提**と、**判断項目（DD）で開く問い**に分けます。

### 再検討しない前提（確定済み）

1. **配置の書き方は 7b で凍結済み。** `slot.*` の書き方、Grid の `Cell` ＋
   直接 `slot.*`（PM-2）、子スロットでの保持（`SlotData`）は
   [docs/dsl_spec.md](../../../../docs/dsl_spec.md) §4.16 /
   [docs/architecture.md](../../../../docs/architecture.md) §6.8.6 / §6.8.4
   に同期済み。Phase 8 は**確定済みの記述を読んで編集で磨く**だけで、書き方を
   作り直しません（[constraints.md §1](./constraints.md)）。
2. **新しいレイアウト部品・寸法計算は作らない。** Grid / WrapPanel / ZStack /
   ScrollView / Box は出そろっています。Phase 8 は統合と編集のフェーズ。
3. **汎用値型（TypedValue）は引き続き先送り。** Phase 7 で「採用しない」と
   判断済みで、Phase 8 の選択中状態は既存の真偽値（`bool`）に乗るため、新たな
   型の必要性は生じません
   （[typed-value-evaluator.md](../../../../docs/notes/typed-value-evaluator.md)）。

### 判断項目（DD）で開く問い

4. **A10 の「選択中」をどう書くか。** 真偽値バインディング（Phase 1）が
   ウィジェットの*属性*を動かせることを示す、M3 最後の機能。`selected: bool`
   属性が自然ですが、独立部品 `ToggleButton`・テーマ経由との比較は
   DD-M3-P8-001 で行います。
5. **公開ドラフトで「何を確定として書き、何を未確定として書くか」。** A12 は
   編集作業ですが、最初の公開ドラフトは社外の読者が依拠し始める**最初の公開
   契約**です。後で変えると破壊的変更になるので、未確定の将来機能
   （PM-2 のラッパー規則・サイズ指定・既定の寄せ方の非対称・綴り）を「確定」と
   誤読させない見せ方が要ります。M4 構文を予約するか否かも計画が「明示的に
   決めよ」と求めています。これらを DD-M3-P8-002 で扱います。

この方針は M3 の機能の幅を広げるものではありません。むしろ、**公開する前に
書き方の見せ方を確定し、未確定の部分を正直に未確定と書く**ための締めくくりです。

### DD-M3-P8-001 — ボタン「選択中」状態の書き方

**問い:**
作者はボタンの「選択中（selected）」状態を `.ui` でどう書くべきか。

**Phase 8 の問いである理由:**
A10 を満たす**唯一の新しい書き方**です。真偽値バインディング（Phase 1）が
ウィジェットの*属性*を動かせることを示す M3 最後のピースで、ギャラリーの
タブ風セクション（複数ボタンのうち 1 つが選択中）を動かします。`selected` は
仕様書にもギャラリーにも未登場のため、ここで初めて書き方を定義します。

**検討する小論点:**

* 書き方の形:
  * **選択肢 1: `selected: bool` 属性**（推奨方向）— 既存の真偽値
    バインディングに乗り、新しい部品が不要。
  * 選択肢 2: 独立部品 `ToggleButton`。
  * 選択肢 3: 見た目テーマ経由のバインディング。
* 見た目の範囲: 選択中の見た目をどこまで作るか。M3 は**最小限**（色や枠の
  違いで判別できる程度）に留め、本格的なテーマは M5。**最小の見た目合格線
  （背景色だけ / 枠線だけ / 色＋枠）は構文だけでなく owner に見せて確定**する
  （[spec.md](../../requirements/spec.md) の Out-of-scope §Visual が「装飾なし
  最小表現、具体形は phase pre-doc で詰める」と定める）。
* 適用対象: タブ風セクションが中心だが、
  [gallery-wireframe.html](../../requirements/gallery-wireframe.html) は
  **サムネイルの強調表示**も選択中状態の surface として持つ。サムネイル選択も
  A10 の再現対象に含めるか、M3 ではタブに限定しサムネイルは最小近似にするかを
  **明示**する。
* 排他（タブ風グループ）の表し方: 各ボタンの `selected` を独立した真偽値とし、
  「1 つだけ選択中」はホスト側のロジックで実現するか、DSL にグループの概念を
  入れるか（推奨: 専用のグループ部品は作らない）。
* 診断（エラー検査）: `selected` が許されるウィジェット（ボタン）と、対応
  しないウィジェットに付けたときの拒否。
* 検証: 真偽値バインディング → `selected` 属性 → 見た目の変化を、純粋ロジック
  テスト / ヘッドレステスト / 陽性対照（選択を切り替えると見た目が連動する
  2 コマ以上）で示す。
* **Out of scope / 将来互換（明示して将来像を狭めない）**: `selected: bool` は
  M3 の**最小 surface** であって「今後唯一の選択部品モデル」ではない。DD-001 は
  次の余地を明示的に残す — (a) `Button selected` は最小属性として残しつつ将来
  `ToggleButton` / `SegmentedControl` / `TabBar` 等の意味部品を追加できる、
  (b) 選択時の見た目は M3 の暫定で M5 テーマ surface に吸収・上書きできる、
  (c) 排他制御は M3 では host ロジックだが将来 group semantics を設計できる、
  (d) accessibility / focus / input semantics は M4 以降で再設計できる。

### DD-M3-P8-002 — DSL 仕様書の公開ドラフト昇格：予約と未確定部分の見せ方

**問い:**
`docs/dsl_spec.md` を公開ドラフトに昇格するとき、(a) M4 向け構文を予約するか、
(b) 未確定 / 暫定の将来機能をどう位置づけて書くか、(c) 公開版の状態マーカーと
社外読者チェックの合格線をどう定めるか。

**Phase 8 の問いである理由:**
A12 は編集作業ですが、最初の公開ドラフトは社外の読者や下流ツール（M5 の VS Code
拡張）が依拠し始める**最初の公開契約**です。「何を確定として書くか」は後で変えると
破壊的変更になるため、未確定部分を正直に未確定と書く判断が要ります。計画は M4
構文の予約を「**予約するか、見送ったと記録するか、明示的に決めよ**」と求めて
います（黙っていると「予約しない」が既定）。

**検討する小論点:**

* **M4 構文の予約**: 公開ドラフトで M4 向けの構文を予約するか、見送ったと
  記録するか（計画の明示要求。沈黙は「予約しない」が既定）。方針として、
  **予約は最小限**に留め、未確定のものは「予約（強い約束）」ではなく
  **将来ノート（future note）**として書く（予約しすぎは M4 の設計空間を狭め、
  予約しなさすぎは互換期待を曖昧にする——その中間を最小予約で取る）。
* **PM-2 の Grid 2 形式**: `Cell` ＋ 直接 `slot.*` の 2 形式を「受理する集合」
  として述べつつ、ラッパー規則は **1.0 前に決める暫定** と明記する
  （[constraints.md §3](./constraints.md)）。
* **サイズ指定（width/height）**: Fill 既定のサイズを確定として書かず、明示
  サイズを **未確定の将来機能**として位置づける
  （[constraints.md §2](./constraints.md)、Problem B Vision DR と連動）。
* **既定の寄せ方の非対称**（Grid は `stretch` / ZStack は `center`）: 正確に
  記述し、社外読者にとって説明可能か / 説明負債かを**明示的に判断**する
  （[constraints.md §4](./constraints.md)）。
* **配置の綴り**（`h-align` 等）: 公開前最後の改訂機会として、維持するか
  改めるかを**明示判断**（[constraints.md §5](./constraints.md)、推奨 ＝ 維持）。
* **配置のバインド可否 / 互換の位置づけ**: 配置は定数であると正確に記述し、
  ドラフトを「永続確定の互換約束」と誤読させない
  （[constraints.md §7](./constraints.md)）。
* **状態マーカーと変更履歴**: `status: public-draft`（または同等）のヘッダ
  マーカーと M3 の変更履歴（CHANGELOG）追記。
* **社外読者チェックの合格線**: 仕様書だけで（C ABI を備えた仮想ホストに対して）
  M3 の機能を再現できるか。できなければ編集の残作業。

**明示サイズの Vision DR はフェーズの判断項目ではない。** Problem B（明示
サイズ）の**責務の割り当て**はロードマップに関わる全体方針なので、フェーズの
決定記録ではなくマイルストーン横断の **Vision DR** で行います（DD-V-022 と同じ
やり方）。Phase 8 の方向づけ段階でそれを起票しますが、判断項目（DD）には
含めません。DD-002 が担うのは「公開ドラフトでサイズ指定をどう書くか」という
編集面だけです。

## 検証方針

Phase 8 の検証は、「**M3 の機能がすべて 1 つのギャラリーで通しで動く**」ことと、
「**仕様書だけで社外読者が再現できる**」ことを示します。

### 目視による通し証明

* **選択中状態（A10。陽性対照が要）**: タブ風セクションで選択を切り替え、
  選択中ボタンの見た目が**連動して変わる** 2 コマ以上を撮ります。1 コマだけでは
  見た目を固定で描いても同じに写るので、真偽値バインディングが属性を動かして
  いる証明になりません（Phase 6 の表示切り替え / Phase 7 の反復と同じ型の
  陽性対照）。
* **ギャラリー統合（A1）**: 統合したギャラリーを起動し、スクリーンショット ＋
  解析。「DSL → 中間表現 → 実行時」の経路（ホスト側で手組みしない）で全画面が
  出ることを確認。見た目は
  [gallery-wireframe.html](../../requirements/gallery-wireframe.html) と照合し、
  **余計な検証 UI / デモメニューが残っていないこと**も確認する。確認する
  ギャラリーの状態は **既定表示 / lightbox 表示 / 選択切り替え 2 コマ /
  折り返し・あふれ**（この状態セットは初期案で、**FD-8-G(1) の合意で確定し
  実装計画に反映**する）。**3 言語のうち UI レビューは代表 1 言語で行い、残り 2
  言語は parity（同じ表示）/ 回帰なしの確認に留める**。
* アシスタント自動の証拠は、起動 ＋ スクリーンショット（`CopyFromScreen`、
  モニタごとの DPI 対応）＋ 解析を含めます。オーナーの目視確認の代わりには
  なりません。規範の核は [AGENTS.md §Testing rules](../../../../AGENTS.md)、
  撮影機構と陽性対照の原理は
  [verification-environments.md Observation 4](../../../../docs/notes/verification-environments.md)。

### A1 機能対応表（どの画面でどの M3 機能が通るか）

余計な UI を足さずに A1 を検証するため、Photo Gallery の各部分と、そこを通る
M3 機能を対応づける。統合作業はこの表を埋めることであって、表にない検証画面を
足すことではない。

**この表は framing 時点の初期対応仮説 / 監査足場であり、最終 UI 仕様そのもの
ではない。** FD-8-G(1) の wireframe 逸脱合意、および DD-001 の選択中状態の
適用対象判断により、行の粒度・対応箇所・仮置き扱いは実装計画で更新され得る。
ただし「A1 の M3 機能を**余計な検証 UI なしに Photo Gallery ターゲットアプリ内で
通す**」という目的はここで固定する。

| Photo Gallery の部分 | そこを通る M3 機能 |
|---|---|
| 全体フレーム | Grid（star sizing / 連結 span） |
| サムネイル一覧 | WrapPanel ＋ ScrollView（折り返し ＋ ビューポート） |
| サムネイル生成 | 繰り返し（iteration）＋ コレクションバインディング |
| ライトボックス | ZStack ＋ 条件レンダリング（真偽値で出し入れ） |
| タブ風セクション（サムネイル強調を含めるかは DD-001 で確定） | 真偽値 ＋ 選択中状態（`selected`） |
| 写真らしき領域 | Box（`aspect`）＋ Text の仮置き |
| 子の配置 | `slot.*`（Grid `Cell` / ZStack） |

### オーナー確認ポイント（packet G の工程化）

phase 末だけに寄せず、実装計画に次の確認を**工程として**置く（packet G の 5
項目に対応）。

1. **wireframe 逸脱の合意**（初回表示の前提）: M3 には実画像・不透明度・
   スクロールバー部品・モーダルフォーカス・本格テーマが無いので、wireframe の
   「忠実に再現する箇所」と「M3 では仮置きとして許容する箇所」を**初回表示の前**に
   owner と合意する（後で揉めない足場）。**この合意結果を A1 機能対応表と
   Phase 8 実装計画へ反映し、以後の UI 確認は更新後の対応表を基準に行う。**
2. **初回表示**: 統合ギャラリーが代表 1 言語で初めて表示できた時点で owner の
   UI 確認（方向ずれを早期に発見する。phase 末では遅い）。
3. **陽性対照**: 選択中状態 / lightbox の切り替え前後 2 コマを owner 確認。
4. **公開ドラフト ＋ M3 handoff**: DD-002 の社外読者チェックに加え、M4 構文の
   予約・未確定表現の強さ・PM-2 / Problem B / 既定寄せ方の先送り説明は owner の
   判断余地が大きいので、公開ドラフトと M3 handoff のドラフトを phase close 前に
   owner 確認。
5. **最終スモーク**: 上記のギャラリー状態セット（既定 / lightbox / 選択 2 コマ /
   折り返し・あふれ）で最終の人間目視スモーク。

### 純粋ロジック / ヘッドレステスト

* 真偽値バインディング → `selected` 属性 → 見た目の伝播（既存の文字列 / 真偽値
  バインディングの証拠パターンの拡張）。
* `selected` を対応しないウィジェットに付けたときの拒否（実際に失敗する
  テスト）。
* 既存機能に回帰がないこと（ギャラリー統合で各画面の寸法計算 /
  バインディングが壊れていない）。

### 仕様書の編集ゲート（A12 の検証）

* **社外読者チェック**: 仕様書だけで M3 の機能を再現できるか。できなければ
  編集の残作業（マイルストーン完了基準 5）。
* 各フェーズの仕様同期が監査可能（各決定記録が「更新した仕様セクション」への
  参照を持つ）。
* 未確定機能（PM-2 / サイズ指定 / 既定寄せ方 / 綴り）が暫定 / 予約として
  **正直に**書かれているか（DD-002 の判断結果が反映済みか）。

## リスク

### R1. 編集が「あとで書く」に流れる
A12 は編集ゆえコードより後回しにしやすい。フェーズ完了基準の「仕様同期」は
厳格ゲート（[plan.md §Risks](../../plan.md)）。仕様文が "TODO" のフェーズは
閉じません。

### R2. 未確定部分を「確定」と書いてしまう
最初の公開ドラフトで PM-2 / サイズ指定 / 既定寄せ方 / 綴りを確定として書くと、
後で変えたとき公開済みの書き方の破壊的変更になります。DD-002 が「暫定 / 予約と
正直に書く」を明示判断として閉じます（[constraints.md §1〜§7](./constraints.md)）。

### R3. 選択中状態の作り込み過剰
見た目やタブグループを作り込むと M5 のテーマ / M4 の入力に食い込みます。M3 は
最小限（色 / 枠）＋独立した真偽値に限定し、グループ部品は作りません（C）。

### R4. 明示サイズの Vision DR が M3 の完了を止める
明示サイズの責務割り当てはマイルストーン横断の全体方針で、確定を急ぐと M3 の
締めが遅れます。Phase 8 は**起票と論点固定まで**を責務とし、最終確定は別ゲート
（packet D）。公開ドラフト側は「未確定の将来機能」と書くだけで先に進めます。

### R5. ギャラリーが大きすぎて CI で回らない
M3 のギャラリーは Hello Counter より大きい。通しの検証は単一の固定ケースとし、
各フェーズのヘッドレステストは各画面を対象にします（[plan.md §Risks](../../plan.md)）。
