## Main Learning

中心的な学びは、**「実装は M2 で landed しているが docs に漏れて
いた表層仕様」を後続 phase で発見した場合、その phase の自然な
spec sync 作業に折り込んで最小範囲で追認するのが、scope-creep を
避けつつ docs を真実に近づける唯一の経路**、という process 観察。

- 今回のケース: `state` 表層キーワードは M2-Phase 6 (commit
  0283093, `feat(wasamoc): parse state declarations (DD-M2-P6-004)`)
  で lexer/parser に landed し、IR §8.4 にも反映されている。しかし
  `dsl_spec.md` §§1–7 (DSL 表層) には記述がなく、§2.1 keywords 表 /
  §3 grammar / §4 semantics のいずれにも `state` が登場しなかった。
  M3-Phase 1 が bool を `state ready: bool = false` の形で
  documenting する段になって、参照先の `state` 構文自体が docs に
  存在しないという不整合が表面化した。
- 取りうる対応は 3 つ: (a) bool を `in-out property` 側だけで
  documenting して `state` の話は触れない (実装と乖離した spec
  にする), (b) `state` 表層を documenting するための独立 ADR /
  task を立てて Phase 1 を待たせる (Phase 1 完了が遅れる; scope
  creep の正規化), (c) Phase 1 の bool spec sync に最小範囲で
  retroactive な `state` 追認を folding (今回採用)。owner 合意の
  上で (c) を選択した根拠は、*"Revise docs, don't work around them"*
  原則 (記憶側で `feedback_revise_dont_workaround` として記録)
  — (a) は実装の
  ad-hoc 運用上の再解釈で docs を黙って sync しない選択、(b) は
  Phase 1 の closing を待たせる代償が docs 正確性の対価に見合わ
  ない、と判断した。
- 学びとして残すのは **「同じ phase の spec sync 作業中に発見した
  retroactive ギャップは、原則として fold して同じ commit セット
  で landing する。範囲は『今回の phase の作業を anchor するのに
  必要な最小』に限る (例: `state` 全体の semantics 解説ではなく、
  bool が `state` で declarable と参照できる程度の subsection
  追加)」** という運用基準。
- この基準は M2-Phase 6 / M2-Phase 7 など先行 phase の漏れが
  M3 後続 (Phase 2-8) で他にも露見する可能性に備えて記録する。
  M3-Phase 2 (string scalar の拡張系) や M3-Phase 6 (conditional
  rendering) で `if` / `else` / `for` 等の surface 構文が docs
  に追加されるとき、関連既存構文 (handler 内の if / control-flow
  既出有無等) のギャップが類似に発見された場合は本基準を参照。

副次的な学び:

- **abi_spec.md は触らない判断の確実性**。T9 retrospective
  §Follow-Up で「T10 で abi_spec.md に bool 経路の意味論を書く」
  という可能性が示唆されていたが、ADR §Spec impact preview は
  "no new ABI surface added" と明記しており、T10 progress
  checklist にも abi_spec.md は列挙されていない。`WASAMO_VALUE_BOOL = 3`
  と `v_bool` フィールドは M2 から存在 (`docs/abi_spec.md` §3.3
  L159, L169 で確認済み) で、wire format は不変。abi_spec.md
  の追記は「semantic prose を増やす」レベルの aspirational task
  であり、Phase 1 の必須 spec sync ではない。検討結果として
  abi_spec.md を T10 で触らない判断を retrospective §Notes に
  明示。
- **revision history の更新は必須**。dsl_spec.md は冒頭に
  `Document version: 0.4` + 最終更新日と、末尾に revision history
  テーブルを持つ。M3-Phase 1 で初めて bool 機能を反映するため
  version を 0.5 に bump し、history table に 1 行追記。これは
M2 phase で precedent ([dsl_spec.md](../../../../docs/dsl_spec.md) 0.1 →
  0.2 → 0.3 → 0.4 の history) があり、phase-end ではなく該当
  phase の spec sync commit (= T10) で必ず行う。architecture.md
  には version 概念がないため bump 不要 (top の Status 文字列
  は phase-end gate で M2/M3 milestone 表現を更新する性質の
  ため T10 では触らず)。
- **doc 内 anchor link の typo 警戒**。dsl_spec.md §4.3 の prose
  に "see §9" と書いたが、widget catalog を §4.8 として配置した
  ため §9 という section はない (現状の dsl_spec.md は §8 が
  末尾の normative section)。`§4.8` に修正済み。doc 内 forward
  reference を書くときは、書き手の "後で追加する番号" の予測と
  実際の section 配置が乖離しやすい。T10 では一度発生したのみ
  だが、edit 順序を「先に anchor を fix → 後で参照 prose を書く」
  に揃えれば回避できる。
