## Main Learning

今回の学びは、**「ADR §Verification の item を実際に discharge した
test を 1 行で名指せるか」を、各 box tick の最終ゲートにすべき**
ということ。

T6 の acceptance bullet は `button_enabled.rs` を ADR item 3 の
evidence として扱っていたが、その test の file-level comment は
冒頭から「binding pipeline を bypass」と明記していた。test 自体は
正しく書かれており、コメントも正しかった。にもかかわらず box が
tick されてしまったのは、ADR item の文言と test ファイルの先頭
コメントを並べて読む照合が、acceptance のどこにも組み込まれて
いなかったから。

これは T12 phase-end review (owner) で初めて気付かれた。Codex 単独
作業では気付けなかった理由は、box の文面 ("CI-gated Windows
integration test for `Button.enabled`") と test 名 (`button_enabled_
property_flips_visual_and_suppresses_click`) が表層的に一致して
おり、ADR §Verification item 3 の「unified chain」要求を表層 match
が押し流してしまったため。retroactive insertion 自体は CLAUDE.md
§Commit rules が許容する正常な path で、その意味では process は
壊れていない。壊れていたのは「ADR item と test を 1 対 1 で
名指せるかの最終照合」が無かった点。

副次的に、**評価環境 (ローカル開発機) で同じ test が green でも
それは guard を通った証明ではない** という
[CLAUDE.md §Testing rules](../../../CLAUDE.md) の原則を、T13 も
そのまま継承して書いた。T13 のスキップガードはローカルでは guard
ハッピーパスしか踏まないので、SSH 環境での fail 検証は
`button_enabled.rs` / `live_widgetnode_headless.rs` の既存
verification に寄りかかっている。これは新しい evidence の追加が、
既存の evidence regime に依存する形でしか成立しないことを示して
おり、guard 設計を 1 回だけ正しく作っておくと後続 test の
edge-case 設計コストが大幅に下がる、という positive な observation
でもある。

実装上の小さな知見:

- `unsafe { value.payload.v_bool } != 0` は Rust parser に
  `unsafe-block-statement; != 0 (expression)` と読まれる。union
  field の読み出しを `let v = unsafe { ... };` で一度 bind すると
  expression として安全に比較できる。今後 ABI union を test で
  扱うときの定型 helper にする価値あり。
- `Button` を component の root に置く lower-tests の shape
  (`component C inherits W { Button { ... } }`) は integration test
  でも有効で、VStack wrapper を増やすと navigation step が一つ
  増える分だけ意味のない冗長度を持ち込む。最小 chain を狙う
  evidence test では root-Button を選ぶのが clean。
