## Main Learning

中心的な学びは「T1 で `IrType::Bool` / `IrLiteral::Bool` /
`HandlerExpr::BoolLit` / `BoolPropRead` の variant を追加した時点
で、loader 側の **validation pass は完成していた**」という対称性。

- `validate_expr_references` は workspace 全体の `match` を
  enum-exhaustive にしておく T1 の方針 (Phase 1 ADR `### T1`
  bullet 1) のおかげで、`BoolLit` / `BoolPropRead` arm が
  T1 段階で機械的に追加されていた。今回 T5 では `validate_*`
  には一切触れずに済み、新規 malformed test が **既に通る**
  状態を確認するだけだった。
- 同じ T1 の方針が `parse_literal` / `parse_expr` には適用
  できなかった点が対照的: parser 側は「`true` / `false` を
  ident と区別する」という新しい dispatch を入れる必要があり、
  これは enum-exhaustive match では発見できない。Parser は
  あくまで「token 列 → variant」への変換であって variant 集合の
  網羅性ガードが効かない、ということが具体例として残った。
- 結果として T5 は「parser に 4 ヶ所 dispatch を追加」+「test
  追加」の純粋な配線作業に収まった。設計判断は発生せず、
  ADR DD-M3-P1-006 の text-grammar 規定をそのまま実装に落とした
  だけ。

副次的な学び: integration test を `wasamoc` の **実 surface**
(lexer → parser → check → lower → emit) を通すように書いたこと
で、T5 単体のテストでありながら **T1–T4 全体の bool 経路に対する
回帰ガード** にもなっている。例えば将来 `wasamoc::emit` が
`BoolPropRead` の S-expr tag 名を変えるような変更を入れた場合、
このテストが「emitter spelling と loader recognition の divergence」
として失敗する。Phase-end までの間に新たに導入される `.ui` 構文
変更 (T11 で fixture を増やす際など) でも保護される。

T5 の commit 分割の判断: parser 変更 + unit tests (part 1) と
cross-crate integration test (part 2) を分けた。これは

1. part 1 だけでも独立して意味を持つ (新 productions を受理可能)、
2. part 2 が `wasamoc` を dev-dep として引く crate-graph の seam
   であり、レビュー上 part 1 と性格が違う、

の二点から。`docs/plans/progress/m3-phase-1-progress.md` の T5
checklist と 1:1 で対応する分割。

## Verification Notes

T5 で追加したテストと、走らせた command を記録する。

新規 unit tests (`wasamo-runtime/src/ir_loader.rs::tests`):

- `state_bool_with_false_default` —
  `state ready: bool = false` が `IrType::Bool` /
  `IrLiteral::Bool(false)` に解決される。
- `state_bool_with_true_default` — `true` 側の対称ケース。
- `prop_bool_literal` — `prop enabled = true` が
  `IrLiteral::Bool(true)` を産む。`IrLiteral::Ident("true")`
  にフォールバックしないことのガード。
- `binding_with_bool_prop_read` —
  `bind enabled = (bool-prop-read ready)` が
  `HandlerExpr::BoolPropRead { path: "ready" }` に解決される。
  T5 acceptance bullet 2 の直接対応。
- `binding_with_bool_literal` —
  `bind enabled = true` が `HandlerExpr::BoolLit(true)`。
- `handler_assign_bool_literal` —
  `(assign ready false)` が `Assign { rhs: BoolLit(false) }`。
- `handler_assign_bool_prop_read` —
  `(assign a (bool-prop-read b))` が `Assign { rhs:
  BoolPropRead { path: "b" } }`。BoolPropRead が `Assign` の
  RHS 位置にネストできることの確認。
- `malformed_bool_prop_read_undeclared` — `(bool-prop-read
  missing)` で未宣言 state を参照すると
  `IrLoadError::Validate` が出る。DD-M2-P6-009
  defense-in-depth が bool 経路にも届いていることのガード。

新規 integration test (`wasamo-runtime/tests/ir_loader_roundtrip.rs`):

- `bool_state_binding_emits_and_parses_bool_productions` —
  `state ready: bool = false; Button { enabled: ready; clicked
  => { root.ready = true; } }` を `wasamoc` で IR text 化し、
  `parse_ir` で読み戻して構造同値を assert。さらに以下を個別に
  チェック:
  - emit 段で `state ready: bool = false` が文字列として出る
  - emit 段で `(bool-prop-read ready)` が S-expr として出る
  - emit 段で `(assign ready true)` が S-expr として出る
  - parse 後の `IrState` が `Bool` 型 / `Bool(false)` 既定
  - parse 後の `Button.enabled` binding が
    `BoolPropRead { path: "ready" }`
  - parse 後の `clicked` handler が
    `Assign { lhs: "ready", rhs: BoolLit(true) }`

T5 acceptance との対応:

| T5 checklist | Test |
|---|---|
| IR text loader accepts new `IrType` / `IrLiteral` / `HandlerExpr` productions | `state_bool_*`, `prop_bool_literal`, `binding_with_bool_*`, `handler_assign_bool_*`, `malformed_bool_prop_read_undeclared` |
| Round-trip (`wasamoc` emit → `wasamo-runtime` load) reconstructs `IrState { ty: Bool, default: Bool(false) }` and `BoolPropRead { path: "ready" }` | `bool_state_binding_emits_and_parses_bool_productions` |

T5 から後続 task への明示的な引き渡し:

- **T6 (`wasamo-runtime` widget catalog):** T5 が parser で受理する
  ようになった `IrType::Bool` state を、`build_signal_registry` が
  `SignalRegistry::bools` (T6 で導入) に登録できるようにする。
  T5 が残した `unimplemented!()` をここで解消する。`Button.enabled`
  の `PROP_BUTTON_ENABLED` キーと bool-typed setter も T6 の責任。
- **T7 (`EvalContext` bool surface):** T5 が parser で受理する
  ようになった `HandlerExpr::BoolLit` / `BoolPropRead` を evaluator
  が解釈するための trait 拡張 (`get_bool` / `read_bool_tracked` /
  `set_bool`) と `evaluate()` の bool-typed `Assign` arm。T5 は
  evaluator 側には触らないので、bool handler を含む `.ui` を T5
  で loaded しても (= 構文木として再構成しても)、それを実行する
  経路はまだ存在しない、という状態が T7 まで続く。
- **T8 (binding evaluator + writer seam):** T5 が parser で受理する
  `BoolPropRead` を含む binding を、reactive engine から bool 値
  として書き出す経路。`evaluate_bool_binding` と
  `widget_write_property_bool` の追加、および
  `resolve_prop_key` の戻り型に `IrType` を載せて writer 選択する
  seam が T8 で組まれる。T5 の round-trip テストは「正しい
  `IrBinding` 構造が parser から取り出せる」ところまでをガード。
