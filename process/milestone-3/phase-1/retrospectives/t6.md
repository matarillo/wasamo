## Main Learning

中心的な学びは、**`PropertyValue` 列挙への variant 追加が、Rust の
exhaustive match によって T9 (ABI value-conversion arms) の作業を
機械的に T6 に引きずり込んだ** こと。

- T6 のチェックリスト上、`PropertyValue::Bool` の追加は
  「widget catalog」スコープに属する。T9 は「`abi.rs` /
  `emit.rs` の `PropertyValue` match arm 拡張」を別タスクとして
  保留していた。
- しかし `PropertyValue` が non-exhaustive ではない以上、新 variant
  を加えた時点で `abi::read_property_value` /
  `abi::write_property_value` / `abi::property_value_to_owned` /
  `emit::owned_to_value` の四箇所すべてが arm を要求する。
  panic arm を残す選択肢もあったが (a) ランタイムで死ぬパスを
  仕込むことの不健全さ、(b) `OwnedArg` も同様に variant を
  必要とする伝播性、を考えると T9 を T6 commit 群に吸収するのが
  最短かつ正しい。
- 結果として **T9 は T6 の part 1 で完了済み**。progress file の
  T9 行も `[x]` に更新し、Notes で「T6 part 1 で fold した」と
  明示する。これは CLAUDE.md `Commit rules` の "Implementation
  reveals that an item should be split or reordered" の典型例。

副次的な学び:

- **Integration test で `Button` の `bg_visual` を手動 SetSize
  する必要があった**。`WidgetNode::button` は label_visual の
  size しか設定せず、bg_visual の size は host window が回す
  `layout::arrange` 経由でしか設定されない。テストは window を
  経由しないため、`button.visual.SetSize(...)` を test 側で呼んで
  hit-test rect を成立させる必要があった。これは Phase 1 単体の
  しわ寄せというより、widget の sizing 責任の分離 (constructor は
  intrinsic size を計算し、layout が arrange する) の M2 設計の
  自然な帰結。T11 で `.ui` fixture 経由のエンドツーエンドを書く
  時には window 経由なので発生しない問題。
- **`set_clicked` をテストで使うと
  `enqueue_signal("clicked", ...)` 経由の observer も呼ばれて
  しまう**点に気付いたが、テストは observer を登録していないため
  `enqueue_property_change`/`enqueue_signal` の drain は
  no-op で済む。Phase 1 の bool 経路に固有の問題ではない。
- **`SignalRegistry::bools` を T6 で先回りして導入**したが、
  これは progress file の T6 Notes (DD-M3-P1-007 関連の per-type
  seam) の言及から自然に導けた。T7 で `EvalContext::*_bool` を
  実装する際に「registry の bool field がまだ無い」状態を避ける
  ことが、T7 のレビュー単位を綺麗に保つために必要。

**SSH dev box 上での guard 経路確認 (2026-05-19 追記):**
本 commit 群 (158e4fa まで含む) を SSH dev box 上で `cargo clean`
後に再ビルドして `cargo test -p wasamo-runtime --test
button_enabled -- --nocapture` を実行した結果、
`wasamo_init: アクセスが拒否されました。 (0x80070005)` で初期化が
失敗し、`runtime_compositor_unavailable` guard が想定通り発火して
"skipping Button.enabled headless test: runtime compositor
unavailable (...)" を stdout に出した上で `1 passed` で完了することを
直接観測した。並走させた `cargo test -p wasamo-runtime --test
live_widgetnode_headless -- --nocapture` も同じ HRESULT で同じ
skip 動作を示し、両 test の guard 判定 (`0x80070005` substring
match) が **DD-M2-P6-011 確立の precedent と完全 parity** であることが
確認できた。Claude Code セッションが回している Windows 環境
(physical machine 相当、Compositor 利用可能) では skip 経路を踏まず
通常実行で `1 passed` だったため、guard の **happy path** と
**skip path** の双方が単一 commit 群で両環境にまたがって検証された
ことになる。

本確認をきっかけに、project-wide rule として
[CLAUDE.md `Testing rules`](../../../CLAUDE.md) に「新規 mock-free
Windows-only test を land する前に、Compositor-unavailable 環境で
skip-guard の発火を観測すること」を 1 bullet 追加し、根拠と env
分類を [docs/notes/verification-environments.md](../../../../docs/notes/verification-environments.md)
§ "Implication for future mock-free Windows integration tests" に
拡張した(本 retrospective と同一コミットで反映)。
