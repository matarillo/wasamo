## Current Judgment

2026-05-19 時点で T4 step-end 基準は **達成済み**。

- `lower.rs` の三つの ident-handling 経路をすべて T3 の `Namespace`
  (`HashMap<String, TypeName>`) 参照に揃えた:
  - `lower_expr` (prop-bind RHS): ident が state 名なら

  - `lower_rhs_expr` (handler RHS): 同じ三分岐を適用するため
    `&Namespace` を新規パラメタとして受け取る。`lower_block` /
    `lower_statement` も signature 拡張で `ns` を carry。
  - `lower_string_parts` (string interp): 既存の Str arm に加えて
    Bool arm を追加し、`BoolPropRead` を返すように。

  - `bool_state_ident_in_prop_bind_lowered_to_bool_prop_read_binding`

## Main Learning

中心的な学びは「T3 で構築した `Namespace` (`HashMap<String,
TypeName>`) と T2 までに整っていた lowering の枠組みのおかげで、
T4 は **ident-handling 三経路の同質化** だけで済んだ」という点。
DD-M3-P1-010 が "identifier resolution at lowering time" と
load-bearing で述べていた構造は、T3 までで既に半分以上できあがって
いた:

- `lower_string_parts` は M2 時点 (T1 以前) で既に `&Namespace` を
  受け取り Str arm を持っていた (interp 内の ident は state ref と
  して扱う必要があったため)。T4 はここに Bool arm を 1 行足すだけ。
- `lower_expr` (prop-bind 用) は M2 時点で `ns` を受け取って
  いたが、`Expr::Ident` arm は ns を見ずに常に `IrLiteral::Ident`
  を返していた。これは M2 では state ident が prop-bind の RHS に
  単独で現れる例が無かった (counter サンプルでは `text:
  "Count: \{root.count}"` のように常に interp 経由) ため、bug
  ではなく「未使用経路」だった。T4 でここを使い始めるとき、
  キーワード ident (`mica`, `system`, `accent`) は ns に無い名前
  なので自動的に `IrLiteral::Ident` 側に落ち、互換性が保たれる。
- `lower_rhs_expr` (handler 用) は M2 時点で `ns` を受け取って
  おらず、interp parts を呼ぶ際に `&Namespace::new()` を渡して
  いた (これは事実上のバグで、handler RHS の interp に state
  ident が混じるケースで `BoolPropRead` / `StrPropRead` の機会
  を逃していた)。T4 は signature を拡張して正しく `ns` を渡す
  ように修正することで、副次的にこのバグも閉じた。

その結果、T4 の実装は「三経路のすべてで `ns.get(name)` の四分岐
パターン (Bool / Str / Int / Float|None) を統一して書く」という
パターンの繰り返しになり、新しい設計判断は発生しなかった。

副次的な学び: prop-bind 経路で「state ident は dynamic、非 state
ident は static」と分けることは、wasamoc 側 catalog (T3 で導入)
が `Button.style: <ident>` のような enum keyword を catalog に
登録しない (soft 扱い) 方針と整合する。catalog 側 soft + lowering
側 ns-check の二段で、M2 corpus に対して非破壊的に reactive
binding を導入できている。

T4 の commit 分割の判断: 三経路の同質化は意味的に一つの change
(同じ ident-resolution rule の異なる適用箇所) であり、build /
test もすべて同時に green を保てるため 1 commit に集約した。
CLAUDE.md の "1 task = 1 commit default" にそのまま乗っている。

## Follow-Up

T4 から後続 task への明示的な引き渡し:

- **T5 (`wasamo-runtime` IR loader):** T4 が emit する
  `IrLiteral::Bool(_)` / `HandlerExpr::BoolLit(_)` /
  `HandlerExpr::BoolPropRead { path }` を runtime 側の IR text
  loader が受理できるようにする。round-trip テスト (`wasamoc`
  emit → `wasamo-runtime` load) で `bind enabled: ready` が
  `IrBinding { expr: BoolPropRead { path: "ready" } }` として
  再構成されることを確認できる粒度の test fixture を T4 のテスト
  形状から流用可能。
- **T7 (EvalContext bool surface):** T4 が産む
  `BoolPropRead { path }` を evaluator が解決するには
  `EvalContext::read_bool_tracked(path)` が必要。T4 はその入力
  形状を確定させた立場。handler RHS の `BoolPropRead` (T4 新規
  経路) は `evaluate()` の bool-typed `Assign` arm (T7) に
  そのまま渡る。
- **T8 (binding writer seam):** `bind enabled: ready` から産まれた
  `IrBinding { expr: BoolPropRead, prop_name: "enabled" }` を
  loader が拾うとき、`evaluate_bool_binding` で評価して
  `widget_write_property_bool` に渡す経路を T8 が組む。T4 の
  ident-resolution が正しく `BoolPropRead` を産んでいることを
  前提にできる。

これらはすべて progress file の T5–T8 として既に列挙済み。T4 単体で
新たに発見された follow-up は無い。
