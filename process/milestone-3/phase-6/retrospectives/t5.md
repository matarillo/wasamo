## Checklist (task-end, items 1–11)

1. **Main learning.**
   - The T4 `IrMember` traversal discipline was load-bearing in exactly the
     way the carry-forward note predicted: the conditional runtime cannot
     derive insertion order from widget-only children. T5's declared-slot
     table is built by iterating `IrMember` in declared order, and every
     mutation recomputes the live index from preceding declared slots plus
     live conditional presence.
   - Visual order and layout metadata are one problem, not two. Fixing
     `insert_child` to use positional `InsertBelow` closed the visible-order
     bug, but ZStack's parent-owned `zstack_placements` vector also had to
     mutate at the same index or layout would drift from the materialised
     tree. The code now updates `WidgetNode.children`, the live Visual
     collection, and the ZStack placement vector together.
   - Self-review found an initially-missed runtime consequence: structural
     conditional mutation must invalidate layout even when the subtree has no
     size-affecting property binding. That was fixed in T5 by marking the
     parent widget's window dirty after successful insert/remove, rather than
     carrying the hole into T7 lightbox evidence.
   - `EffectHandle::new` was the right structural seam: initial condition
     evaluation, true→false / false→true transitions, and true→true /
     false→false no-ops all run through one closure. That kept T4's static
     presence reducer from becoming a second semantic path.
2. **Specification document changes:** none. No `abi_spec.md`,

   match DD-M3-P6-004 / DD-M3-P6-005. The implementation-specific ZStack
   metadata mutation constraint is recorded as carry-forward (item 10), not
   folded into living specs mid-task.

4. **Design judgments / trade-offs to consult PO:** no owner-blocking

   reported with `eprintln!` and do not enter the runtime health /
   divergence path. This mirrors the current non-ABI diagnostic style rather
   than adding a host-facing error, but it should be revisited if Phase 7's
   range mutation needs stronger structural failure observability.
5. **Out-of-task refactors or structural changes:** **yes, implementation

10. **New cross-task / cross-phase design constraints:** **yes —
    `carry-forward` candidate.**
    - **Constraint:** structural mutation under a container with
      parent-owned positional metadata must update the materialised child
      list, parent-owned metadata vector, and live Visual sibling order as a
      single invariant; a future range primitive cannot treat insertion as
      widget-only.
    - **Evidence:** T5's ZStack conditional path needed
      `insert_child_with_zstack_placement` plus `remove_child` placement
      removal; otherwise initial/reinserted conditional children would keep
      Visual order but drift from ZStack layout placement metadata. Pinned by
      `conditional_toggle_preserves_declared_visual_order_and_disposes_registry`,
      `conditional_zstack_reinsert_uses_declared_placement_metadata`, and the
      existing ZStack layout/Visual integration tests.
    - **Phase 6 GUI-evidence obligation:** conditional structural
      insert/remove layout invalidation was initially missing but is now fixed
      in T5 (`mutate_conditional_subtree` marks the parent widget dirty after
      successful mutation). That fixes the mutation primitive, but it does
      **not** fully prove the real HWND path. T7/T8 must observe the
      click-driven lightbox toggle without relying on a resize, so the
      production path `mark_layout_dirty_for` → `drain_if_outermost` →
      `flush_layout` is exercised under `WindowState`. If that evidence
      exposes the separate pre-existing question that dirty-flush uses
      `run_layout` rather than `run_layout_as_window_root`, the fix remains
      Phase 6-owned (T7 if found by assistant evidence, T8 if found by owner
      smoke) unless it requires a normative spec/ADR change.
    - **Reactive-loader coupling:** the initial presence of conditional
      subtrees now depends on `EffectHandle::new` running the structural
      binding immediately. A future reactive-engine change that delays
      initial Effect execution must either preserve this load-time
      materialisation contract or add an explicit loader initialisation path.
      This uses the existing raw-pointer widget mutation seam, but extends it
      from property writes to structural child insertion.
    - **ZStack mutation API footgun:** ZStack children with placement props
      must be inserted through the placement-carrying path
      (`insert_child_with_zstack_placement` / equivalent future range API).
      Plain `append_child` intentionally defaults ZStack placement to
      centered for length synchronisation, so using it for an aligned child
      silently drops parent-owned placement metadata.
    - **Structural failure observability:** T5 keeps build / insert / remove
      failures on the conditional mutation path as log-only diagnostics.
      Phase 7 range mutation should re-evaluate whether this remains
      sufficient once multi-child structural edits can fail partially.
    - **Placement:** `carry-forward` candidate for Phase 7
      `ForLoopSubtree` / range mutation design. This is stricter than the
      earlier T4 traversal rule: T4 says declared-member positional
      traversals must dispatch on `IrMember`; T5 adds that mutation
      primitives must carry parent-owned positional metadata through the
      same materialised order.
11. **Downstream-task revision (no current-ADR impact):** **yes — folded

    left documented as property-change-only. This does not require a new ADR
    by itself; an ADR addendum is only needed if the observed fix changes
    normative layout semantics rather than aligning implementation with the
    existing window-root contract.
