## Checklist

1. Main learning:
   - The `IrMember` migration is workable when widget-only traversals are
     explicit (`IrNode::widget_children()`), while semantic control-flow
     sites dispatch on `IrMember`. That kept the schema change, compiler
     emit/lower, runtime textual IR parser, validation, and static
     presence reducer in one buildable unit.
   - The review follow-up showed that this was not enough: introducing a
     new tree/member variant creates a semantic migration, not just a type
     migration. Every traversal must be classified by contract before the
     task can truthfully claim closure: widget-only invariant, declared
     member order, materialised child order, positional metadata, or
     validation/defense-in-depth. A helper such as `widget_children()` is a
     proof obligation, not a proof; each use must have a reason why
     dropping `ControlFlow` is intentional and tested. This lesson carries
     directly into T5's reactive positional insertion, T7/T8's Visual-tree
     evidence, and any later phase that adds `else` / `switch` / iteration
     or retained keyed subtrees.
   - Retrospective item 10 should treat implementation-level invariants as
     cross-task constraints when later tasks can step on them. The original
     "no new ADR-level constraint" framing missed that T5/T7 could be
     broken by traversal and positional-metadata choices even without an
     ADR change. For later tasks / phases / milestones, "not an ADR
     change" must not imply "no carry-forward": if a future owner must
     preserve an ordering, identity, validator, or materialisation rule,
     record it as carry-forward with evidence and a re-trigger criterion.

    - **Constraint 1 — `IrMember` traversal discipline (`carry-forward`)**:

      computes positional metadata, or materialises declared members must
      dispatch on `IrMember` unless it has a documented widget-only
      invariant. `IrNode::widget_children()` is only valid for invariants
      where dropping `ControlFlow` is intentional and tested.
      - **Evidence**: follow-up #1 added validator member-dispatch helpers
        for Phase 2/3/4/5/ZStack gates, static ZStack placement extraction
        through `collect_static_zstack_placements`, and tests for
        ControlFlow-body validator descent plus ZStack placement order.
        Follow-up #2 added the explicit traversal call-site audit
        ([log.md](../implementation/log.md)) and closed the Box/ScrollView
        count-basis under-count it found (ten new reject/accept tests,
        including the Codex-review-flagged `*_conditional_only_member_rejected`
        provenance for the DD-M3-P6-007 centre case and the
        `*_multiple_conditional_siblings_*` count-basis proofs).
      - **Placement**: `carry-forward` candidate for T5/T7 and phase-end
        review. T5's reactive positional insertion must use the same
        declared-member/materialised-child ordering discipline. The audit's
        generalised rule ("dispatch `IrMember`; prefer compile-error-forcing
        mechanisms over silent-absorb helpers") is also carry-forward, with
        rule-ification deferred to the next semantic migration (≥ 2 samples
        before a vision decision record).
    - **Constraint 2 — ScrollView conditional-empty policy
      (`carry-forward`)**: the conditional-only ScrollView interim (reject)

        `validate_rejects_scrollview_with_conditional_only_member` (the
        value a (b) relaxation would flip); decision recorded in
        [DD-M3-P6-007](../decisions/dd-m3-p6-007-scrollview-conditional-content-policy.md),
        ownership in plan task T4b.
