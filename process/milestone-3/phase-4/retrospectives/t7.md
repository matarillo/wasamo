## Main Learning

中心的な学びは **「step-end と phase-end は scope と所有が異なる別
gate であり、retrospective ファイルも progress doc bullet も
分割して扱うべきで、混合させると reviewer の摩擦が増える」** という
構造的気づき。原始 T6 (phase-end gates and Moment 2 re-sync) が
"Phase-end retrospective recorded under `docs/notes/m3-phase-4/`" を
単一 bullet として持っていたことが Q3 で問題化し、step-end と
phase-end の retro / gate を **物理的に異なるファイル + 異なる
bullet** に分けた。Q3 owner answer 「不毛なレビューを減らすには、
T7 progress checklist にある "Phase-end retrospective recorded"
みたいな行が一番危ない」を直接受けた構造的修正で、Phase 5 以降に
同じパターンが再発しないよう ownership lens を強化する素材
(item 10 参照)。

副次的な学び:

- **Plain-chat clarifying question が options/pros/cons/recommendation
  形式で機能した.** Q1/Q2/Q3 すべてで recommendation 案を提示し、
  Q1 と Q2 で owner critical review が recommendation を強化する形
  (Q1 → A' refinement、Q2 → 期限 + Phase 5 pre-doc gate 追加) で
  反応した。design choices を「決定済みの提案」ではなく
  「assistant 推奨案 + 余地」として提示することが owner の付加
  judgment を引き出している。feedback_doc_driven の
  "design choices = options/pros/cons/recommendation" 規律が
  T7 規模の意思決定群でも崩れず機能した動作確認。

- **"window-root WidgetNode is sized to client rect" を §6 一般
  layout に置く decision が正しかった.** §6.5 ScrollView 専用節に
  置くと「window-root sizing は ScrollView 固有の規約」と誤読される
  可能性があった。T6 retro Item 10 (1) が `architecture.md §6` (= 6.3
  default-constraints table 隣接) を配置先に指定した判断は、本 T7
  Moment 2 で実際に §6.3 末尾 paragraph として落とした時点で
  「Default constraints by widget type の表と並ぶ runtime-boundary
  override 規約」として読めるので適切だった。spec 配置先の選定は
  「読み手がどの context で読むか」を基準にすべき、という再確認。

- **§6.5 parent_abs_offset shift の一般則化が将来 widget 拡張の
  前提を整備した.** T4 retro Item 10 配置先を `doc-folded` →
  `phase-sync` に T5 retro で訂正した経緯は、本 T7 で実際に §6.5 に
  paragraph として落とした際に「ScrollView 固有の規約」のままに
  しておくか「intermediate Visual を持つ任意の widget の一般則」と
  して書くか、の 2 択になった。後者を採ったことで、Phase 6 以降の
  widget catalog 拡張 (例: ZStack の Layer-Visual / clip-Visual) が
  spec を read するだけで `parent_abs_offset` shift 規約を継承
  できる。spec の最も近接した文脈で一般則化する判断は、後続 phase
  pre-doc の readability を上げる pre-emptive な投資。

- **"single sentence" 枠の expansion を retro で flag する規律.**
  Q1 owner answer は "single sentence" 枠で `architecture.md §6` への
  追加を承認したが、実 Moment 2 で書いてみると override の機構
  (`run_layout_as_window_root`)、plain `run_layout` 側不変の言明、
  `window.rs` の 2 call site 明示、`degenerate_fill_in_shrink_parent_
  clamps_to_zero` 含む convention 不変の言明、を 1 文に収めると
  情報密度が極端に高くなり読みづらいので **四文の paragraph 化**
  した。owner approved 枠を超えるか超えないかは判断要件だが、
  超える場合は retro で明示的に flag するのが安全。本 retro
  Item 2 で再評価する (assistant 判断で expansion したことの owner
  確認待ち)。

- **TodoWrite + system reminder の status field 欠落エラー再現.**
  本 step 初回 TodoWrite で `status` field 欠落エラーを誘発しなかった
  が、`feedback_todowrite_status_required` memory に従って全項目に
  status を明示する規律は意識的に守った。再発防止が機能した動作
  確認。
