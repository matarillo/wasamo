## Main Learning

中心的な学びは **「ScrollView の structural error gate (unbounded
scroll axis) は measure ではなく arrange で発火させなければ
ならない」** という発見。

- 直観的には measure と arrange のどちらでも fire できそうだが、
  measure-time の `avail_h = INFINITY` は **Shrink-height 親が
  children に渡す標準 idiom** であり、固有の不安定状態を示すもの
  ではない。VStack / HStack の measure コードは children へ
  `f32::INFINITY` を渡しており、ここで ScrollView が
  `ScrollViewUnboundedAxis` を返すと **Shrink-height 親に
  ScrollView を置いた瞬間に常に layout error** が出る (たとえ
  arrange で finite cell が allocate される場合でも)。
- 一方 arrange-time の `h = INFINITY` は親が viewport を渡せて
  いないことを意味し、これこそ DD-M3-P4-002 がカバーする
  structural error 条件。
- この差は DD-M3-P4-005 が `measure` / `arrange` のどちらに
  ScrollView の "viewport" を持たせるかという設計判断に直結する。
  ScrollView の outer size = viewport は **arrange-time の親
  allocation で決まる** ので、unbounded-axis 検出も arrange に
  集約するのが自然 (gate と data source の局所性を一致させる)。
- 副次効果として、`measure_scroll_view` は child を recurse せず
  自身の constraint だけを返す simplest possible 実装になり、
  WrapPanel の measure→arrange cross-bound cache のような
  measure→arrange 整合性問題が構造的に発生しない (T7 review で
  発覚したクラスのバグを T2 では避けられる)。

副次的な学び:

- `applied_offset_y` cache は WrapPanel の
  `wrap_measured_cross_bound` cache と shape が似ているが、用途は
  **逆方向**。WrapPanel cache は measure → arrange の整合性を
  保つための同フェーズ内 forward cache だが、`applied_offset_y` は
  arrange → `sync_visuals` (T4 の Visual-layer 同期) へ結果を渡す
  cross-phase cache。同じ `Cell<f32>` pattern を使うが、初期値が
  異なる (cache は `NAN` sentinel で "未計算" を表すが、
  `applied_offset_y` は arrange 完了前は単に `0.0` で十分)。
- `Fill`-width child の cross-axis 解決は VStack / HStack の
  arrange-time Fill 解決と同じ pattern: `if child.width == Fill {
  viewport_w } else { cw_desired }`。新規の解決規則を発明する
  必要はなく、既存 single-child container の convention を踏襲。
- scroll-axis 側の Fill 解決は **意図的に degenerate** (Fill 軸
  measure は 0 を返すため content_h = 0 になり、scroll 不可能な
  zero-height content に collapse する)。これは既存
  `degenerate_fill_in_shrink_parent_clamps_to_zero` test と同じ
  挙動で、特別扱いせずに済む。
