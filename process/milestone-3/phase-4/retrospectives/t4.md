## Main Learning

中心的な学びは **「ScrollView の sync_visuals が children に渡す
parent_abs_offset は、自身の `computed.offset` ではなく
"intermediate Visual の絶対座標 = `(computed.offset.0,
computed.offset.1 - applied_y)`" にしなければならない」** という
発見。これは architecture.md §6.5 の絶対 vs parent-relative
convention を Phase 4 ScrollView に拡張する際に load-bearing な
細部で、層が一段増えたぶん `Visual.Offset` の二重適用を避ける
shift が必要になる。

- 直観的には sync_visuals は今まで通り `parent_abs_offset =
  computed.offset` を子に渡せばよさそうに見えるが、ScrollView の
  場合は **layout engine が child を `(x, y - applied)` 絶対座標で
  arrange している** ため、その値をそのまま `child_abs -
  computed.offset` で parent-relative 化すると `(0, -applied)` に
  なる。Visual tree 上では child Visual は intermediate (offset
  `(0, -applied)`) の下にいるので、Composition の累積は
  outer(0,0) + intermediate(0,-applied) + child(0,-applied) =
  (0, -2·applied) という **二重シフト** になり content が
  期待位置から余分にスクロールしてしまう。
- 正しい shape は: sync_visuals の ScrollView 分岐で
  `child_parent_abs = (computed.offset.0, computed.offset.1 -
  applied)` を子に渡す。すると child.Visual.Offset = child_abs -
  child_parent_abs = (x, y - applied) - (x, y - applied) = (0, 0)
  に解決され、Composition 累積は outer(0,0) + intermediate(0,-applied)
  + child(0,0) = (0, -applied) と **scroll が exactly once**
  contributed される。
- この shift は ScrollView が intermediate Visual を 1 枚追加した
  ことの代償。Phase 2 / Phase 3 までは 1 WidgetNode = 1 Visual で
  parent_abs = computed.offset がそのまま成り立っていたが、
  Phase 4 で local 拡張した時点で convention の整合性は
  parent_abs_offset の shift を 1 行追加することで再確立される。
- T2 retrospective Item 10 で前送りした `applied_offset_y` cache
  contract が "T4 が consumer" と明示していたのはまさにこの shift
  のためで、Cell<f32> を arrange → sync_visuals に渡す single-writer
  / single-reader 経路が T4 で閉じた。

副次的な学び:

- `InsetClip{0,0,0,0}` の zero-insets pattern は WinRT
  Composition の "clip to my own bounds" idiom で、毎 layout pass の
  size 書き込みに自動追従する。RectangleClip + 明示的な extent
  bookkeeping を選ぶと毎回 (window resize、scroll、content change)
  で clip rect を書き直す必要があるが、Phase 4 はそれを回避できた
  (DD-M3-P4-004 Option A 自然な帰結)。
- `content_container_visual()` helper の導入は append_child 等 4
  site の 1 行書き換えで済み、ScrollView 以外の widget の動作には
  零影響。Phase 3 までは self.visual を直接 cast していた pattern を
  helper 化することで Phase 4 の local 拡張を吸収。helper-pattern
  refactor の典型例で、ScrollView 以外の widget に new 2nd-Visual を
  入れる将来の widget (例: Window chrome) でも同じ拡張点を再利用
  可能。
- `BuiltUi::__set_i32_state_for_test` の追加で `SignalRegistry` の
  `pub(crate)` 可視性を保ったまま integration test から state mutate
  が可能になった。`__*_for_test` 命名は既存 `__box_state_for_test`
  / `__install_owning_thread_for_test` precedent と整合。`#[doc(hidden)]
  pub fn` ペアは rustdoc を汚染しない well-established pattern。
- DD-M3-P4-003 の "narrow string-to-`i32` parse step at ScrollView's
  per-widget `set_property` arm" は **新規 `PropertyValue` variant
  を一切導入せずに** 実装可能だった。`PropertyValue::String` 経路
  (M2 string-baked binding writer) をそのまま流用し、ScrollView arm
  で `s.parse::<i32>()` を一行追加するだけ。F5 (`TypedValue` deferral)
  が引き続き保たれている。
- size_affecting clause を「layout-affecting」の意味で借用したのは
  read 上やや誤読を生むが、既存 hook 機構をそのまま活かせる最小変更
  で、コメントで意図を明示した。将来 layout-affecting 専用の hook が
  分離されたタイミング (e.g. M4 input handling) で再分類すればよい。
