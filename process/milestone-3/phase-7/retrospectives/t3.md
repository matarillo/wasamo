### 自己分析（どの層が外れたか）

外れた層は、実装可能性ではなく **proof key の粒度設定**だった。私は
Implemented-branch test map を作ったことで T2 の反省を適用できたと判断したが、
map の行が「collection assignment rejects」「placement contexts」のように
太く、実装 branch と 1:1 に近い粒度まで分解できていなかった。結果として、
実装済み branch の一部を「代表ケースで見た」と扱ってしまった。

もう一つ外れた層は、`constraints.md` を close 前の double-loop input として
十分に使わなかったこと。T3 は Accepted DD と implementation plan を主入力に
進めたが、constraints §7 の `TypedValue` 圧力判断は、T3 の author syntax で
「field access っぽいものを通さない」ことにも効く。これは runtime/T10 送り
ではなく、T3 の author check が閉じるべき surface だった。

また、positive control の定義も浅かった。`for` が1つ lower されることは
証明していたが、gallery-like shape という計画上の証明対象は、ScrollView /
WrapPanel / Box / Text / body-external handlers の組み合わせとして pin して
初めて T8 への入力になる。ここを「後続のgallery taskで見る」と考えたら、
T3 の author surface proof を弱める。

最後に、retro のダブルループ欄を短い要約で済ませたこと自体が、今回の
再点検目的から外れていた。完了報告後に owner が要求した構造は、単なる
振り返り文ではなく、次 task の close 判断に再利用できる反証可能な検査面である。

**2 段階目の自己分析（is/ought のギャップ）。** owner follow-up で *Branch-map
granularity test* と *Smuggle scan* という是正テストを「記録」したにもかかわらず、
in-task review でさらに 2 行が漏れていた。外れた層は粒度設定でも constraints
活用でもなく、**是正策の「記録」と「運用」のギャップ**だった。是正テストを
retro に書くことと、それを DD-007 の全行に対して実際に走らせることは別の
行為であり、私は前者で後者を済ませたと錯覚していた。具体的には、(a) plan の
散文列挙に無い DD-007 行（loop-external read）は branch map にも現れず、散文を
継承した map は DD の網羅性を保証しない、(b) Smuggle scan を「structured item /
qualified loop-local」だけに適用し、bool 要素という別の deferred surface に
広げていなかった。教訓は「是正テストの SSOT は plan の散文でなく DD の matrix
表そのもの。close 前にその表を 1 行ずつ probe する」こと。

### 計画仮説・前提の問い直し（オーナーと）

1. **「T3 は Accepted DD と plan を読めば足り、constraints.md は主に
   pre-doc 入力」という仮説。** 反証された。constraints §7 は
   `TypedValue` / structured item smuggle を防ぐ T3 author-check input でも
   あった。
2. **「branch map は matrix row 単位で十分」という仮説。** 反証された。
   matrix row が複数 branch を含む場合、実装 branch 単位まで砕かないと
   direct test gap が残る。
3. **「gallery shape は T8 で本格的に見るので、T3 は最小 `for` lower で十分」
   という仮説。** 反証された。T3 の plan が "gallery shape compile and lower"
   を明記している以上、T3 は T8 に渡す author 形の骨格を直接 pin する必要がある。
4. **「qualified names は既存の state-reference 規則に任せればよい」という
   仮説。** 反証された。loop-local binder と qualified name が交差すると、
   structured item fields に見える構文が state read として通り得る。
5. **「T6/T7/T10 送りは適切だった」という仮説。** 大枠では反証されなかった。
   loader dual-gates、static materialisation、runtime guarded reads /
   collection writer / `ForLoopSubtree` は T3 外のまま。ただし T10 送りに
   する前に T3 author diagnostic と direct tests で閉じるべきものがあった。
6. **「是正テストを retro に記録すれば、それで適用したことになる」という
   暗黙仮説。** 反証された（最も load-bearing な反証）。記録した *Branch-map
   granularity* / *Smuggle scan* を DD-007 全行に実走させていれば、loop-external
   read と bool-binder interpolation の 2 行は owner follow-up 時点で閉じられた
   はず。是正策は「書く」でなく「走らせる」まででひとつ。

### 反証可能な是正テスト

次 task 以降の close 前チェックは、T2 由来の five artifacts に加えて、次を
明示的に実行する。

- **Constraints-to-task row:** `requirements/constraints.md` の各採用項目を、
  task-owned / later-owned / non-applicable に分類し、task-owned なら直接の
  code/test/log artifact を書く。DD / plan だけで代替しない。
- **Branch-map granularity test:** implemented-branch test map は matrix row
  単位ではなく、実装の `match` arm / `if` diagnostic branch / parser diagnostic
  branch 単位まで分ける。1 行に複数 branch を束ねる場合、同一テスト内の
  subcase 名または needle を列挙する。
- **Smuggle scan:** deferred surface（`TypedValue`, structured item fields,
  keyed identity, per-item handler reads, **scalar 要素型ごとの display 契約
  ＝ bool 要素の interpolation など**）について、「実装していない」
  だけでなく「似た構文が既存規則で偶然通らない」ことを直接テストする。
  対象集合は plan の散文でなく **DD の matrix 表**から取る。
- **Positive-control shape test:** plan が "gallery shape" / "fixture shape"
  と書く場合、最小機能テストとは別に、その形に近い fixture を compile/lower
  pin する。後続の E2E task に丸投げしない。
- **Matrix-row probe（in-task review remediation で追加）:** 是正テストを
  retro に「記録」するだけでは不可。close 前に DD（本 phase なら DD-007）の
  reject matrix を **1 行ずつ**、ビルド済みコンパイラへの throwaway probe
  （`errors(src)` / `parse_err_msg(src)`）で実走し、各行が named diagnostic を
  出すことを確認する。silent acceptance / 誤誘導 diagnostic を「既存規則任せ」と
  仮定しない。owner-correction count はこの probe を**走らせた後**に数える。
- **Retro format check:** task retrospective のこの欄は、必ず
  `観測された事実` / `自己分析` / `計画仮説・前提の問い直し` /
  `反証可能な是正テスト` の4サブセクションを持つ。形式欠落は close 不可。
