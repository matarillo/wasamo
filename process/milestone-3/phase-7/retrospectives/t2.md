### 自己分析（どの層が外れたか）

外れた層は実装手順ではなく、**完了基準の設定**だった。私は最初の完了判断で
「plan の T2 checkbox が埋まり、workspace が green で、trap #1 audit table が
ある」ことを主な出口条件にしていた。これはシングルループの達成指標としては
有効だが、T2 の本当の問いである「plan 自体が妥当か」「T2 で pin すべき
挙動を T6/T7 に誤って送っていないか」までは検証しない。

特に trap #4 の扱いで、**T6 が full DD-007 matrix を所有する**という正しい
前提を、**T2 で既に実装した reject branch まで T6 に送れる**という誤った
免罪符として使った。これは ownership 境界の読み違いで、正しい基準は
「T2 が実装した branch は T2 が直接発火テストを持つ。T2 が実装していない
matrix 行だけ T3/T6/T7 に送る」だった。

また、T2 close audit は `rg` table という forcing artifact を持っていたが、
それは call-site classification の artifact であって、**テスト深度の artifact
ではない**。私は audit table の強さを、branch pin の十分性にまで過大拡張した。

T1 由来の exit 基準についても同じ構造の過大拡張があった。「未解決点の所有者が
決まっている」ことを「T2 が背負うべき証明は残っていない」ことと同一視した。
実際には、未解決点を後続へ送る判断の前に、**その項目が本当に未解決なのか、
それとも T2 で既にコード化したため T2 がテストすべきものなのか**を分離する
必要があった。

merge-prep review で外れた層はさらに一段メタだった。私は「次 task では
Implemented-branch test map を作る」と書いたが、T2 自身へ遡及適用するときに
それを **実際の `rg` 出力との突合表**にしなかった。これは是正策を「知っている」
ことと、その是正策を gate として実行することを取り違えた失敗だった。

もう一つ外れた層は、**仕様文書を編集していない = observable behavior change
なし**という前提だった。`validate_state_default` は direct textual IR の
scalar default を厳格化しており、これは仕様文書編集なしでも後続 task が踏む

直列化しない判断は、`annotate_collection_expr_types` 後にのみ elem が権威を

表では見えていなかった。

### 計画仮説・前提の問い直し（オーナーと）

問い直すべき仮説は 6 つある。

1. **「T2 は schema migration なので shape と buildability が主で、reject
   深度は後続でよい」という仮説。** これは半分だけ正しい。T2 は full matrix
   を背負わないが、T2 で実装した loader/evaluator reject seam は T2 の証明対象。
   今回の追加テストでこの境界を修正した。
2. **「call-site audit table があれば trap #1 の主要リスクは閉じる」という
   仮説。** call-site miss には効くが、compiler-silent filter の意味論を将来
   変えないためには実行可能な pin も有効だった。`widget_children()` の
   `For` body 非再帰テストを追加して補強した。
3. **「後続 task ownership は log / retro に書けば十分」という仮説。**
   T2 後の再点検で、`item-read` / `index-read` の loader dual-gate は
   plan.md の T6 bullet にも明示した方がよいと判明した。実行責任は
   retrospective だけでなく task list 上に見える必要がある。
4. **「T1 由来の exit 基準だけで close 判断に足りる」という仮説。**
   これは不十分だった。未解決点の所有・範囲・影響を見切る基準は有効だが、
   それは carry-forward 管理の基準であって、T2 自身の implemented branch
   proof を保証しない。close 判断には両方が必要。
5. **「是正基準を retrospective に書けば、次から効く」という仮説。**
   これは反証された。T2 自身で見つけた是正基準は、T2 自身の close にも
   適用しなければならない。`Implemented-branch test map` は散文ではなく、
   `rg` 列挙とテスト名/所有 task の突合表として log に残して初めて gate になる。
6. **「仕様文書を編集していなければ項目 2/10 は変わらない」という仮説。**
   文書編集の有無と observable behavior / invariant の有無は別物だった。
   scalar default の loader 厳格化と collection elem 再導出 invariant は、
   normative spec 未編集でも後続 task の前提として carry する必要があった。

この問い直し後も、T2 の大枠仮説「shared schema migration は 1 buildable
bundle で切る」は維持する。反証されたのは bundle 境界ではなく、**bundle 内で
pin すべき branch の深さ**、**後続所有のplan上の可視性**、および
**是正策を forcing artifact として自己適用する厳密さ**だった。

### 反証可能な是正テスト

次の実装タスク（特に T3 / T6）では、完了報告の前に次の artifact を作る。

- **Implemented-branch test map:** その task で実装した reject / diagnostic /
  size / semantic branch を列挙し、各行に「直接発火するテスト名」または
  「この task では実装していないため、所有 task = X」を書く。`cargo test`
  green だけでは合格にしない。列挙元は `rg` などの機械出力にし、散文の
  「代表的に見た」では不可。
- **Plan-hypothesis challenge row:** task の close log に、「plan の仮説として
  疑ったこと」「反証されたこと」「反証されなかったこと」「所有を移した未解決」
  を 3〜5 行で残す。単に「計画通り」とは書かない。
- **Owner-correction count:** 完了報告後に owner 指摘で追加実装・追加テスト・
  plan ownership 修正が発生した回数を signal として数える。次 task でこの値が
  0 にならなければ、是正は失敗。0 でも、implemented-branch test map が無ければ
  偶然の可能性が残るため失敗扱い。
- **Two-key exit check:** T1 由来の exit 基準を維持しつつ、close 前に
  (a) carry-forward key = 残った未解決点の所有者・範囲・影響、
  (b) proof key = この task で実装した branch / semantic pin の直接テスト、
  の 2 つを別々に満たしたか確認する。片方だけでは close 不可。
- **Behavior/invariant carry scan:** 仕様文書を編集していなくても、loader
  strictness、serialization omission、annotation-derived authority のような
  observable behavior / invariant が生まれていないかを close 前に列挙し、
  項目 10 または plan の後続 task に配置する。

T2 に再度遡及適用した結果、3 本の未pin reject branch は追加テストで閉じ、
`IrLoadError::Validate` branch map は [../implementation/log.md](../implementation/log.md)
に forcing artifact として残した。現在残る未解決点は item 9〜11、
implementation log の carry-forward 表、および T6/T7 plan bullet に集約され、
引き取る task と再トリガ条件が見えている。

## Merge-prep 訂正 addendum（2026-06-14）

上の「implemented branch の未pinは追加テストで閉じた」という判断は、さらに
厳密な review で反証された。T2 close と宣言した後も、T2-owned な
`IrLoadError::Validate` branch が 3 本未 pin のまま残っていた:
scalar/scalar default 型不一致 catch-all（旧 :268）、
scalar expression が collection state を読む branch（旧 :1291）、
append に collection state を要素として渡す branch（旧 :1411）。
本補修で `scalar_state_rejects_type_mismatched_default`、
`scalar_read_of_collection_state_rejected`、
`append_collection_state_as_element_rejected` を追加した。

これにより、反証可能な signal は **owner 起点で完了判断が覆った回数 = 2**
から、**owner/reviewer 起点で完了判断が覆った回数 = 3** に更新する。原因は、
「Implemented-branch test map」を是正基準として書いたにもかかわらず、T2
自身へは散文で適用し、`rg -n 'IrLoadError::Validate'
wasamo-runtime/src/ir_loader.rs` の列挙結果との突合表にしていなかったこと。
本補修では [../implementation/log.md](../implementation/log.md) に production
reject arm ごとの「直接発火するテスト名」または「T2 では未実装、所有 task」
を貼り、`cargo test` green だけでは合格にしない形へ格上げした。

項目 2 の「仕様文書の変更なし」は、文書編集の有無としては維持するが、T2
の observable behavior としては訂正が必要。`validate_state_default` により、
direct textual IR の scalar default は型厳格化された。たとえば
`state count: i32 = true` は以降 loader reject になる。この仕様同期は
phase-end の Moment 2 候補であり、T3/T6 はこの strict loader gate を前提にする。

項目 10 の carry-forward も 2 件不足していた。第一に、textual IR の
`list-prop-read` / `list-append` / `list-drop-last` は elem 型を直列化せず、
parser は仮置きし、`annotate_collection_expr_types` が state 宣言から再導出する。
不変条件は「collection 系 `HandlerExpr.elem` は annotate 実行後にのみ権威を持つ」
こと。T7 が handler 評価のため collection `HandlerExpr` を loader 以外の経路で
構築する場合に再トリガする。第二に、上記 scalar default 型チェックは direct
textual IR の厳格化として T3/T6/phase-sync が引き取る。

補修後の検証は `cargo fmt --all -- --check`、`cargo build --workspace`、
`cargo test --workspace` が green。`wasamo-runtime --lib` は 381 tests green で、
上記 3 本の新規 reject pin を含む。
