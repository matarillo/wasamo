なお、T1 レトロで設定され、今回のタスクプロンプトにも入った exit 基準

### 自己分析（どの層が外れたか）

外れた層は実装手順ではなく、**完了基準の設定**だった。私は最初の完了判断で
「plan の T2 checkbox が埋まり、workspace が green で、trap #1 audit table が
ある」ことを主な出口条件にしていた。これはシングルループの達成指標としては
有効だが、T2 の本当の問いである「plan 自体が妥当か」「T2 で pin すべき
挙動を T6/T7 に誤って送っていないか」までは検証しない。

特に trap #4 の扱いで、**T6 が full DD-007 matrix を所有する**という正しい
前提を、**T2 で既に実装した reject branch まで T6 に送れる**という誤った
免罪符として使った。これは ownership 境界の読み違いで、正しい基準は
「T2 が実装した branch は T2 が直接発火テストを持つ。T2 が実装していない
matrix 行だけ T3/T6/T7 に送る」だった。

また、T2 close audit は `rg` table という forcing artifact を持っていたが、
それは call-site classification の artifact であって、**テスト深度の artifact
ではない**。私は audit table の強さを、branch pin の十分性にまで過大拡張した。

T1 由来の exit 基準についても同じ構造の過大拡張があった。「未解決点の所有者が
決まっている」ことを「T2 が背負うべき証明は残っていない」ことと同一視した。
実際には、未解決点を後続へ送る判断の前に、**その項目が本当に未解決なのか、
それとも T2 で既にコード化したため T2 がテストすべきものなのか**を分離する
必要があった。

### 計画仮説・前提の問い直し（オーナーと）

問い直すべき仮説は 3 つある。

1. **「T2 は schema migration なので shape と buildability が主で、reject
   深度は後続でよい」という仮説。** これは半分だけ正しい。T2 は full matrix
   を背負わないが、T2 で実装した loader/evaluator reject seam は T2 の証明対象。
   今回の追加テストでこの境界を修正した。
2. **「call-site audit table があれば trap #1 の主要リスクは閉じる」という
   仮説。** call-site miss には効くが、compiler-silent filter の意味論を将来
   変えないためには実行可能な pin も有効だった。`widget_children()` の
   `For` body 非再帰テストを追加して補強した。
3. **「後続 task ownership は log / retro に書けば十分」という仮説。**
   T2 後の再点検で、`item-read` / `index-read` の loader dual-gate は
   plan.md の T6 bullet にも明示した方がよいと判明した。実行責任は
   retrospective だけでなく task list 上に見える必要がある。
4. **「T1 由来の exit 基準だけで close 判断に足りる」という仮説。**
   これは不十分だった。未解決点の所有・範囲・影響を見切る基準は有効だが、
   それは carry-forward 管理の基準であって、T2 自身の implemented branch
   proof を保証しない。close 判断には両方が必要。

この問い直し後も、T2 の大枠仮説「shared schema migration は 1 buildable
bundle で切る」は維持する。反証されたのは bundle 境界ではなく、**bundle 内で
pin すべき branch の深さ**と、**後続所有のplan上の可視性**だった。

### 反証可能な是正テスト

次の実装タスク（特に T3 / T6）では、完了報告の前に次の artifact を作る。

- **Implemented-branch test map:** その task で実装した reject / diagnostic /
  size / semantic branch を列挙し、各行に「直接発火するテスト名」または
  「この task では実装していないため、所有 task = X」を書く。`cargo test`
  green だけでは合格にしない。
- **Plan-hypothesis challenge row:** task の close log に、「plan の仮説として
  疑ったこと」「反証されたこと」「反証されなかったこと」「所有を移した未解決」
  を 3〜5 行で残す。単に「計画通り」とは書かない。
- **Owner-correction count:** 完了報告後に owner 指摘で追加実装・追加テスト・
  plan ownership 修正が発生した回数を signal として数える。次 task でこの値が
  0 にならなければ、是正は失敗。0 でも、implemented-branch test map が無ければ
  偶然の可能性が残るため失敗扱い。
- **Two-key exit check:** T1 由来の exit 基準を維持しつつ、close 前に
  (a) carry-forward key = 残った未解決点の所有者・範囲・影響、
  (b) proof key = この task で実装した branch / semantic pin の直接テスト、
  の 2 つを別々に満たしたか確認する。片方だけでは close 不可。

T2 に遡及適用した結果、implemented branch の未pinは追加テストで閉じた。
現在残る未解決点は item 9〜11、implementation log の carry-forward 表、
および T6/T7 plan bullet に集約され、引き取る task と再トリガ条件が見えている。
