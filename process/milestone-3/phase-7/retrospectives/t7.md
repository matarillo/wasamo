## 目標・前提・計画仮説の再点検

### 観測された事実（反証可能な signal）

T7 は最初に `log.md` の carry-over を読み、T7 の責務を再分類した。重要だったのは、
collection writer を T7 に残す判断だった。これを T8 に送ると、T7 の runtime fixture は
`__set_*_list_state_for_test` だけで cardinality を動かすことになり、author が `Add` /
`Remove` で cardinality を駆動できるかを証明できなかった。結果として、handler append は
`handler_collection_append_is_observable_before_click_returns` で click-return 前の drain まで
観測できた。

中核実装は独立レビューで妥当と判定された。splice seam 統合、stage-then-commit、
same-batch removed item guard、positional retention、ZStack child-carried placement の
責務境界は大きく崩れていなかった。一方で、レビューは明確な proof gap を見つけた。
`collection_assignment_supports_string_and_bool_items` は append だけを証明しており、
`string[]` / `bool[]` の drop-last と literal reset は未実行だった。また、
`large_breadth_tail_append_converges_beyond_mutation_cap` は 64 child と末尾 text だけを見ており、
非発散の観測が無かった。

remediation では、`collection_assignment_string_bool_drop_last_and_literal_reset` を追加し、
`list_literal_string` / `list_literal_bool` を直接通した。cap fixture は 0 -> 8 と 8 -> 64 の
二段にし、`runtime_health == Healthy` と divergence diagnostics none を各段階で assert した。
さらに range mutation 後に conditional false/true toggle を実行し、共有 splice seam の
conditional 側も T7 fixture で直接踏んだ。

### 自己分析（どの層が外れたか）

責務境界の再点検はかなり効いた。T7 は T6 の static materialisation を奪わず、T8 の
screenshot evidence にも踏み込まず、T7 が閉じるべき runtime/headless behavior に集中できた。
特に collection writer を T7 に含めた判断は正しかった。T7 が writer を持ったことで、
handler evaluation、signal dirtying、reactive drain、range splice を同じ author path で結べた。

外れたのは、branch map の型 matrix と陽性対照の強度だった。実装者は i32 で append /
drop-last / literal-reset をまとめて証明し、string/bool は append のみで「型対応」と見ていた。
しかし implementation branch は element type と operation の直積を作る。`ListLit` の
string/bool helper は別関数であり、append が通っても literal reset は通らない。これは
T6 の i32 item-read miss と同じ失敗形で、type matrix を「代表型 + 追加型の append」で
閉じた気になっていた。

cap fixture でも同じことが起きた。64 child が作られた事実は「大きい N の materialisation」
であって、「scheduler が diverged していない」証明ではなかった。T7 の設計上、breadth は
effect cascade depth を消費しないはずだが、その invariant を観測せずに child count だけを
assert していた。レビュー後に health / diagnostics を直接見たことで、初めて cap fixture が
DD-M3-P7-007 の証跡に近づいた。

### レビュー分担の批判的検討

T7 でのレビュー分担は、merge 前に core design と proof gap を切り分けられたという意味では
成功している。実装者が start/end gate を残し、Claude がそれを機械的に照合し、指摘された
不足を remediation で閉じた。結果として、T7 はレビューなしより明らかに強い状態で着地した。

ただし、この成功を「今の分担で十分」と読むのは危ない。レビューが拾った不足のうち、
string/bool drop-last / literal-reset は implementation agent が自力で拾うべき planned proof
だった。`matrix row に複数 sub-branch がある場合は subcase / needle まで書く` という gate
条件を知っていたにもかかわらず、初回 close map は operation x type の直積を展開していない。
つまりレビューは未知の高度な欠陥を見つけたというより、既存ルールの適用漏れを救済した。
ここを「レビューが成功したからよい」で済ませると、次の high-risk task でも同じ種類の
self-proof drift を reviewer に押しつけることになる。

一方、レビューの価値も過小評価しない方がよい。T7 は runtime structural change で、
handler evaluator、reactive scheduler、loader state、Widget/Visual mutation、registry/effect
teardown が同時に動く。実装者は happy path の mental model に引っ張られやすく、
cap fixture のような「見た目は通っているが invariant を見ていない」テストを作りやすい。
full independent review は、この mental model の外側から「その assertion は何を区別しているか」
を問う装置として機能した。T7 のレビュー分担は、実装者の完全性を仮定したから成功したのではなく、
実装者の artifact を reviewer が反証できる形にしていたから成功した。

次に直すべきは、レビュー lane の選定ではなく、実装者側の close artifact の作り方である。
operation x type、size x health、structure x Visual order のように軸が複数ある場合、
start gate の planned proof obligations から表を作り、その行を close gate で消さない。
レビューはその表の外側にある盲点を探す工程に寄せるべきで、表の内側の既知 sub-branch を
拾う最後の網にしてはいけない。

### 計画仮説・前提の問い直し

1. **「T7 は collection writer を含むべき」という仮説。** 反証されなかった。
   authored handler append が click-return 前に range mutation を観測できたため、T7 が
   writer と reader effect を同時に閉じた意味はあった。
2. **「T7 は static materialisation を再実装せず、initial effect no-op を証明する」
   という仮説。** 反証されなかった。初期 `["A", "B"]` fixture は double-create せず、
   その後の append/reset/remove で同じ slot state を更新した。
3. **「stage-then-commit は staging failure proof まで T7 で閉じる」という仮説。**
   部分的に成り立った。invalid memory IR body による staging failure は tree unchanged と
   Visual order で直接証明した。一方、insert partial-failure rollback は mock-free fault surface
   が無く defensive carry として残した。
4. **「i32 の append/drop/reset + string/bool append で collection assignment type support を
   十分に証明できる」という暗黙仮説。** 反証された。string/bool drop-last と literal-reset は
   別 sub-branch だった。
5. **「64 child materialisation は cap convergence proof になる」という暗黙仮説。**
   反証された。health / divergence diagnostics を直接見る必要があった。
6. **「T7 は GUI evidence を持たなくてよい」という仮説。** 反証されなかった。ただし
   headless/runtime evidence は visible proof の代替ではない。T8/T9 owner はそのまま残る。

### 反証可能な是正テスト

- **Operation x type matrix:** handler / evaluator が `IrType` と operation の直積を持つ場合、
  close map は type support を代表型でまとめない。各 operation について i32/string/bool の
  direct test または non-applicable reason を書く。
- **Invariant assertion rule:** size/cap/convergence fixture は materialized count だけで閉じない。
  scheduler health、diagnostics absence、or equivalent invariant を直接観測する。
- **Positive-control pairing:** structural seam を共有化した場合、新旧両 consumer を少なくとも
  1 fixture で直接踏む。T7 では range mutation 後の conditional toggle がこの役割を持つ。
- **Defensive branch ledger:** mock-free に fault できない defensive branch は、未記載にせず、
  owner / scope / impact / close condition 付きで log または retro に残す。
- **Start/close row preservation:** start gate の planned proof obligations を close gate の
  implemented-branch test map と照合し、消えた row は「実装しなかった」のか「owner を送った」
  のかを必ず書く。

### 後続タスク / オーナーへ共有すること

T8 は T7 の runtime/headless proof を可視証跡へ接続する task であり、T7 の green をもって
visible behavior を証明済みにしてはいけない。gallery composition では structured-item /
`TypedValue` trigger が最初の subtask で owner-confirm を必要とする。T7 の collection writer は
scalar-item mutation を動かせるが、thumbnail が複数 per-item attributes を同時に必要とするなら、
それは T8 で scope decision として明示する。

T10 / phase-end へは、DD-M3-P7-007 residual rows、insert partial-failure rollback proof carry、
positional un-keyed identity baseline、whole-value collection assignment semantics、splice side-effect
bundleを handoff/spec sync 候補として渡す。特に partial-failure rollback は「現在テスト不能なので
忘れてよい」ではなく、future production-like fault surface が開いた時点で再発火する defensive
branch として扱う。

運用面では、T7 の full independent review は有効だった。しかし次回以降は、reviewer が
既知 matrix sub-branch を発見する状態を「成功」とだけ呼ばない。成功の基準は、
実装者が machine-derived branch map を subcase まで展開し、reviewer がその外側の設計・証明の
弱さを探せる状態にすること。T7 はそこに一歩届かなかったが、remediation で具体的な改善形は
見えた。
