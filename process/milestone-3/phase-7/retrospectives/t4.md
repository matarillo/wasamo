## 目標・前提・計画仮説の再点検

### 観測された事実（反証可能な signal）

T4 は最初の close report 後、独立レビューで blocker なしと判定された。レビュー
結論は「実装本体と start/end gate は適切、Phase 6 regression は skip せず green」
で、不足は minor 2 件 + 任意の深さ補強 1 件のみだった。follow-up では、任意
補強の合成テスト追加、`TailRangePlan` の冗長 field 削除、旧 thin wrapper 削除を
すべて実施し、`cargo test -p wasamo-runtime` は 383 → 384 unit tests になった。

実装中の deterministic failure は 1 件だけ。`ForLoop` cardinality を 0 にした後の
prefix offset 期待値を `4` としていたが、正しい算術は
`1 + 1 + 0 + 1 + 0 = 3` だった。実装バグではなく fixture arithmetic のミスとして
root-caused し、再実行で green にした。これは T4 log の trap #6 に記録済み。

### 自己分析（どの層が外れたか）

大きな責務境界は外れていなかった。T4 は `for` materialisation や runtime splice
へ踏み込まず、pure seam と conditional migration に留められた。一方で、最初の
実装は「T7 が実際に使うときの読みやすさ」を少し軽く見ていた。base offset と
tail-local plan の合成は T7 寄りと考えたが、pure に書ける contract なら T4 で
pin しておく方が seam の目的に忠実だった。

また、`materialized_index_for_declared_member` を wrapper として残したのは
call-site stability というより慣性だった。production call site が 1 個しかない
状況では互換 shim の価値は薄く、C1 canonization という goal には旧名を消して
正準 seam 名に寄せる方が合っていた。

### 計画仮説・前提の問い直し（オーナーと）

1. **「T4 は pure seam と conditional migration に絞る」という仮説。**
   反証されなかった。独立レビューでも T6/T7 へ残した境界は妥当と判断された。
2. **「tail plan の derivation は T4 が持つが、execution は T7」という仮説。**
   反証されなかった。ただし、T7 が消費する合成 point は T4 で pure test として
   pin できたため、proof depth は追加した。
3. **「`TailRangePlan` の exact shape を T4 で前方契約として強めてよい」という
   暗黙仮説。** 部分的に反証された。T4 が固定すべきなのは behavior であり、
   consumer-facing enum shape は T7 が確認・置換できる余地を残すのがよい。
4. **「旧 conditional helper 名を wrapper として残すと migration が読みやすい」
   という仮説。** 反証された。call site が少ないため、正準 seam へ直接寄せる方が
   T6/T7 の読み手に優しい。
5. **「Phase 6 regression gate は T4 で十分な observable proof になる」という
   仮説。** 反証されなかった。`conditional_toggle_preserves_declared_visual_order...`
   と `conditional_zstack_reinsert_uses_declared_placement_metadata` は skip せず green。

### 反証可能な是正テスト

- **Consumer-composition pin:** pure seam を後続 task が使う場合、個々の helper
  だけでなく「後続 consumer が行う合成」を 1 本は pure test として pin する。
  T4 では `expansion_seam_composes_for_slot_offset_with_tail_plan` がこれに対応。
- **Shape-vs-behavior split:** 後続 task が consumer になる enum / helper は、
  T4 が固定する behavior と、後続が変更してよい representation を close log に
  分けて書く。T4 では `TailRangePlan` の exact shape を T7 確認対象として残した。
- **Thin-wrapper audit:** seam canonization task では旧名 wrapper を残したら、
  production call-site 数と bridge value を明示する。価値が薄ければ commit 前に
  削除する。
- **Deterministic arithmetic failure rule:** prefix / cardinality test の失敗は
  期待値算術を明示的に式へ戻して root-cause する。retry green だけで済ませない。

### T4 の進み方が改善した理由の批判的分析

T4 は T2/T3 より明らかに安定して進んだ。最初の独立レビューで blocker は無く、
指摘は minor 2 件 + optional depth 1 件に留まり、すべて commit 前 follow-up で
閉じられた。これは単に「今回は運が良かった」ではなく、少なくとも 2 つの
改善が効いた可能性が高い。

第一に、start gate / end gate の責務をかなり明確にした。T4 start では、
`ForLoop` production construction、loader dual-gates、`ForLoopSubtree`、collection
writer、ZStack placement migration を明示的に T4 外へ出し、T4 は「pure seam +
conditional migration」に絞った。この境界が先に log に残ったため、実装中に
T6/T7 の runtime materialisation へ手を伸ばす誘惑が減った。end gate も
`rg` / `git diff` 起点の branch map にしたため、レビュー側は主張を再現しやすく、
議論が「見落とし探し」ではなく「契約をもう少し深く pin するか」に移れた。

第二に、独立レビューを最初から前提に置いたことで、T3 のように重いセルフチェックを
増殖させずに済んだ。T3 の meta double-loop で見えた通り、実装者自身の
checklist は「自分が列挙できたもの」以上を見つけにくい。T4 では自分で完全性を
過剰に証明しようとするより、機械出力に基づく最小限の audit artifact を作り、
独立 reviewer がそこを ground truth と照合する形に寄せた。この方が実際に効いた:
reviewer は implementation defect ではなく、consumer-composition test、contract
shape、thin wrapper という、実装者の視界では「許容」として流れやすい読み手負担を
拾った。

ただし、ここから「セルフチェックは不要」と一般化するのは危険。T4 は T3 と違って
author diagnostic matrix を持たず、branch surface も pure cardinality / offset /
tail-plan に限られていた。つまり改善の一部は task の性質にもよる。T6 の loader
dual-gates や T7 の splice side-effect bundle は、T4 より branch / side-effect
surface が広いので、同じ軽さで足りるとは限らない。

後続へ共有すべき運用上の結論は次の形がよい。

- start gate は「この task が何をしないか」を owner / reviewer が反証できる粒度で
  先に書く。これが一番効く。
- end gate は散文の自己申告ではなく、`rg` / `git diff` / named tests を reviewer が
  その場で再走査できる artifact にする。
- 完全性チェックは実装者だけで抱え込まない。特に high-risk lane では、独立レビューを
  proof apparatus の一部として最初から設計し、セルフチェックは reviewer が照合しやすい
  材料作りに絞る。
- ただし diagnostic matrix / side-effect bundle が広い task では、セルフチェックの
  簡素化は「branch map を薄くする」ことではない。外部 SSOT（DD matrix、side-effect
  bundle、plan bullets）を列挙元にすることは維持する。
