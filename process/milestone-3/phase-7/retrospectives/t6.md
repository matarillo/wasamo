# T6 レトロスペクティブ

タスクブランチ: `feat/m3-phase-7-t6`

T6 は loader static path: textual IR の `for` を runtime loader で
materialise し、初の production `DeclaredMemberSlot::ForLoop` を構築するタスク。
T2/T4 で意図的に残していた deferred-load reject / production-dead slot を閉じ、
初期 collection cardinality から 0..N 個の generated children を作り、各 child の
loop-local `item-read` / `index-read` binding を `ForItemEvalContext` 経由で評価する
ところまでを実装した。T7 の structural `ForLoopSubtree` effect、handler-side
collection writer、tail append/remove、cap fixture、GUI evidence は T6 の範囲外として
明示的に残した。

start gate / close gate / review remediation / rereview closure は
[../implementation/log.md](../implementation/log.md) の T6 entries に記録済み。

実装コミット: `76198e8`。

## 目標・前提・計画仮説の再点検

### 観測された事実（反証可能な signal）

T6 は開始時に `log.md` の carry-over を読み、T6 が閉じるものと閉じないものを
分け直した。これにより、当初 plan にあった「T6で no-op `ForLoopSubtree` effect を
登録する」仮説は退け、T6 は static load の single-pass materialisation、T7 は
structural effect の initial reconcile / mutation と分けた。この境界設定は最後まで
崩れなかった。

一方で、初回実装には重大な実欠陥があった。i32 item read の runtime path は
validator では許可されていたのに evaluator が string item reader を呼んでいたため、
計画では「string / i32 item and index cases」を証明するはずだったものが、close map で
string 側へ縮んでいた。これは単なる test omission ではなく、「計画した proof obligation が
実装後の artifact で黙って消えた」ことが機能欠陥と一致した例だった。

独立レビュー後の remediation では、i32 item stringify、string item -> i32 target reject、
index -> bool target reject、`if` + `for` slot offsets、production ZStack placement、
component-body parser reject、Box `if { for }` nested-control-flow reject を追加し、
runtime integration tests は再レビュー環境でも skip せず実走した。

### 自己分析（どの層が外れたか）

T6 の大枠の責務境界は比較的よく守れた。T7 の mutation writer / structural effect へ
踏み込まなかったこと、T8 の GUI-visible proof を T6 に引き込まなかったこと、
T5 の child-carried placement を static generated children に接続したことは、start gate の
再分類が効いた結果だった。

外れたのは、typed branch の網羅と close artifact の忠実性だった。`ItemRead` は
`HandlerExpr` 上では1種類でも、runtime では i32/string/bool で評価経路が異なる。
実装者は「string binding context なら item value を文字列として扱う」という意図に
引っ張られ、実際には string list しか読まない呼び出しを置いた。さらに、開始時に
i32 を planned proof として書いていたにもかかわらず、close map では string fixture だけで
満足してしまった。これは branch map の粒度以前に、start-gate obligation と close-gate
row の差分を機械的に照合していなかった失敗である。

T5 のレビュー分担は成功していた。T5 では start gate / close gate / independent review が
scope drift と proof overclaim をかなり抑えた。T6 でも同じ分担は最終的に成功したが、
それは「実装エージェントが最初から正しく避けた」からではなく、レビューで大きめの穴を
検出できる構造があったからだった。ここは楽観してはいけない。runtime structural work は
branch surface が広く、実装者は自分がいま触っている happy path のモデルに強く引きずられる。
型、container、slot offset、placement、effect ownership が同時に増える task では、
実装者単独の初回 self-review が全 branch を拾い切ることを期待するのは現実的でない。

ただし「避けられない」で済ませるのも弱い。今回の欠陥は、start obligation と close map の
差分検査、element-type matrix の direct test skeleton、`read_item_i32_tracked` が
実際に到達するかの coverage-like needle を入れていれば、実装者側でも早く見つけられた。
つまり問題は能力ではなく、self-check の形がまだ人間の記憶と散文に寄りすぎていたことにある。

### 計画仮説・前提の問い直し

1. **「T6 は no-op structural effect ではなく static materialisation を閉じる」
   という修正仮説。** 反証されなかった。T6 は pre-effect static load を閉じ、T7 に
   initial effect no-double-create を明示 owner として残せた。
2. **「initial per-item binding registration は T6 の責務」という仮説。**
   反証されなかった。static children が `item-read` / `index-read` を正しく評価するには
   T6 で必要だった。
3. **「loader dual-gate matrix は T6 で閉じられる」という仮説。**
   部分的に成り立った。直接 container、body shape、loop-local scope/type、
   component-body parser surface は閉じた。一方で mutation-time runtime diagnostics は
   T7 owner として残る。
4. **「T5 で成功したレビュー分担を T6 に適用すれば大きな穴は避けられる」
   という暗黙仮説。** 反証された。分担は穴を発見・修復する仕組みとしては有効だが、
   初回実装で機能欠陥を予防し切る保証ではない。
5. **「integration happy path があれば semantic branch は十分」という仮説。**
   反証された。`static_for_materialises_initial_children_and_loop_local_bindings` は
   string item + index を見ていたが、i32 item path は全く通っていなかった。
6. **「component-level `for` は root widget の直下 `for` と同じように判定できる」
   という rereview中の一時仮説。** 即時反証された。`ParentKind::Root` は root node の
   parent を表すだけで、component body member slot ではない。textual IR の component body
   grammar と root widget body grammar を混同してはいけない。

### 反証可能な是正テスト

- **Start/close obligation diff:** start gate の planned proof obligations を close gate の
  implemented-branch test map と照合し、消えた row があれば「owner task」「scope」「impact」
  を必ず書く。T6 の i32 row はこの diff で見つけるべきだった。
- **Typed branch skeleton first:** `IrType` / `IrStateType` / `HandlerExpr.elem` が branch を
  作る task では、実装前または実装直後に i32/string/bool の direct test skeleton を置く。
  happy path integration が1型だけなら「semantic branch complete」と書かない。
- **Dead-method reachability needle:** 新しい trait method や type-specific reader を足したら、
  `rg` で call path を列挙し、少なくとも1つの direct test がその method を到達可能にしている
  ことを close map に書く。T6 では `read_item_i32_tracked` が初回 dead-ish だった。
- **Positive-control expansion:** slot-offset / placement / layout など wrong implementation が
  同じ単発見た目を出せる branch は、true/false、default/explicit、empty/nonempty のような
  陽性対照を最初から fixture に含める。
- **Rereview residual triage:** レビューで「低優先・ブロッカーではない」とされたものでも、
  DD matrix の row に対応する場合は task内で閉じるか、owner/scope/impact/close condition を
  log に追加する。T6 の component-level row はこの扱いが必要だった。
- **Parser-vs-validator surface check:** textual parser で表現不能な matrix row と memory IR
  validator が担う row を分ける。component body-level `for` は parser surface、root widget
  body-level `for` は validator/materialisation surface。

### 後続タスク / オーナーへ共有すること

T7 は T6 よりさらに危ない。T6 は static load だけでも i32 item path を落としたが、T7 は
collection writer、structural effect、tail range splice、generated child staging、
effect disposal、same-batch removed item、cap convergence、ZStack placement mutationを同時に扱う。
実装者 self-check だけで十分という仮説は置かない。T7 start gate では、DD-M3-P7-007 の
runtime validation / cap fixture rows と T6/T5 carry-forward rows をそのまま branch skeleton に
落とし、close gate で row が消えていないことを機械的に確認する。

T7 への具体的な引き継ぎは次の通り。

- `ForItemEvalContext` / `read_item_binding_tracked` は T7 の tail-inserted children でも同じ
  semantics を使う。i32 stringify と bool string-display reject を変えない。
- T6 の static materialisation は structural effect 導入前の single-pass proof でしかない。
  T7 は `ForLoopSubtree` effect の初回 run が既存 static children を double-create しないことを
  独立に証明する。
- T5/T6 の ZStack path は production loader + layout で child-carried placement を証明済み。
  T7 は mutation-time range splice で同じ carrier を staging/commit する。
- component body-level `for` と root widget body-level `for` の区別を崩さない。

オーナーへの運用上の共有は、T5 のレビュー分担は成功しているが、T6 が示した通り、
「大きめの機能欠陥を実装エージェントが初回から回避する」ことには限界がある、という点。
今後の high-risk task では独立レビューを最初から予定するだけでなく、実装者側が
start/close obligation diff、typed branch skeleton、machine-derived branch map を
必ず用意する。レビューは品質保証の外付けではなく、実装者の artifact を反証する工程として
設計する。
