## 目標・前提・計画仮説の再点検

### 観測された事実（反証可能な signal）

T5 は実装前に `log.md` から T4/T1/T3 の carry-over を読み直し、T5 が閉じるものと
閉じないものを表にした。これにより、ZStack placement storage migration は T5、
unified splice seam と `ForLoopSubtree` は T7、textual-IR `for` materialisation は
T6、Grid placement migration trigger は将来の Grid structural-mutation task と
いう境界を実装前に記録できた。

実装後の独立レビューは blocker なしだったが、proof structure には有効な指摘が
あった。初回は test-module mirror が production logic を複製しており、branch map も
「直接 production branch を発火するテスト」として強く書きすぎていた。follow-up では
mirror structs を削除し、production helper を抽出して production code と tests が
同じ関数を呼ぶ形へ直した。さらに、double default site と per-container field choice を
close gate の behavior / invariant carry scan に追記した。

post-commit verification は green。`cargo fmt --all -- --check`、`cargo clean`、
release build、debug build、`cargo test --workspace` はすべて成功し、既存 warning
以外の新規 failure は無かった。

### 自己分析（どの層が外れたか）

大きな責務境界は外れていなかった。T5 は T7 の splice execution や T6 の loader
materialisation へ踏み込まず、ZStack child-carried placement migration と現行
static / conditional path の preservation に留まった。この点では、T4 が残した
carry-forward と T5 start gate の再分類が効いた。

一方で、証明の層は初回で外れた。mirror tests は「logic をテストしている」ように
見えるが、production branch そのものを通っていないため、branch map の direct-test
claim と一致しない。これは T3 で見えた branch-map granularity 問題の小型版であり、
T5 でもまだ「自分の実装意図」と「reviewer が機械的に照合できる証跡」の差を
過小評価していた。

独立レビューを最初から予定していたことは有効だったが、それは self-proof の代替では
ない。T5 の初回 close gate は、reviewer が照合できる材料を十分に残したからこそ
修正可能だった。しかし、レビューが予定されている安心感が、branch map の過大主張を
許す方向へ働いた可能性もある。したがって「独立レビュー前提」は、証明を軽くする
許可ではなく、証明を反証可能な形に整える制約として扱うべきだった。

### 計画仮説・前提の問い直し（オーナーと）

1. **「T5 は ZStack placement storage migration を閉じ、splice seam は T7 に残す」
   という仮説。** 反証されなかった。実装も review conclusion もこの境界を支持した。
2. **「child-carried placement は layout tree だけでなく runtime child slot に必要」
   という仮説。** 反証されなかった。runtime mutation が carrier を持つことで、
   conditional path と future splice seam が同じ storage model を使える。
3. **「Grid `cell_placements` は T5 で移さず static-only として残せる」という仮説。**
   反証されなかった。ただし future Grid structural mutation の前には migration
   trigger を必ず再評価する必要がある。
4. **「OS-bound type の placement logic は test-module mirror で十分」という初期仮説。**
   反証された。T5 の logic は pure helper へ抽出でき、production code と tests が
   同じ helper を呼べるため、mirror より free-function extraction が適切だった。
5. **「start/end gate を明確化し、独立レビューを最初から予定すれば十分」という仮説。**
   部分的にしか成り立たなかった。gate は scope drift を抑え、review は proof gap を
   見つけたが、gate 自体は初回 branch map の過大主張を防げなかった。
6. **「T4 の成功パターンを T5 へ引き継げる」という仮説。** 部分的に成り立った。
   T4 の carry-forward discipline と start/end gate の形は T5 の scope control に
   効いた。一方、T5 には T5 固有の proof blind spot があり、T4 の成功は
   自動的な品質保証ではなかった。

### 反証可能な是正テスト

- **Mirror-before-extraction check:** OS-bound production type に unit-testable logic が
  混じる場合、test-module mirror を使う前に pure helper extraction が可能かを
  明示的に検討する。抽出できるなら mirror は使わない。抽出できない場合だけ、
  なぜ production API を歪めるかを close gate に書く。
- **Direct-test claim audit:** Implemented-branch test map の各 test 名について、
  その test が production branch / helper / integration path のどれを直接通るかを
  source query と一致させる。test-only reducer や mirror を通る場合は
  direct production branch と書かない。
- **Double-default split:** default behavior が insertion と arrange fallback のように
  複数箇所に存在する場合、それぞれの役割を分けて記録する。production default と
  defensive fallback を同じ証明行へ混ぜない。
- **Review-as-apparatus rule:** 独立レビューは proof apparatus の一部として最初から
  組み込むが、実装者は reviewer が反証できる machine-derived artifact を用意する。
  「レビューされるから粗くてよい」ではなく、「レビューで照合可能な形にする」が条件。
- **Carry-over absorption table:** task start では、前 task の carry-forward rows を
  task-owned / later-owned / non-applicable に分類してから plan を修正する。T5 では
  効いたので、T6/T7 でも継続する。

### 後続タスク / オーナーへ共有すること

T6/T7 は、T5 と同じ start/end gate 形式を使う価値がある。ただし T7 は T5 より
side-effect surface が広く、splice primitive、Visual sibling order、layout dirty、
effect teardown、registry disposal、range materialisation を同時に扱うため、
T5 と同じ軽さでは足りない。T7 では full independent review を前提にしつつ、
branch map と side-effect table の列挙元を `rg` / `git diff` / DD rows へさらに
強く寄せる必要がある。

T7 への具体的な引き継ぎは、ZStack generated children が arrange fallback ではなく
runtime child slot placement を持って commit されること。T5 の insertion default は
そのための production path であり、`arrange_zstack` の `None` fallback は manually
constructed layout tree への defensive behavior として扱う。

オーナーへの運用上の共有は、T4/T5 の「start gate 明確化 + 独立レビュー前提」は
有効だったが、self-check を不要にするものではない、という点。むしろ有効だった理由は、
reviewer が反証できる artifact を先に残したことにある。今後も high-risk task では
独立レビューを最初から予定しつつ、実装者側の close gate は過大主張を避け、
machine-derived artifact と direct-test ownership を一致させる。
