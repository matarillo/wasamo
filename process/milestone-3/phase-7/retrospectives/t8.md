## 目標・前提・計画仮説の再点検

### レビュー分担の批判的検討（owner 設問）

owner は「T8 のレビュー分担は成功していると思う」とした。安全性の意味
では成功している — レビューは merge 前に ① add2 frame の clip（折返し
8 個目が下端で判読不能なのに end gate が "NEW #7 gone" と主張）と ②
capture invocation の再現性欠落を捕まえ、両者は remediation で閉じた。
しかし「成功」と評するのは**危うい**。批判的に見ると 3 点ある。

**第一に、レビューが拾ったのは未知の欠陥ではなく、実装者が既に持って
いたルールと観測の未適用だった。** start gate で私は自分の言葉で
「a positive control no one can read is not evidence」と viewport-visibility
制約を armed していた。さらに最初の add2（760 幅）を読んだ時点で
「NEW #7 は折返し第2行で部分可視」と**自分で観測**していた。にもかかわ
らず end gate には「add2 = 8 (+NEW #7) → remove: NEW #7 gone」と、clip を
legibility 失敗として扱わずに書いた。ルールも観測も手元にあり、両者を
結びつけなかった。レビューはその結線を肩代わりした。

**第二に、これは T7 retro が既に指摘した self-proof drift の再発である。**
T7 では「operation × type の直積」を代表型で閉じた気になり、reviewer に
sub-branch を拾わせた。T7 retro の corrective は「直すべきは review lane
でなく実装者側 close artifact の作り方」だった。T8 はその corrective が
**evidence legibility の層へ転移しなかった**ことを示す。drift の表面は
「branch matrix」から「prose vs pixels の自己整合」へ移ったが、根（実装者
の close artifact を ground truth に対して自己反証していない）は同じ。
しかも T8 は Rust 無変更で注意予算が大きい簡単なタスクであり、そこで
再発した事実は「review が拾えたからよい」では済まないことを示す。

**第三に、では review に価値が無いかというと逆である。** ① は reviewer が
**実 pixel を私の prose 主張と突き合わせた**から surface した。もし
reviewer が end gate 文（"NEW #7 gone"）を信用していれば clip overclaim は
通過した。つまり review の価値は「実装者の textual claim を ground truth
で反証する」点に明確にあった — それは本来実装者の自己分析が果たすべき
工程である。

**結論（批判的）:** T8 のレビュー分担は *safety net としては機能したが、
clean success ではない*。成功の正しい基準は「reviewer が実装者の既知
ルール適用漏れを救済すること」ではなく、「実装者が close artifact を
ground truth（GUI は pixel、branch は機械出力）に対して**自己反証済み**で
渡し、reviewer はその外側の盲点を探せること」。T8 はこの基準に一歩
届かず、T7 と同じ位置で躓いた。是正は review lane の変更ではなく、
**GUI evidence の end gate を書く前に、各 frame を主張文と pixel で
1 対 1 照合する self-falsification step を必須化する**こと（下記
是正テスト）。

### owner-confirm gate のやり取りと前提・仮説の差異（owner 設問）

start gate の仮説は「owner-confirm は structured-item / `TypedValue`
trigger の **単一** consult、推奨は single-attribute 縮約、routing は
M4/M5 で **settled**」だった。実際の対話には次の差異があった。

1. **trigger は単数でなく cluster だった。** framing（DD-002 / T1
   addendum 4）は「gallery が `TypedValue` trigger を発火させる」と予測
   した。実際に gallery が surface したのは**3 つの別 deferred 軸**で、
   かつ「per-item fill を変えたい」の真の阻害は `TypedValue` でなく
   **bindable-`fill`（DD-M3-P2-004）**だった。framing の方向（per-item
   record データ）は正しかったが、**binding 制約の帰属を取り違えて
   いた**。これは forcing-artifact 級の差異で、item 10 に記録した。
2. **consult は one-shot でなく多ラウンド探索だった。** start gate は
   暗黙に「推奨提示 → owner 受諾」を想定したが、実際は owner が 3
   composition を順に出し、各回 source 検証を要した。決定の**数**（1
   決定）は仮説どおりだが、**過程**は反復探索。これは owner-confirm の
   あるべき姿で問題ではないが、「単一 yes/no」モデルからの差異。
3. **owner が Phase 7b を留保した（仮説に無し）。** start gate は trigger
   の M4+ routing を settled として記録していた。owner はこれを「M4+ は
   現行想定、Phase 7b 挿入を留保」へ**前提改訂**した。どの先行 doc にも
   無かった軸で、log.md に明示記録した。
4. **owner が Clear / Reset 追加を要求した。** owner は clear/reset の
   ハンドラが実装されているかを確認し、gallery でも見せるよう求めた
   （clear/reset は ADR どおり literal 代入 `xs = []` / `xs = [...]` で
   実装済み）。私の end gate は append/drop-last のみで item 5 を満たすと
   し、4 form 全ては見せていなかった。これは私の「最小 evidence」志向 vs
   owner の「authored surface を全部見せたい」志向の差で、Clear/Reset
   追加 + 2nd capture sequence により全 4 form を可視化して解消した。

総じて、owner-confirm gate は「単一 trigger を上げる」という構造仮説は
当たったが、**(i) trigger の数と帰属、(ii) routing の確定性、(iii)
demonstration の網羅度**で前提とずれた。いずれも scope 拡張や AC 変更
ではなく、in-task で記録・吸収できた範囲。

### 反証可能な是正テスト

- **GUI evidence self-falsification:** GUI 陽性対照の end gate を書く前に、
  各 frame の主張文（"X が現れた" / "Y が消えた" / "Z 個"）を**実 pixel と
  1 対 1 で照合**し、判読不能な要素を主張に含めない。clip / fold 越え /
  blur は「主張から外す」か「撮り直す」かを明記する。
- **Trigger 帰属の検査:** deferred 機能の trigger を記録する際、framing が
  予測した軸（例: `TypedValue`）だけでなく、**実際に reject を発火させた
  source ルール**（例: `box_fill_state_ident_rejected`）まで辿り、帰属を
  source で固定する。
- **Demonstration 網羅の宣言:** authored surface に N 個の form がある場合
  （collection mutation = append/drop-last/clear/reset の 4）、evidence で
  何を見せ何を省くかを明示し、省略は「証明は別テストにある」と pointer
  を付ける（append/drop-last は visible、clear/reset も owner 要求で visible
  化、全 4 form を `iteration`/`clearreset` 2 sequence で被覆）。
- **Routing 確定性の保留:** deferral の milestone routing を記録する際、
  owner 留保（Phase 7b 等）があれば "settled" と書かず provisional 限定詞
  を付す。
