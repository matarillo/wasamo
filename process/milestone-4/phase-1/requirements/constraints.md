# M4-Phase 1 制約引き継ぎ

ワークフロー [§2.1](../../../procedures/workflow.md) のアウトプット。前
フェーズの永続記録から本フェーズ（**モニターごとの DPI 対応と座標空間の
境界**）に効く制約を切り出し、本フェーズの論点・範囲・検証方針に合わせて
組み直す。単純な写しではなく、各項目に「Phase 1 でどう効くか」と**採否**
（本フェーズの制約として引き込むか / 別の持ち主へ送るか）を付す。

**引き継ぎ源が 3 本あるのは、本フェーズが M4 の最初のフェーズだから**で
ある。通常は前フェーズの `implementation/handoff.md` 1 本だが、M4-Phase 1 の
「前フェーズ」はマイルストーンをまたぐため、次の 3 本を源とする:

- [M3-Phase 8 handoff](../../../milestone-3/phase-8/implementation/handoff.md)
  — 直前フェーズの技術的な持ち越し制約（本フェーズに効くのは 4 件）。
- [M3 マイルストーン handoff](../../../milestone-3/handoff.md) — M3 が
  M4 に残した残務群。本フェーズが消化するのはそのうち 1 行だけであり、
  切り分けの明示が §3 の仕事。
- [M3-Phase 5 handoff](../../../milestone-3/phase-5/implementation/handoff.md)
  — DPI の技術的実体を書いた文書。
  [DD-V-022](../../../cross-milestone/decisions/dpi-awareness-m4-deferral.md)
  が「これは方針の決定であって技術の引き継ぎではない、技術の中身は
  Phase 5 の handoff が持つ」と明示的に委ねた先であり、本フェーズにとって
  実質的な第一の入力である。

Phase 1 の前提（[plan.md](../../plan.md) M4-Phase 1 行）:

- **プロセス / ウィンドウの DPI 対応を宣言し、DIP と物理ピクセルの変換を
  レイアウト / 描画 / 入力の境界に局所化し、モニターをまたぐ
  `WM_DPICHANGED` を扱う。**
- **新しい作者向けの面（DSL 面）を持たない。** 消費者は既存の写真
  ギャラリーであり、plan のフェーズ終了基準 5 はこの形のフェーズを
  「既存アプリを新しい実行時の性質のもとで示す」ことで満たすと定めている。
- **最初に置かれた理由は、後続のすべてが座標変換を消費するから。**
  当たり判定（Phase 2）、カーソルと変換中文字列の画面矩形（Phase 5・6）、
  最前面層の配置（Phase 9）、ウィンドウごとの倍率（Phase 8）。1:1 の
  世界で作ってから倍率を入れると、それらの目視の証拠を撮り直しになる。

## 1. 実行時が DPI 非対応であるという技術的実体（**採用 — 本フェーズの出発点**）

[M3-Phase 5 handoff §持ち越し制約](../../../milestone-3/phase-5/implementation/handoff.md)
の第 1 項が、M4 の方針固めが読むべき技術の中身として次を確定している。
本フェーズの起草時点（2026-07-28）に現物を再確認し、**3 点とも当時のまま
変わっていない**ことを確かめた:

- [`wasamo-runtime/src/window.rs`](../../../../wasamo-runtime/src/window.rs)
  の `create_hwnd` は DPI 対応を一切宣言しない（`SetProcessDpiAwarenessContext`
  の呼び出しもアプリのマニフェストもない）。したがって高 DPI モニターでは
  DWM がウィンドウ全体を画像として引き伸ばす（125% なら論理 800×600 が
  物理 1000×750 として描かれ、全要素が一様に滲む）。
- レイアウトは `GetClientRect` のクライアントピクセルを論理単位として
  1:1 で消費する（`window.rs` の `set_root` と `wnd_proc` の `WM_SIZE`）。
  倍率は一度も掛からない。
- `WM_DPICHANGED` の処理は存在しない。

**Phase 1 でどう効くか:** これが本フェーズが直す対象そのものである。
AC7 の 3 つの要求（宣言する / 高 DPI で鮮明に描く / モニターをまたぐ
変化を扱う）は、上の 3 点に一対一で対応する。

**採否:** **採用（本フェーズの出発点）**。ただし「何を直すか」は確定でも、
「どこで変換するか」は未確定であり、§2 と §4 が示す論点として設計判断へ
送る。

## 2. `layout-engine.md` §3.1 の再考トリガーは M3 内で発火し、未処理のまま来ている（**採用 — 設計判断の入力**）

[layout-engine.md §3.1](../../../../docs/notes/layout-engine.md) は M1 の
時点で「**物理ピクセルをエンジンが意識すべきか。DirectWrite のヒンティング
精度に影響する。M1 では論理ピクセルのみで動作。Grid / ScrollView 導入時に
再考が必要**」と書いている。その再考の合図（Grid / ScrollView）は M3 で
発火したが、M3 の中では処理されなかった（[DD-V-022](../../../cross-milestone/decisions/dpi-awareness-m4-deferral.md)
の Context がその事実を記録している）。

**Phase 1 でどう効くか:** このノートの問いは本フェーズの中心的な設計判断
そのものである。しかも問いの本体は「ウィンドウを何倍にするか」ではなく
**「DirectWrite のヒンティング精度」**、つまり文字が鮮明に出るかどうかで
ある。§4 の棚卸しが示すとおり、文字は
[`text.rs`](../../../../wasamo-runtime/src/text.rs) で
`CompositionDrawingSurface` にラスタライズされてから Visual に載る。
「レイアウトの数値に倍率を掛ける」だけでは、この面の解像度が上がらない
限り文字は鮮明にならない。**本フェーズの難所は座標の掛け算ではなく
ラスタライズ面の解像度**である、というのがこのノートから引き出すべき
含意である。

**採否:** **採用（設計判断の入力 — 結論は先取りしない）**。ノートの問いへの
答え（レイアウトが物理ピクセルを意識するか否か）は本フェーズの判断項目で
決める。決めたあとは
[docs/architecture.md](../../../../docs/architecture.md) の未解決事項の表に
ある DPI の行（「Open」のまま）と、ノート本体の両方を同期する義務が伴う。

## 3. M3 残務群のうち本フェーズが消化するのは 1 行だけ（**採用 — 範囲の切り出し**）

[M3 マイルストーン handoff §M4 Residual Cluster](../../../milestone-3/handoff.md)
は 6 行の残務を挙げている。本フェーズが消化するのは最後の 1 行
（**実行時の DPI 対応と DPI を局所化したレイアウトの証拠**）**だけ**で
あり、他の 5 行は M4 の別のフェーズが持つ:

| M3 残務群の行 | 持ち主 |
|---|---|
| 実画像の部品 / 画像の読み込み | M4-Phase 4 |
| サムネイルの当たり判定 | M4-Phase 2 |
| ホイール / ドラッグでのスクロールと実スクロールバー | M4-Phase 4 |
| ライトボックスのモーダルフォーカスと入力の閉じ込め | M4-Phase 2 |
| 動的なウィンドウタイトル / 動的な件数表示 | 件数 = M4-Phase 3、タイトル = M4-Phase 8 |
| **実行時の DPI 対応と DPI を局所化したレイアウトの証拠** | **M4-Phase 1（本フェーズ）** |

**Phase 1 でどう効くか:** 本フェーズはギャラリーを消費者として使うが、
**ギャラリーの機能を進めるフェーズではない**。ギャラリーは「同じ絵が
鮮明に出るか」を見るための素材であって、サムネイルのクリックもスクロール
も本フェーズでは動かない。証拠の読み方（§7）と、範囲外の線引き（framing の
範囲の節）の両方に効く。

**採否:** **採用（範囲の切り出し）**。上表は framing の「含まないもの」の
根拠として再利用する。

## 4. 座標を運ぶ既存経路の棚卸し（**採用 — 本フェーズの面積の実体**）

前フェーズの handoff には書かれていないが、本フェーズの面積を見切るために
現物を読んで確定した事実。変換境界をどこに置くかの判断（§2）は、この
経路の一覧に対して閉じていなければならない。

| 経路 | 現在の単位 | 本フェーズでの扱い |
|---|---|---|
| `wnd_proc` の `WM_SIZE`（`lparam` のクライアント幅・高さ）→ `run_layout_as_window_root` | 物理ピクセル | 入口。変換が要る |
| `set_root` の `GetClientRect` → 初回レイアウト | 物理ピクセル | 入口。変換が要る |
| `wnd_proc` の `WM_MOUSEMOVE` / `WM_LBUTTONDOWN` / `WM_LBUTTONUP`（`lparam` の x・y）→ `update_hover` / `hit_test_click` | 物理ピクセル | 入口。変換が要る。**当たり判定は M3 時点で既に存在する**（Button のホバーと押下）ため、Phase 2 の新面を待たずに本フェーズが直す対象 |
| `widget.rs` の `Visual::SetOffset` / `SetSize` | レイアウト座標をそのまま | 出口。Composition の Visual は HWND のクライアント物理ピクセル空間にある |
| `window.rs` の根の `SetRelativeSizeAdjustment(1,1)` | HWND クライアント（物理）に追従 | 出口。根に倍率変換を掛ける案を採るなら、この設定との相互作用を確かめる必要がある |
| `text.rs` の `TextRenderer::measure`（DirectWrite の計測値）→ レイアウト | 96 DPI 相当の論理単位 | レイアウトが DIP のままなら**変換不要**。この一点が「レイアウトは DIP のまま」を支える |
| `text.rs` の `draw_text` → `CreateDrawingSurface(Size)` + 既定 96 DPI の D2D コンテキストへ描画 | 論理サイズ = 面のピクセル数 | **出口かつ本フェーズの難所**（§2）。面の実解像度と D2D 側の DPI を上げない限り、倍率を掛けても文字は鮮明にならない |
| `TypographyStyle::size_sp`（12 / 14 / 20 / 28）| 論理単位 | DIP と定義すれば変更不要。定義の明文化が要る |

**Phase 1 でどう効くか:** 入口 3 種・出口 4 種の計 7 か所が変換境界の候補
であり、判断項目はこの一覧に対して「どこで変換するか」を答える。**一覧に
ない経路がないこと**（新しい座標の入口を見落としていないこと）は、
[implementation-gates.md](../../../procedures/implementation-gates.md) の
呼び出し箇所の監査表で閉じる。

**採否:** **採用（面積の実体 + 実装ゲートの監査対象）**。

## 5. C ABI と規範スペックが単位を定義していない（**採用 — 論点入力。plan との緊張つき**）

現状、外向きの契約は単位を一言も定義していない:

- [`docs/abi_spec.md`](../../../../docs/abi_spec.md) §4.2 の
  `wasamo_window_create(title_utf8, title_len, width, height, out)` は
  `width` / `height` の単位を規定していない。**座標を運ぶ ABI 関数は現状
  これ 1 本だけ**である（`WindowState` にはマウス・リサイズの callback の
  受け口があるが、ABI から設定する関数は存在せず、実行時の内部でのみ
  使われている）。
- [`docs/dsl_spec.md`](../../../../docs/dsl_spec.md) は寸法を「レイアウト
  座標系のピクセル extent」と書く。その座標系が何インチ分なのかは
  書かれていない。
- [`docs/architecture.md`](../../../../docs/architecture.md) の未解決事項の
  表は DPI の行を「Open」のまま持っている。

**Phase 1 でどう効くか:** 倍率が 1 でなくなった瞬間、「`width: 800` とは
何か」は答えが要る問いになる。本フェーズはこの 3 つの記述を同時に確定
させる義務を負う（plan のフェーズ終了基準 4「仕様の同期」）。

**plan との緊張（framing で判断を要する）:** [plan.md](../../plan.md) は
**M4-Phase 7 をマイルストーン唯一の ABI 面のフェーズ**と書いている。本
フェーズが `wasamo_window_create` の既存引数の**意味論を明文化する**だけ
なら署名は動かず、両立する。しかし判断項目の結論として**ホストが倍率を
問い合わせる新しい関数**が要ると出た場合、それは plan の記述と衝突し、
[DD-V-026](../../../cross-milestone/decisions/plan-revision-discipline.md)
の 2 段階目（範囲・達成条件・フェーズ構成）の改訂手続きが要る。この分岐は
framing のオーナー合意事項として明示的に扱う（黙って広げない）。

**採否:** **採用（論点入力 — 未結論。plan 改訂の要否も含めて framing で
扱う）**。

## 6. 宣言的な C / Zig ホストの境界を崩さない（**採用 — 設計制約**）

[M3-Phase 8 handoff](../../../milestone-3/phase-8/implementation/handoff.md)
の持ち越し制約 4。ギャラリー（およびカウンタ）の C / Zig ホストは
**宣言的**であり、コンパイル済みの `.uic` を埋め込んで
`wasamo_load_ui(WASAMO_LOAD_MEMORY, …)` を呼ぶだけで、ホスト側での部品の
操作を持たない。この境界を変えるのはホスト移植の細部ではなく、それ自体が
独立した判断である。

**Phase 1 でどう効くか:** DPI 対応の宣言方法の選択に直撃する。アプリの
マニフェストで宣言する方式は、**3 つのホスト実行ファイルそれぞれに
マニフェスト資産とビルド設定を要求する**ため、この境界を実質的に押し広げ
る（ホストが「埋め込んで呼ぶだけ」でなくなる）。実行時 API を DLL 側で
呼ぶ方式ならホストは何も変わらない。どちらを採るかは判断項目で決めるが、
**この境界に触れるか否かを比較の明示的な観点に入れる**ことは本フェーズの
制約である。

**採否:** **採用（設計制約 — 比較の観点として必須。結論は先取りしない）**。

## 7. 可視の証拠の規律と、捕捉の手順が DPI に結合していること（**採用 — 検証方針の前提**）

規範の核は
[AGENTS.md §Testing rules](../../../../AGENTS.md)、捕捉の仕組みと陽性対照の
原理は
[verification-environments.md 観察 4](../../../../docs/notes/verification-environments.md)
にある（M3-Phase 5・6 で確定済み。ここで再導出しない）。加えて
[M3-Phase 8 handoff](../../../milestone-3/phase-8/implementation/handoff.md)
の持ち越し制約 3 が、座標に依存する捕捉スクリプトを「サーフェスに結合した
壊れやすい証拠経路」として扱い、**座標をサーフェスごとに導出し直す**
（過去の座標を正しいものとして引き継がない）ことを求めている。

**Phase 1 でどう効くか — 2 つの向きがある:**

- **本フェーズの証拠として:** 「鮮明に描かれた」は目で見るしかない性質で
  あり、単一のフレームでは証明にならない（100% のモニターで撮れば
  DPI 非対応でも同じ絵が出る）。陽性対照の設計は framing の検証方針の節が
  持つ。
- **本フェーズが捕捉の前提を変える側でもある:** 観察 4 は「ホストが
  DPI 非対応なので DWM が論理 800×600 を物理 1000×750 に引き伸ばす。
  DPI 非対応の捕捉ツールでは切り取りや倍率がずれる」と書いており、
  **この記述はホストが DPI 非対応であることを前提にしている**。本フェーズ
  が実行時を DPI 対応にすると、その前提が成り立たなくなる。ノート側の
  記述の更新と、以降のフェーズが使う捕捉手順の座標の導出し直しが、本
  フェーズの成果物に付随する。

**採否:** **採用（検証方針の前提 + 本フェーズが更新する対象）**。

## 8. 規範スペックの改訂履歴は追記式（**採用 — 軽量**）

[M3-Phase 8 handoff](../../../milestone-3/phase-8/implementation/handoff.md)
の持ち越し制約 5。`docs/dsl_spec.md` / `docs/architecture.md` /
`docs/abi_spec.md` の改訂履歴の表への修正は、新しい日付の行として足す。
過去の行を書き換えない。

**Phase 1 でどう効くか:** 本フェーズは 3 つの規範スペックすべてに触れる
見込み（§5）なので、3 か所すべてで効く。

**採否:** **採用（軽量 — 実装時の手順）**。

## 9. オーナーゲートの証拠とサーフェスの結合を毎回確かめる（**採用 — プロセス前提**）

[M3-Phase 8 handoff](../../../milestone-3/phase-8/implementation/handoff.md)
の持ち越し制約 6 と主な学び 2。過去のフレーム・スクリプト・受け入れ記録を
オーナーゲートの材料として再利用する前に、その証拠を撮った時点のコミット
との差分を経路を絞って確認する。

**Phase 1 でどう効くか:** 本フェーズは **DPI 対応前のフレームを陽性対照の
片側として使う**可能性が高い（§7 の「改修前 / 改修後」の対比）。その場合、
改修前のフレームがどのコミットのサーフェスで撮られたものかを明示的に
結び付ける必要がある。ギャラリーの絵は M3-Phase 8 の T7 で撮られたものが
最後であり、その後にサーフェスが動いていないことを確認してから使う。

**採否:** **採用（プロセス前提）**。

## 10. プロセスの学び（最終ステップの所有分割 / 計画は書き換える / 実装ゲート）（**採用 — プロセス前提**）

先行する M3 の各フェーズから受け継ぐ作業の規律。ここで再導出せず、適用の
確認だけを行う:

- **仕様同期を 2 回に分ける** — 設計同期（ADR が Accepted になった時点）と
  実装同期（フェーズを閉じる時点）。
- **「まとまり」はコミットの単位ではない** — 文書側のコミットはレビューの
  関心単位で切る（[AGENTS.md §Commit rules](../../../../AGENTS.md)）。
- **全マージはオーナーの明示承認を要する**。押し出し（push）は別のゲート。
- **最終ステップの所有を分ける** — 手元の再ビルドはコードを変えたステップ
  が持ち、CI の実行 id はフェーズ末が持つ。実装計画の最終項目を最初から
  この分割で書く。
- **凍結した作業一覧は途中のオーナー判断で古くなる** — 迂回策で辻褄を
  合わせず、可変の計画の方を書き換える。
- **実装ゲート** — 着手時に該当する失敗モードを選んで**記録**し、終了時に
  監査可能な成果物で閉じる（[implementation-gates.md](../../../procedures/implementation-gates.md)）。
  本フェーズで効く見込みが高いのは、呼び出し箇所の監査（§4 の経路一覧が
  そのまま対象）と、構造的な副作用の列挙（再レイアウトが何を巻き込むか）。

**採否:** **採用（プロセス前提）**。実装計画とフェーズクロージングの進め方に
反映する。

## 11. 新しい部品の追加に伴う 2 つの規律は本フェーズには効かない（**不採用 — 理由の記録**）

[M3-Phase 8 handoff](../../../milestone-3/phase-8/implementation/handoff.md)
の持ち越し制約 1（新しい部品の種類には「未知の部品の警告が出ないこと」を
示す肯定的な検査が要る）と 2（実行時の読み込み側でコンパイラ側の許容表を
写す）。

**不採用の理由:** 本フェーズは**部品の種類を 1 つも足さない**。新しい
DSL 面も持たない（§3）。両制約の再発の合図（新しい部品の種類の追加）は
本フェーズでは鳴らない。M4 でこれらが効くのは Phase 4（`Image`）と
Phase 5（入力欄）である。

## 先行フェーズの残件の点検

§2.1 の源は前フェーズの handoff だが、それ以前のフェーズの範囲外の残件が
本フェーズに新しい制約を持ち込まないことを確認する。

| 出所 | 残件 | 扱い |
|---|---|---|
| M3-Phase 2 | レイアウト時の実行時エラー専用の ABI コード（`wasamo_run_layout` 相当の入口を導入する時に解決） | **本フェーズ非該当**。DPI の変換は新しいレイアウトのエラー入口を作らない。再レイアウトが失敗しうる経路が増えるかは判断項目の設計次第で、増える場合は既存の resilient なレイアウトの扱いに従う |
| M3-Phase 3 R1 | `.gitignore` の `*.uic` パターン | **本フェーズ非該当**。ビルドの衛生の横断項目 |
| M3-Phase 3 R2 | `sync_visuals` と純レイアウトの境界の試験の穴 | **解決済み（M3-Phase 4 T4）**。ただし本フェーズが Visual への書き込み単位を変えるなら、その試験が引き続き通ることが回帰の防波堤になる |
| M3-Phase 5 | 実行時の DPI 対応の欠如 | **本フェーズが持ち主**（§1） |
| M3-Phase 7 | 反応的な排出の残件（循環検出 / 順序の同着 / 上限との関係） | **本フェーズ非該当**。DPI の変化は 1 回の再レイアウトであり、束縛の排出を扇状に広げない |
| M3-Phase 7b | 配置（placement）の面は凍結済み | **読むだけ**。本フェーズは配置の綴りにも意味論にも触れない |

先行フェーズの残件は本フェーズに**新しい制約を持ち込まない**。

## 前送り対象に含めないもの（指し示すだけ）

- **PM-2 の Grid の入れ物の規則 / 既定の整列 / 配置の綴り** — M4 では
  再開の合図が鳴らない見込み（[M4 framing.md §1.1](../../requirements/framing.md)）。
  本フェーズは配置に触れないため、なおさら該当しない。
- **選択状態の 5 つの先送り軸**（[M3 handoff](../../../milestone-3/handoff.md)）—
  等値選択の軸は M4-Phase 3、双方向束縛の軸は M4-Phase 7、残りは M5。
  本フェーズ非該当。
- **`TypedValue` の「ABI への影響: 不明」の解消** — M4 期間中のどこかで
  消化する宿題（[M4 framing.md](../../requirements/framing.md)
  §検討ノートのケース分類と宿題）。前倒しの条件は成立しておらず、本
  フェーズはその宿題の持ち主ではない。ただし §5 で `docs/abi_spec.md` を
  開けるため、ついでに読む機会ではある（義務ではない）。
- **作者によるサイズ指定（Problem B）の試掘** — M4-Phase 10 が持ち主。
  本フェーズが単位を DIP と定義することは、試掘が扱う「作者が明示サイズを
  書けるか」とは別の問いである（単位の定義は、明示サイズの有無に関わらず
  必要）。
- **触覚（タッチ）の検証環境の判断** —
  [M4 framing.md](../../requirements/framing.md)
  §採択後・各フェーズへ送る決定事項 2 が M4-Phase 2 の計画に送っている。
  本フェーズの検証環境の判断（異なる倍率のモニターが要る）は同型の問いだが
  別件であり、本フェーズは自分の分だけを framing の検証方針で決める。
- **仕様に折り込み済みの意味論** — レイアウトの 2 パス、ピクセルの整数丸め
  を行わない方針、resilient なレイアウトの誤り処理はいずれも
  [docs/architecture.md](../../../../docs/architecture.md) /
  [docs/dsl_spec.md](../../../../docs/dsl_spec.md) に折り込み済み。本
  フェーズが拡張する土台であり、制約として写さずスペックを直接読む。
