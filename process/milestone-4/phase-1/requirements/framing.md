# M4-Phase 1 フレーミング

**状態:** accepted（オーナー合意済み 2026-07-28。合意事項 ①〜⑤ 全項目 OK）
**対象フェーズ:** M4-Phase 1（モニターごとの DPI 対応と座標空間の境界）—
**M4 の最初のフェーズ**

開発プロセス（[workflow.md §2](../../../procedures/workflow.md)）に従い、本
ドキュメントは設計判断（ADR）を書く前に**オーナーと方向性を合意する**ための
入力資料です。個々の判断の選択肢・比較・推奨は、ここでは確定しません。ここで
固めるのは、Phase 1 は何を届けるフェーズなのか、どの問いを判断項目（DD）
として予約するのか、どこまでを Phase 1 の担当範囲とし、どこからを「きっかけ
が来たら後続フェーズで」と送るのか、そして検証のしかたです。

前フェーズからの制約引き継ぎ（プロセスの §2.1）は
[constraints.md](./constraints.md) で済んでおり、本ドキュメントはその上に
乗ります。M3 の各フェーズから受け継ぐ作業の規律（仕様同期を 2 回に分ける /
文書側のコミットはレビューの関心単位で切る / 全マージはオーナー承認を要する /
最終ステップの所有を分ける / 実装ゲート / 陽性対照）はここで再説明せず、
[constraints.md §10](./constraints.md) を参照します。

> **用語の最小限の補足（初出のみ）:**
> - **DIP** … 96 分の 1 インチを 1 とする長さの単位。倍率 100% のモニター
>   では物理ピクセルと一致し、150% では 1 DIP = 1.5 物理ピクセルになる。
>   Windows のアプリが「論理的な大きさ」を書くときの共通単位。
> - **倍率（スケール）** … そのモニターの DPI を 96 で割った値。125% なら
>   1.25。
> - **DPI 対応の宣言（awareness）** … 「このプロセス / ウィンドウは自分で
>   倍率を扱う」と OS に伝えること。宣言しないと、OS 側（DWM）がウィンドウを
>   画像として引き伸ばして辻褄を合わせる（= 全体が滲む）。
> - **モニターごとの対応（Per-Monitor）** … 倍率をプロセス起動時に 1 度
>   決めるのではなく、ウィンドウが乗っているモニターごとに、かつ移動の
>   たびに扱う水準の宣言。
> - **ラスタライズ面** … 文字を描き込む中間の画像。Wasamo は DirectWrite で
>   この面に文字を描き、その面を Visual に貼っている。

## Phase 1 の主題（何を届けるフェーズか）

本フェーズは「高 DPI 対応」という機能を足すフェーズではない。**Wasamo の
座標空間を定義するフェーズ**である。

M1 から現在まで、Wasamo には座標空間が 1 つしかなかった。`GetClientRect` の
返す数値がそのままレイアウトの入力になり、レイアウトの出した数値がそのまま
Visual の位置と大きさになり、DirectWrite の計測値がそのまま長さとして混ざる。
これが成立していたのは、倍率が常に 1 だったから（正確には、倍率が 1 でない
環境では DWM がウィンドウを画像として引き伸ばし、Wasamo からは 1 に見えて
いたから）である。

本フェーズは、この 1 つの空間を **DIP の空間**と**物理ピクセルの空間**に
分け、両者の変換を数えられる箇所に閉じ込める。主題は 3 点に分解できる。

1. **レイアウトは DIP のまま。** 作者が `.ui` に書く数値、レイアウトが
   計算する数値、部品どうしの相対的な配置は、すべて DIP で閉じる。150% の
   モニターで折り返しの位置が変わってはならない — これは倍率が上がると
   「論理的な広さ」が増えるという誤りであり、本フェーズが最も避けたい
   失敗である。
2. **物理ピクセルを知るのは境界だけ。** OS からのメッセージが入ってくる
   3 か所（ウィンドウの大きさ・初回のクライアント矩形・マウスの座標）と、
   Composition / DirectWrite へ出ていく箇所である。
   [constraints.md §4](./constraints.md) の経路の一覧が、その境界の全数で
   ある。
3. **「鮮明」の実体はラスタライズ面の解像度である。** これが本フェーズの
   難所であり、座標の掛け算ではない。文字は
   [`text.rs`](../../../../wasamo-runtime/src/text.rs) で
   `CreateDrawingSurface` の面に 96 DPI の D2D コンテキストで描かれてから
   Visual に貼られる。座標だけを 1.5 倍しても、この面のピクセル数が増え
   なければ、貼られた画像が引き伸ばされるだけで DWM 拡大と同じ滲みが出る。
   [layout-engine.md §3.1](../../../../docs/notes/layout-engine.md) が
   M1 の時点で「DirectWrite のヒンティング精度に影響する」と書いていたのは、
   まさにこの点である。**AC7 の「鮮明に描画する」は、この面を物理解像度で
   確保して初めて満たされる。**

主題の裏返しとして、**本フェーズが変えないもの**も主題の一部である:
レイアウトの計算方法（2 パス、`f32`、サブピクセル境界を丸めない方針）、
部品の種類、DSL の文法、配置の意味論。plan の第 4 のリスク「DPI を先に
置いたことが主題の作業を止める」は、この線を越えたときに発火する。越えた
と判断した場合は、その場で計画の改訂を提案してから進む
（→ 合意事項 ①）。

### なぜ M4 の最初に置かれているか（計画の追認）

[plan.md](../../plan.md) M4-Phase 1 行の理由づけをここで再導出しない。
本フレーミングにとって重要なのは、その帰結が**本フェーズの終わり方**を
規定することである: 本フェーズの後に撮られる目視の証拠はすべて、本
フェーズが決めた座標空間の上で撮られる。逆に、本フェーズより前に撮られた
証拠（M3-Phase 8 の T7 で撮ったギャラリーのフレーム）は、DWM 拡大された
世界のものである。この 2 つの世界の切り替わり点が本フェーズであり、
**捕捉の手順の座標は本フェーズで導出し直す**必要がある
（[constraints.md §7](./constraints.md)）。これは負債ではなく、最も安い
時点で 1 度だけ払うことを選んだ結果である。

  オーナー合意済み 2026-07-28）。順序の再検討は計画の改訂であり、本

- **本フェーズは新しい DSL 面を持たず、消費者は既存のギャラリーである**

- **比較の主軸は製品としての価値であり、実装・改訂のコストは決め手が

  境界を変えるなら、それは本フェーズの副産物ではなく独立した判断である。
- **仕様に折り込み済みの意味論**（レイアウトの 2 パス、resilient な誤り
  処理、整数丸めを行わない方針）は
  [docs/architecture.md](../../../../docs/architecture.md) /
  [docs/dsl_spec.md](../../../../docs/dsl_spec.md) を直接読む。本フレーミング
  に写さない。

## 論点一覧（DD 番号の予約）

本フェーズの ADR（`decisions/preamble.md` + 判断項目ごとに 1 ファイル）が
担う問いを列挙し、**DD-M4-P1-001〜004 の番号を予約**する。各判断項目の
選択肢・比較・推奨は §3 設計判断で書く。ここでは「何を判断するか」と
「なぜ本フェーズの問いか」だけを固定する。

### DD-M4-P1-001 — DPI 対応の宣言（水準・宣言する場所・失敗時の扱い）

**問い:** どの水準の DPI 対応を、どこで、誰が宣言するか。宣言に失敗した
場合どう振る舞うか。

**Phase 1 の問いである理由:** AC7 の 1 つ目の要求そのもの。かつ、宣言する
場所の選択が[宣言的なホストの境界](./constraints.md)に直撃する — アプリの
マニフェストによる宣言は 3 つのホスト実行ファイルに資産とビルド設定を
要求し、「ホストは `.uic` を埋め込んで呼ぶだけ」という M3 で守ってきた形を
崩す。実行時 API による宣言ならホスト側は何も変わらない。この非対称は
比較の明示的な観点にする。

**下位の問い:** 宣言の水準（モニターごとの対応の第 2 版 / 第 1 版 /
プロセス起動時に 1 度だけ決める形）と、第 2 版が持つ非クライアント領域の
自動対応にどこまで頼るか。宣言の時点（`wasamo_init` の中か、ウィンドウ
生成の直前か）。ホストが Wasamo を呼ぶ前に Win32 に触れて対応水準が既に
確定していた場合の扱い（誤りとして返すか、警告に留めるか、その倍率のまま
続けるか）。対応 API を持たない古い Windows での退避。3 つのホストの
ビルドに変更が要るか否かの確認。

### DD-M4-P1-002 — 座標空間の定義と変換境界の置き場

**問い:** レイアウト座標系を何と定義し、DIP と物理ピクセルの変換を
[constraints.md §4](./constraints.md) が列挙した 7 か所のどこで行うか。
そして、**文字のラスタライズ面をどう物理解像度で確保するか**。

**Phase 1 の問いである理由:** [layout-engine.md §3.1](../../../../docs/notes/layout-engine.md)
が M1 から持ち越してきた問い（エンジンが物理ピクセルを意識すべきか）への
答えであり、後続 5 フェーズが消費する契約でもある。本フェーズの中心。

**下位の問い:** レイアウトを DIP のまま持つか、物理ピクセルへ移すか。変換の
実現手段（根の Visual に倍率変換を掛ける / 各 Visual への書き込み時に
掛ける / 入口と出口だけで掛ける）と、それぞれが根の
`SetRelativeSizeAdjustment(1,1)` とどう相互作用するか。**根に倍率変換を
掛ける案は座標としては最小の変更だが、文字のラスタライズ面ごと引き伸ばす
ため AC7 の「鮮明」を買えない可能性がある** — この可否の見極めが判断の
実質。`CreateDrawingSurface` の面のピクセル数と D2D 側の DPI の与え方。
`TextRenderer::measure` の戻り値の単位（DIP のままにできるか）。整数丸めを
行わない現行方針を維持するか。非整数倍率（125% / 150%）での丸めの方向と
誤差の蓄積。変換を担う型を新設するか `f32` のまま扱うか。

### DD-M4-P1-003 — 倍率の変化への追従

**問い:** ウィンドウ生成時の初期倍率をいつどこから取るか。倍率の変化
（`WM_DPICHANGED`）を受けたとき、何を、どの順序で行うか。

**Phase 1 の問いである理由:** AC7 の 3 つ目の要求。かつ M4-Phase 8
（複数ウィンドウ）が「ウィンドウごとに異なる倍率」を載せる土台になる —
倍率をどこが保持するかをここで決めておかないと、Phase 8 で per-window 化
する際に構造から作り直しになる。

**下位の問い:** 倍率の保持場所（`WindowState` に持つか、都度
`GetDpiForWindow` を引くか）。ウィンドウ生成直後の倍率が仮の値でありうる
ことへの対処。`WM_DPICHANGED` が渡す推奨矩形を適用するか否か。再レイアウト
と文字のラスタライズ面の作り直しの順序と、無効化の粒度
（[layout-engine.md §3.4](../../../../docs/notes/layout-engine.md) の
「ウィンドウ全体を汚す」現行方針で足りるか）。再レイアウトが巻き込む
構造的な副作用の列挙（実装ゲートの成果物）。失敗時の扱い。複数ウィンドウ
への前送りの形を、本フェーズで塞がない形にしておく責務。

### DD-M4-P1-004 — 外向きの単位の契約と仕様への記述

**問い:** `wasamo_window_create` の `width` / `height`、DSL の寸法値、活字の
大きさの単位を何と定義し、3 つの規範スペックにどう書くか。ホストが倍率を
知る手段を M4 で持つか。

**Phase 1 の問いである理由:** 倍率が 1 でなくなった瞬間、「`width: 800` とは
何か」は答えが要る問いになる。しかも
[docs/abi_spec.md](../../../../docs/abi_spec.md) は M6 で凍結される。**単位の
意味論を後から変えることは互換性の破壊**であり、凍結前に確定させる必要が
ある。現状 3 つのスペックはいずれも単位を定義していない
（[constraints.md §5](./constraints.md)）。

**下位の問い:** `wasamo_window_create` の引数を DIP と定義した場合の
後方互換（100% のモニターでは同値なので実害は無いが、そう書いてよいかの
確認）。ホストが倍率を問い合わせる関数の要否 — **要るという結論なら、
計画の「M4-Phase 7 が唯一の ABI 面のフェーズ」との衝突を
[DD-V-026](../../../cross-milestone/decisions/plan-revision-discipline.md)
の 2 段階目の改訂として提案してからでなければ入れない**（→ 合意事項 ③）。
`docs/dsl_spec.md` の「レイアウト座標系のピクセル extent」という記述の
書き換え。`docs/architecture.md` の未解決事項の表にある DPI の行の解決。
[layout-engine.md](../../../../docs/notes/layout-engine.md) の扱い（§3.1 は
本フェーズで解決するが、§3.2 = AccessKit との同期は M4-Phase 11 が持つため
ノート自体は live のまま）。活字の大きさ（12 / 14 / 20 / 28）を DIP と
明記すること。

## 検証方針

本フェーズの検証は、「**倍率 1 の環境で撮った 1 枚と区別できるか**」を中心に
組む。高 DPI 対応は、正しく実装しても間違って実装しても、100% のモニターでは
まったく同じ絵が出る。したがって単一のフレームは証拠にならない。

### 純ロジックの単体テスト

本フェーズは**純粋な計算のロジックが実際に生まれるフェーズ**であり、
[AGENTS.md §Testing rules](../../../../AGENTS.md) の「純 Rust のロジックには
単体テストを書く」が正面から当てはまる（Win32 / WinRT に依存しない）。

- 倍率と DIP / 物理ピクセルの相互変換。125% / 150% / 200% を含む。
- 矩形の変換（位置と大きさを別々に変換したときの一貫性）。
- 往復の誤差（DIP → 物理 → DIP）と丸めの方向。
- 判断項目 2 が変換を担う型を新設した場合、その型の演算。

### Windows 統合テスト（mock なし）

実行時の状態を実物の OS の面に対して確かめる。CI で必要な能力が無い場合は
**黙って skip せず落ちる**。skip の防護を入れるなら、能力の無い環境で実際に
発火することを landing 前に確かめる
（[verification-environments.md](../../../../docs/notes/verification-environments.md)）。

- 宣言された対応水準が、判断項目 1 が選んだ水準になっていること。
- ウィンドウ生成後、その倍率が実行時の状態に反映されていること。
- 倍率の変化に対して再レイアウトが走り、レイアウト結果の DIP 値が**変わらない**
  こと（= 論理レイアウトが倍率に依存しない）。これは陽性対照を統合テスト側で
  持つ形になる。
- **限界の明示:** `WM_DPICHANGED` を合成して送る形の試験は、実際のモニター
  移動を証明しない。実物の側は下の可視の証拠が担う、という分担を ADR に
  明記する。

### 可視の証拠と陽性対照

アシスタントの自動証拠は、起動 + 捕捉 + 捕捉した画像の解析を含める
（起動して落ちないことは補助的な合図に過ぎない）。オーナーの目視の
確認はこれとは別枠。

陽性対照は 3 種を用意する。**単独では対照にならないものを対照として
数えない**ことに注意する。

| 対照 | 撮り方 | なぜ対照になるか |
|---|---|---|
| **A. 鮮明さの前後比較** | 改修前（DWM 拡大）と改修後の同じ文字を、同じ倍率のモニターで拡大切り出しして並べる | 改修前は縁が滲み、改修後は縁が立つ。**2 枚の対比が対照であり、改修後の 1 枚だけでは証明にならない**。改修前のフレームを再利用する場合は、それを撮ったコミットとサーフェスの結合を確認してから使う（[constraints.md §9](./constraints.md)） |
| **B. 論理レイアウトの不変性** | 100% と高倍率のモニターで、同じ `.ui` の同じ論理サイズのウィンドウを撮り、要素の折り返し位置・並びを比較する | 変換を誤って物理ピクセルを論理として扱うと、高倍率では「論理的に広い」ことになり WrapPanel の折り返し数が変わる。**不変であることが正しさの証拠**。逆に「ウィンドウの物理サイズが倍率に比例する」ことは DWM 拡大でも成り立つので**対照にならない** |
| **C. 倍率変化への追従** | 倍率変化の前後 2 フレーム（モニター間の移動、または表示設定の倍率変更） | 追従しない実装は、変化後に滲むか、論理レイアウトが崩れる。変化後も鮮明かつ論理レイアウトが不変であることが対照 |

### 環境と証拠の分担（確定 2026-07-28）

対照 A / B / C はいずれも**可視の Windows デスクトップ**を要する。利用可能な
環境をオーナーに確認し、実測で裏を取った結果、次の分担で全対照が撮れる。

**開発マシンの実測値（2026-07-28）:** 単一モニター、物理 2452×1291、
DPI 120（= **125%**）、`SESSIONNAME=Console`。M3-Phase 5 の T6 と同じ
高 DPI の環境級であり、[verification-environments.md](../../../../docs/notes/verification-environments.md)
の分類では「可視デスクトップ」に当たる。

| 証拠 | 撮る場所 | 担い手 |
|---|---|---|
| 対照 A（鮮明さの前後比較） | 開発マシン（125%） | **アシスタントの自動捕捉**。改修前後の同じ文字を拡大切り出しして並べる |
| 対照 B（論理レイアウトの不変性） | 開発マシン。表示設定で 100% ↔ 125% を切り替えて 2 枚 | **アシスタントの自動捕捉** |
| 対照 C の**経路** | 開発マシン。表示中に表示設定の倍率を変更すると `WM_DPICHANGED` が飛ぶ | **アシスタントの自動捕捉**。追従の実装が動いていることはここで示せる |
| 対照 C の**文字どおりの形**（モニターをまたぐ） | ラップトップ + 外付けディスプレイ（倍率の異なる 2 面） | **オーナーの目視**。ウィンドウを画面間へドラッグして、鮮明さと論理レイアウトが保たれることを見る |

この分担は [AGENTS.md §Testing rules](../../../../AGENTS.md) の建て付けと
一致する — アシスタントの自動捕捉はオーナー目視の**前段の基準線**であって
代替ではない。単一モニターでの倍率変更は同じ `WM_DPICHANGED` の経路を通る
ため実装の正しさは確かめられるが、**モニター間の移動そのものを証明しない**
ので、最後の 1 行はオーナー目視が担う。

**実装計画に持たせる実務:** ラップトップは開発マシンとは別の機体なので、
そこで動く一式（ホストの実行ファイル + `wasamo.dll` + コンパイル済みの
`.uic`）を届ける手順が要る。ラップトップにビルド環境を用意するか、
成果物一式を運ぶかの選択を含め、オーナー目視の手引きとして書き起こす
（M3-Phase 8 の T10 でオーナー目視の手引きを作った前例に倣う）。この手引きは
サーフェスに結合した文書なので、再利用の前に対象コミットとの差分を確認する
（[constraints.md §9](./constraints.md)）。

`docs/abi_spec.md` / `docs/dsl_spec.md` / `docs/architecture.md` を本
フェーズの中で更新し、「外部の実装者がこの記述だけで単位を再現できるか」を
フェーズ終了時の水準にする。改訂履歴は追記式（[constraints.md §8](./constraints.md)）。
`docs/notes/layout-engine.md` §3.1 は解決済みとして本文を更新するが、

着手時に該当する失敗モードを選んで**記録**し、終了時に監査可能な成果物で

本フェーズで効く見込みが高いのは:

- **構造的な副作用の列挙** — 倍率の変化が巻き込むもの（レイアウトの再実行、

- **目視の陽性対照** — 上の対照 A / B / C。

## リスク

### R1. 「境界での変換」がレイアウト単位の再設計に膨らむ

plan の第 4 のリスクそのもの。判断項目 2 の検討中に、DIP のままでは
表現できない何か（たとえば境界の丸めが積み上がって折り返しがずれる）が
見つかると、レイアウトの計算方法そのものに手が伸びる。そうなると M4 の
中心（フォーカスモデル）の着手が遅れる。

**軽減:** 越えたと判断した時点で、その場で計画の 2 段階目の改訂を提案して
から進む。黙って広げない（→ 合意事項 ①）。判断項目 2 の比較には「レイアウト
の計算方法を変えるか否か」を明示的な観点として置く。

### R2. 座標だけ直して「鮮明」を買えないまま閉じる

本フェーズで最も現実味のある失敗。根の Visual に倍率変換を掛ければ、
ウィンドウの大きさもマウス座標も辻褄が合い、統合テストも通り、**100% の
モニターでは何も問題が見えない**。しかし文字のラスタライズ面が引き伸ばされて
いるため、高 DPI では DWM 拡大と同じ滲みが残る。AC7 の 3 要求のうち 2 つ目
だけが達成されないまま閉じる形になる。

**軽減:** 主題（§3 点目）でこれを本フェーズの難所として先に名指しし、
判断項目 2 の中心に据える。検証側では、対照 A（鮮明さの前後比較）を
「あれば良い」ではなく AC7 の 2 つ目を discharge する必須の証拠として
扱う。

### R3. 別機体での目視が段取り不足で後ろ倒しになる

環境そのものは確保済み（開発マシンが 125%、ラップトップ + 外付けで倍率の
異なる 2 面）。残るリスクは**段取り**である。「モニターをまたぐ」の目視は
開発マシンとは別の機体で行うため、そこで動く一式を届ける手順が要る。これを
フェーズ終盤まで用意しないと、実装は終わっているのに AC7 の 3 つ目だけが
閉じない状態が生まれる。

**軽減:** 届ける手順（ビルド環境を用意するか、成果物一式を運ぶか）を
実装計画の項目として**前倒しで**持たせ、オーナー目視の手引きに書き起こす。
アシスタント側の対照 A / B / C の経路は開発マシンで先に閉じられるので、
目視待ちで止まるのは最後の 1 行だけに限定される。

### R4. 単位の明文化が「Phase 7 が唯一の ABI 面」という計画の記述と衝突する

判断項目 4 が新しい ABI 関数を要求した場合に発火する。

**軽減:** 合意事項 ③ で「意味論の明文化に留める」を基本線とし、新関数が
要ると出た場合は計画の改訂を提案してから入れる手順を先に固定しておく。
既存引数の意味論の明文化に留まる限り署名は動かず、衝突しない。

### R5. 以降のフェーズが使う捕捉手順の座標が総入れ替えになる

本フェーズが座標空間を変えることの必然の帰結。M3-Phase 8 の持ち越し制約 3
（座標はサーフェスごとに導出し直す）が本フェーズで大規模に発火する。

**軽減:** これはリスクというより、本フェーズを M4 の最初に置いた理由の
裏返しである。後に置けば、その時点までに撮ったすべての証拠が撮り直しに
なる。今払うのが最も安い。本フェーズの成果物に「捕捉手順の座標の導出し
直し」を明示的に含める（範囲の節の最終項）。

### R6. 統合テストの合成メッセージを実物の証明と取り違える

`WM_DPICHANGED` を自分で送る試験は、その処理経路が正しく動くことは示すが、
実際にモニターをまたいだときに OS が同じものを送ってくることは示さない。

**軽減:** 分担を ADR に明記する — 経路の正しさは統合テスト、実物の挙動は
可視の対照 C。どちらか一方で AC7 の 3 つ目を閉じたと書かない。
