# T4 レトロスペクティブ

タスクブランチ: `feat/m4-phase-1-t4`

T4 は `WindowState` に倍率を載せ、`GetDpiForWindow` から初期値を取り、
DIP で指定されたウィンドウサイズを物理サイズに直す task。T9 まで完全に
inert —— プロセスが DPI awareness を宣言していないので OS は 96 DPI を
返し、倍率は 1、補正は恒等になる。

plan が名指ししていた未決の論点 2 件が本体だった:

- **丸め規則**: `round`（最近接）を選び、**`DipScale` の中に**
  `window_size_to_physical` として置いた。
- **補正の設置位置とフラグ**: `GWLP_USERDATA` 設置の**前**、
  `SWP_NOMOVE | SWP_NOZORDER | SWP_NOACTIVATE`。

start gate / close gate は
[../implementation/log.md](../implementation/log.md) の T4 entry。
close gate の中心は四つ: **10 行の呼び出しサイト監査**（DD-002 の監査表
13 行目をここで閉じた）、**13 行の副作用列挙**（メッセージ集合は推測でなく
実測）、**丸め規則の 4 変異表**、そして **throwaway probe が印字した生成
順序と実測した 3 つのウィンドウ状態**。

T4 commits:

- `40757c8 docs(m4-phase-1): record the T4 start gate`
- `ba1c8f7 feat(runtime): add the DIP window-size rounding rule to DipScale`
- `12684e5 feat(runtime): seed the per-window DIP scale and realise DIP window sizes`

doc gates（`cargo fmt --all -- --check` / `git diff --check`）は
post-commit state で実行、ともにゼロ終了。**retro 記録後に remediation
commit を積んだ場合は final branch state で再実行し、上の一覧も更新する**
（T1 で一度落とし、T3 で 3 回追記が必要になったクラス）。

実装は **2 commit**。丸め規則は呼び出し側のない純ロジックとして単独で
着地させ、`Win32_UI_HiDpi` feature・`WindowState` のフィールド・その
seeding・補正を次の 1 commit にまとめた。フィールドだけ先に入れると
「読まれないフィールド」の警告が出て、feature は同じ commit の
`GetDpiForWindow` の前提でもあるため。3 つ目の小さな commit は、probe が
実測したメッセージ集合を設置位置のコメントに折り込んだもの。

## チェックリスト（task-end、項目 1〜11）

### 1. 今回の主な学び

四つ。

**(a) 「順序で検証する」は、順序が起きない世界では検証にならない。**
end gate は「倍率が最初のレイアウトより前に seed されていることを、
コメントでなく順序で検証」だった。probe で実測したところ、倍率 1 では
サイズを変えない `SetWindowPos` は `WM_SIZE` を**一切送らない**。つまり
設置位置の判断が答えている問い（「入れ子のメッセージは何に届くか」）は
T9 より前には**発生しない**。見えないのではなく、到達不能。F-4 が
「緑のテストは変換の正しさの証拠にならない」なら、これは「緑の実行は
順序の正しさの証拠にならない」で、一段外側の同じ話（F-31）。
だから設置位置は「今のところ壊れていない」でなく**構造**で論じた ——
入れ子の dispatch が到達できるランタイム状態が存在しない位置に置く。

**(b) probe は自分が立てた対照を否定した。それが一番の収穫だった。**
start gate で「aware + 補正あり」はタイル 7 個に戻るはずと書いた。実測は
**9 個**。正しいのは 9 で、外れたのは予測のほう —— 補正はウィンドウの
外形を直すが、client 幅を DIP に割り戻す inbound 変換は T5 の担当なので、
レイアウトは 982 をそのまま DIP として受け取る。半分しか着地していない
task に対して機構全体を前提にした予測を立てていた。ついでに、plan が
T10 用に持っていた失敗署名「7 → 6」も T4 では再現しないことが分かった
（F-27）—— T1 の数字は機構一式入りのビルドのもので、plan の要約が条件を
落としていた。

**(c) 丸めの向きは「似た規則がすでにあるか」でなく「量の契約が何か」で
決まる。** `surface_pixels` が `ceil` なのは、面が**確保**であり切り捨てると
グリフの最終列が欠けるから —— 片側にしか壊れないので片側の規則。
ウィンドウ矩形にはその非対称性がなく（client 幅は測って読み直す）、
代わりに**論理サイズの忠実性**という契約がある。だから最近接。第二の
独立した根拠として、最近接は OS 自身が `WM_DPICHANGED` の推奨矩形を作る
規則（`MulDiv`）でもあるので、生成時と OS の後日の提案が同じ数になる。
型の中に入れたのは「丸め契約を 2 つ持つのが嫌」より「**丸め規則が住む
場所を 2 つにしない**」が上位だから —— 呼び出し側に書くと `factor()` に
手が伸びる（F-15 の再発条件そのもの）。

**(d) mutation ループ自体が偽陰性を作りうる。** `Copy-Item` は元ファイルの
更新時刻を保つので、バックアップから復元すると mtime が巻き戻り、cargo が
「ビルド済み」と判断して**変異版のテストバイナリを再実行**した。復元後の
実行が緑のはずなのに赤だったので気付いた。F-21・F-5 と同族 ——
「何かをしたように見えて何もしていないビルド手順」。

### 10. 新たに発見・導入した cross-task / cross-phase の設計制約

**あり。3 件。いずれも `carry-forward`**（phase-end retro の項目 15 で
handoff への確定を判断する。`implementation/handoff.md` には T4 時点の
記録として既に行を足してある）。

**制約 1 — 倍率はウィンドウ単位で `WindowState` が正本、`pub(crate)`。**

- **エビデンス**: T4 の実装と呼び出しサイト監査。`emit::flush_layout` が
  別モジュールから読むので `pub(crate)` が必要で、`pub` にすると
  `pub use` された型に倍率が乗り、DD-004 が「ホストは倍率を必要としない」
  と結論した面をそのまま出荷することになる。
- **配置先**: `carry-forward`。M4-Phase 8 が加算的に消費する前提。
  再発条件は「倍率の第二の出所（プロセス全体のキャッシュ、使用箇所での
  再取得、二つ目の seeding）」。

**制約 2 — 補正は `GWLP_USERDATA` 設置の前に走り、そのフラグ集合は
`WM_DPICHANGED` 経路のものではない。**

- **エビデンス**: probe の実測（125% で補正が投げる 9 通のメッセージ
  すべてで `state_ptr` が null）。および F-30 —— `realize_dip_window_size`
  は runtime 唯一の `SetWindowPos` で `SWP_NOMOVE` を渡すが、T7 は
  **OS が渡す物理矩形**（中身は新しい位置とサイズそのもの）を適用するので、
  `SWP_NOMOVE` を継ぐとモニター跨ぎのたびにウィンドウが固定される ——
  しかもテストは全部緑のまま。
- **配置先**: `carry-forward`。plan §T7 に独立の項目として書いた。

**制約 3 — 論理サイズが実現されるのは**外形**矩形で、client 矩形は同じ
倍率では追随しない。**

- **エビデンス**: 実測。125% で 800 DIP 外形はちょうど 1000 物理だが、
  client は 784×561 DIP → 785.6×562.4 DIP になる（非クライアント枠が
  96 DPI で片側 8px、120 DPI で 9px）。レイアウトは client を受け取る。
- **配置先**: `carry-forward`。倍率跨ぎで比較するすべての evidence gate
  と、将来の client サイズ指定属性（M4-Phase 8 / AC11）が対象。
