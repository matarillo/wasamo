## チェックリスト（task-end、項目 1〜11）

1. **今回の主な学び。** 四つ。

     変換機構一式と V2 宣言を全部入れて 125% の開発機で回しても、32 個の
     テストバイナリが全部 green で、baseline と区別がつかなかった。既存の
     layout 統合テストは `WidgetNode` を直接叩き、window を経由しないので、

   - **(b) 引き回し形は「壊れる呼び出し箇所の数」ではなく「window を
     持たない経路があるか」で決まった。** パラメータ引き回し 28 箇所 /
     ノード保持 7 箇所という差も大きいが、決め手は
     `update_text_content` / `update_text_style` / `update_button_label`
     が `set_property` 経由で `*mut WidgetNode` しか持たずに再ラスタライズ
     する点。パラメータ形にはこの経路の答えが無く、
     `emit::mark_layout_dirty_for` と同じ O(windows × nodes) の探索を
     強いられる。件数はコンパイラに数えさせたが、選択自体は件数では
     決まらなかった。

   - **(c) ADR の audit table は「行の内容」だけでなく「行が指すサイト」も
     照合しないと意味が無い (F-1 / F-2)。** row 12 は Box を挙げているが

     layout をやっている。どちらも「行の結論」は正しいので、結論だけを

## 目標・前提・計画仮説の再点検

> 後続タスクの retrospective でも流用するダブルループ振り返り欄。
> 実行の巧拙（シングルループ）でなく、**設定した目標・前提・事前計画
> （= 検証すべき仮説）自体が妥当だったか**を、反証可能な signal とともに
> オーナーと問い直す。下の 5 サブセクションがひな型。

### 観測された事実（反証可能な signal）

- 変換機構 + V2 宣言を全部入れて 125% で `cargo test --workspace` →
  32/32 green、baseline と同一。「テストが通ること」が設計の正しさを
  一切支持しない状態が実測された。
- plan / preamble の R-5 は「2 production sites + at least four
  integration tests」。実測は `run_layout_as_window_root` が 2 + 13 (6
  ファイル)、`run_layout` が 1 + 8 (3 ファイル)。後者は見積もりに
  そもそも出てこない。
- DD-002 audit table の 13 行のうち 2 行がサイトを取り違え / 取りこぼし
  (F-1 / F-2)、加えてテーブルが挙げていない座標経路が 1 種 (F-3)。
- `cargo check --workspace --all-targets` は最初から最後まで green
  だったが、`cargo test` はリンクで落ちていた (F-5)。

### 自己分析（どの層が外れたか）

外れたのは **前提の層**であって、実行でも目標設定でもない。

- 「T2–T8 は buildable かつ suite green」という sequencing thesis の
  合格条件は**満たされたが、条件として弱かった**。thesis は
  「intermediate commit が正しい」ことの根拠に suite green を挙げていたが、
  suite が scale に無感覚なので、この条件は変換が全部正しくても全部
  間違っていても同じ値を返す。目標 (declaration を最後に置く) は妥当な
  まま、**その妥当性の証拠として選んだ signal** が外れていた。
- audit table を「ADR が書いたのだから照合対象は行の内容」と扱う前提が
  外れていた。行が指すサイトの実在性は別の照合。plan.md §T1 は正しく
  「row whose file / function has moved」「path the table does not name」
  の両方を要求していたので、**計画は当たっていて、危なかったのは
  読み方のほう**。
- R-5 の見積もりは planning-time recon の性質上ずれるのが当然で、
  「T1 で compiler に数えさせる」という計画自体が正しかった。ここは
  外れではなく、計画が意図どおり働いた例。

### 計画仮説・前提の問い直し（オーナーと）

- **問い直し 1: T2–T8 の各 end gate に「suite green」を書き続けるか。**
  F-4 の後では、これは満たしても何も言っていない条件に近い。提案は
  「suite green は回帰検出としては残すが、*正しさの証拠として数えない*」と
  明記し、T5 は audit table、T6 は描画、T7 は side-effect 列挙を各自の
  実質的な gate とする (現 plan は既にそう書けているので、文言の
  格下げだけ)。
- **問い直し 2: T8 の重みが上がったが、位置は今のままでよいか。**
  T8 が R-2 の唯一の自動防御なら、T5 / T6 の直後に前倒しして
  「変換が入った直後に scale ≠ 1 を撃つ」形も考えられる。現行順
  (T7 の後) だと T5 / T6 の変換漏れは T8 まで検出されない。ただし T8 は
  `WM_DPICHANGED` 経路を使うので T7 に依存しており、前倒しには
  「handler を介さず scale を差し替える test seam」を足す必要がある。
  現状維持を推奨するが、判断はオーナーに置きたい。
- **問い直し 3: ポインタ DIP の型 (項目 4)。** `f32` 推奨。

### 反証可能な是正テスト

- **是正 1 (F-4 に対して)**: T5 close 時に、audit table の任意の 1 行を
  わざと未変換のまま残した状態で suite を回し、**green のままであることを
  確認する**。green なら「suite は R-2 を検出しない」が実証され、T8 の
  必要性が主張ではなく観測になる。fail するなら F-4 の一般化が過大で、
  suite にまだ検出力が残っていることが分かる。どちらに転んでも情報が出る。
- **是正 2 (前提の測定について)**: 以降の task で「ADR / plan が地の文で
  述べている OS の挙動」に依存する判断をするとき、その挙動を 1 本の
  probe で測ってから進む。T1 の probe は 30 秒で 3 つの前提
  (96 DPI / 宣言後 120 / 二回目 init) を同時に潰した。
- **是正 3 (spike 所見の反映について、F-6〜F-10 に対して)**: spike の
  close gate に「**所見が名指ししていない task も含め、plan の全 task を
  所見に照らして読み直したか**」を明示的に足す。反証可能な形は
  「読み直しの結果、追加訂正 0 件」を主張すること — F-6〜F-10 の 5 件は
  一度目の反映後に「0 件のはず」と暗黙に主張していた状態で見つかった
  ので、この主張を**明示させれば**次は検証対象になる。M3-Phase 7 T1 の
  goal substitution と同じ根 (「割り当てられた項目を消化した」で
  「責務を果たした」に置換する) なので、[[feedback_spike_discipline]] の
  更新候補としてオーナーに上げる。

### 後続タスク / オーナーへ共有すること

- audit table は「行の結論」ではなく「行が指すサイトの実在」から照合する。
  T5 は F-1 / F-2 / F-3 込みの 15 行相当を閉じることになる。
- **同じ誤りを spike 所見の反映でも繰り返した**: 所見が名指しした task
  だけを直し、所見が**含意する** task を読み直さなかった (F-6〜F-10、
  オーナー指摘で発見)。「所見 → 名指しされた箇所」は照合ではなく転記。
  spike の close gate に「plan 全体を所見に照らして読み直したか」を
  足すべきだった (下の是正 3)。
- 「緑だから正しい」を今フェーズでは使わない。T5 / T6 / T7 の close は
  それぞれの auditable artifact で行う。
- T1 の crispness 前後比較は spike evidence であって T10 の positive
  control A ではない。T10 は自分で撮り直す (T1 の frame は T4 未実装の
  ビルドなので窓の論理サイズが違う)。
