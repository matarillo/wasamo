### 自己分析（どの層が外れたか）

**前提の層 —— 証拠設計が確証志向だった。** 「挙動同一リファクタなので
フレームが一致すれば良い」という gate 記述をそのまま受け取り、
**一致することを示す**方向にセットを組んだ。一致は確証であって
反証ではない。「この同じ絵を出す**誤った**実装は何か」を明示的に
問うたのは、フレームを撮り終えてからだった。問うた結果、盲点（消し
忘れ側）と欠けた識別子（引き伸ばされたボタン）が同時に出て、変更前
フレームの撮り直しが要った。**gate が「一致」を要求する形をしている
とき、証拠設計は放っておくと確証側に倒れる。**

T2 で「green は fire を示すまで情報を持たない」と学んだのに、
その一般形——**「一致・緑・通過という形の観測は、赤くなることを別途
示すまで情報を持たない」**——に持ち上げられていなかった。T2 の教訓を
「単体テストという artifact 種別」に紐付けていたのが外れた層で、
これは T2 retro が「spike という task 種別に紐付けたのが誤り」と
書いたのと**同じ紐付け間違いの再演**（対象が spike → 単体テストに
変わっただけ）。

**disposition の層 —— 事象を直して、クラスを直していなかった（F-18）。**
T1 の F-2 は「row 12 は Box でなく ZStack」で、disposition は
「T5」。読んでいた行に対しては正しい。だが同じ主張が DD-003 row 10 にも
独立に書かれていて、そちらは **T7 の close artifact**。findings の
disposition が「この行を消費する task はどれか」だけを問い、
**「同じ主張はどの文書に載っているか」を問っていなかった**。再監査の
規律（T2 で入れた）は「plan の全 task を読み直す」形をしていて、
**ADR 側の重複を見に行く形にはなっていない**。今回それが顕在化した。

**手順の層は改善した。** 再監査を close gate の中の独立項目にした結果、
オーナーの問いかけ前に検出できた。T2 retro の是正テスト (2) は
初回について有効側の結果。ただし「有効だった」と言えるのは 1 回分で、
規律として定着したかは T4 以降が示す。

### 計画仮説・前提の問い直し（オーナーと）

三つ。

**(1) レビューレーンの引き上げをどう履行するか（マージ前に要判断）。**
F-17 で T3 を full independent review に上げたが、**その独立レビューを
実行できる主体が今この場に居ない**（自分の成果物を自分でレビューする
のは独立レビューではない）。選択肢は、(a) codex 等の別エージェントに
レビューさせる、(b) オーナーが読む、(c) 今回に限り「呼び出しサイト監査
＋ 3 変異のフレーム」を independent review の代替として受け入れ、
**代替であることを log に明記して**マージする、のいずれか。
(c) を選ぶ場合、代替として何が担保され何が担保されないかを書き残す
必要がある（変異は自分で設計したものなので、自分が思いつかなかった
誤り方は覆えない）。

**(2) T2 で保留した問い（純ロジックの end gate に「誤実装を当てて赤を
確認する」を明文化するか）に、T3 が二点目のデータを足した。**

効き、しかも**証拠パイプライン側の欠陥（F-21）を見つけた**。
つまり候補ルールは「純ロジックに限る」より広い形——**「gate の
artifact が『緑』『一致』『通過』という形をしている場合、それが
赤くなることを別途示す」**——かもしれない。広い形にすると trap #4 の
close artifact だけでなく trap #7（GUI positive control）の記述にも
効くので、vision decision record の範囲が T2 時点の想定より大きくなる。
今 phase 中に起こすか Phase 1 を閉じてからかは引き続きオーナー判断。

### 反証可能な是正テスト

三つ。(1) は T2 から継続、(2)(3) は今回新設。

**(1)（継続）plan 再監査を close gate の中に置く。** T3 は
オーナーの問いかけ前に 5 件検出したので、初回は**有効側**。
反証条件は変わらない: ある task が「0 件」と自己申告した後に

いない。T4 以降も同じ形（読み直した task 名 → 判定の表）で継続する。

**(2')（(2) の強化、2 巡目由来）disposition の列挙対象に「その主張を
*要約している*箇所」を含める。** S-3 は、(2) の規律を **finding を
載せている文書**にだけ適用し、**同じ文書の中の要約段落**や retro の
学び・共有事項に適用しなかったために起きました。訂正のたびに、
その主張の**全文・要約・引用**の 3 種類を検索する。**有効だったと
言えるのは、次の訂正で「要約側にだけ残っていた箇所」が 1 件以上
見つかったとき。**

**(2)（新設）findings の disposition に「同じ主張が載っている他の
文書」を書く欄を設ける。** F-18 は、正しい disposition（T5）を
書いたことで**探索が終わった**ために生き残った。次に ADR の記述を
falsify する finding が出たとき、disposition の前に「この主張は他に
どこに書かれているか」を明示的に列挙する。**有効だったと言えるのは、
その列挙で 1 件以上の二重箇所が見つかったとき。**列挙してもゼロ件が
続くなら、F-18 は DD-002 と DD-003 が同じ事実を独立に書いていた
という個別事情で、規律にする必要はないという反証になる。

**(3)（新設）証拠を撮る前に、却下案ごとに「それはどんなフレームを
出すか」を書き出す。** 「同じフレームを出す」と書ける却下案が
一つでもあるなら、証拠セットはまだ足りていない。T3 では撮った後に
気づいて撮り直しになった。**有効だったと言えるのは、T6 か T10 で
この事前列挙が撮影セットへの追加を 1 件以上強制したとき。**追加が
一度も発生しないなら、T3 の取りこぼしは「ギャラリーに引き伸ばされた
ボタンが無い」という個別事情だったという反証になる。

**(4)（新設・レビュー由来）副作用列挙は「壊れる経路」から数える。**
R-1 / R-2 / R-3 は、レイアウト経路を数えて網羅を主張したために
**レイアウトを走らせない経路**を落とした、という一つの失敗です。
次に trap #2 を close するとき（T7 が最有力）、経路の列挙を
「その機能が通る経路」からではなく **「この変更で成立しなくなる
前提は何か、その前提を満たさない経路はどれか」** から始める。
**有効だったと言えるのは、その順序で 1 件以上、機能側から数えたら
出てこなかった経路が出たとき。**出なければ、T3 の抜けは
「`window_add_widget` という例外的な API が存在した」という個別事情
だったという反証になる。

**(6)（新設）エスカレーションの前に確認ゲートの 3 基準を当てる。**
`window_add_widget` を「オーナー判断が要る」として上げたが、
どの基準にも当たらなかった。**発見が予想外だったこと**を
**判断が自分の手に余ること**と取り違えている。次に「オーナーに
判断を仰ぐ」と書くときは、3 基準のどれが発火したかを 1 行で書く。
**有効だったと言えるのは、それを書こうとして書けず、自分で決めて
進めた事例が 1 件以上出たとき。**

**(5)（新設・レビュー由来）ビルド・ツールの機構を主張するときは
実測する。** F-21 の原因を切り詰めたログから推測して間違えた
（R-5）。**次にビルドシステムやツールの挙動を findings として書く
ときは、タイムスタンプ・`cargo tree`・成果物の中身のいずれかを
実際に取ってから書く。**症状と対処が正しくても根拠が誤っていると、
後続がその根拠に基づいて別の判断をする（今回なら「鮮度チェックを
足せばよい」という誤った対処に至りうる —— 実測すると DLL の
タイムスタンプは更新されるので効かない）。**有効性の判定は、次に
同種の findings を書いたときに実測が入っているかどうか**で、
入っていなければ規律が定着していない。

## 独立レビュー（Codex）の結果と、そこから出た学び

結果は **major 1 / minor 4**。「ゼロ」ではありませんでした。全件を
ソースで再検証してから受け入れています（レビュアの言葉のままでは
受け取らない）。disposition の表は
[../implementation/log.md](../implementation/log.md)
§Independent review disposition。

**この 5 件のうち 3 件は、私が log に書いた主張を否定するものでした。**
種類が 2 つに分かれます。

**(A) 副作用列挙が「レイアウト経路」だけを歩いていた（R-1 / R-2 / R-3）。**
13 行の表は、ラベルのジオメトリを**レイアウトが書く**という前提で
経路を数えていました。そのため、
- `window_add_widget`（**意図的にレイアウトを走らせない**公開 API。
  ここだけは「次のパスで直る」ではなく**永久に直らない**）
- `append_child` / `replace_child`（`insert_child` と同類なのに列挙漏れ）
- **レイアウトが失敗した場合**（`?` で `sync_visuals` に到達しない）

の 3 種を落としていました。**「レイアウトを走らせない経路」こそが
この移動で壊れる経路**なのに、レイアウト経路を数えて網羅を主張して
いたわけです。列挙の枠組みが、探すべきものを構造的に見えなくしていた。

**(B) ビルドの機構を、切り詰めたログから推測して書いた（R-5）。**
F-21 の原因説明「cargo の依存辺が無いから再コンパイルされない」は
**誤り**でした。`cargo tree` には辺があり、実測すると
`wasamo.dll` は**再リンクされている**（タイムスタンプが更新される）。
古いのは `wasamo-dll/build.rs` が `/WHOLEARCHIVE` する
**uplift された rlib** のほうで、これは primary-package ビルドでしか
更新されない —— **F-5 とまったく同じ根因**で、症状が逆（F-5 は
うるさく失敗、F-21 は静かに成功）。私は最初の実行で
`Select-Object -Last 2` で出力を切り詰めており、「Compiling
wasamo-runtime が見えなかった」ことから機構を**推測**しました。
症状と対処（`--workspace` でビルドする）は正しかったので、
間違いは結論ではなく**根拠**にだけ現れていました。

なお実測で分かった追加の事実として、**DLL のタイムスタンプは新しく
なる**ので、鮮度チェックではこの罠を検出できません。

**2 巡目（差分レビュー）で 7 件。**  major 1 / minor 4 / nit 2、全件が
実在しました。1 巡目の教訓が、より鋭い形で再演しています ——
**訂正は当てた場所では正しく、当てる場所が足りていなかった。**

- **S-1（major、4 件目の経路）**: row 6 / 6b は **ABI ラッパ**を数えて
  いました。`WindowState::root_widget` / `root`、`WidgetNode::visual` は
  いずれも `pub` で、`append_child` などは `WidgetNode` の `pub fn` です。
  **境界は ABI ではない。** 経路を「ラッパ」ではなく**機構**で括り直し
  ました。
- **S-3（minor）が一番痛い**: F-21 の旧説明が、retro の学びと共有事項、
  log の再監査要約の 3 か所に残っていました。**F-18（「事象を直して
  クラスを直していない」）に対する訂正が、まさに F-18 と同じ形で
  不完全だった** —— finding を**載せている**文書は直し、
  **要約している**文書を直していない。
- **S-5 → 幅の穴は「記録」でなく「封鎖」しました。** 証拠 UI の初期値を
  9 にして 9 → 10 で桁が増えるようにし、stale-width 変異（N4）で
  カウントボタンが**完全に空白になる**ことを確認。高さ側は、
  `label_style` に setter が無く単行なので `lh` が font metric の定数に
  なり、**この証拠セットでは原理的に赤くできない** —— 発火しない変異を
  作文せず、再発トリガ（フォントフォールバック・複数行・style setter）
  付きで穴として記録しました。
- S-2 / S-4 / S-6 / S-7 は記述の不整合で、いずれも訂正済み。

**証拠 UI が既存の欠陥を 1 件掘り当てました（F-23）。** クリック後の

M3-Phase 4 T6 の不具合が、drain 経路にだけ生き残っています。
