## チェックリスト（task-end、項目 1〜11）

1. **今回の主な学び。** 陽性対照は「差が出ること」だけでは対照にならない。
   **差が出てはいけない脚**を同じ対照の中に持って初めて、差の原因を主張に
   結びつけられる（F-50）。今回それは 100% のモニタで、変換が恒等になる側。
   実際そこで両者が桁まで一致したことが、150% / 175% の差を「倍率認識の差」
   と言える根拠になった。副次的に、指標そのものの妥当性検査にもなっている
   —— 恒等の脚で差が出たなら、その指標は窓の同一性や撮影条件を測っていた
   ことになる。

   **再測定ではなく傍証**として記録した（撮影が DWM の拡張フレーム境界を
   返すため、外形そのものは測れていない）。Moment 2 の同期は T12。

## 目標・前提・計画仮説の再点検

> 後続タスクの retrospective でも流用するダブルループ振り返り欄。
> 実行の巧拙（シングルループ）でなく、**設定した目標・前提・事前計画
> （= 検証すべき仮説）自体が妥当だったか**を、反証可能な signal とともに
> オーナーと問い直す。下の 5 サブセクションがひな型。

### 観測された事実（反証可能な signal）

- **plan の §T11 は 3 項目で、陽性対照を 1 つも持っていなかった。**
  [AGENTS.md](../../../../AGENTS.md) がオーナー目視 smoke にも対照を要求して
  いるのに、7 タスク前から書かれていたこの節はそれを満たしていなかった。
  start gate の再監査で足したが、**気づいたのは着手時であって計画時では
  ない**。
- **plan が「注視せよ」と書いた項目は、人間の観測能力を超えていた。**
  ドラッグ中は窓が動いていて視線が追従し、対象は 60 Hz で 1〜2 フレーム。
  これを指摘したのはオーナーで、私はチェックリストに書いて渡していた。
- **「一致」と書いたものが一致していなかった。** 100% の 2 窓は統計値が
  桁まで一致するが画素は 17,712 個違う。窓幅を手で揃えたため（515 px と
  522 px）タイルの割り付けがずれていた。報告に出したあとで自分の測定に
  よって覆した。
- **タスクマネージャーの読み戻しを「2 プロセスが動いていた」と書きかけた。**
  一覧はソート済みかつスクロール中で、先頭行の上は隠れている。オーナーの
  「6-taskmgr-dpi.png の中身は確認したか」という一言がなければ、
  スクロールバーを見に行っていない。

### 自己分析（どの層が外れたか）

- **外れたのは実行ではなく計画の層。** §T11 は「オーナーが実行するから
  start gate なし」と書いてあった。これは*誰が観測するか*と*タスクに
  ゲートがあるか*を混同していて、その混同のせいで、対照の欠落も観測不能
  項目も 7 タスクぶん検出されずに残った。人が実行する項目にはゲートが
  要らない、という前提が誤っていた。
- **未測定を否定側に書かない規律が、また片側にしか効いていない。** T10 の
  retro が「未測定を肯定側に書かない」は守り「否定側」は守らなかったと
  書いている。今回それは**3 回**出た（画素一致、プロセス数、中間投影）。
  1 回目と 2 回目は自分で検出し、3 回目はオーナーの一言で検出した。改善は
  しているが、独力での検出率は 100% ではない。
- **良かった側の分析も要る。** 中間投影の項目は、実行前に、オーナーの
  指摘を受けて範囲外にした。**実行後に「見えなかった」と書く**のと、
  **実行前に「見られない」と書く**のとでは記録の値が全く違う。前者は
  否定的観測に見えてしまう。ここは前提の層で正しく直せた唯一の例。

### 計画仮説・前提の問い直し（オーナーと）

- **「オーナー実行だから start gate なし」という書き方を、この phase の
  外にも持ち出すか。** 今回は plan の該当行を訂正した（誰が実行するかと
  ゲートの有無は別）。同じ書き方が他の phase の plan にもあるなら、
  同じ訂正が要る。process 側のルールにするほどかは、オーナーの判断。
- **陽性対照に「一致する脚」を要求するのを、規約にするか。**
  [AGENTS.md](../../../../AGENTS.md) の現行文は「間違った実装でも同じに
  見える 1 枚は証拠にならない」と*差*の側だけを書いている。F-50 は
  その裏側で、handoff には入れたが、規約本文に足すかは structural change
  なので vision decision record 案件。T3 の「赤くなることを示す」義務の
  記録（phase-end 項目）と同じ棚に並ぶ話に見える。
- **人手手順を commit する運用を続けるか。** 今回 protocol.md を
  リポジトリに置いたことで逸脱（窓を縮めた）が可視化された。チャットに
  しか手順がなければ、フレームは計画どおりに見えていた。コストは
  1 ファイル。

### 反証可能な是正テスト

- **是正 1（F-50）**: 以降の GUI/証拠ゲートで対照を設計するとき、
  start gate に「この対照が**差を出してはいけない**条件」を 1 行書く。
  書けない対照は対照として弱いと判定する。
  *反証*: 次に対照を作るタスクが、その行を書かずに close できてしまったら
  この是正は効いていない。
- **是正 2（F-51）**: 一覧・リスト型の UI をそのまま証跡にするとき、
  「この画像が網羅性を示すか」を明示的に 1 行書く。示さないなら、
  網羅性はオーナー申告として別に記録する。
  *反証*: 次にスクリーンショットを証跡にするタスクが、写っていない行の
  可能性に触れずに「N 個だった」と書いたら効いていない。
- **是正 3（計画層）**: 人が実行する項目を plan に書くとき、
  **その観測が物理的に可能か**を書いた時点で自問する（持続時間・
  対象の運動・分解能）。
  *反証*: 次に人手項目を書くタスクで、実行者から「それは見られない」と
  指摘されたら効いていない。今回はオーナーが指摘した側だった。
