# T7 レトロスペクティブ

タスクブランチ: `feat/m4-phase-1-t7`

T7 は DD-M4-P1-003 の 5 step を実装した。scale を先に commit し、OS 提示の
physical rectangle を適用し、`SetWindowPos` が同期 dispatch する再入
`WM_SIZE` が new target で tree を投影し、その後に text を再 rasterize し、
`LRESULT(0)` を返す。T6 が分離した geometry / raster の 2 primitive を、
accepted order を動かさずに組み合わせた。

再入 `WM_SIZE` では通常の post-layout text refresh を抑止し、投影の**成功**
だけを記録する。`SetWindowPos` が失敗した場合、成功しても size 不変で
`WM_SIZE` が飛ばなかった場合、再入投影が失敗した場合のいずれでも、現在の
physical client rect を同じ committed scale で DIP 化して whole-tree fallback
を行う。step 4 は成功した投影の後だけ許可し、どちらの投影も失敗したら log
して cache / raster marker を進めない。

コード確定・テスト済みの実装コミットは次の 2 本:

- `e63586e feat(runtime): propagate WM_DPICHANGED in the accepted order`
- `712818b docs(runtime): weaken the step-order claim to what mutation M1 measured`

補助記録は `b58c336`（責務再監査 + start gate）、`7e886a7`（end gate）。
文書コミットは上の「コード確定時点」一覧に混ぜない。

## チェックリスト（task-end、項目 1〜11）

### 1. 今回の主な学び

**(a) 「構造で order を守った」は、mutation を走らせるまで強さが分からない。**
task list は step 1 / step 2 の順序を comment ではなく構造か反証可能な probe で
示すよう要求していた。`begin_scale_change` が scale と marker を同時に書く形に
したので「順序は構造が持つ」と書いたが、mutation M1（2 つの呼び出しを入れ替え）
で integration test 4 本すべてが green のままだった。marker が無い再入 pass は
未認識ゆえ未報告となり、fallback が同じ scale で再投影するので**最終状態は
どちらでも収束する**。残るのは DD-003 が警告している stale factor での 1 回の
投影であり、構造が変えたのは「恒久的な誤り」を「一時的で自己修復する誤り」に
した点だけだった。実装 doc comment 2 箇所と plan の記述を弱めた。強い主張を
書いた時点では自分では気づいておらず、気づかせたのは probe であって推論では
ない。

**(b) 抑止が「規範への忠実さ」ではなく「正しさ」である理由は、隣の arm を
読まないと出てこない。** 着地済みの `WM_SIZE` arm は geometry の `Result` を
捨てて text refresh を無条件に呼ぶ。通常の resize では target が動かないので
無害（失敗 node の retry にしかならない）だが、scale change では target が
動くので、投影が成功したかに関わらず raster marker が new DPI へ進む。これは
T6 独立レビューが shared cache の形で却下した「収束の偽装」が message loop
経由で再来する形だった。task list を読むだけでは step 番号への忠実さに見え、
arm を読むと正しさの要件に見える。責務再監査で `wnd_proc` を通読した 5 件の
追加のうち 4 件がこの種類だった。

**(c) 「every test stays green」と handoff が予告した hazard は、test を
1 行変えるだけで green でなくなった。** T4 の handoff row は `SWP_NOMOVE` を
この path に継承すると「monitor をまたぐたび window が pin されるのに test は
全部 green のまま」と書いていた。size だけ変える suggested rectangle ならその
通りだが、**position も動かす rectangle** にして realised rect を assert すれ
ば mutation M5 は fail する。予告された「検出不能」は、fixture の選び方の
問題だった場合がある。

**(d) `.ui` driven test は green かつ空でありうる。** 最初の test は
`Text { content: "..." }` と書いていた。DSL の属性は `text:` で、
`check::check` は**エラーを出さない**。結果として content が空・measured width
が `0.0` の Text node に対して `assert_close(after, before * 1.25)` が
`0.0` と `0.0` を比較して通っていた。救ったのは surface pixel の assertion
（`ceil(0.0) = 0` が `surface_pixels` の 1 px floor と食い違った）だけで、
witness について 2 つの事実を読んでいたことが検出条件だった。「k 倍された」
形の assertion は 0 で充足される。

**(e) 再入は borrow の問題であって message の問題だけではない。** T4 の
creation-time correction は `GWLP_USERDATA` 未設置の間に nested message を
流すので、`wnd_proc` が live な state に到達しない。T7 は pointer が live な
状態で初めて再入する。既存の全 arm は `&mut *state_ptr` を arm 集合全体に
渡って保持しているので、その中に arm を置くと nested frame の `&mut` と
alias する。arm を block の**上**に置き、`SetWindowPos` を挟む前後で短命な
アクセスだけにした。これは message 順序の話ではなく、置き場所の健全性の話で、
task list には無かった。

### 観測された事実（反証可能な signal）

事前計画の 1 命題と、実装中に自分で立てた 1 命題が別々の signal で反証された。

計画側: 「T7 の close artifact は enumeration（= 記述）なので、T7 自身の
gate では正しい順序と誤った順序を区別できない」。これは T7 の分岐 test が
無かった時代の想定で、実際には fallback を直接発火する test を書けたため、
gate は記述だけではなくなった。ただし**その test でも順序の入れ替えは
検出できない**ことが M1 で分かったので、計画の懸念は形を変えて残った。

自分の実装側: 「marker と scale を同一 primitive で書けば順序は構造が守る」。
M1 で 4/4 green。派生 copy が収束するので最終状態からは区別できない。

さらに、handoff が「every test stays green」と予告した `SWP_NOMOVE` hazard
（M5）は、fixture に position 変更を入れるだけで検出可能になった。予告は
fixture 設計を含意していなかった。

### 自己分析（どの層が外れたか）

外れたのは API 選択でも責務モデルでもなく、**主張の強度**と**fixture の
設計**。主張の強度については、「構造で守る」と書いた時点で、その構造が
何を不可能にするのかを状態遷移で確かめていなかった。marker 不在時に何が
起きるかを追えば mutation を走らせる前に分かった話で、T6 の学び (a)
「atomicity の単位は状態が表す命題ごとに選ぶ」と同型の見落ちである。
fixture については、hazard が「検出不能」と予告されていたのを、fixture を
変える余地の検討なしに受け入れかけた。

責務モデル自体は妥当だった。task list に無かった 5 件はいずれも
`wnd_proc` の通読で出てきたもので、「実コードを読んでから責務を確定する」
という手順が機能した。

### 計画仮説・前提の問い直し（オーナーと）

問い直したいのは、**「構造で守る」を close artifact として認める条件**。
本 task は「structural argument があれば probe は不要（not mandated）」と
書かれていたが、実際には structural argument の強度そのものが probe なしに
は確定しなかった。今後は「構造で守る」と書く場合、**その構造が排除する
状態を列挙し、排除しない状態を明示する**ことを条件にしたい。M1 のような
mutation は 1 build で済むので、コストは低い。

もう 1 点、handoff の「every test stays green」型の予告は、**現行 fixture
での事実**として読み、fixture を変えれば検出できるかを毎回問う扱いにしたい。
今回は 1 行で hazard が test 化できた。

### 反証可能な是正テスト

- 「構造が order / identity を守る」と書く task は、close 前に**その構造を
  崩す mutation を 1 つ以上 build して走らせ**、通ったか落ちたかを記録する。
  通った場合は主張を測定結果まで弱める。
- handoff / plan が「test では検出できない」と書いている hazard は、close
  gate で **fixture を変えて検出できないか**を 1 回問う。できた場合は test 化
  し、handoff row を更新する。
- `.ui` driven test は、witness について**独立な 2 つ以上の事実**を assert
  する（片方が退化しても他方が食い違う形にする）。「k 倍」型の assertion は
  0 で充足されることを前提に読む。
