  まで書くと gate が自分を通してしまう。
- **申し送りの単位を「命題」に固定できるか。** フェーズは「訂正は名前で
  なく命題で伝播する」を plan §Task list に既に持っている。今回わかった
  のは、**同じ規律が retrospective の申し送りにも要る**こと。T8 の
  申し送りは訂正ではなく予告だったので、この規律の対象外に見えていた。
  「予告も命題で書き、命題を assert している file を列挙する」まで
  広げるか。
- **計測器の前提を artifact に書かせるか。** F-48 は「ツールが正しく
  設定されている」という暗黙の前提が測定値を静かに変える例。GUI evidence
  の規約（CLAUDE.md §Testing rules、Observation 4）は capture の**機構**は
  規定しているが、**計測プロセス自身の posture** は規定していない。
  T10 に fold はしたが、Observation 4 側（T12 所有）に上げるべきか。

### 反証可能な是正テスト

- **免除条項の先書き**: 以後の plan / preamble を「gate の判定結果を
  planning 時に書いていないか」で検査する。**反証**: レビュアーが、
  planning 時点で結果まで書かれた gate 条項を新たに見つけたら失敗。
- **申し送りの命題化**: 次の task retrospective の「後続への影響」欄が、
  影響を **命題 1 文 + それを assert している file の列挙** の形で
  書かれているか。**反証**: 次 task が、申し送りに名前が挙がっていない
  file で同じ命題に起因する breakage を踏んだら失敗。
- **計測器 posture**: T10 の evidence artifact が、計測・capture を
  行ったプロセスの DPI awareness を明記しているか。**反証**: 明記の
  ないまま座標・矩形が artifact に載ったら失敗。
- **今回適用して効いた是正（記録）**: 「全称の主語を書いたら数え上げた
  表を残す」。close gate の call-site 表に
  「`clear_last_error()` の 24 箇所はすべて success-path clear」と
  書きかけ、数えたところ **21 が entry point の success clear、2 は
  `#[cfg(test)]` 内、1 が `wasamo_init` 自身**だった。書く前に数えたので
  landing していない。

### F-49 が足す型 — 「危険を指摘してから、その場で打ち消す」

レビューが名指しした 3 件（major 1 / major 3 / minor 6）は「その実行では真、
変更についての主張としては偽」だった。F-49 は**さらに悪い形**で、レビューでは
出ず、オーナー実行で初めて出た。

**危険は正しく指摘されていた。** end gate の landing blocker 段落は
「この binary は guard の外で OS を触る唯一の binary だ」と自分で書いている。
そして**同じ段落の中で**「Compositor を必要としないので成立するはず」と
打ち消した。予測は推論で、測定していない。

**これが「気づかなかった」より悪いのは、予測が検査を止めるから。**
危険に気づいていなければ「確かめよう」に進む余地があるが、気づいた上で
「大丈夫」と書くと、そこで検討が閉じる。読む側も「検討済み」と受け取る。

これは「危険に気づいた上で、その場で打ち消した」型であって、フェーズがこれまで
記録してきた「主張が対象より広い」型とは別の型。**是正**: **危険を書いたら、
その段落の中で打ち消さない。** 打ち消してよいのは測定した場合だけで、
測定していないなら「未確認」と書いて確認手段を添える。

**反証可能な是正テスト**: 以後の close artifact / plan で「〜という懸念が
あるが〜なので問題ない」の形を書いたとき、後半が測定に基づいているか。
**反証**: 測定の裏付けなく打ち消した予測が、後の実行で外れたら失敗。

## 独立レビューの結果を踏まえた追記

full independent review で **major 3 / minor 4 / nit 5 件**。全件 confirmed、
disposition は
[log.md §T9 independent review](../implementation/log.md) に表で記録。
ダブルループとして意味があるのは **3 件が同じ型だった**こと。

**major 1・major 3・minor 6 は「その実行では真、変更についての主張としては
偽」という同一の欠陥。** さらに major 1 と major 3 は、より鋭い同じ形をして
いる — **120 DPI の開発機では discriminate するが 96 DPI では vacuous な
assertion を、テストの性質として提示した**。

- major 1: `cached == os_dpi` は、seeding を `DipScale::IDENTITY` に
  置き換えても 96 DPI 機では通る（`IDENTITY.dpi()` が 96 だから）。
  差し替えた awareness precondition もそこでは独立に true。つまり
  **seeding path は CI で一切カバーされていない**。自分で再現して確認した
  （宣言を外し seeding を潰すと、落ちるのは `is_v2` の行だけで
  `cached == os_dpi` は通る）。
- major 3: `normalise_to_reference_baseline` の scale assertion は
  96 DPI 機では `96 == 96` で、commit が起きたかどうかに関係なく通る。
  「T8-M7 が広く発火するようになった」は開発機の性質であって fixture の
  性質ではない。

**これが痛いのは、両方とも「fixture を machine-independent にする」ことを
目的とした作業の中で起きたから。** 一般化そのものは正しく（arithmetic は
両機で同一）、外したのは **一般化の成果をどう主張するか**の側。フェーズが
T4 から 8 回記録してきた「主張が対象より広い」型が、9 回目・10 回目として
自分の是正作業の中に出た。

**この task が記録に足す是正**: **fixture を machine-independent と主張する
なら、その fixture が実際に走る機械それぞれで主張を評価する。** この
リポジトリでは 96（CI）と 120（開発機）の 2 つで、assertion の強さは
**弱いほうの機械で決まる**。「一般化したので機械に依存しない」は
arithmetic についての主張であって、assertion の discriminating power に
ついての主張ではない — 2 つは別で、今回は前者を後者として書いた。

**反証可能な是正テスト**: 以後、machine-independence を主張する fixture に
ついて、その主張が「96 DPI でも同じ assertion が発火するか」を明示的に
書いているか。**反証**: レビュアーが、片方の機械でのみ発火する assertion を
machine-independent と書かれた artifact の中に再び見つけたら失敗。

major 2（伝播 pass の enumeration artifact 欠落 + 見落とし 1 件）は別型で、
既知の「名前で伝播して命題で伝播しない」型の 9 回目。見落とし site は
**是正した site と同じ file の中**にあった。原因は enumeration の第 3 段階
（検索）に enumeration 自体を決めさせたこと — 命題を書き、assert している
物を列挙し、**それから**検索する、の 3 段目で列挙が検索結果に置き換わった。
[log.md](../implementation/log.md) §The propagation pass に両命題の
site 表を追加した。
