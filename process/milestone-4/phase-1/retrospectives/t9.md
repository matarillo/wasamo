- **申し送りの粒度が実際の影響範囲と 1 桁違った。** 予告 = 1 binary 1

### 自己分析（どの層が外れたか）

**外れたのは「事前計画」層で、しかも 2 方向に外れた。**

- **過小**: plan は T9 を「宣言 1 行 + テスト + 3 ホスト再ビルド」と
  見積もっていた。実際には ABI entry point の編集（F-46）と、他 task の
  証拠 binary 2 本の書き換え（F-47）が入った。どちらも「宣言を入れる」の
  必然的な帰結で、planning 時に landing site を読めば見えたはずのもの。
  T1 spike は `runtime.rs` の `init` を読んでいるが、`abi.rs` の
  `wasamo_init` が **success arm で clear する**ことは
  [log.md](../implementation/log.md) §T1 の per-file 表に記録されている
  — つまり**情報はあり、含意が結ばれていなかった**。
- **過大**: plan は trap #4 に stated limit の逃げ道を用意していた。
  これは「発火できないだろう」という planning 時の予測を、gate の
  免除条項として先に書いてしまった形。予測が gate に埋め込まれると、
  実装時に予測を検証する動機が消える。

**目標・前提層は外れていない。** 宣言の site（one-shot の下）、失敗許容、
「scale 1 と仮定する分岐を足さない」はすべて成立し、mutation で反証可能

### 計画仮説・前提の問い直し（オーナーと）

- **gate に免除条項を先書きしてよいか。** plan §T9 と preamble の両方が
  「発火できなければ stated limit でよい」を書いていた。今回は re-audit で
  拒否できたが、これは規律ではなく偶然に近い（依頼文が「trap #4 の判定を
  明示的に再実行」と念押ししていた）。**「gate の免除条項は、免除が必要に
  なった時点で書く。planning 時に先書きしない」** を規約に上げる価値が
  あるか。planning 時に書けるのは「ここで判断が要る」までで、判断の結果
  まで書くと gate が自分を通してしまう。
- **申し送りの単位を「命題」に固定できるか。** フェーズは「訂正は名前で
  なく命題で伝播する」を plan §Task list に既に持っている。今回わかった
  のは、**同じ規律が retrospective の申し送りにも要る**こと。T8 の
  申し送りは訂正ではなく予告だったので、この規律の対象外に見えていた。
  「予告も命題で書き、命題を assert している file を列挙する」まで
  広げるか。
- **計測器の前提を artifact に書かせるか。** F-48 は「ツールが正しく
  設定されている」という暗黙の前提が測定値を静かに変える例。GUI evidence
  の規約（CLAUDE.md §Testing rules、Observation 4）は capture の**機構**は
  規定しているが、**計測プロセス自身の posture** は規定していない。
  T10 に fold はしたが、Observation 4 側（T12 所有）に上げるべきか。

### 反証可能な是正テスト

- **免除条項の先書き**: 以後の plan / preamble を「gate の判定結果を
  planning 時に書いていないか」で検査する。**反証**: レビュアーが、
  planning 時点で結果まで書かれた gate 条項を新たに見つけたら失敗。
- **申し送りの命題化**: 次の task retrospective の「後続への影響」欄が、
  影響を **命題 1 文 + それを assert している file の列挙** の形で
  書かれているか。**反証**: 次 task が、申し送りに名前が挙がっていない
  file で同じ命題に起因する breakage を踏んだら失敗。
- **計測器 posture**: T10 の evidence artifact が、計測・capture を
  行ったプロセスの DPI awareness を明記しているか。**反証**: 明記の
  ないまま座標・矩形が artifact に載ったら失敗。
- **今回適用して効いた是正（記録）**: 「全称の主語を書いたら数え上げた
  表を残す」。close gate の call-site 表に
  「`clear_last_error()` の 24 箇所はすべて success-path clear」と
  書きかけ、数えたところ **21 が entry point の success clear、2 は
  `#[cfg(test)]` 内、1 が `wasamo_init` 自身**だった。書く前に数えたので
  landing していない。
