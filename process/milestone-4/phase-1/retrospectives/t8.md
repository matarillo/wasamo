## チェックリスト（task-end、項目 1〜11）

### 1. 今回の主な学び

**(a) 一番の収穫は「落ちるはず」の mutation が通ったこと。** M5 は fixture の
client extent を 24 の倍数でない 785 × 480 にする mutation で、start gate に
書いた F-44 の帰結（「正規化しないと per-node の幾何 assertion を等値には
できない」）が正しければ落ちるはずだった。**通った。** WrapPanel の tile は
固定 cross-size で start-pack されるので、client extent が 0.2 DIP ずれても
1 つも動かない。つまり不変性の連続側は client extent について**何も読んで
いなかった**。root node の Visual（window-root の `Fill` 上書きにより client
矩形そのもの）を readback に足して初めて、同じ run が `981.0` vs `981.25` で
落ちるようになった。F-44 の算術は生き残り、そこから導いた帰結は生き残ら
なかった。分けたのは推論ではなく mutation である。

**(b) 同じ run が、丸めとは無関係な物理制約を測った。** client を 784 × 561
にすると 192 DPI の目標は 1568 × 1122 で、window が実現するのは 1568 ×
**1014** — モニタの max track size である。丸めの議論をずっとしていて
「そもそも入らない」を予測していなかった。`set_client_extent` の
realised-client assertion があるのでこれは名前のついた失敗になったが、
無ければ「なぜか少し違う」で終わっていた。

**(c) ADR の evidence item (2) は、2 つの主張に見えて 1 つの方程式だった
（F-45）。** before-state が `s = 1` である限り、「DIP layout 結果が不変」と
「Visual が比率で動いた」は同値である。runtime が提供する唯一の「DIP layout
結果」の読み方が「Visual を読んで割る」だからで、`after = before × ratio` と
`after ÷ ratio = before` は同じ式でしかない。分けるには**離散的**な事実が
要る。plan が §T10 用に記録していた 9-vs-7 の tile 数がそれで、headless test
で `(9, 2)` vs `(7, 2)` として実際に出た。

**(d) 「厳密等値か許容誤差か」は測って初めて正当化できる。** `factor_is_exact`
を `true` に固定する probe は 100 DPI の root 高さで `500.0` 読み値に対し
`499.99997` 期待値で落ちた。どちらが不正確かが重要で、**runtime はちょうど
500 を出しており、不正確なのは test の期待値**（`480 × f32(100/96)`）の方
だった。runtime が layout した DIP extent は `500 ÷ f32(100/96)` = 480.00003
だからである。不変性は 100 DPI でも成立していて、その素朴な言い換えだけが
厳密でない。

**(e) 一手で 4 つの DPI 全部が厳密になる。** `96 = 2^5 × 3` なので、
100 / 120 / 144 / 192 DPI が要求する分母は 24 / 4 / 2 / 1 であり、physical
client を **24 の倍数**に正規化すれば全部が整数目標になる。`wasamo_load_ui`
が作る 784 × 561 からは 1 つも厳密にできない（561 × 1.25 = 701.25）。

### 観測された事実（反証可能な signal）

**start gate で自分が書いた finding の「帰結」が、その finding の「前提」より
先に壊れた。** F-44 は 2 つの文からできていた。(i) 784 × 561 からは DIP client
extent を厳密に保存できない（算術）。(ii) だから正規化しないと per-node の
幾何 assertion を等値にできない（帰結）。mutation M5 は (ii) を反証した。
(i) は今も正しい。start gate に書いた時点では 2 つを区別していなかった。

**もう 1 つ、計画側の命題が測定で置き換わった。** plan の T8 bullet は
「T8 は矩形を選ぶので tolerance ではなく equality を assert できる」と書いて
いた。これは T8 が矩形を選べることの帰結として正しいが、**どの矩形でもよい
わけではない**という条件が落ちていた。条件を補ったのが 24 の倍数の正規化で、
それを補わないと何が起きるかは丸め誤差ではなく「window がその大きさに

**厳密性の分岐も測定で決まった。** 100 DPI で `assert_eq!` を強制する probe を
1 本走らせるまで、tolerance が必要かどうかは推論でしかなかった。走らせたら
落ち、しかも不正確なのは runtime ではなく test の期待値の方だった。

### 自己分析（どの層が外れたか）

外れたのは API 選択でも責務モデルでもなく、**算術の正しさから測定の感度を
推論した**層。「この数は厳密に保存できない」から「だから assertion が厳密に
ならない」へ 1 歩で進んでいて、その間にある「assertion が読んでいる量は
その数の関数か」を問うていなかった。WrapPanel の tile が start-pack される
という、fixture を選んだときに自分で書いた性質を読めば mutation の前に
分かった話である。

T7 の学び (a)「『構造で order を守った』は mutation を走らせるまで強さが
分からない」と同型で、対象が構造ではなく **fixture の感度**に移っただけ。
T6 の学び (a)「atomicity の単位は状態が表す命題ごとに選ぶ」も同じ形をして
いる。3 回とも「自分が書いた主張の適用範囲を、測る前に見積もった」ことが

責務モデル自体は妥当だった。責務再監査で出た 4 件はいずれも「assertion が
実際に何を読むことになるか」を紙の上で追って出てきたもので、task list を

### 計画仮説・前提の問い直し（オーナーと）

問い直したいのは、**start gate に finding を書くときの粒度**。今回 F-44 を
「算術 + 帰結」の 1 件として書いたために、帰結だけが誤っていることが close
まで見えなかった。今後は「**X なので Y**」型の finding を書いたら、X と Y を
別の主張として分け、**Y の側に 1 本 mutation を割り当てる**ことを条件にしたい。
T7 の是正テスト（「構造が守る」と書いたら崩す mutation を走らせる）の一般化で、
コストは同じく 1 build である。

もう 1 点、**「落ちるはずの mutation が通った」を finding として扱う運用**を
明示しておきたい。今回はそれが最大の収穫だったが、plan の bullet は
「A mutation that leaves every test green is the finding, not the failure」と
書いていながら、それが自分に起きる想定では書かれていなかった。

### 反証可能な是正テスト

- **「X なので Y が必要」と close artifact に書いたら、X を外した build を
  1 回走らせ、Y が本当に壊れるかを記録する。** 壊れなければ Y を測定結果まで
  弱めるか、Y を成立させる readback を足す。T8 では後者を選んだ。
- **fixture を選んだら、assert する量が「不変に保った入力」の関数かを 1 回
  問う。** 関数でなければその assertion は入力について何も言っていない。
  最短の確認は入力を壊す mutation 1 本。
- **厳密等値と許容誤差の分岐は、厳密側を強制する probe を 1 回走らせてから
  書く。** 落ちた場合は、どちらの値が不正確なのか（runtime か test の期待値
  か）まで記録する。今回は後者だった。
- **evidence 系 task では「入らない・作れない」型の失敗を丸めより先に疑う。**
  数値の議論は目立つが、window size / surface size / monitor 制約の方が先に
  当たる。
