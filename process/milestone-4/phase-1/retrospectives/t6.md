# T6 レトロスペクティブ

タスクブランチ: `feat/m4-phase-1-t6`

T6 は、テキスト面を window DPI のデバイス解像度で確保・描画し、
`CompositionSurfaceBrush` を 1 texel = 1 device pixel に固定した。また、
window に属する content tree の node-side scale cache を、fallible な brush
準備と infallible な cache commit の 2 pass で揃えるようにした。初回
`set_root` と両 layout entry が同じ primitive を通るため、IR conditional /
`for` で増えた subtree は scheduled layout で正規化される。direct tree
mutation は自身では layout を schedule しない既存 limit を保つが、後の
layout が geometry を初めて書く直前には同じ正規化を通る。

- `4c536ac feat(runtime): rasterize text at the window DPI`

補助記録は `7c4ddc7`（責務再定義 + start gate）と `6946791`（end gate +

## チェックリスト（task-end、項目 1〜11）

### 1. 今回の主な学び

**(a) tree-wide operation の atomicity は、最終状態でなく途中の失敗点から
設計しないと見えない。** 元の plan は、1 回の再帰で brush を作りながら
cache も更新する想定だった。途中の 1 node で WinRT error が出ると、それ
より前だけ cache が新しくなり、次の `sync_visuals` が 1 tree を複数倍率で
投影する。start gate の副作用列挙でこれを反証できたので、production code
編集前に prepare-then-commit へ変えた。結果として、失敗時に一部 brush が
準備済みになることはあっても geometry cache は旧倍率で一様なままで、次回
は stale cache を根拠に再試行できる。

**(b) 「100% なら不変」は、倍率演算だけを見た仮説だった。** D2D DPI と
atlas-origin conversion は 96 DPI で恒等だが、`ceil` による整数 surface
確保と DD-M4-P1-006 の `None` / top-left mapping は恒等ではない。親版と
T6 版は 96 DPI でも 6 枚すべて materially different で、brush setter だけ
を外した mutation でも 6 枚すべて変わった。予想と違う frame を退行として
押し戻さず、計画の「unchanged」を反証された命題として訂正できたのが重要。

**(c) GUI の before/after だけでは、正しい機構を特定できない。** 125% の
対は「小さくぼけた parent」と「client 全体に広がり、glyph の stem/counter
が改善した T6」を区別する。ただし複数の row-7 変更をまとめて観測するだけ。
そこで default-brush mutation と、live WinRT property を読む mock-free
integration test を追加し、`Uniform` / `0.5` と `None` / `0.0`、非比例な
source/destination、整数・小数 origin を別の positive control にした。

**(d) build freshness と source identity は同じではない。** 親 worktree と
task tree が同じ target を使った比較では、親を build した直後に task 側の
runtime が fresh と判定された。さらに mutation capture は、source を戻す
だけでは DLL を戻さない。比較 source tree ごとの target 分離と、mutation
後の package clean + accepted-source rebuild が必要である。最終 6 frame が
受入版 6 frame と client 内 byte-identical になったことまでを close にした。

## 目標・前提・計画仮説の再点検

> オーナーと問い直す。下の 5 サブセクションがひな型。

### 観測された事実（反証可能な signal）

事前 plan の二つの命題が別々の signal で反証された。単一 fallible walk は
中間失敗点を置くと mixed cache を作る。100% rendering unchanged は fresh
parent/T6 6-frame pair が全件 material difference を示す。さらに、同一
source を意図した最終 frame が accepted pair と byte-identical になるまで
clean rebuild しないと、mutation artifact の残留を否定できなかった。

### 自己分析（どの層が外れたか）

外れたのは API 選択ではなく、**責務モデル**と**証拠モデル**。責務モデルは
成功時の最終 tree だけを見ており、O(text nodes) の途中失敗と incremental
attach を含めていなかった。証拠モデルは「倍率 1 = 全操作が恒等」とまとめ、
ceil と brush mapping を DPI conversion から分離していなかった。start gate
の副作用列挙は前者をコード前に止めたが、後者は実画像を撮るまで止められなかった。

### 計画仮説・前提の問い直し（オーナーと）

T6 の目的を「DPI 引数を text renderer に通すこと」と狭く置くべきでは
なかった。出荷される責務は、window content tree が geometry を書く時点で
scale cache と text surface が同じ window scale に収束していること。その
ため initial attach と incremental attach を 1 primitive で覆う現在の責務が
妥当だった。一方、直接 Composition visual を足す `window_add_widget` まで
暗黙に含めると retained root のない別 API を再設計するため、明示 limit の
ままが妥当。将来この API が content root を保持する時点が再検討 signal。

### 反証可能な是正テスト

後続の tree-wide fallible operation は、approach 選択前に「先頭成功、途中
失敗、末尾未実行」の状態表を書き、authoritative / derived data の各 writer
が何を残すかを確認する。GUI の「倍率 1 では不変」は、変更操作を列挙し、
各操作が本当に identity かを別々に判定する。cross-tree / mutation evidence
は source tree、artifact directory、build command、最終 accepted rebuild を
4 点セットで記録し、最終 capture を既知 accepted capture と比較する。

### 後続タスク / オーナーへ共有すること

T7 は current combined primitive をそのまま呼べない。`WindowState::scale`
だけを先に変えると root cache が authoritative target を失い、通常 layout は
旧 root cache を target に選ぶため stale-cache retry が成立しない。R1 の
推奨 split を採るか別案を選び、failure state を再列挙する必要がある。
T8 は legitimate attach path では stale descendant を作れないので hidden seam
を使う。T10/T12 は F-40 の target isolation と accepted rebuild を evidence
手順として実行・同期する。オーナーには、別エージェントの full review が
zero-major になるまで merge gate を開かないことを共有する。
