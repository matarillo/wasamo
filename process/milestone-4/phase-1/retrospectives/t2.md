## チェックリスト（task-end、項目 1〜11）

1. **今回の主な学び。** 四つ。

   - **(a) 「純ロジックだからテストが情報を持つ」は半分しか正しくなかった。**
     plan は T1 の F-4 を受けて「T3〜T8 では green は証拠にならない、ただし
     T2 は例外で、純ロジックなので自分の単体テストが本当に情報を持つ」と
     書いている。実際に書いてみると、11 本 green の状態が言っていたのは
     「11 本とも ok」だけで、**そのテストが fire するかどうかは別の主張**
     だった。誤実装を 7 種類当てて赤を確認して初めて、green に意味が
     生まれた。F-4 の教訓は task の種類を変えても生き残る形をしている。

   - **(b) convert-once 規則は 100% と 200% では観測できない。**
     倍率が 2 の冪だと乗算が誤差なしなので、「DIP で引いてから掛ける」と
     「掛けてから引く」が**完全に一致する**。総当たりで探して 200% では
     反例がゼロだった。150% では `abs=10.1 / parent=5.7` で
     once=6.600001（正しく丸めた値そのもの）に対し twice=6.6000013 と
     1 ulp ずれる。F-4 の算術レベル版で、**この phase の規則が検証可能な
     倍率は 125% と 150% だけ**という事実が、GUI だけでなく `f32` の
     世界でも同じ形で出た。

   - **(c) 型の形がテストの仕事を一部肩代わりした。** 想定した誤実装の
     うち一つ ——「幅を、左端と右端をそれぞれ変換して引き算で出す」——
     は `extent_to_physical` に対しては**書けなかった**。シグネチャが
     寸法しか受け取らず位置を知らないため。テストで守るより型で守る
     ほうが強い、の具体例なので log に「書けなかったこと」として残した。

   - **(d) witness は手で選ばず総当たりで探した。** 丸めの向きが両側で
     あることの証拠も、convert-once の反例も、それらしい値を手で置いて
     いたら「たまたま一致する組」を選んで tautology になっていた可能性が
     高い（200% では全部一致する、が実例）。探索してから書く、を先に
     決めて start gate に書いておいたのが効いた。

### 観測された事実（反証可能な signal）

- 11 本のテストが green になった時点と、7 種類の誤実装を当てて赤を
  確認した時点とで、**手元にある証拠の質が別物**だった。前者は
  「テストが存在して通った」しか言っていない。
- 総当たり探索の結果、200% では convert-once 規則の反例が **1 件も
  無かった**。100% でも同じ。125% / 150% でだけ差が出る。
- 2 の冪倍率では往復変換が**厳密に恒等**になる（200% で 200 万個の
  連続 `f32` に対し誤差ゼロ）。125% では同じ範囲で 75 万件が非厳密。
- 想定した誤実装 8 種のうち 1 種が、API のシグネチャ上**書けなかった**。

### 自己分析（どの層が外れたか）

**前提の層。** plan は task ごとの gate 置換表で「T3 は描画フレーム、
T5 は監査表、T7 は副作用列挙、T8 は自前のアサーション」と、いずれも
**エージェントが捏造しにくい auditable artifact** を割り当てている。
ところが T2 にだけ「自分の単体テスト」が割り当たっていて、これは
「テストを書いて green にしました」という、最も捏造しやすい形の主張に
なりうる。F-4 が「green は証拠にならない」と結論したのに、その例外条項
（純ロジックなら情報を持つ）に**条件が書かれていなかった**のが穴。
正しくは「純ロジックであり、かつ **fire することを示せば**情報を持つ」。

今回は mutation 表を足して埋めたが、それは start gate で trap #4 を
「新しい算術分岐はそれを fire させるテストと一緒に出す」と読んだ結果
たまたま辿り着いたのであって、plan がそう要求していたからではない。
同じ穴は M4 の他フェーズにある純ロジック task でも再発しうる。

### 計画仮説・前提の問い直し（オーナーと）

問い一つ。**純ロジック task の end gate に「誤実装を当てて赤を確認する」
を明文化するか。** 今回は task 一つ分の追加コストが 15 分程度で、
得られた情報（どのテストがどの誤りを捕まえるかの対応表）は
そのままレビュー材料になった。一方でこれを規約にすると、テストを書く
たびに mutation を回す義務が発生する。折衷案は「新しい**丸め規約 /
単位変換 / 境界条件**を持つ純ロジックにのみ課す」で、T2 のような
「規約を一か所に置くための型」が対象になる。

規約化するなら実装ゲートの trap #4 の close artifact 側（「分岐ごとの
テスト名」→「分岐ごとの、赤を確認した誤実装」）を触ることになるので、
process rule lifecycle の**構造変更**に当たり、vision decision record が
要る。今 phase 中に起こすか、Phase 1 を閉じてから判断するかはオーナーの
判断を仰ぎたい。

### 反証可能な是正テスト

次に純ロジックの単体テストを書く task（M4 内で言えば M4-Phase 2 の
イベント経路の純ロジック部分が最有力）で、**テストを書いた直後に最低
1 種類の誤実装を当てて赤を確認する**運用を試す。是正が有効だったと
言えるのは、その 1 回で「実は fire していなかったテスト」が 1 本でも
見つかったとき。1 本も見つからなければ、この規律は T2 固有の事情
（丸め規約という、正しく見える誤答が多数ある領域）に依存していた
という反証になり、規約化しない根拠になる。

### 後続タスク / オーナーへ共有すること

- **125% / 150% でしか観測できない規則が、GUI だけでなく算術にもある。**
  T8 の重みは F-4 で一段上がったが、さらに「200% を足しても
  convert-once 規則の検証にはならない」ことが分かった。T8 の 125 /
  150 / 200% の三点のうち、**規則の検証に効くのは前二つ**で、200% は
  桁の大きい確認という位置づけになる。
- T6 は `surface_pixels` を呼ぶこと。`ceil` を手書きしないこと。
  T5 は `relative_offset_to_physical` を呼ぶこと。`factor()` を掴んで
  掛け算を手書きしてよいのは T6 の `96 × s` だけ。
- T6 は `surface_pixels` が `(u32, u32)` を返すことを前提に、
  `CreateDrawingSurface`（`f32` の `Size`）に渡すならキャストが要る。
  `CreateDrawingSurface2`（`SizeInt32`）に切り替える選択肢が DD-002 に
  明記されているので、T6 が選ぶ。

## オーナーに確認したいこと（項目 4 の中身）

いずれも「このまま進める」で構わないが、判断としては共有しておきたい。

1. **DPI ゼロを恒等倍率に落とす分岐を入れた。** `GetDpiForWindow` は
   無効なウィンドウハンドルに対して 0 を返す。0 のまま持つと `to_dip`
   がゼロ除算して、原因から遠い場所で座標が無限大になる。
   DD-001 が option F3 として却下した「宣言に失敗したら倍率 1 と
   みなす」とは別物だと考えている —— F3 は**実在するが未知の倍率**を
   当てにいって外す話で、こちらは倍率そのものが得られていない。
   ただし「防御分岐を足した」ことに変わりはないので、不要という判断
   なら外す。

2. **`96 × s`（D2D コンテキストの解像度）を型に入れなかった。**
   plan が名指ししたのは `ceil` の規則だけで、その理由は「丸めという
   間違えうる規約を持つから」だと読んだ。`96 × s` には丸めが無く、
   `factor()` から乗算 1 回で出る。入れると、OS 描画に依存しないことが
   取り柄の型に DirectWrite 側の関心が入る。T6 が呼び出し側で書く。

3. **`surface_pixels` の返り値を `(u32, u32)` にした。** 丸め規約の
   要点が「実数がピクセル数という整数になる唯一の場所」なので、
   整数で返して後段のキャストで戻せないようにした。代償として T6 が
   `CreateDrawingSurface` に渡すときキャストが要る（あるいは
   `CreateDrawingSurface2` に替える）。
