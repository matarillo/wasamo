## Carry-forward to later phases

Known at planning time from the ADR's forward-compat exposure; each is
re-confirmed or revised at phase close, and each carries a re-trigger
criterion rather than a date.

| Item | Lands at | Re-trigger criterion |
|---|---|---|
| Layout-derived hit rectangles — stop reading geometry back off the Visual; cache each node's arranged DIP rectangle during layout | M4-Phase 2 | The event-routing model needing layout-derived hit rectangles, or a DIP-denominated minimum hit target. Both expected in that phase. The T5 pointer / readback conversions cancel today precisely because hit-testing sources geometry from the visual tree; they stop cancelling here |
| Host-visible scale or work-area query | M4-Phase 7 ABI wave, or M4-Phase 8 with `WindowConfig` | A host must express or receive a length not expressible in DIP — a device-pixel budget, a monitor work area, a screen coordinate. Not retrofitted into this phase, and not pre-built on a prediction |
| Per-window differing scale factors | M4-Phase 8 | Additive by construction — the scale is already per `WindowState`. Confirm no shared state crept in |
| Client-size window semantics | M4-Phase 8 / AC11 | Arrives as a new named attribute, never as a reinterpretation of `width` / `height` |
| Screen-coordinate mapping (IME caret and composition rectangles; top-layer placement) | M4-Phase 5 / 6, M4-Phase 9 | Lands as `visual absolute physical → ClientToScreen` with **no** scale multiplication, because the visual tree is in the space the Win32 call expects. The concrete downstream payoff of keeping the visual tree physical |
| Resolution-dependent image asset selection | M4-Phase 4 | The second rasterized asset kind arrives on the same surface-resolution contract |
| Integer pixel snapping | Deferred | Would extend the rounding contract inside `DipScale` rather than change the space definition |
| Text rendering-quality tuning (rendering mode, gamma, explicit hinting) | M5 theming wave | This phase's obligation ends at "drawn at the correct resolution" |
| Custom title bar / client-area frame extension | M5 theming wave | Would make V2's automatic non-client scaling scale a surface Wasamo also paints; the full reliance must then be re-decided |
| Non-zero clip insets | Whenever introduced | Clip insets are exempt from conversion only because they are all zero. A non-zero inset puts that audit row back into the converted set |
| A scale-dependent `measure` (explicit hinting, snapped metrics) | M5 text-quality wave | Would turn T7's re-rasterize-after-re-layout ordering from a free choice into a correctness constraint; the reason is recorded so it can be re-derived rather than rediscovered |
| Phantom-typed length newtypes (`Dip<T>` / `Px<T>`) | Available, not scheduled | Adopted only if a unit-mixing defect actually recurs — not on a prediction that it might |
| `WM_GETDPISCALEDSIZE` | Available, not scheduled | A phase wanting to propose its own post-change window size (author-specified sizing, AC11 / M4-Phase 8) |
| Synthesised pointer update after a scale change | M4-Phase 2 event model | If hover correctness across a resize turns out to matter |
| **The per-node geometry-scale cache has exactly one writer** — `commit_scale_recursive`; `WindowState` holds the authoritative value, and production layout receives it explicitly rather than recovering it from the root copy (T1 decision, corrected at T6 independent-review R1) | In force from T5 onward | Any path that attaches, re-parents, or re-materialises a subtree must eventually enter the production layout boundary with the owning window's target. **Corrected at T3 (F-24): `lib.rs::window_add_widget` is deliberately outside that boundary** — it attaches a Visual without entering `root_widget`, so the subtree gets no layout, no geometry-cache write and no re-rasterization. **Widened at T5 (F-32) and resolved at T6:** the IR conditional / `for` paths schedule dirty layout; direct `WidgetNode::append_child` / `insert_child` / `replace_child` and ABI wrappers do not, so they wait for a later `WM_SIZE` or size-affecting property pass. That first later pass projects the whole tree at explicit `WindowState::scale`, commits geometry, and refreshes text against an independent last-rasterized-DPI marker. A text failure therefore cannot erase the authoritative target or prevent geometry, and only the failed raster marker remains stale. |
| **`cargo test --workspace` needs `cargo build -p wasamo-runtime` first from a cold target directory** — `wasamo-dll/build.rs` whole-archives the *uplifted* `<profile>/libwasamo_runtime.rlib`, which cargo produces only once `wasamo-runtime` has been built as a primary package (T1 finding F-5; pre-existing, not introduced by this phase) | T12's clean-rebuild gate; [AGENTS.md §Build ordering](../../../../AGENTS.md) | Any clean rebuild, any CI cache miss, or any toolchain update that invalidates the uplifted rlib. Cold-directory failure is `LNK1356`; a stale uplifted rlib fails later as `LNK2019` on `core` / `std` symbols. `cargo check` never links and stays green through both |
| **The same whole-archive path also fails *quietly*: a host-package build relinks `wasamo.dll` around the stale uplifted rlib** — cargo recompiles `wasamo-runtime` as a dependency and relinks the DLL, but refreshes `<profile>/libwasamo_runtime.rlib` only on a primary-package build, so the fresh DLL carries the previous runtime (T3 finding F-21, the row above's root cause with the opposite symptom; pre-existing, not introduced by this phase) | Every GUI evidence gate — T6, T9, T10 — and [AGENTS.md §Build ordering](../../../../AGENTS.md) at T12 | Any capture, smoke, or host run intended as evidence for a runtime change. Fails **silently and green, with a fresh DLL timestamp**, so a freshness check does not detect it. Precede every capture with `cargo build --release --workspace` |
| **`emit::flush_layout` uses the wrong layout entry** — `window::set_root` and the `WM_SIZE` arm call `run_layout_as_window_root` (root forced to `Fill` / `Fill`); the reactive drain's layout phase calls the plain `run_layout`, so a root `VStack` holding a `Fill` child lays out correctly on resize and **collapses that child on any property write**. The M3-Phase 4 T6 failure, still live on the drain path. Found incidentally by T3's evidence UI; pre-existing, not introduced by this phase | Recommended: **T5**, which already edits that call site for audit row 2b — as its own commit with its own before/after frames | Any re-layout triggered by a property write rather than a resize, on a tree whose root container is `Shrink` with a `Fill` descendant |
| **Button-family widgets render no label without a layout pass**, and `lib.rs::window_add_widget` deliberately runs none — so that path shows a Button's background and not its label (T3, Codex review finding R-1) | Documented at T3 as a stated limit; **`window_add_widget` itself is a cleanup candidate** — a caller-less public entry left behind when `window_set_root` superseded it at `163067a` | Any new attach path that puts a widget on screen **as content** without a layout pass. The label geometry now lives only in `sync_visuals`, so "attached" and "laid out" stopped being separable for Button-family widgets |
| **Every Composition geometry write in the runtime happens in exactly one pass** (`sync_visuals`) — the property that makes DD-002's conversion-site audit complete rather than approximately complete (T3) | In force from T3 onward | Any task adding a `SetOffset` / `SetSize` / `SetScale` outside `sync_visuals` — a constructor, a property setter, or T6's re-rasterization walk — breaks it silently and reintroduces exactly the class DD-002 §Row 6 detail closed |
| **`ButtonData.label_size` has exactly two writers**, both of which also write `label_text` and the node's `SizeConstraint::Fixed` pair (T3) | In force from T3 onward | A third path that changes a Button-family label — a typed property writer, an iteration-materialised label rebind, M4-Phase 2's event model — must write all three, or the label renders at the previous text's extent |
| **The scale is per window and authoritative on `WindowState`**, seeded once from the monitor the OS chose and held as a `pub(crate)` field (T4) | In force from T4 onward; **consumed additively by M4-Phase 8** | Any second source of a window's scale — a process-global cache, a `GetDpiForWindow` at a point of use, a second seeding site — reintroduces the drift DD-003 rejected as options S1 / S3, and a second window on a differently-scaled monitor is where it surfaces. The `pub(crate)` is load-bearing too: it keeps the factor out of the `pub use`-exported surface, which is DD-004's "no host needs the scale factor" expressed as visibility |
| **`window::realize_dip_window_size` runs before the `GWLP_USERDATA` install, and its flag set is not the `WM_DPICHANGED` path's** (T4) | In force from T4 onward | Any task that moves the correction later, adds a geometry call to `create` after the pointer install, or **reuses this helper for the change path**. The last is the live hazard: the helper converts a *DIP size* and passes `SWP_NOMOVE`, while `WM_DPICHANGED` applies an *OS-supplied physical rectangle* whose whole content is a new position and size — inheriting `SWP_NOMOVE` there pins the window on every monitor crossing while every test stays green |
| **The window's logical size is realised on the *outer* rectangle; the client rectangle does not follow by the same factor** (T4, measured) | Every evidence gate that compares layout across scales, and any future client-size `WindowConfig` attribute (M4-Phase 8 / AC11) | Any check that treats a DIP client size as derivable from the DIP outer size. Measured at 125%: 800 DIP outer is exactly 1000 physical, while the client is 785.6 DIP rather than 784, because the non-client frame scales by its own DPI-indexed system metrics rather than by `s`. Decomposed with `GetSystemMetricsForDpi` on the probe machine (T4 independent review finding R-6): width `2 x (SM_CXSIZEFRAME + SM_CXPADDEDBORDER)` = 2 x (4+4) = 16 at 96 DPI and 2 x (4+5) = 18 at 120 DPI; height adds `SM_CYCAPTION`, giving 2 x (4+4) + 23 = 39 and 2 x (4+5) + 29 = 47. The numbers are this machine's theme metrics, not a universal rule; the invariant is that they are DPI-indexed and independent of `s`. Layout receives the client extent, so "identical wrap positions across scales" is invariance to about 1.6 DIP of width, not bit-exact |

| **A hit-test / hover traversal divides every `visual_rect` readback by the *traversal root's* scale — one divisor, not each node's own** (T5) | In force from T5 onward | The readback is parent-relative and the traversal accumulates it, so the composited position is `Σ(local_dip × scale_i)`; dividing each term by its own scale matches the pointer's space **only if every node's scale is the window's**, while one divisor needs only the traversal root's. **That is a precondition on the public entry, not an invariant the runtime maintains.** `hit_test_click` / `update_hover` take the divisor from the **receiver**, so entering on a *subtree* uses that subtree's cache against a pointer `wnd_proc` divided by the window's; `scale` is private, so a caller cannot supply the right divisor even knowingly, and `togglebutton_runtime_integration.rs` enters that way. Every **production** caller enters on `WindowState::root_widget`, and T6's walk starts at the root, so the shipped path holds. *Re-trigger:* any entry that hit-tests a subtree not rooted at the window's root. M4-Phase 2's option H3 — hit rectangles cached from layout — deletes the row entirely |
| **The two conversions on the hit-test path cancel today** — the pointer is divided at `wnd_proc` and the `visual_rect` readback is divided again, and hit-testing sources its geometry from the visual tree (T5; the honest accounting DD-M4-P1-002 §Which space hit-testing runs in gave at ADR time) | In force from T5 onward | The moment M4-Phase 2 sources hit geometry from layout, or introduces a DIP-denominated hit-area or minimum-touch-target rule, they stop cancelling and the readback conversion becomes load-bearing rather than symmetric. Until then no test can distinguish a correct row 9 from a missing one |
| **`hit_test_click` / `update_hover` take DIP `f32`, and every `WindowState` callback slot that carries a coordinate is DIP** — of the six slots, **four** carry one (`resize_fn` plus the three pointer slots) and **three** changed type from `i32` to `f32` so the declared unit is not truncated away; `resize_fn` was already `f32` and changed unit only (T5) | In force from T5 onward; consumed by M4-Phase 2's event model and by M4-Phase 7's ABI wave | Any host-facing event surface that carries a coordinate. The slots have **zero installers** today, which is why the change was free; the first host or ABI function to install one fixes the unit as shipped API. DD-M4-P1-004's "no host needs the scale factor" is what makes DIP the right side of that door |
| **A test that does OS work before its skip guard must not treat that work as certain to succeed** (T9 finding F-49, measured by the owner's guard-verification run) | Every Windows integration binary that needs OS state established *before* `wasamo_init` | `dpi_awareness_tolerated_failure_integration.rs` sets the process's DPI awareness before the shared helper's Compositor-unavailable skip decision, because it must precede `wasamo_init`. The first version `expect`ed that call to succeed — reasoned, not measured — and on the owner's session it returned `ERROR_ACCESS_DENIED` (the awareness was already set before any test code ran), so the binary **failed on exactly the environment where every other binary skips**. Same on-disk executable as every local run, so the cause is environmental; the mechanism is **not identified** and is not claimed. *Re-trigger:* any new test that must touch the OS ahead of the guard. The shape that works: attempt it, **discard the result**, read back the state actually in force, and put every assertion behind the guard — so the test asserts what is true rather than what it arranged. **The deeper re-trigger is the reasoning pattern, not the API**: this plan had already named the hazard ("this binary does OS work outside the guard") and then predicted it away in the same paragraph. Noticing a hazard and predicting it harmless is worse than not noticing it, because the prediction is what stops the check being run. **A second, separable trap surfaced closing this**: cargo's test-executable filename hash is derived from package / target / profile **metadata, not content**, so it is byte-identical across a source change and **cannot be used to tell which build ran** — a freshness signal that looks authoritative and is not, in the family of F-5 and F-21. What distinguishes builds is behaviour only reachable in one of them |
| **An unaware observer cannot measure an aware window's rectangle** (T9 finding F-48, measured by getting it wrong first) | Every assistant-side or tooling-side measurement of a Wasamo window from T9 onward — **T10 immediately** | A DPI-unaware process asking `GetWindowRect` / `GetClientRect` about an aware window is answered in **virtualized** coordinates: the real rectangle divided by the system scale. Measured: the three-host probe first reported `outer=800x600` for windows that are really `1000x750`, which is internally consistent, plausible, and off by exactly the scale factor — the signature this phase exists to remove. Declaring the probe Per-Monitor-Aware V2 and changing nothing else turned the same three readings into `outer=1000x750  client=982x703`, matching T4's independent measurement. **`GetDpiForWindow` and `GetWindowDpiAwarenessContext` are *not* virtualized**, so a level or DPI readback is trustworthy from an unaware caller and a coordinate readback is not. *Re-trigger:* any tool, script, or capture harness that reads a Wasamo window's geometry, screen coordinates, or cursor position from outside the host process. The tool must declare its own awareness first, and "the numbers looked sensible" is not a check |
| **`wasamo_init` clears the thread-local last-error on *entry*, not on its success arm** — and it is the only entry point in `abi.rs` that does (T9 finding F-46) | In force from T9 onward | The DPI-awareness declaration's diagnostic is written by `runtime::init` *during* the call (DD-M4-P1-001 §Failure handling, [abi_spec §4.1](../../../../docs/abi_spec.md)), so a success-path clear runs after that write and discards it. Counted rather than asserted: `abi.rs` has 24 `clear_last_error()` call sites — 1 here, 21 success-path clears in other ABI entry points, 2 in the `#[cfg(test)]` module. *Re-trigger:* any change that moves this clear back to the `Ok` arm, or that adds a second producer of a diagnostic during `wasamo_init`. Falsified rather than argued — mutation T9-M2 restores the old shape and `a_host_that_already_declared_keeps_its_level_and_is_told_ours_did_not_take` goes red |
| **`ERROR_ACCESS_DENIED` is `0x80070005`, the same string `tests/common/mod.rs` matches to decide "Compositor unavailable"** (T9) | In force from T9 onward; every Windows integration binary | The collision is harmless today only because the helper checks `status == WASAMO_ERR_RUNTIME` **first**, and on that arm `wasamo_init` overwrites the declaration diagnostic with `"wasamo_init: {e}"`. Two conjuncts, in a helper the DPI work does not own. *Re-trigger:* any change that reports a declaration failure through the returned *status* rather than as a diagnostic, or that relaxes the helper's status check to a bare last-error match — either would make every Compositor test skip on a machine whose host declared its own awareness, silently and green |
| **The declaration sits below `runtime::init`'s existing one-shot, and that is now observed rather than argued** (T1 F-10, given a readback at T9) | In force from T9 onward | Moving `SetProcessDpiAwarenessContext` above the `RUNTIME.get().is_some()` early return leaves the effective level correct **and** `wasamo_init` still returning `WASAMO_OK`; the only reachable symptom is that a second `wasamo_init` takes `ERROR_ACCESS_DENIED` against the process's own earlier correct declaration and reports it to a host that did nothing wrong. *Re-trigger:* any reordering of `init`'s prologue, or any new OS work inserted ahead of the declaration. Pinned by the second-init readback in `dpi_awareness_declaration_integration.rs`; mutation T9-M3 shows it fires |
| **A DPI fixture must establish its before-state, never inherit it** (T9 finding F-47) | In force from T9 onward; every future test that drives a scale change | Both DPI evidence binaries encoded "the creation-time scale is 1" in constants derived from 96, which was a fact about an undeclared process. T9's declaration made it a fact about the developer's monitor instead: 5 tests failed across **2** binaries, not the 1 the T8 retrospective handed forward. `dpi_change_propagation_integration` now derives its target as twice the window's committed creation DPI; `dpi_scale_matrix_integration` synthesises one `WM_DPICHANGED` to 96 and asserts both the realised client and the committed scale. *Re-trigger:* any new fixture that names a literal DPI, or that assumes the created window's scale. Measured, not claimed: with the declaration deleted entirely, all four T7 tests and two of three T8 tests still pass |
| **A committed frame set is not a later task's baseline, and one capture is not a baseline** (T5 finding F-33, measured) | Every GUI evidence gate — T6, T10 — and later milestones that read [verification-environments.md](../../../../docs/notes/verification-environments.md) Observation 4 as procedure | Any comparison of rendered frames across builds. At the *identical commit*, two settled captures a day apart differ by 25 of 827,904 pixels and a session's **first launch** differed from its own second and third by 149, at up to 13 per channel. **Classified rather than described**: every differing pixel is a text pixel, no tile fill or background moves, and **not one flips between background and covered**, so the coverage mask is identical and only the intensity of already-covered pixels changes. Antialiased pixels differ; **antialiasing is not established as the cause**. Checking the commit the evidence was captured at — the procedure the ADR set's verification-closure item 3 and [constraints §9](../requirements/constraints.md) state — is necessary and **not sufficient**. Agree **multiple captures on each side** of the change. **The residual has a decision rule, measured rather than described**: every differing pixel was a text pixel and **not one flipped between background and covered**, so the coverage mask is identical and only the intensity of already-covered pixels moves, bounded at **13 per channel**. **The max per-channel delta is asymmetric evidence, and only that.** A **large** delta proves only that the difference is **outside the drift bound this phase measured** — not what caused it, since an intensity-only defect can exceed it too and the drift's own mechanism is unidentified. A **small** delta proves nothing, because (i) a rasterization defect changes intensity without moving geometry — a wrong D2D context DPI is exactly that, i.e. **T6's defining failure would read as drift**; (ii) a sub-pixel positional error need not flip any pixel between covered and uncovered; and (iii) contrast belongs to the edge, not to the change, so a geometry move across two near colours gives a small delta. "Palette-independent" was false. [evidence/compare-frames.ps1](./evidence/compare-frames.ps1) therefore **exits non-zero on any difference by default** and reports the delta as information; `-AllowDrift` opts into treating a small-delta difference as a pass, which is a judgement the runner records rather than a default a gate inherits. Atlas packing was instrumented and **ruled out** as the mechanism; nothing else is claimed, which is why a drift-only result is recorded with its numbers rather than filed as a clean pass. **Concrete instance left by this phase**: T3's committed `evidence/after/` is stale for two frames — the F-23 fix changed `labelupdate-clicked` and `-clicked-twice` by 30,800 px each — so reusing it as "the last known-good set" reports a regression that is not one. The current reference set is named in [evidence/README.md](./evidence/README.md) |
