案 B4 — 思いつきメモ（Quick Capture Inbox。リストごとの複数 window）

第二 app の担当分B4 での証明形
単一行の文字編集 + IME◎。短い item を捕捉して追加・改名することが app の中心。複数行編集を要求しない
multi-window○。1 list = 1 window（Inbox / Ideas / Shopping）。launcher から該当 window を開き、または既存 window 間で focus を移動する。新規 list は自動命名で window を即作成し、launcher 行から改名する
top-layer（構造 + 外側 click 型）○。各 item の「…」menu。ScrollView / for の内部から開くので、最前面層が構造的に要求される
動的 title（window config props）◎。Ideas — 12 items は項目追加・archive で自然に変化する。title の値源（束縛か host 合成か）は該当フェーズ ADR で決める。initial size も list window として自然
閉じ込め × 最前面層（modal dialog）◎。item の「…」→ Rename dialog。ScrollView 内の行を起点にするため、根 ZStack では代用できない
focus / UIA 検証の密度○。list navigation・TextField・Add button・item row・menu・dialog を横断する Tab 順と role。B2 より部品種は少ない
host state boundary の書き戻し方向◎。追加・改名・archive を host store へ write-back。表示中の host 書き込み（供給・差し替え）は A の担当に留める

強み: 一行入力 + IME と write-back が製品の中心にあり、複数行編集を招かない。 item を単なる文字列 collection として扱えるため、B3 の sender / time などの並行配列を避けやすい。 Mica の小さな複数 window が並ぶ絵も、Wasamo の multi-window surface を素直に見せられる。
弱み: 1 list = 1 window は自然だが、B1 の 1 note = 1 window や B3 の 1 conversation = 1 window より製品上の必然性は少し弱い。 focus / UIA の部品多様性も B2 には及ばない。

メモ — ポイントと総合判断

ポイント

  • 「Todo」ではなく capture inbox に留める。完了・優先度・期限を入れると CheckBox / Toggle・構造化 item data・追加の状態遷移を呼び込む。M4 の B4 は未整理の文字列を追加・改名・archive するだけにする。
  • データ形状の上限を守る。各 list の item は文字列 collection に留める。item ごとの status・色・日時・担当者を持たず、TypedValue / 構造化データの保留を破らない。
  • 表示中の host 書き込みを重複させない。供給・差し替えの方向は A が担う。B4 は TextField を起点とする追加・改名・archive の write-back に集中する。この上限が launcher の形を決める: launcher 行は list 名のみを持ち、件数を出さない。件数を出すと、ある list window での追加が別 window（launcher）の表示へ波及し、A が担う「表示中の host 書き込み（差し替え）」を B4 が重ねて要求してしまう。行が「名前 + 件数」の 2 値を持つ点も、項目データを文字列に留める上限に触れる。window の title と status bar の件数は、その window 自身の追加・archive で変わるだけなので上限を破らない。
  • title の値源を予断しない。動的 title は list 名と件数が変わることで自然に必要になるが、その値を束縛で渡すか host 合成で渡すかは該当フェーズ ADR に委ねる。
  • dialog は行の文脈から開く。Rename dialog は ScrollView / for 内の「…」を起点にする。Archive は menu から直接実行し、確認 dialog を出さない（表・wireframe と一致）。「＋ 新しいリスト」も同じ理由で名前入力 dialog を持たない — 根から開く名前入力 dialog は ZStack で足りてしまい、閉じ込め × 最前面層の組合せを実証しない（framing §粒度の定義〔重ね表示〕）。自動命名 + launcher 行からの改名にすることで、launcher 行にも item 行と同じ「…」menu が付き、操作の一貫性も上がる。

総合判断

B4 は B3 に対する有力な低リスク代替案。単一行編集・IME・write-back・動的 title・最前面層・modal dialog を自然に揃えつつ、複数行編集と並行配列の圧力を避ける。B3 と比べて弱まるのは、複数 window の必然性と、動きのある showcase 性である。

B1 / B2 / B3 との横並びの重み付け読み（第一基準・副次基準の比較と、どれを採るかの読み）は target-app-wireframes.html §カバレッジの重み付け読みが持つ。 本ファイルはここでは繰り返さない。

B3 を選ぶ場合のリスク低減メモ: message は messages: [string] のみとし、 時刻・既読・icon・任意 metadata は M4 に持ち込まない。それでも発言者ごとの左右寄せ・背景色を分けるには、 項目ごとの真偽値 collection を別に持つか、剰余を含む算術を式言語に導入する必要がある。後者は M-expr1 の範囲外であり、 M-expr2a の算術に剰余を含めるかも未定である。前者は並行配列を残す。したがってこの制約は圧力を減らしうるが、B3 の並行配列リスクを無償には解消しない。

候補境界のメモ

メール・ノート・カンバンは見栄えが良くても、本文の複数行編集・構造化 record・drag 操作を自然に要求するため M4 の第二 app には重い。設定プロファイル編集器のような開発者向け app は B4 と同程度に一行入力と write-back を満たせるが、最初の見本アプリとしての広い訴求は B3 / B4 に劣る。
