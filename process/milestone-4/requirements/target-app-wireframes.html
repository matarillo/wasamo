0. 前提 — 2 本立てと証明対象

題材アプリは 2 本立て（framing F6）: A（Photo Gallery 成熟）= 採択確定 + 第二 app（B1 / B2 / B3 から選定、未決 = Q2）。 証明対象は M4 で実装する機能リスト — M4 acceptance criteria （_roadmap.md §M4）+ §1.1 で take 合意済みの pool item — で、カバレッジは 2 本の組で満たす。機能リストの精緻化と 優先順位（P1〜P4）・A の役割と担当分担の正本は framing.md §機能リスト / §題材アプリ二本立てと役割分担。 下記は app 候補に依存しない共通項:

  • per-monitor DPI / AccessKit・UIA / Mica・Acrylic + accent — どの候補でも同等に証明可能（app の絵柄に依らない）。
  • sizing spike（Problem B、M4 計画で振り分け記録）— app 非依存。
  • stretch 層（Image widget / literal fill）— 取り込み確定、A が消化（F6）。
  • M3 handoff の M4 residual cluster は A が M4 で消化する（F6）。動的な window タイトルのみ第二 app の担当（理由は framing §題材アプリ二本立てと役割分担）。

読み（2026-07-09 時点。採択は未決 = Q2）

  • B3: 担当分に穴がない唯一の案。全行 ○ 以上、◎ 4。文字入力 + IME は 「日本語で会話を打つことが app の本体」で単一行が自然。書き戻し + host 起点 write の 両方向が製品動作で、A の担当（供給・差し替え）と正確に補完。改名 / 名前入力 dialog は 閉じ込め × 最前面層 × 文字入力 × IME の四重の組合せを 1 か所で証明し、 multi-window と合わせて「モーダルの及ぶ範囲はウィンドウ単位」の論点も作為なしに発火する。 残る注意は並行配列の圧力のみ（framing の TypedValue 宿題を前倒し点検）。
  • B2: 密度最強・穴 2 つ。focus / UIA / top-layer の検証密度と 「PC 名を変更」dialog の本家先例は最強。ただし multi-window と動的タイトルに自然な 出番がなく、証明の別建てが 2 件必要 — 作為の除去という 2 本立ての狙いと逆行する。 focus 密度の優位は、app 非依存の義務として確定済みのフォーカス意味論の機構検証 fixture が部分的に下支えする。
  • B1: multi-window 最強・複数行コストとセット。2 本立てで負担は 軽くなるが、本筋が複数行編集である構造は変わらず、P4 行の事実上中核化 （コスト増）を引き受ける判断が前提のまま。
  • modal dialog の設計条件（全候補共通）: dialog は項目ごとの文脈 （for / ScrollView 内）から開く形に設計し、最前面層が構造的に要求されるようにする。 根宣言の dialog では ZStack で足りてしまい、組合せを実証しない （framing §粒度の定義〔重ね表示〕）。
