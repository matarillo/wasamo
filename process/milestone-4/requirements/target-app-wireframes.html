本ファイルは M4 target app の候補比較のための探索アーティファクトである （M3 の target-app-wireframes.html と同役割）。 採択の SSOT は本ファイルではなく、採択後に書く requirements/spec.md（M4 target app pre-doc）。 判断基準（優先機能リストのカバレッジ第一・副次基準）の正本は framing.md §機能リスト / §target app の選定であり、 本ファイルは重み付け前の素読みまでを記録する。 オーナー確認の反映と採択判断は未実施（末尾の placeholder 節参照）。

0. 前提 — 候補が証明すべきもの

証明対象は M4 で実装する機能リスト — M4 acceptance criteria （_roadmap.md §M4）+ §1.1 で take 合意済みの pool item。機能リストの精緻化と優先順位（P1〜P4）の正本は framing.md §機能リスト。 下記は app 候補に依存しない共通項:

  • per-monitor DPI / AccessKit・UIA / Mica・Acrylic + accent — どの候補でも同等に証明可能（app の絵柄に依らない）。
  • sizing spike（Problem B、M4 計画で振り分け記録）— app 非依存。
  • stretch 層（Image widget / literal fill）は A 前提の take。B 系採択時は pool へ戻す（1 行 disposition）。
  • B 系はいずれも M3 handoff の M4 residual cluster（実画像・thumbnail hit-testing・wheel/drag scroll・lightbox modal focus・dynamic title・DPI のうち AC 化されていないもの）を M4 で消化しない。採択時は M5 への carry を framing で明示する。

副次基準（第一基準が拮抗した場合の判断材料）

副次基準 A: GalleryB1: 付箋B2: 設定B3: チャット
1. 実装・spec 工数（相対）小（資産継続）中〜大中中
2. 構造リスク低高（複数行）低中（並行配列）
3. identity / outreach 訴求○◎◎○
4. M3 residual 消化◎△△△

補足

  • TextField / IME 行: M4 thesis の中心は text input と focus。 A は検索欄どまりで thesis 検証としては薄い。B3 は日本語会話そのものが app の本体。
  • multi-window 行: B1 のみ「window の生成・破棄が製品操作」。 A/B3 は「開ける」レベル、B2 は作為なしには出番がない。B2 採択時は multi-window AC の discharge 方法（最小 fixture の別建て等）を framing で決める必要がある。
  • 副次基準 2（構造リスク）: B1 の複数行編集は TextField AC の 「minimum」解釈を最初に確定しないと工数が読めない。B3 の並行配列は typed-value-evaluator.md の 再評価トリガ（List item context binding）に接近する。A/B2 は既知 surface の範囲。
  • 副次基準 4（residual 消化）: A のみ M3 handoff の M4 residual cluster を そのまま消化。B 系採択時は M5 への carry を framing で明示 disposition（silent drop 禁止）。
  • 副次基準 1（工数）: A は gallery.ui + 3 ホストの継続で最小。 B 系は `.ui`・host・wireframe を新規に書く。B1 はさらに複数行 TextField を含むと最大。
重み付け前の読み: 単独首位はない。B3 = P1 の text 系 + P3 host state で最強・ リスク中、B2 = focus / overlay / UIA の検証密度で最強だが multi-window に穴、B1 = multi-window と identity で最強だが複数行リスク高、A = 工数・残務消化で最強だが text 系が薄い。 P1 のうちどの機能を重く見るか（text 系か multi-window か focus 密度か）と副次基準の 効かせ方で採択が変わる構図であり、framing 問い 1（機能リストの精緻化・優先順位の確認）が 決定打になる。
