# M4 開始時の方針固め（start framing）— Interaction stack

M4 開始時のマイルストーンレベルの方針固め（workflow §1.3 の framing）。
M3 の前例（[M3 framing.md](../../milestone-3/requirements/framing.md)）と
同じく、題材アプリの採択・ROADMAP 達成条件の見直し・計画の起草に先立って、
主眼の読み・取り込み方針・判断基準を固定する。

判断の順序は次のとおり（F4）:

1. **M4 で実装する機能リストを精緻化し、優先順位を付ける**（§機能
   リスト）。
2. **その優先機能をどれだけ自然にカバーできるかで題材アプリを決める**
   （§題材アプリの選定。比較記録は
   [target-app-wireframes.html](target-app-wireframes.html)）。
   題材アプリは 2 本立て（F6・F8）: 写真ギャラリー成熟（題材候補 A）+
   思いつきメモ（題材候補 B4）。いずれも採択確定。カバレッジは
   1 本で背負わず 2 本の組で満たす。

アプリが先にあって機能が従うのではない。機能リストが先にあり、アプリは
その証明手段として選ばれる。

**本文書の読み方**: 前半（§主眼の読み〜§機能リスト〜§題材アプリの選定）
は合意済みの前提と確定内容の本文、後半は管理事項。**オーナーに決定を
求める事項は §オーナーへの問い に集約**しており（Q1・Q2 とも確定済み。
本方針固めに未決の問いは残っていない）、本文中の「Q1」「Q2」の記号は
その節を指す。オーナーが今決める必要のないものは §採択後・各フェーズへ
送る決定事項に、着地先を固定して送る。

## M4 主眼（thesis）の読み

[_roadmap.md](../../_roadmap.md) §M4 の主眼（thesis）:

> input, multi-window, text input, and accessibility share a focus
> model; they ship together so the focus model is settled once.

これを次のように読む:

- **M4 の中心成果物はフォーカスモデルの一回確定**である。入力処理・
  入力欄 TextField・IME・AccessKit・複数ウィンドウは個別の機能ではなく、
  同一のフォーカスモデルを共有する利用者として一括で設計・出荷する。
- したがって M4 への取り込み判断の基準は、日程の都合ではなく
  「**フォーカスモデル確定の質を脅かすか**」に置く（F1）。
- Mica / Acrylic + アクセント色 + モニターごとの DPI 対応は「Wasamo
  らしさが目に見える形になる」ための土台であり、最初の見本アプリ
  （協力者への呼びかけ用）が見える証明を担う。

## 方針決定の記録（F1〜F8）

本方針固めの前提となる決定の台帳。**F1〜F8 すべて確定済み**
（最後まで残っていた F5 = 題材アプリの採択は F8 で確定）。

- **F1 — M4 はフォーカスモデルのマイルストーンと読む**（2026-07-07
  合意）。中心成果物はフォーカスモデルの一回確定。追加範囲の取り込み
  判断の基準は「フォーカスモデル確定の質を脅かすか」。詳細は
  §主眼の読み。
- **F2 — 取り込みは二層（中核 / 予備）で行う**（2026-07-07 合意）。
  中核 = フォーカスモデルと結合する項目の AC 昇格。予備 = 切り離し
  可能な葉である題材アプリ機能（AC 非昇格）。予備の再評価点 =
  フォーカスモデル中核 ADR の Accepted 時点。詳細は §二層取り込み方針。
- **F3 — 「なるべく M4 で実施」を方針の出発点とする**（2026-07-07
  合意）。候補プールの M4 関連項目は最大限題材アプリに取り込む方向で
  方針を固める。逃げ道は F2 の二層構造が提供する。詳細は
  §二層取り込み方針。
- **F4 — 機能リストが先、題材アプリはそのカバレッジで選ぶ**
  （2026-07-08 指示）。冒頭の「判断の順序」がその実行。判断基準の正本は
  §題材アプリの選定。
- **F5 — 題材アプリの採択。確定**（→ §オーナーへの問い Q2）。
  A（写真ギャラリー成熟）の採択は F6 で、第二アプリ B4（思いつきメモ）
  の採択は F8 で確定。採択の明文化は `requirements/spec.md`
  （§1.2 の成果物）。
- **F6 — 題材アプリは 2 本立て。A 採択 + A の役割定義**（2026-07-09
  合意）。A（写真ギャラリー成熟）+ 第二アプリの 2 本の組でカバレッジを
  満たす。A の役割 = 自然な範囲の取り込みに限定し、**M3 で先送りした
  事項の消化を優先**する。文字編集 / IME・複数ウィンドウ・最前面の
  重ね表示・ウィンドウ設定プロパティは A に入れない（検索欄・別
  ウィンドウビューア・コンテキストメニューを持たない）。詳細は
  §題材アプリ二本立てと役割分担。
- **F7 — 第二アプリの候補に B4（思いつきメモ）を追加**（2026-07-27
  指示）。第二アプリの選択肢は B1 / B2 / B3 の 3 案から **B1 / B2 / B3 /
  B4 の 4 案**になる。追加の理由は、B3（チャット）の唯一の注意点
  （並行配列の圧力）を負わずに同じ担当分をカバーする案が成立するため —
  第一基準では B3 と同格（穴なし）で、副次基準の「構造リスク」だけが
  異なる。Q2 の判断材料が増えるだけで、判断基準（F4）・A の役割（F6）・
  機能リストの粒度（Q1）は変わらない。候補節は
  [target-app-wireframes.additional.html](target-app-wireframes.additional.html)、
  横並びの重み付け読みは
  [target-app-wireframes.html](target-app-wireframes.html)。
- **F8 — 第二アプリは B4（思いつきメモ）を採択**（2026-07-27 決定。
  F5 の残余が確定し、題材アプリは A + B4 の 2 本で確定）。**決め手は
  副次基準の「構造リスクの低さ」**。第一基準（担当分のカバレッジ）では
  B3（チャット）と B4 が同格 — どちらも担当分に穴がない — ため、選定は
  副次基準に委ねられ、そこで B4 の「項目を文字列の並びに留められる」
  構造を、B3 の訴求の動きより重く取った。B3 の並行配列の圧力
  （`TypedValue` / 構造化された項目データの保留に接近する）を M4 に
  持ち込まない判断である。落選 3 案の読みは
  [target-app-wireframes.html](target-app-wireframes.html) に歴史的記録
  として残す。採択に伴う制約は §第二アプリの採択に依存して変わるもの。

## 二層取り込み方針（オーナー合意済み）

オーナー意向「候補プールの M4 関連項目はなるべく M4 で実施したい」を
方針固めの出発点として明文化する（F3）。ただし無条件の最大取り込みは、
(a) 撤回時の手続きコストの非対称（AC 化した項目の削除は DD-V-026
tier 2 の縮小手続き）、(b) 題材アプリの機能詰め込み化による主眼検証の
希薄化、を招くため、取り込みを二層に分ける（F2）:

- **M4 中核（core、AC 昇格）** — フォーカスモデルと設計が結合する項目。
  ROADMAP の M4 AC に昇格し、落とす場合は DD-V-026 tier 2 の縮小手続き
  （再開条件つき先送りの表つき）を踏む。
- **M4 予備（stretch、題材アプリの機能、AC 非昇格）** — 主眼と独立に
  切り離せる葉。`requirements/spec.md` のアプリ仕様には入れるが ROADMAP
  の AC にはしない。落とす場合は候補プールへ戻す 1 行の処遇記録で済む
  （安価で監査可能な逃げ道）。
- **再評価点（checkpoint）** — フォーカスモデルの中核 ADR が Accepted に
  なった時点で予備の残量を再評価する（「どうしても収まらない」の判定を
  感覚ではなく事前に決めた時点で行う）。

## M4 実装機能リストの精緻化と優先順位付け

題材アプリの選定に先立ち、M4 で実装する機能を列挙し優先順位を付ける。
出自は 3 系統: AC（[_roadmap.md](../../_roadmap.md) §M4）、§1.1 の
候補プール処遇合意、そして **§1.1 の発火ノートが課す議題・義務
（着地表）**。着地表の各行は、本リストの行・§粒度の定義・管理節・
§採択後・各フェーズへ送る決定事項のいずれかに必ず割り付ける（黙った
取りこぼしの防止）。行として独立させるのは、実装対象の surface で
あって、選定の重みまたは AC 審査の点検単位として独立に読めるものに
限る — それ以外の議題・義務は既存行の粒度定義や管理節に吸収する。
M3 引き継ぎの残務群は行にせず、A（F6）が消化する（§題材アプリ二本立てと
役割分担）。ここでの優先順位は**題材アプリ選定の重み**である
（実装順序・フェーズ割り当ては §1.4 plan.md で別途決める）。A は採択
確定（F6）のため、この重みは**第二アプリの選定**に適用する — A が担当
する行は選定上の重みを持たない（担当の割り付けは §題材アプリ二本立てと
役割分担）。

| 優先 | 機能 | 出自 | 選定上の扱い |
|---|---|---|---|
| **P1** | フォーカスモデル + イベント配送（event routing） | AC / 検討ケース 6 | 差別化要因（証明の密度がアプリで変わる）。粒度の定義は §粒度の定義（フォーカスモデル） |
| **P1** | 入力処理（キーボード / マウス / タッチ） | AC | ほぼ非差別化（どのアプリにも同等にある） |

  利用者 + 入力そのもの）。題材アプリはこれらを**本筋として**証明できる
  ほど良い。

  入れない。
- **P3** = 中核の取り込み（AC 昇格予定）。P1 に準じて重いが、主眼の
  名指しではない分 P1 の下に置く。
- **P4** = 予備（候補プール由来）、または AC 解釈の上積み（複数行の
  文字編集）。カバーできるアプリなら加点、できなくても減点は小さい。
  撤回は、予備なら候補プールへ戻す 1 行の処遇記録、上積みなら M5 への
  申し送りのみ（候補プールの項目ですらないため）。ただし複数行の行には
  付箋アプリ（題材候補 B1）連動の注意がある（→ §粒度の定義〔文字編集〕）。

### 粒度の定義（Q1・F6 で確定済み）

機能リストの行のうち、粒度が自明でない箇所の確定内容（Q1・F6、
2026-07-09 オーナー確定）。

#### フォーカスモデル + イベント配送（P1 行）

配送モデルそのものの選択（capture / target / bubble の三相か、対象のみ +
高水準シグナルか — 検討ケース 6）は、採択後最初期のフェーズ ADR に送る
（→ §採択後・各フェーズへ送る決定事項）。ただし本方針固めの時点で、
その ADR が扱うべき設計ケースと実証の形を固定する:

- フォーカスモデルの設計ケースには、M5 の公式部品一式
  （[_roadmap.md](../../_roadmap.md) §M5）が消費者として要求する意味論を、
  部品を作らずに含める: (a) グループ内の矢印キー移動と「Tab はグループ
  全体を 1 停止と扱う」グループ化（ラジオボタン相当）、(b) フォーカスは
  本体に留めたまま開いた一覧内の活性項目だけを動かす、フォーカスと
  活性項目の分離（ドロップダウン相当）。これを M4 で固めておかないと、
  主眼「フォーカスモデルの一回確定」が M5 の部品実装で破れる。
- (a)(b) は紙の設計ケースに留めず、**フォーカスモデル中核 ADR の
  Accepted 前に動くもので実証する**: 走査の中核（木 + スコープ注釈 →
  次のフォーカス先）を Win32 非依存の純ロジックとして切り出して単体
  テストで固定し、イベント経路は既存材料（Button・selected 状態・
  最前面の層）を組んだ機構検証用の最小 fixture で通す。fixture は
  公式部品として公開しない（spec.md・部品一覧に載せず、綴りは fixture
  限定の非規範。部品一式の正規の買い手は M5）。仮の RadioButton /
  ComboBox を部品として作ることはしない — グループの `.ui` 綴りは M5 の
  設計判断であり、M4 で既成事実化しない。
- 既存の `Button.clicked` シグナルと Button 以外への汎用クリック処理の
  関係（検討ケース 3。ヒットテスト適格性 — 視覚を持つ部品は全て対象か、
  明示の属性が要るか — を含む）を、同じフェーズ ADR の必須論点とする
  （[検討ノートの義務 4](../../../docs/notes/m4-interaction-intake.md)
  の着地先）。

#### 文字編集 — 単一行（P1 行）と複数行（P4 行）

文字編集は「単一行か複数行か」という事前の二者択一を置かず、単一行
（P1）と複数行（P4）の 2 行として扱う。分割線は、コストの崖（単一行 →
複数行で部品の論理・検証面が跳ねる）とアプリ差別化の線（複数行を本筋で
要するのは付箋アプリ〔題材候補 B1〕だけ）が一致する場所にある。
複数行の優先度は再点検のうえ **P4 で確定**: AC・主眼・フォーカスモデルの
いずれも複数行を要求せず（複数行は部品内部の座標仕事で、フォーカス
モデルからは単一の停止点）、格上げは「機能リストが先」（F4）の重み付けを
特定候補寄りに歪める。

なお部品の形（単一の TextField に複数行属性を持たせるか、TextInput /
TextArea の 2 部品にするか）は文法・API の設計判断であり、行の分割は
これを予断しない（後続フェーズの ADR で決める）。

**P1 行（単一行の文字編集）の粒度** — 技術的な根拠: IME/TSF 検証
（`ITextStoreACP` 相当のテキスト保持部の実装）が要求するのは、テキストの
中身の保持・**範囲選択の内部モデル**（IME が変換中に選択範囲の取得・
設定と範囲置換を行う）・カーソルと変換中文字列の画面上の矩形（変換候補
ウィンドウの配置、GetTextExt 相当）であり、**複数行は TSF 検証に
不要**。逆に範囲選択は、利用者向けの操作を削っても内部モデルとしては
必須になる。よって AC の「minimum editable text widget; required by IME
verification」はこの行だけで満たせる。掘り下げ（自前エディタの成熟段階
D0〜D4・責務分解・実装の重さの内訳）は補足資料
[single-line-text-editing.md](single-line-text-editing.md) を参照。構成:

1. **カーソル（caret）** — クリック位置への配置（位置判定）・← → /
   Home / End・描画・はみ出し時の追従スクロール。
2. **範囲選択（selection）** — 内部モデル（TSF 必須）+ 利用者向けの操作
   （マウスでなぞる・Shift+← →・反転表示）。
3. **クリップボード** — Ctrl+C / X / V（`CF_UNICODETEXT`。貼り付け
   文字列に含まれる改行の扱いは後続フェーズの ADR で決める）。
4. **IME/TSF** — 変換中文字列のその場表示（下線）・変換候補ウィンドウの
   配置・範囲置換。
5. **双方向束縛 / 書き戻し** — ホスト状態境界の取り込み・
   [expression-language-roadmap.md](../../../docs/notes/expression-language-roadmap.md)
   の M-expr5 双方向束縛の発火と一体。
6. **UIA** — AccessKit 経由の Text / Value 相当の最小の役割付け。

どの行にも載せない（M4）: 元に戻す（undo）、パスワード用の伏せ字、
装飾つきテキスト。単語単位の移動・ダブルクリック選択などの安価な
便利機能は後続フェーズの ADR の裁量（AC にしない）。Enter を送信の
合図にするか・未入力時の薄字表示（placeholder）はフェーズ ADR /
アプリ仕様へ委譲。

**P4 行（複数行の文字編集）の粒度**: 折返し・上下のカーソル移動・
Enter での改行・縦スクロールとカーソル追従・複数矩形の範囲選択。
AC 非該当（AC の "minimum" は P1 行で満たす）。載せない / 落とす場合の
手続きコストはゼロに近い（候補プールの項目でもないため、記録は M5 への
申し送りのみ）。工数が跳ねるのは描画より部品の論理側（DirectWrite が
折返しと位置判定を持つため）。

**二層構造との整合の注意**: P4 の建て付けは「安く落とせる」ことが前提
だが、**付箋アプリ（題材候補 B1）は複数行が本筋**のため、B1 採択時に
この行は事実上中核化し、落とすとアプリごと崩れる。B1 を選ぶ判断は
「複数行のコストを中核並みに引き受ける」判断とセットであることを、
カバレッジの重み付け読み（Q2）で明示する。

#### 最前面の重ね表示（P3 行）

確定粒度: **最前面の層という構造（宣言位置からウィンドウ水準の最前面層
へ実体を移す、Portal 相当）を作り、その上で閉じ方・フォーカスの規則一式
— 外側クリックで閉じる / Esc / フォーカスの閉じ込め / 閉じた時の
フォーカスの戻し / 読み上げ順序 — を証明する。部品への吸着は含めない。**
配置は粗い手動でよく（具体の仕組みはフェーズ ADR）、アプリ側のメニュー /
選択肢一覧 / 絵文字選択などはこの粗い配置で証明する（見本アプリの AC は
仕上げ細部の粗さを許容する — "rough around polish-level details"）。

理由の核: 中核として取り込む根拠「フォーカスモデルと設計が結合する」に
該当するのは上記の規則一式であり、吸着位置の解決（部品の名前参照・座標
変換・重なり回避）はフォーカスモデルと独立の座標計算であるため、結合
部分だけを本物の最前面層の上で固める。これにより
[dsl-grammar.md](../../../docs/notes/dsl-grammar.md) Q1（部品の名前参照）
を M4 で開かずに済む。設計空間の正本は
[top-layer-overlays.md](../../../docs/notes/top-layer-overlays.md)。

**実証の分担（F6）**: A のライトボックスは **ZStack のまま**とし、フォーカスの
閉じ込め（モーダル規則）はそこで実証する。ライトボックスは根に宣言され
脱出すべき clip / 重なり順の境界を持たないため、最前面層への載せ替えは
「何も脱出しない Portal」という退化した使い方であり作為になる。加えて
根の重ね表示 = ZStack + if という規範スペックの生きた実例を温存できる。
分担は次のとおり:

- **閉じ込め（モーダル規則）× ZStack** — A のライトボックス（M3 の
  拡張、検討ノートの義務 3 の解決）。
- **最前面層の構造 + 外側クリックで閉じる / Esc / フォーカスの戻し /
  読み上げ順序** — 第二アプリのメニュー / 選択肢一覧 / 小窓。
- **閉じ込め × 最前面層の組合せ** — 独立行（機能リスト P3、層は予備）。
  第二アプリの**モーダルダイアログ**（項目の削除確認・改名・名前入力
  など）が担う。ダイアログは**項目ごとの文脈（for / ScrollView 内）から
  開く**形に設計し、最前面層が構造的に要求されるようにする — 根宣言の
  ダイアログでは ZStack で足りてしまい、組合せを実証しない。ダイアログは
  既存部品（Box / Text / Button / 入力欄）の作者合成であり、`Dialog`
  という公式部品は作らない（正規の買い手は M5 の部品一式）。予備層の
  ため、自然な出番が成立しなければ撤回は M5 への申し送り 1 行で済む。

この分担が課す設計条件（フォーカスモデル中核 ADR の必須論点に追加）:

1. **フォーカスの閉じ込めは構造非依存の概念として設計する** — 「最前面
   層に載ったものが閉じ込める」という層の性質ではなく、任意の部分木に
   付けられる「モーダルなフォーカス範囲」として定義し、ZStack の枝
   （ライトボックス）と最前面層の中身（ダイアログ）の両方を同じ概念の
   消費者にする。主眼「フォーカスモデルの一回確定」を 2 つの構造で
   実証する形になる。
2. **ZStack 兄弟間の遮蔽規則** — scrim（全面の Box）が下の兄弟への
   クリックを遮る、重なり順を考慮した当たり判定。汎用クリック処理
   （P1 行）の設計点として同じ ADR で扱う。
3. **読み上げ（UIA）のモーダル性もフォーカス範囲基準** — 背後の内容を
   読み上げから隠す規則は層ではなくフォーカス範囲に付く。

**吸着小窓（anchored popover）は M4 に含めない**（→ §M4 に入れない
もの）。[候補プール](../../candidate-pool.md)に記録済み（2026-07-09）。
正規の買い手は M5 の公式部品一式（Menu / ComboBox）。

検討ケースへの帰結: ケース 2（外側クリックで閉じる）・4（フォーカス
閉じ込め）・5（Esc で閉じる）は本粒度により M4 範囲が実質確定
（正式分類の記入は採択後の改訂で一括、§検討ノートのケース分類と宿題）。

#### M3 先送り事項の吸収（F6）

M3 で先送りした DSL 面のうち A が消化するものは、新しい行を立てず
既存行の粒度に吸収する（行の割り付け原則どおり）。出自は
[M3 handoff](../../milestone-3/handoff.md) と M3-Phase 7 ADR の
将来面リスト:

- **項目ごとのハンドラ**（ハンドラ位置での item / index 参照。M3 で
  reject、「M4 の項目ごとの対話で着地」と先読み済み）→ 汎用クリック
  処理（P1 行）。A のサムネイルクリックが最初の具体ケース。
- **ループ外からの collection 読み取り**（件数・空判定・添字読み）→
  述語式（P3 行）。A の動的な件数表示（ステータスバー）と
  ライトボックスのキャプション（選択中写真の名前 = 添字読み）が消化。
- **項目ごとの条件表示**（if 条件でのループ変数参照。M3 で reject、
  再開条件「項目ごとの表示 / 状態分岐を要する最初の具体 UI ケース」が
  A で発火）→ 述語式（P3 行）。
- **選択状態の先送り軸**（M3 handoff の 5 軸）のうち**等値選択の軸
  のみ**を A で消化する（述語式が `==` を持ち込むことで再開条件が
  発火。選択中サムネイルの排他選択）。グループ部品・部品保有状態・
  汎用 Toggle の軸は M5 の部品一式へ、双方向束縛の軸は文字編集
  （構成 5）= 第二アプリ側へ、それぞれ従来どおり。

なお動的な件数表示は、静的 Text と束縛 Text の並置（`photos:` +
束縛された数値）で書けるため文字列連結を要しない — 文字列合成を式
言語に持ち込まない（M4 の式は述語まで、という Q1 の線を破らない）。

## 題材アプリ二本立てと役割分担（F6）

題材アプリは 2 本立て: **A（写真ギャラリー成熟）** +
**B4（思いつきメモ）**。いずれも採択確定（A = F6、B4 = F8）。1 本のアプリに
全機能を背負わせると、どの案でもどこかに作為が入る（ギャラリーに
検索欄を足して文字入力を証明する、設定画面に作為的な別ウィンドウを
足す、など）。2 本の組はこの作為を除去し、各機能を本筋として証明できる
アプリに割り付ける。

### A（写真ギャラリー成熟）の取り込み範囲

見た目の正本は M3 の
[gallery-wireframe.html](../../milestone-3/requirements/gallery-wireframe.html)
を継続する（検索欄・別ウィンドウビューア・コンテキストメニューを
**持たない**）。取り込みは自然な範囲 + M3 先送り事項の優先消化:

- フォーカスモデル + イベント配送の基本形（Tab でのフォーカス移動）、
  入力処理、汎用クリック処理（サムネイルクリック → ライトボックス。
  項目ごとのハンドラを含む）。
- ホイール / ドラッグでのスクロールと実スクロールバー（M4 残務群）。
- ライトボックス: **ZStack のまま**モーダルの閉じ込め・Esc・← → を
  実証（§粒度の定義〔重ね表示〕の実証分担）。キャプションに選択中
  写真の名前（添字読み）。
- ホスト状態境界のうち**供給・差し替えの方向**（写真 collection の
  ホスト供給・ホストによる差し替え）。書き戻しの方向は文字編集と
  一体のため第二アプリ側。
- 述語式 + M3 先送りの DSL 面 + 等値選択の軸
  （§粒度の定義〔M3 先送り事項の吸収〕）。
- `Image` 部品・`fill` の直値指定・実画像（予備 2 件の取り込み確定）。
- 動的な件数表示（ステータスバー）。

**A が担わないもの（理由の記録）**: 文字編集 / IME・複数ウィンドウ・
最前面の重ね表示・ウィンドウ設定プロパティ。動的なタイトルも担わない —
ギャラリーの単一ウィンドウにタイトルの自然な動的化の出番がないため。
(a) 同一ウィンドウ内のモーダル表示（ライトボックス）でタイトル（タスク
バー / Alt+Tab / 読み上げにおけるウィンドウの同一性）を切り替えるのは
UX 慣習に反し、それが買う DSL 面（添字読み）はライトボックスの
キャプションで同等に取れる。(b) 「Gallery — N photos」型のタイトルは
文字列連結（式言語の範囲外）かホスト合成の往復を要する。件数の動的表示は
ステータスバーが担う。

### 第二アプリ = B4（思いつきメモ）が担うもの

Q2 の選定基準であったこの担当分を、採択確定（F8）により B4 が担う。
各項目を B4 のどこが証明するかは
[候補節](target-app-wireframes.additional.html)の表が正本:

- 単一行の文字編集 + IME（主眼の中心を本筋として証明する）— 一行の
  入力欄への項目入力と改名が B4 の中心操作。
- 複数ウィンドウ — 1 リスト = 1 ウィンドウ。
- 最前面の重ね表示（構造 + 外側クリックで閉じる型の規則）— 項目行の
  「…」メニュー。一覧の内部から開くため最前面層が構造的に要る。
- ウィンドウ設定プロパティ（**動的タイトルを含む**。タイトル文字列の
  値の出どころ — 束縛かホスト合成か — は該当フェーズの ADR）— リスト名
  と件数がタイトルに出る。
- 閉じ込め × 最前面層の組合せ（モーダルダイアログ、予備層）— 項目行の
  「…」→ 改名ダイアログ。文字入力を内蔵するため、閉じ込め × 最前面層 ×
  文字入力 × IME を 1 か所で実証する。
- フォーカス / UIA 検証の密度（異種部品の Tab 順）— 一覧・入力欄・追加
  ボタン・項目行・メニュー・ダイアログを横断する。
- ホスト状態境界の書き戻しの方向（双方向束縛と一体）— 追加・改名・
  保管をホスト側へ書き戻す。**供給・差し替えの方向は A の担当に留める**
  （→ §第二アプリの採択に依存して変わるもの の上限）。

## 題材アプリ（target app）の選定 — 判断基準と候補

### 判断基準（正本はこの節）

- **第一基準 — 優先機能のカバレッジ**: P1 → P3 → P4 の順の重みで、
  各機能を「アプリの本筋として証明できる（◎）/ 自然に組み込める（○）/
  周辺的・作為が要る（△）/ 出番がない（×）」で読む。A の採択確定
  （F6）後は、読みの対象は**第二アプリの担当分**
  （§題材アプリ二本立てと役割分担）に絞られる。
- **副次基準**（第一基準が拮抗した場合の判断材料）:
  1. 実装・仕様書きの工数（M3 資産の再利用性）
  2. 構造リスク（複数行の文字編集の圧力・`TypedValue` / 並行配列の圧力）
  3. Wasamo らしさ / 協力者への呼びかけの訴求力
  4. M3 残務群の消化
- カバレッジの行列と読みの記録は
  [target-app-wireframes.html](target-app-wireframes.html) に置く
  （比較記録。判断基準の正本は本節）。B4 の候補節（ワイヤーフレーム・
  担当分ごとの証明形・設計メモ）だけは
  [target-app-wireframes.additional.html](target-app-wireframes.additional.html)
  にあり、横並びの読みは前者に集約する。

### 候補（5 案）と採択結果

| 案 | 概要 | 結果 |
|---|---|---|
| **A** | 写真ギャラリーの成熟（M3 継続） | **採択（F6）**。役割 = 自然な範囲 + M3 先送り事項の消化（§題材アプリ二本立てと役割分担） |
| **B4** | 思いつきメモ（リストごとの複数ウィンドウ、完了状態なし） | **採択（F8）**。担当分に穴がなく、構造リスクが最も低い（項目は文字列の並びのみ） |
| **B1** | 付箋（Sticky Notes） | 非採択。複数ウィンドウ / らしさで最強だが、複数行の文字編集（P4 行）を事実上中核として要求 |
| **B2** | 設定画面の再現 | 非採択。フォーカス / 重ね表示 / UIA の密度で最強だが、複数ウィンドウ・動的タイトルに穴 |
| **B3** | チャット（ローカルのおうむ返しボット） | 非採択。第一基準では B4 と同格だったが、並行配列の圧力を M4 に持ち込まない判断で B4 を採った（F8） |

### 第二アプリの採択に依存して変わるもの

**B4 採択（F8）の帰結**: 他 3 案が課したはずの追加の帰結は生じない。
複数行の文字編集（P4 行）は「載れば取る」の建て付けのまま（付箋案
〔B1〕のような中核化が起きない）、並行配列の圧力も生じないため
`TypedValue` の宿題は前倒ししない（→ §検討ノートのケース分類と宿題）。
`fill` の直値指定は A のみの出番に留まる。

代わりに、**B4 の低い構造リスクを買った判断（F8）を維持するための上限**
を、アプリ仕様（`requirements/spec.md`）に明記して採る。この 2 つは
「守れば安い」ではなく「破ると採択理由そのものが失われる」制約である:

1. **項目は文字列の並びに留める** — 項目ごとの状態・色・日時・担当者を
   持たない。破ると `TypedValue` / 構造化された項目データの保留
   （§M4 に入れないもの）に触れ、B3 に対する優位が消える。
2. **一覧ウィンドウの行に件数を出さない** — 行はリスト名のみ。件数を
   出すと、あるリストウィンドウでの追加が別ウィンドウ（一覧）の表示へ
   波及し、A が担う「表示中のホスト書き込み（差し替え）」を B4 が重ねて
   要求してしまう（→ [候補節](target-app-wireframes.additional.html)の
   ポイント 3）。ウィンドウのタイトルとステータスバーの件数は、その
   ウィンドウ自身の操作で変わるだけなので上限を破らない。

あわせて、**新規リストの作成は自動命名 + 一覧行からの改名**とし、根から
開く名前入力ダイアログを持ち込まない（根宣言のダイアログは ZStack で
足りてしまい、閉じ込め × 最前面層の組合せを実証しない —
§粒度の定義〔重ね表示〕）。

## 初期フェーズ分割の仮説

採択（F8）を織り込んだ依存方向の見立て。フェーズ数・境界・順序を決める
のは §1.4 plan.md であり、本節は入力に留まる:
イベント配送 / フォーカスモデルが最初期、単一行の文字編集 +
IME とホスト状態境界がその上、複数ウィンドウと最前面の重ね表示が
フォーカスモデル確定後、見本アプリの統合と AccessKit / Mica / DPI の

一行の入力欄と最前面層を足す形のため、A の初期フェーズが固めた土台を
そのまま踏める。
フォーカス閉じ込め・モーダル・アクセシビリティを同一フェーズで扱うか
分割するか（検討ノートの義務 5）は、§1.4 のフェーズ分割で確定する。
本節は依存方向の見立てに留め、フェーズ数・境界・順序は §1.4 が決める。

## 採択後・各フェーズへ送る決定事項

2. **タッチの検証環境** — タッチの AC をどの環境・どの証拠の形で消化

3. **サイズ試掘の置き場** — どのフェーズに置くか（既定は M4 実施。

   で確定する。
4. **動的タイトルの値の出どころ** — 束縛かホスト合成か。B4 のタイトルは

だった。B4 はどちらも本筋として持つため、証明の別建ては不要になった。
