# 単一行の文字編集 — 機能掘り下げ（補足資料）

[framing.md](framing.md) §粒度の定義（文字編集）が定義する **P1 行
「単一行の文字編集」** について、オーナーの理解を深めるための補足資料。
**意思決定文書ではない。** 粒度の正本は framing.md、API・設計の確定は
後続フェーズの ADR が行う。本資料の役割は、(1) 自前エディタの成熟段階の
全体像、(2) 責務単位の分解と M4 での扱い、(3) 「重さ」の中心がどこに
あるか、を先に見えるようにすることである。

## 0. 前提 — なぜ「完成部品を借りてくる」選択肢がないか

Windows には完成した編集部品（Win32 の EDIT / RichEdit、WinUI の
TextBox）が存在するが、Wasamo はこれらの埋め込みを取らない:

- Wasamo の部品は Windows.UI.Composition の視覚ツリーへ直接描画される
  （[architecture.md](../../../docs/architecture.md) の Text 部品と同じ
  基盤）。既製部品は子ウィンドウ（HWND）として載るため、Composition の
  描画内容との重なり順を制御できない（いわゆる airspace 問題）。最前面の
  重ね表示・clip・DPI・テーマとことごとく干渉する。
- 既製部品は自分のフォーカス・キーボード処理を持ち込む。M4 の主眼は
  「フォーカスモデルを一度で固める」ことなので、借り物のフォーカス動作が
  混在すると主眼そのものが壊れる。

したがって入力欄は自前実装が前提であり、問いは「自前で**どこまで**
作るか」になる。以下はその段階の整理である。

## 1. 自前エディタの成熟段階（D0〜D4）

段階の軸は「文字入力、特に日本語入力（IME）との接続をどこまで正式に
行うか」。表中の記号 D0〜D4 は本資料内の呼び名である。

| 段階 | 一言でいうと | 文字入力の経路 | 日本語入力（IME） | 評価 |
|---|---|---|---|---|
| **D0. 表示 + 選択だけ** | 編集できない読み取り専用 | なし | なし | エディタではなくビューア。ログ表示・読み取り専用テキスト向け。編集の AC を満たさない |
| **D1. キーイベントだけの簡易編集** | 英数字なら打てる | 生のキーイベント（WM_CHAR 相当）のみ | 既定の IME ウィンドウ経由で**確定後の文字列だけ**は届く | 見かけ上は日本語も入るが、変換中の文字列がその場に出ない・候補ウィンドウが正しい位置に出ない・IME 状態と同期しない。**AC の「IME 検証」を満たさない** |
| **D2. 旧 API（IMM32）接続** | ひととおりの日本語入力 | キーイベント + WM_IME_* メッセージ | IMM32 | 動くが、IMM32 は保守モードの旧 API で、新規実装への推奨は TSF。IME 側の新しい機能には TSF 前提のものがある。**新規の基盤としては不採用** |
| **D2'. CoreTextEditContext 接続** | UWP 系の抽象化を使う | キーイベント + CoreText の通知 | CoreTextEditContext（Windows.UI.Text.Core） | 抽象度は TSF 直実装より高い。ただしデスクトップ（Win32）アプリでの CoreTextServicesManager は Microsoft の対応表で「Windows Insider Preview ビルドのみ」とされており、WinUI を使わない Wasamo の安定基盤にならない。**不採用** |
| **D3. TSF text store 実装** | 本格路線（正攻法） | キーイベント + TSF 経由の範囲置換 | `ITextStoreACP` / TSF | Win32 系カスタムエディタの正攻法。実装は重いが、IME 互換性・将来性とも最良。**M4 の P1 行はこの路線の「単一行の部分集合」** |
| **D4. 製品級カスタムエディタ** | VS Code / ブラウザ / IDE 相当 | 完全実装 | TSF 本格対応 | 複数選択・矩形選択・双方向文字・縦書きなど。UI 部品というより下位システム。**目指さない** |

この表で重要な性質は 2 つ:

1. **D1 → D3 は段階的に深くなるが、途中に「そこで完成」と言える段が
   ない。** D1 は変換中の表示が成立せず、D2 は旧 API、D2' は基盤が
   不安定。日本語入力を製品品質で扱える最初の段が D3 であり、だからこそ
   AC（[_roadmap.md](../../_roadmap.md) §M4）は「minimum editable text
   widget; **required by IME verification**」と TSF 検証を目的として
   名指ししている。
2. **キーイベント処理だけでは日本語入力に足りない。** IME が有効な間、
   変換を伴う入力はキーイベントの列としては届かず、IME が消費する。
   アプリ側が変換中の文字列・下線・候補ウィンドウ位置を正しく扱うには、
   入力基盤（TSF）との双方向の取り決めに参加する必要がある。

## 2. 責務単位の分解と M4 での扱い

D3 路線を採ったとき、入力欄は次の責務の束になる。右端の列が M4 の
P1 行（単一行）での扱い。framing の P1 行の構成 1〜6 はこの表の
「必須」群を粒度定義として束ねたものである。

| 構成要素 | 最小責務 | 主な API / 技術 | M4 P1 行での扱い |
|---|---|---|---|
| テキスト保持 | 文字列・選択範囲・編集操作の適用。位置は UTF-16 符号単位で TSF とやり取り | 自前のデータ構造 | **必須**。単一行なので行構造は持たない（1 本の文字列 + 選択範囲） |
| 配置計算 | 文字位置の測定 | DirectWrite（IDWriteTextLayout） | **必須（縮小）**。折返し・行分割は不要。単一行の測定と、はみ出し時の水平オフセットのみ |
| 描画 | 字形・選択背景・カーソル・変換中の下線 | DirectWrite + Direct2D（既存 Text 部品と同系の CompositionDrawingSurface） | **必須** |
| 位置判定 | 座標 → 文字位置、文字位置 → 矩形 | IDWriteTextLayout の hit test API | **必須**。クリックでのカーソル配置・ドラッグ選択・IME 候補位置の 3 つが全部ここに乗る |
| キーボード編集 | 矢印・Backspace / Delete・Home / End・ショートカット | ランタイムのイベント配送（M4 フォーカスモデル） | **必須**。フォーカスを持つ部品への配送そのものが M4 の設計対象 |
| 文字入力 | 確定文字を編集操作へ変換 | 直接入力はキーイベント、変換を伴う入力は TSF の範囲置換として届く | **必須** |
| IME 合成 | 未確定文字列の表示・下線・確定・取消 | `ITextStoreACP` + 合成通知（ITfContextOwnerCompositionSink）+ 表示属性 | **必須**。AC の中心 |
| IME 候補位置 | 候補ウィンドウを正しい画面座標へ出す | GetTextExt（文字範囲 → 画面矩形） | **必須**。DPI・ウィンドウ座標変換と絡む |
| 選択・カーソル | 範囲・カーソル矩形・追従スクロール | 自前 + TSF へ公開（GetSelection / SetSelection） | **必須**。利用者向け操作を削っても、内部モデルは TSF が要求する |
| 書き戻し | 編集結果を宣言された状態へ戻す | 双方向束縛（[host-state-boundary.md](../../../docs/notes/host-state-boundary.md) と一体） | **必須**。Wasamo 固有の接続点 |
| クリップボード | コピー / 切り取り / 貼り付け | Win32 クリップボード（`CF_UNICODETEXT`） | **必須（縮小）**。文字列のみ。貼り付けに含まれる改行の単一行化はフェーズ ADR |
| 元に戻す（undo / redo） | 編集履歴と合成入力の整合 | 自前 | **含めない**。TSF の技術要件ではなく製品期待。M5 以降 |
| アクセシビリティ | 読み上げ・テキスト範囲の公開 | AccessKit（UIA provider 実装を肩代わり） | **必須（経路が特殊）**。自前で UIA provider を書くのではなく、AccessKit へ意味木とテキスト状態を供給する。テキスト範囲対応の到達度はフェーズで検証 |
| 国際化テキスト | サロゲートペア・書記素クラスタ・双方向文字・縦書き | DirectWrite のクラスタ境界 | **部分必須**。カーソル移動・削除は書記素クラスタ単位（絵文字・結合文字を割らない）— 単一行でも避けられない。双方向文字の完全対応・縦書きは含めない |

単一行の前提で**丸ごと消える**責務もある: 行分割・折返し、上下の
カーソル移動、縦スクロール、複数矩形の選択描画。これらは framing の
P4 行（複数行の文字編集）に属し、載せない場合のコストはゼロに近い
（framing §粒度の定義〔文字編集〕）。

## 3. 「重い」の内訳 — D3 の実装で何が難しいか

D3 が「重いが正攻法」と言われる理由を、単一行の範囲に絞って分解する:

- **ロック規約（RequestLock）** — `ITextStoreACP` は「IME がテキストを
  読み書きする間、アプリ側が内容を変えない」ことを同期 / 非同期の
  ロックで取り決める。再入（IME からの呼び出し中にアプリが編集する等）の
  扱いを誤ると壊れ方が分かりにくく、実装の初期で最も事故りやすい部分。
- **変更通知の整合** — 利用者のキー操作・貼り付け・ホストからの
  書き込み（双方向束縛）でテキストが変わったら、AdviseSink 経由で
  IME 側へ通知する。「TSF を通らない変更」の通知漏れが典型的な不具合源。
  ホスト状態境界（書き戻し・ホスト書き込み）と設計が交差するのは
  ここである。
- **座標の橋渡し** — GetTextExt は文字範囲を**画面座標の矩形**で返す
  必要がある。部品ローカル座標 → ウィンドウ → 画面、および DPI 変換を
  正しく通す。M4 の DPI 対応（モニターごと）と絡む。
- **検証の形** — 変換中の下線や候補ウィンドウ位置は、静止画 1 枚では
  偽装と区別できない。実 IME（Microsoft 日本語 IME）での操作 +
  スクリーンショット解析 + 陽性対照、という GUI 証拠の規約
  （CLAUDE.md §Testing rules、
  [verification-environments.md](../../../docs/notes/verification-environments.md)
  Obs 4）に沿った検証設計が要る。

## 4. まとめ — M4 の P1 行は「D3 の単一行部分集合」

- 経路の選択: **TSF 直実装（D3）**。D1 は AC を満たさず、D2（IMM32）は
  旧 API、D2'（CoreText）は Win32 デスクトップで基盤が不安定、D4 は
  目指す対象ではない。
- D3 の全体から、(1) 単一行前提で消えるもの（行分割・上下移動・
  縦スクロール・複数矩形選択 → P4 行）、(2) 技術要件でなく製品期待の
  もの（undo / redo など → M5 以降）を除いた集合が、framing の P1 行の
  構成 1〜6 に一致する。
- 残る重さの中心は、ロック規約と変更通知の整合（ホスト状態境界との
  交差点）、候補ウィンドウの座標橋渡し（DPI との交差点）、書記素
  クラスタ単位のカーソル操作、の 3 つ。いずれも後続フェーズの ADR の
  主要論点になる見込み。
