拒否する側にいた。もう 1 つは **2 つのゲートの一致**で、片側ずつ緑にしても

carry-forward の取りこぼし（`focus-group` 側の振る舞い）も同じ形で、
`focus_role` の**呼び出し元**を辿らずに、自分が変えた**関数**の側だけを
見て「振る舞いは足していない」と書いた。監査可能 artifact は、
**自分の意図ではなく変更そのものから導く**ときにだけ監査可能である。

3 層目は **一般化の根拠数**である。T3 の CF-3 は `Box` で測って
「per-kind 規則は無い」と書き、その一文が T8 の plan に入り、私の start
gate まで来た。私自身も 7 kind の容器リストを作るとき、`Grid` と `ZStack`
を確かめずに「container なら通る」と書きかけた。救ったのは規律ではなく、
たまたま probe に 11 kind 全部を入れていたことである。

4 層目は **委任の粒度**である。subagent は仕様どおりに実装しテストも
足したが、「到達不能な腕を様式のために残す」判断をした。これは仕様の
外側にある**規律の適用**であり、指示に書いていなければ従われない。
今回は lead の読解で拾えたが、拾えなければ分岐表に「テストの無い分岐」が
1 行載っていた。

### 計画仮説・前提の問い直し（オーナーと）

- **close gate の分岐表・副作用列挙は、diff から作る。** 「足すつもり
  だったもの」から作ると、まるごと新規の関数の内側の腕が落ちる。
- **「振る舞いを足さない」と書くときは、変えた関数ではなく
  その呼び出し元まで辿る。** 値域を広げただけでも、呼び出し元が
  production のメッセージ経路なら振る舞いは変わる。
- **2 つのゲートを持つ規則を足す task は、両方を 1 つの入力に通すテストを
  最低 1 本持つ。** 本 phase では §4.9 / §4.12 / §4.16 が既に two-gate 形を
  採っているので、これは新しい規則ではなく**既存の形に対する検証義務**の
  明文化である。
- **「どの kind でも」「どこでも」と書く主張は、代表 1 つで一般化しない。**
- **独立レビューは効いた。** 本 task で見つかった 2 件（分岐表の穴・
  carry-forward の穴）は、どちらも lead 自身の artifact の穴であり、
  自己点検では出なかった。branch/test-focused lane を「full review より
  軽い」と読むのではなく、**書いた本人以外が diff から表を作り直す**ことが
  中身である、と読み直したい。

### 反証可能な是正テスト

以後の task の **start gate に 1 行**を足す（T1 の「新しい store / 単位 /
座標系」、T2 の「消す性質を pin しているテスト」、T3 の「次の task に要求
する evidence を 1 回構築したか」、T4 の「依拠する否定的予測を 1 回測ったか」、
T5 の「またいで保持する識別子の寿命」に並べる）:

「**この task が足す規則はゲートをいくつ持つか。2 つ以上なら、それら全部を
1 つの入力に通すテストを最低 1 本持っているか。**」

反証条件: 以後の task で「片方のゲートだけ通る／落ちる」不一致が
見つかったら、この是正は効いていない。

**close gate に 2 行**:

「**分岐表を diff から作り直したか。まるごと新規の関数については、
その内側の腕まで数えたか。**」
反証条件: レビューまたは後続 task が「テストの無い分岐」を見つけること。

「**この task が広げた関数の呼び出し元を辿ったか。『振る舞いは足して
いない』は、呼び出し元まで見て初めて言える。**」
反証条件: 後続 task が「T6 以降で挙動が変わっていた」と測ること。

## マージゲート

- **Review lane**（[implementation-gates.md §4](../../../procedures/implementation-gates.md)）:
  **branch/test-focused review**。preamble の予測どおりで、start gate で
  確認し close gate で再確認した —— checker / loader の追加であり、
  その成果物そのものが reject 分岐である。runtime の構造変更ではない
  （寿命を持つ新しい store も、メッセージ腕の戻り経路の変更も、第 2 の
  書き手も無い）し、描画される物が無いので GUI 証拠の lane にも当たらない。
  `focus_role` の拡張は、関数の形・呼び出し元・単一導出という性質が
  変わらず**値域だけが広がる**ため構造変更に当たらない —— ただし
  値域が広がると**呼び出し元の振る舞いは変わる**（項目 1 (c)）。
- **実施状況**: 実装は subagent（Sonnet）が 2 段（checker / runtime）で
  著作し、レビューは task lead が各段の差分に対して実施。subagent の
  報告のうち検証可能な主張は lead が独立に測り直した ——
  テスト総数は clean rebuild 後に再実行して確認、
  到達不能な診断腕は lead の読解で検出して型で消し、
  `dismiss` の述語が「容器であること」を見ていなかったのを lead が
  是正してテスト 2 本を追加、
  変異証人 8 本はすべて lead が入れ、**ファイルから読み戻して変異の
  存在を確認してから**走らせ、revert 後も再読（`check.rs` は
  `git diff --stat` が空になることでも確認）した。
  **加えて、コードを書いていない別 subagent による独立の
  branch/test-focused review を実施**し、指摘 4 件のうち 2 件を
  コード（`6d77dae`）、2 件を記録（`ff351b8`）で是正した。
  レビューの指摘 1 件は lead が呼び出し箇所を読んで訂正した上で
