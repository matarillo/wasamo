# T7 レトロスペクティブ

タスクブランチ: `feat/m4-phase-2-t7`（`feat/m4-phase-2` = `850cb64` から作成）

T6 が与えた 2 つの注釈に、実行時の振る舞いを付けた。スコープは
**部分木が現れたこと自体で入る**（復帰先を捕捉し、フォーカスを中へ移す）、
**消えたこと自体で出る**（復帰が構造的後継に優先する）。グループの中では
矢印キーがメンバ間を動き、Esc は入っているスコープ宛の要求に変わる。
スパイクの足場（`focus_spike`・`__focus_spike`・override map）は撤去した。

plan は本 task を「グループ走査・スコープの出入り・seam・dismissal・
スパイク撤去」と framing していたが、着手前の実測で **3 つの bullet が
仕事の場所を外していた** ことが分かり、加えて **plan にない前提条件が
1 つ** 出た —— 保持される `FocusId` は毎回作り直す projection の座標で
しかなく、modal stack の entry は実行時で最も寿命の長い保持 id になる。
座標系を先に作らなければ、entry / exit は「黙ってノードの名前が変わる鍵」
の上に建つことになる。

### 自己分析（どの層が外れたか）

外れた層の 1 つめは **「規範文の一文を作業指示として読む」** ことである。
規範文は *性質* を述べる。「除去前に後継を計算する」は、
「ノードの同一性は再構築を越えない」という理由から導かれた性質であって、
「除去前に走査する機構を作れ」という指示ではない。同じ性質は
「事前に取れないものだけを事前に取る」でも満たせる。start gate の
normative-answer 表（DD-V-031）は「何が固定されているか」をよく書いたが、
「その固定が実装のどの形を要求するか」は別に測るものだと分かっていなかった。

2 つめは **close gate の「発火」の定義** である。T6 の是正で、分岐表を
自分の意図ではなく diff から作るようにした。今回それは効いた（表の行は
全部実在した）。効かなかったのは、各行に書いたテストが **その分岐を
通っているか** を確かめていないことだった。「関係するテスト」と
「その分岐を発火させるテスト」は違う。とくに、production 経路が
drain Phase 2 を通る分岐は、`SendMessageW` だけの fixture では絶対に
通らない —— これはコードを読めば分かることで、テスト名を眺めても
分からない。

3 つめは **doc comment の寿命** である。T6 の close gate は
CF-T6-1 / CF-T6-5 を `focus_role` の doc comment に畳んだ。それは
当時正しい判断で、「`widget.rs` だけを読む人にも見える」という理由も
妥当だった。しかしその本文は「今こうなっている」という現在形で書かれ、
欠陥が直った瞬間に偽になる。前送りの分類 `doc-folded` は、
**記録する側**の義務しか定義していない。閉じる側の義務が要る。

4 つめは **委任の視野** である。3 回の subagent 実行はどれも「この diff で
何を足すか」の指示だった。「この変更が **他のファイルの** 何を偽にするか」
は誰の作業項目でもなかった。今回は独立レビューが拾ったが、
レビューが無ければ `widget.rs` に偽の段落が 3 つ残っていた。

### 計画仮説・前提の問い直し（オーナーと）

- **規範文は性質、実装は形。** start gate の normative-answer 表に、
  各行「その性質を満たす実装は何通りあり、どれを採るか」を測る欄が要る。
  今回はそれが無いまま fact 5 で偶然拾った。
- **close gate の分岐表は、テスト名ではなく「そのテストが通る production
  経路」を書く。** 「fixture がある」は発火の証拠ではない。
- **`doc-folded` は閉じる側にも義務を生む。** ある task が carry-forward を
  doc comment に畳んだら、それを閉じる task の作業項目に「その本文を
  現在形に直す」が入る。分類の定義（[retrospectives.md](../../../procedures/retrospectives.md)
  項目 10）は記録する側しか書いていない。
- **「この変更が偽にした主張」は diff の外にある。** 委任のたびに
  「触っていないファイルの主張を無効にしていないか」を 1 行入れる。
- **独立レビューは 3 task 連続で lead 自身の artifact の穴を見つけている。**
  T6（分岐表の穴・carry-forward の穴）、T7（未発火分岐 3・偽の主張 4）。
  自己点検では出ない層である、という観測が 2 回続いた。

### 反証可能な是正テスト

以後の task の **start gate に 1 行**を足す（T1 の「新しい store / 単位 /
座標系」、T2 の「消す性質を pin しているテスト」、T3 の「次の task に要求
する evidence を 1 回構築したか」、T4 の「依拠する否定的予測を 1 回測ったか」、
T5 の「またいで保持する識別子の寿命」、T6 の「この規則はゲートをいくつ
持つか」に並べる）:

「**この task が閉じる carry-forward のうち `doc-folded` のものはどこに
畳まれているか。閉じたらその本文を現在形に直すことを、作業項目に
書いたか。**」

反証条件: 後続 task またはレビューが「直っていない doc comment」を
見つけること。

**close gate に 1 行**:

「**分岐表の各行は、そのテストが通る production 経路まで書いたか。
drain Phase 2 やメッセージ経路を通らない fixture を『発火』と数えて
いないか。**」

反証条件: レビューまたは後続 task が「テストはあるが分岐を通らない」を
見つけること。今回 3 件見つかったので、この是正は **現時点で未達**
であり、次の task が最初の測定機会になる。
