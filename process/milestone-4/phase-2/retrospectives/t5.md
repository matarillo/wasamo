### 自己分析（どの層が外れたか）

外れたのは **「テストと変異証人で実装の正しさは担保できる」という
前提**の層である。

T4 の是正で入れた「復元変異を 1 本」は、`W1` として正しく機能した ——
fixture 群が**機能の不在**を捕まえることを示した。だがクラッシュは
機能の不在ではなく、**設計が暗黙に置いた前提（保持する識別子は次に読む
ときも同じものを指す）が破れた状態**である。実装の変異はこの層に届かない。
変異は「書いた式を壊す」道具であり、「書かなかった前提」を壊せない。

もう 1 層は計画側。`FocusId` = 投影の pre-order index という契約は
`focus_core.rs` に書いてあり、スパイク自身が「id は rebuild を生き延び
ない」と明示していた（`focus_after_removing` の doc）。それでも
**production 化する task の plan と ADR のどちらも、その含意を持ち込む
側の問題として書いていない**。同じ phase で T4 は path（境界検査つき）を
選び、T5 は index（範囲外でパニック）を選んだ —— 2 つの保持識別子が
別々の寿命規約で並んだのに、どちらの task もその比較をしていない。

### 計画仮説・前提の問い直し（オーナーと）

- **メッセージをまたいで識別子を保持する task は、start gate でその識別子の
  寿命を明示する。** 「次に読むとき同じものを指す保証はあるか。無いなら
  範囲外になるのか、別ノードを指すのか」。T4（path）と T5（index）で
  答えが違っており、T7 / T9 は 3 回目に同じ問いを踏む。
- **純ロジックの core を「実装として採用する」決定は、その core の識別子
  契約も採用している。** ADR がそこに触れないなら、production 化する task
  が start gate で補うのが持ち主として自然である。
- **変異証人の限界を規律に書く。** 実装の変異は設計の穴を測れない。
  型で表現できる不変条件は型で表現する（今回 `path()` を `Option` に
  したのがそれ）方が、規律より強い。

### 反証可能な是正テスト

以後の task の **start gate に 1 行**を足す（T1 の「新しい store / 単位 /
座標系」、T2 の「消す性質を pin しているテスト」、T3 の「次の task に要求
する evidence を 1 回構築したか」、T4 の「依拠する否定的予測を 1 回測ったか」
に並べる）:

「**この task がメッセージ／フレームをまたいで保持する識別子は何か。
次に読むとき同じものを指す保証はあるか。無い場合、範囲外になるのか
別のものを指すのか、どちらの失敗になるかを書く。**」

反証条件は明確で、以後の task で「保持した識別子の寿命」起因の欠陥が
見つかったら、この是正は効いていない。

もう 1 つ、**close gate に 1 行**:「変異証人のうち、**実装の変異ではない
もの**は何本か。0 本なら、この task の証拠は『自分の実装を見ている』こと
しか示していない。」（W1 のような復元変異、または設計前提を破る変異が
これに当たる。）
