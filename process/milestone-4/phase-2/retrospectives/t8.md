### 自己分析（どの層が外れたか）

外れた層の 1 つめは **「分岐を足さない」判断の扱い**である。
実装ゲートの罠 #4 は「足した分岐にはそれを通すテストを」と書かれており、
close gate の artifact もその形をしている。私は分岐を 1 つ *足さない* と
決め、理由を添えて記録した —— 形式としては丁寧だが、**理由が測定されて
いなかった**。「到達不能」は 1 つの経路について測れば真になってしまう
主張で、経路が 2 つあるときに壊れる。足す判断には「テストが赤くなるか」
という反証手段があるのに、足さない判断には対応するものが無い。

2 つめは **罠 #3 の artifact の読み方**である。「単一の所有者を置いた」
まで書いて、artifact として十分だと思っていた。実際に要るのは
「その所有者の出力が、間違ったときに *どこで* 赤くなるか」であり、
今回はどこでも赤くならなかった。単一所有は drift（2 つが食い違う）を
防ぐが、両側が同じ関数を通る以上、**その関数自体の誤りは対称に伝播して
不可視になる**。罠 #3 の artifact には「非対称に消費するテスト」の欄が
要る。

3 つめは **W12 と W9 が示した同じ形** —— 「効果を読むテストは経路を
拘束しない」。7 本の fixture はどれも handler が走ったことを状態から
読んでいる。それは handler が走る条件を確かめるが、**走った後に何が
起きないか**（slot に届かない、他のキーのハンドラが走らない）は
確かめない。T7 retro の是正「分岐表の各行に production 経路を書く」は
適用したが、それは *通る* 経路の話で、*通らないことを保証する* 側は
別に要る。

4 つめは **plan 項目の粒度**である。T5 が「T8 が dispatch を置く」と
書いたのに T8 の項目にその行が無かった。task 項目は
「この task が何を持つか」を書くが、**他の task が この task に送った
もの**を集約する欄が無い。start gate の再監査でそれを拾えたのは
偶然に近く（T5 節を読んだのは boundary を書くためだった）、
仕組みではない。

### 計画仮説・前提の問い直し（オーナーと）

- **罠 #4 は「足した分岐」だけでなく「足さないと決めた分岐」も
  対象にすべきではないか。** 足さない判断は、その根拠が
  「到達不能」「不要」という *否定的な主張* であり、否定的な主張は
  1 つの経路を測れば成立してしまう。close gate の #4 artifact に
  「declined した分岐と、その到達不能性を *どの経路について* 測ったか」
  の欄を足す提案。
- **罠 #3 の artifact は「単一の所有者を置いた」では足りない。**
