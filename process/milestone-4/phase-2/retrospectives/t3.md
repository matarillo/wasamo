# T3 レトロスペクティブ

タスクブランチ: `feat/m4-phase-2-t3`（`feat/m4-phase-2` = `11d0edb` から作成）

クリックの配送を「解決した対象で撃って終わり」から「対象 → 祖先の順に
歩き、最初に何かを実際に走らせた節で消費する」へ変えた。plan は本 task
を「伝播（propagation）」と framing していたが、着手前の実測で**欠けて
いたのは伝播よりも汎用配送のほう**だった — `clicked` は Button 族以外
でも checker が通し、lower も emit も loader も運んでおり、
`hit_test_click` が Button 族でなければ即 return していただけである。

もう 1 つ、T2 が前送りした前提が実測で覆った。「Button の子の上の
クリックは T2〜T3 の間だけ何も撃たない」という carry-forward が指す形は、
そもそもレイアウトに乗らない。

   閉じた。祖先側に防御チェックを書くと、罠 #4 が禁じる「発火させられ
   ない分岐」になる。**危険が述べられたら、その半分が到達可能かを先に
   導く。**

   **(d) 排出境界の「突き合わせ」は、動かすことではなく論証だった。**
   DD-001 の「dispatch ごとに 1 回、歩行の完了後」は、排出が今いる場所
   （メッセージループ境界）でそのまま満たされている。動かす案は具体的な
   危険で退けた: 排出の phase 3 はホストのコールバックを呼び、abi_spec §6

   の中で排出するとホストが `wasamo_window_destroy` を呼び、runtime が
   まだ返り値の経路で保持している `&mut WindowState` を解放できてしまう。

### 観測された事実（反証可能な signal）

- **plan が T3 の必須 evidence として書いた項目が、構築不能だった。**
  形を作る `.ui` は debug ビルドの load で abort する。plan の要求が
  実装事実によって満たせないと判明したのは本 phase で初めて。
- **T3 の中心的な主張が、plan の framing とずれていた。** plan は
  「伝播」と書いたが、赤→緑で区別されるのは**汎用配送**（Box の
  ハンドラが発火するか）で、伝播はその上の小さい半分。T8 が予測して
  いた checker 拡張は実測では**すでに存在**していた。
- **意味論の答えが ADR ではなく規範 spec にあった。** 無効 Button が
  消費するかは DD-001 / DD-002 のどちらにも書かれておらず、Moment 1 で
  先行同期した §4.8 / §4.19 に書かれていた。
- **変異証人 6 本のうち、単独の fixture だけを赤にしたのは 2 本**
  （W1・W6）。残り 4 本は複数を赤にした。producer 単位・アーム単位で
  pin が分かれている確認になった一方、W3（消費の削除）が 4 本を赤に
  したことは、evidence の重心が消費規則に寄っていることも示している。

### 自己分析（どの層が外れたか）

外れたのは **carry-forward の生成規律**（T2 側）と、それを無検査で
引き受けた **T3 の計画前提**。

T2 の close gate は「Button の子」の形について、checker・loader・spec
実例の 3 層を確認して「authorable」と結論した。確認していないのは
**その形を一度走らせること**だけである。T2 retro の是正線は
「*この task が消す性質*を pin している**既存**テストの棚卸し」を
足したが、向きが逆の穴 — 「*次の task に要求する* evidence が構築
可能か」 — は塞いでいない。T1 → T2 の学び（証拠の scale / 証拠の意味の
置き場所が 1 task ずれる）と同じ層の話で、今回は**証拠の存在可能性**が
ずれた。

もう 1 つは、Moment 1 で spec を先に同期する phase 固有の読み順の問題。
preamble は「規範テキストは Accepted 時に同期し、T13 で再検証する」と
書いているが、**実装 task が判断に詰まったときどこを読むか**は書いて
いない。ADR を読み込んで「これは新しい設計判断だ、オーナーに上げるか」
まで行きかけたのは、その読み順が明文化されていないため。

### 計画仮説・前提の問い直し（オーナーと）

- **carry-forward が次の task の「evidence 必須項目」になる場合、その形を
  1 回作って走らせてから前送りする。** 走らせられないなら、それは
  carry-forward（次の task が閉じる制約）ではなく finding（持ち主を
  決める必要のある欠陥）である。分類が違えば、受け取る task の計画も
  変わる。
- **Moment 1 を持つ phase では、実装 task の start gate に 1 行足す。**
  「この task が実装する挙動について、規範テキスト（spec）が**すでに
  答えている**文はどれか」。ADR は理由、spec は答え、という読み順を
  明示にする。
- **「この task が何を足すか」の framing 自体を start gate で測り直す。**
  T3 は「伝播を足す」と書かれていたが、実測の中心は汎用配送だった。
  compiler 側の表面がどこまで到達しているかは、実装前に 1 回 `.ui` を
  通せば分かる。

### 反証可能な是正テスト

以後の task の **close gate に 1 行**の判定を足す（T1 の「新しい store /
単位 / 座標系」、T2 の「消す性質を pin しているテスト」に並べる）:
「この task が次の task に **evidence を要求する**なら、その形を一度
構築して走らせたか。走らないなら carry-forward ではなく finding として
持ち主を決めたか。」
反証条件は明確で、以後の task で「plan が要求した evidence が構築
不能だった」が再び出たら、この是正は効いていない。

もう 1 つ: **意味論の質問は spec → ADR の順に当たる。** 反証条件は、
規範テキストにすでに答えがある事項を「新しい設計判断」として扱った
ケースが再び出たら効いていない。

### 後続タスク / オーナーへ共有すること

- **T4 は 1 件を引き取る。** クリックが木を構造的に作り替えても
  **再レイアウトは起きない**（排出のレイアウト段はメッセージループ

  しなかったキーを `DefWindowProc` に落とす」の 2 つで、後者に必要な

- **T8 は 3 件を引き取る**（CF-1 / CF-2 / CF-3）。`clicked` の作業は
