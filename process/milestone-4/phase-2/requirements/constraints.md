# M4-Phase 2 制約引き継ぎ

ワークフロー [§2.1](../../../procedures/workflow.md) のアウトプット。前
フェーズの永続記録
[M4-Phase 1 handoff](../../phase-1/implementation/handoff.md) から、本
フェーズ（**イベント配送・フォーカスモデル・汎用クリック処理** — M4 の
中心フェーズ）に効く制約を切り出し、本フェーズの論点・範囲・検証方針に
合わせて組み直す。単純な写しではなく、各項目に「Phase 2 でどう効くか」と
**採否**を付す。あわせて、handoff より古い残件のうち本フェーズで発火する
もの（M3-Phase 7 の反応的な排出の残件）を §先行フェーズの残件の点検で
拾う。

Phase 2 の前提（[plan.md](../../plan.md) M4-Phase 2 行）:

- **マイルストーンの重心。** 配送モデル（三相 capture / target / bubble か、
  対象のみ + 高水準シグナルか）を選び、フォーカスの保持場所と走査を確定し、
  **構造非依存のモーダルフォーカス範囲**を定義する。キーボードとマウスの
  入力をそのモデルに載せ、Button 以外への汎用クリック処理と項目ごとの
  ハンドラ（ハンドラ位置での item / index 参照）を出荷する。
- **ADR Accepted の前に、動くものでの実証（スパイク）が必須。** 走査の
  中核（木 + スコープ注釈 → 次のフォーカス先）を Win32 非依存の純ロジック
  として切り出して単体テストで固定し、イベント経路は既存材料を組んだ
  機構検証用の最小 fixture で通す。fixture は公式部品として公開しない。
- **消費者は A（写真ギャラリー）**: サムネイルクリックでライトボックスが
  開く、Tab 走査、Esc で閉じる、← → で前後、ZStack の枝のままのモーダル
  閉じ込め。
- **本フェーズの ADR Accepted フリップが、予備（stretch）取り込みの
  再評価点**でもある（[plan.md](../../plan.md) §Cross-phase dispositions 3）。

## 1. 当たり判定の幾何の出どころ — レイアウト由来の矩形キャッシュが本フェーズに着地する（**採用 — 中心論点の入力**）

[Phase 1 handoff](../../phase-1/implementation/handoff.md) の前送り表の
第 1 行が、本フェーズを名指しで着地先にしている: **Visual からの幾何の
読み戻しをやめ、レイアウト時に各ノードの確定 DIP 矩形をキャッシュする**。
発火の合図は「イベント配送モデルがレイアウト由来の当たり矩形を要すること、
または DIP 建ての最小ヒット領域」で、いずれも本フェーズで見込まれる。

現物の再確認（2026-08-04、[widget.rs](../../../../wasamo-runtime/src/widget.rs)）:

- `hit_test_click` / `update_hover` は今も **Visual の `visual_rect`
  読み戻し**を走査根の倍率で割って DIP に戻す形であり、判定は「最初に
  当たった Button 族の `clicked_fn` を発火」という M3 由来の最小経路の
  まま。
- **当たり判定経路の 2 つの変換は今日は相殺している**（T5 の記録）:
  ポインタ座標は `wnd_proc` で割られ、`visual_rect` 読み戻しも割られる。
  幾何の出どころが Visual 木である限り両者は対称で、行 9 の変換の欠落を
  試験で区別できない。**本フェーズが幾何の出どころをレイアウトに変えた
  瞬間、この相殺は消え、読み戻し側の変換が実荷重になる**。
- 走査根 1 つの除数という規則は**公開入口の前提条件であって実行時が維持
  する不変量ではない**（T5）。部分木から入る当たり判定は誤る。レイアウト
  由来の矩形キャッシュ案はこの行そのものを消す。

**Phase 2 でどう効くか:** 幾何の出どころ（レイアウト由来キャッシュか、
Visual 読み戻しの継続か）は、本フェーズの当たり判定の判断項目の中心的な
比較軸である。前フェーズは方向を推奨しているが結論は先取りしない —
ただし移行するなら**混在状態（ある経路はキャッシュ、ある経路は読み戻し）を
残さない**ことが、Phase 1 の DD-M4-P1-002 が単一パス監査で買った性質の
継承条件になる。

**採否:** **採用（判断項目の入力 + 移行時の全数監査義務）**。

## 2. イベントの受け口は DIP で確定済み、そして設置者はまだゼロ（**採用 — 配送モデルと綴りの入力 + ABI 制約**）

T5 の記録: `WindowState` の callback 受け口 6 個のうち座標を運ぶ 4 個
（resize + ポインタ 3 個）は **DIP の `f32`** に確定済み。そして
**設置者（installer）は現在ゼロ**であり、最初にこれを繋ぐホスト向けの面
または ABI 関数が、この単位を出荷 API として固定する。「ホストは倍率を
知る必要がない」（DD-M4-P1-004）が DIP を正しい側にしている。

**Phase 2 でどう効くか:** 本フェーズのハンドラは DSL 側（`.ui` の
ハンドラ）が第一の消費者であり、既存の C ABI シグナル経路（`clicked` の
シグナル登録）が第二の消費者である。計画は **M4-Phase 7 をマイルストーン
唯一の ABI 面のフェーズ**と定めている（Phase 1 と同じ緊張）。本フェーズが
汎用クリックやフォーカス変化をホストへ通知する**新しい ABI 関数**を要すると
判断した場合は、[DD-V-026](../../../cross-milestone/decisions/plan-revision-discipline.md)
の 2 段階目の改訂を提案してからでなければ入れない。既存のシグナル登録
経路の**語彙を増やす**だけなら署名は動かず、この線に触れるか否かの判定は
ADR に明記する。

**採否:** **採用（設計制約 — 座標を運ぶ面はすべて DIP。新 ABI 関数は
基本線として足さない）**。

## 3. ハンドラの状態書き込みは同期 drain の契約に乗る（**採用 — 配送モデルの入力**）

本フェーズのハンドラ（クリック・キー操作）は状態を書き、その書き込みは
M3-Phase 7 が閉じた**同期・非バッチの drain 契約**（同一呼び出し内で
静止状態まで排出する）に乗る。[M3-Phase 7 handoff](../../../milestone-3/phase-7/implementation/handoff.md)
の該当残件を点検した:

- **循環検出の方針は先送りのまま**（残件 1）。再発の合図は「生成された
  部分木の effect が状態を書く面」。本フェーズの項目ごとのハンドラは
  **利用者起点の書き込みであって effect ではない**ため文言上は発火しない
  が、`for` の中のハンドラが collection 自身を書き換える形（クリック →
  自分の載る部分木の再生成）は近傍にある。ADR で発火の有無を明示する。
- **effect 間の順序の同着は先送りのまま**（残件 2）。観測可能な順序契約を
  本フェーズが導入しない限り発火しない。
- **除去済み部分木への非配送の保証**は intake の検討ケース 6 の未決事項
  そのもの — 条件表示の枝がハンドラ実行の途中で消えた場合の規則は、
  配送モデルの判断項目が持つ。

加えて現物確認（2026-08-04、[emit.rs](../../../../wasamo-runtime/src/emit.rs)）:
Phase 1 handoff が carry-forward として残していた「**排出経路のレイアウト
入口の誤り**（`run_layout` を使いルートを Fill 強制しない）」は、**T3 の
F-23 で修正済み**である — 排出のレイアウト段は現在
`run_layout_as_window_root_at_scale` を呼ぶ。本フェーズのクリック
ハンドラは property 書き込みごとにこの経路を通す（実行時で最も忙しい
再レイアウト経路になる）ため、この修正済みの形が Phase 2 の土台である。
退行させない。

**採否:** **採用（配送モデルの判断項目の入力 + 修正済み事実の確認）**。

## 4. レイアウト境界と Visual 書き込みの単一性（**採用 — 実装制約**）

T1〜T6 で確立し phase-end まで維持された 3 つの単一性。本フェーズは
入力・フォーカスの状態変化で再レイアウトと表示更新を頻発させる側なので、
全部が正面から効く:

- **幾何と倍率のキャッシュの書き手は 1 つ**（`commit_scale_recursive`）。
  部分木を付け替える・再実体化するあらゆる経路は、最終的にその窓の倍率で
  production レイアウト境界に入る。`lib.rs::window_add_widget` は意図的に
  境界の外（呼び手なしの掃除候補）。ラベルの幾何は `sync_visuals` にしか
  ないため、**レイアウトを通らない取り付け経路は Button 族のラベルを
  描かない**。
- **Composition への幾何の書き込みは `sync_visuals` の 1 パスだけ**。
  本フェーズがフォーカスの視覚表示（フォーカスリング等）や押下状態の
  表示を足すとき、`SetOffset` / `SetSize` を別の場所に書いた瞬間、
  DD-M4-P1-002 の監査が閉じた性質が黙って壊れる。
- **`ButtonData.label_size` の書き手は 2 つで、どちらも `label_text` と
  `SizeConstraint::Fixed` を同時に書く**。handoff は「第 3 の経路 —
  M4-Phase 2 のイベントモデル — がラベルを変えるなら 3 点を揃えて書く」
  ことを名指しで求めている。

**採否:** **採用（実装制約。実装ゲートの構造的副作用の列挙と呼び出し箇所
監査の対象）**。

## 5. 倍率変化後のポインタの合成更新（**採用 — 配送モデルの下位論点**）

Phase 1 は「倍率変化の後にポインタ位置の合成更新（synthesised pointer
update）を行うか」を、**hover の正しさがリサイズをまたいで問題になるなら
M4-Phase 2 のイベントモデルで**と送っている。hover / pressed 状態の持ち主と
enter / leave の規則は本フェーズの配送モデルが定義するので、この問いは
その下位論点として吸収する（採る・採らないの結論は先取りしない。採らない
場合も理由を ADR に書く）。

**採否:** **採用（判断項目の下位論点）**。

## 6. ギャラリーのツールバーは狭い幅で重なる（**部分採用 — 証拠の基準線として。Row の意味論は Phase 4 へ送る提案**）

T11 のオーナー実機で観測: クライアント幅が内容より狭いとき、ツールバーの
`Row` は折り返しも切り詰めもせず**重なって描かれる**。倍率非依存
（100% でも起きる）で、幅起因。handoff の着地先欄は「M4-Phase 2
（layout / event work）」を名指ししている。

**Phase 2 でどう効くか — 2 つに分けて扱う:**

- **証拠の基準線として（採用）:** 本フェーズの目視証拠はギャラリーを
  題材に撮る。内容より狭い幅のフレームには既知の重なりが写り込み、
  本フェーズの退行と誤読されうる。捕捉は内容が収まる幅で行うか、狭い幅を
  使う場合は既知事象として明記する。
- **`Row` のはみ出し意味論の決定として（不採用 — 送り先の変更提案）:**
  「子が収まらないとき Row が何をするか」はレイアウトの設計判断であり、
  本フェーズの主題（配送・フォーカス）と結合しない。ギャラリーの
  レイアウト面を進める **M4-Phase 4（スクロール・スクロールバー・実画像）
  へ送る**のが自然である。handoff の名指しからの変更になるため、
  **framing のオーナー合意事項として明示的に確認する**（黙って変えない）。

**採否:** **部分採用（証拠基準線）+ 送り先変更の提案（オーナー確認待ち）**。

## 7. GUI 証拠の捕捉の規律（**採用 — 検証方針の前提**）

Phase 1 が測って確定した捕捉の規律。本フェーズの証拠は「操作の前後」を
対で撮る対話的なものになるため、全行が効く:

- **捕捉の前に release のワークスペース全体ビルド**（F-21）。ホスト
  パッケージ単体のビルドは古い実行時を抱えた新しい DLL を**静かに緑で**
  作る。実行時を変えた後の証拠はすべて
  `cargo build --release --workspace` を先行させる。
- **1 枚は基準線にならない**（F-33）。同一コミットでも文字ピクセルは
  最大 13/チャネルの揺れを持つ。変更の両側で**複数回**捕捉し、
  [compare-frames.ps1](../../phase-1/implementation/evidence/compare-frames.ps1)
  は既定で「差分があれば非零終了」。小差分を通すのは実行者が記録する
  判断であり、ゲートが継承する既定ではない。参照フレーム集合は
  [evidence/README.md](../../phase-1/implementation/evidence/README.md) が
  名指しするものを使う（T3 の `after/` は 2 フレーム古い）。
- **フレーム集合の形は同一性の一部**（T10）。過去の窓矩形 6 枚集合と
  クライアント矩形 1 枚集合は比較不能。比較はクライアント矩形どうしで。
- **観測側も DPI 対応を宣言する**（F-48）。非対応の観測プロセスが
  ギャラリーの窓矩形・画面座標・カーソル位置を読むと、倍率で割られた
  仮想値が返る。「数字がそれらしい」は検査にならない。座標を読む捕捉
  スクリプトは Per-Monitor 第 2 版を宣言してから読む。
- **陽性対照には「一致すべき側の脚」も要る**（F-50）。「A と B が違う」
  だけでは任意の 2 物で満たせる。性質が効きえない場所（例: モーダルが
  閉じている状態での同じクリック）で**区別が付かない**ことを対で示す。
- **一覧の写しはその行の証拠でしかない**（F-51）。プロセス一覧や UI の
  スクロール表示を証拠に使うときは、写っている行についてだけ主張する。

**採否:** **採用（検証方針の前提。framing の検証方針の節が具体化する）**。

## 8. テスト fixture とガードの規律（**採用 — 検証方針の前提**）

- **ガードより先に OS を触るテストは、その成功を前提にしない**（F-49）。
  試みて結果を捨て、実際に効いている状態を読み戻し、すべての assert を
  ガードの内側に置く。危険なのは API ではなく「危険に気づいて同じ段落で
  無害と予測する」推論の型。
- **`0x80070005` の衝突**（T9）: `tests/common/mod.rs` の「Compositor
  なし」判定は status 先行の 2 条件で成立している。宣言失敗を status で
  返す・素の last-error 照合に緩める変更は、全 Compositor テストを
  **黙って緑で** skip させる。本フェーズが統合テストの共通ヘルパに触る
  場合は、この 2 条件を崩さない。
- **fixture は前提状態を自分で確立する**（F-47）。生成直後のフォーカスが
  どこにあるか・hover が無いことを、継承せず読み戻して固定してから
  操作を注入する。
- **冷えた target での `cargo test --workspace` は先行ビルドが要る**
  （F-5。`LNK1356` が実測の症状）。
- **窓の外形とクライアントは同じ倍率で結ばれない**（T4 実測）。寸法を
  assert する統合 fixture はクライアント基準で書く。
- **純ロジックの red-test 義務**（[DD-V-029](../../../cross-milestone/decisions/dd-v-029-pure-logic-red-test-obligation.md)）:
  丸め・単位変換・**境界条件**の純ロジックを足すとき、誤実装が名指しの
  テストを落とすことを示す。本フェーズでは当たり矩形の縁の含否
  （境界条件）が該当見込み。走査中核は義務の narrowed scope 外だが、
  一般形（緑・同一観測）は uncodified のまま — 変異証人を置くかは
  タスク側の裁量で記録する。

**採否:** **採用（検証方針とテスト設計の前提）**。

## 9. プロセスの学び（**採用 — プロセス前提**）

M3〜Phase 1 から継承する作業の規律。再導出せず適用の確認だけ行う:

- 仕様同期は 2 回（設計同期 = Accepted 時、実装同期 = クローズ時）。
  文書コミットはレビューの関心単位。全マージはオーナー明示承認、push は
  別ゲート。
- **実装ゲート**（[implementation-gates.md](../../../procedures/implementation-gates.md)）
  を task の開始と終了の両方で読む。**開始時のゲート選択は予測であり
  古くなる**（F-53）— task が作る予定のなかった script / fixture を
  作ったら、終了時に選択を再決定する。
- **書かれた人手手順からの逸脱は「何を壊したか」で切り分けて記録する**
  （F-52）。手順を書く時点で、観測の可否だけでなく**その配置が組めるか**
  を確かめる。
- 何かを測った task は、close gate の中で task list 全体を読み直す
  （再監査の規律 — M4-Phase 1 T2 で再発）。

**採否:** **採用（プロセス前提）**。

## 10. 本フェーズに効かない handoff 項目（**不採用 — 理由と持ち主の記録**）

| handoff 項目 | 持ち主 | 不採用の理由 |
|---|---|---|
| ホストから見える倍率・作業領域の照会 | M4-Phase 7 の ABI 波、または Phase 8 | 本フェーズは DIP で完結し、ホストに長さを渡す新面を開かない |
| ウィンドウごとに異なる倍率 | M4-Phase 8 | 2 つ目のウィンドウが生まれるまで発火しない |
| クライアント寸法基準のウィンドウ意味論 | M4-Phase 8 / AC11 | 新属性として来る。本フェーズは触れない |
| 画面座標への変換（IME のカーソル矩形・最前面層の配置） | M4-Phase 5 / 6・Phase 9 | 本フェーズの座標はクライアント DIP で閉じる |
| 解像度に応じた画像資産の選択 | M4-Phase 4 | 画像は本フェーズに存在しない |
| 整数ピクセル吸着・文字描画品質・カスタムタイトルバー・非零 clip inset・倍率依存の measure | 保留（各行の合図どおり） | いずれの合図も本フェーズで鳴らない |
| 幻影型の長さ newtype（`Dip<T>` / `Px<T>`） | 予約（採用条件つき） | 単位混同の欠陥が実際に再発したら。予測では入れない |
| `WM_GETDPISCALEDSIZE` | 予約 | 自分のサイズを提案するフェーズ（Phase 8 / AC11）向け |
| 中間投影のフレーム提示の未解問題（F-34） | `WM_DPICHANGED` の手順順序に触れる task | 本フェーズは倍率変化の手順に触れない。フレーム水準の計測器を持ち込む予定もない |
| `wasamo-sys` の紛らわしい警告（F-54）とビルドグラフの修理 | 未スケジュールの工事 | 本フェーズの仕事ではない。指示と再発合図は handoff に記録済み |
| 別機体へ届く一式（Rust ホストの絶対パス焼き込み） | 別機体へ渡す task が読む | 本フェーズのオーナー確認は開発マシン上で行う見込み。別機体が要る場合に読み直す |
