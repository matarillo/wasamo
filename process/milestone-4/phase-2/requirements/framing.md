# M4-Phase 2 フレーミング

**状態:** accepted（オーナー合意済み 2026-08-05。合意事項 ①〜⑦ 全項目
承認 — ⑥ を除き「現在の情報に基づく仮説」としての承認であり、新しい
発見があれば見直す）
**対象フェーズ:** M4-Phase 2（イベント配送・フォーカスモデル・汎用クリック
処理）— **M4 の中心フェーズ**

開発プロセス（[workflow.md §2](../../../procedures/workflow.md)）に従い、本
ドキュメントは設計判断（ADR）を書く前に**オーナーと方向性を合意する**ための
入力資料です。個々の判断の選択肢・比較・推奨はここでは確定しません。ここで
固めるのは、Phase 2 は何を届けるフェーズなのか、どの問いを判断項目（DD）
として予約するのか、どこまでを担当範囲とし、どこからを後続フェーズへ送るのか、
そして検証のしかたです。

前フェーズからの制約引き継ぎ（プロセスの §2.1）は
[constraints.md](./constraints.md) で済んでおり、本ドキュメントはその上に
乗ります。捕捉・fixture・ビルド順・プロセスの規律はそちらの §7〜§9 を参照し、
ここで再説明しません。

> **用語の最小限の補足（初出のみ）:**
> - **イベント配送（event routing）** … OS から届いた入力（クリック・キー
>   押下など）を、どの部品のどのハンドラに、どの順序で渡すかの規則。
> - **三相配送（capture / target / bubble）** … Web の DOM が採る形。根から
>   対象部品へ降りる相（capture）、対象部品の相（target）、対象から根へ
>   戻る相（bubble）の 3 段階で、途中の部品にも横取り・後処理の機会を与える。
> - **対象のみ + 高水準シグナル** … 相を持たず、当たった部品（または
>   フォーカスされた部品）のハンドラだけを呼ぶ形。`clicked` のような
>   意味づけ済みの通知（高水準シグナル）を主な面にする。
> - **当たり判定（hit-testing）** … ポインタの座標から、どの部品が対象かを
>   解決すること。
> - **フォーカス走査（traversal）** … Tab / Shift+Tab / 矢印キーで
>   フォーカスを次の部品へ動かすときの、次はどれかの規則。
> - **モーダルなフォーカス範囲（modal focus scope）** … 開いている間、
>   フォーカスと入力をその部分木の内側に閉じ込める範囲。本マイルストーンは
>   これを「層の性質」ではなく**任意の部分木に付けられる構造非依存の概念**
>   として一度だけ定義する。
> - **scrim（暗幕）** … 重ね表示の背面に敷く全面の半透明な `Box`。下の
>   兄弟へのクリックを遮る役を担う。

### 合意事項 ② の補足 — 何の話で、決めないと何に困るか

**今の仕組み。** クリックが来たとき、実行時は「どの部品に当たったか」を、
画面表示用のオブジェクト（Composition の Visual）に**現在の位置と大きさを
問い合わせて**判定している（読み戻し）。レイアウトは各部品の位置を計算
しているのに、その結果を保存しておらず、表示側に書き込んだ値を読み
戻している。

**これまで困らなかった理由。** 判定が「Button の上か」だけと単純で、かつ
Phase 1 の変換が対称 — ポインタ座標を倍率で割る操作と、読み戻した位置を
倍率で割る操作が**偶然打ち消し合って**いる — ため、間違いがあっても
見えなかった。

**Phase 2 で困ること（具体例）。**

1. **高 DPI でだけ出る入力の不具合を作り込みうる。** 本フェーズで
   重なり順や DIP 建ての判定規則（例: 最小ヒット領域）を 1 つでも
   入れると、上の打ち消しが崩れる。誤ると「**150% のモニターでだけ、
   サムネイルをクリックすると隣が開く／右端のボタンだけ反応しない**」
   という不具合になる — 開発機の 100% では出ず、テストも緑のまま。
   Phase 1 が描画側で 1 フェーズかけて潰した種類のバグを、入力側に
   残す形になる。
2. **重なり順・遮蔽の判定が検証しづらいロジックになる。** 「暗幕が下の
   兄弟へのクリックを遮る」「どのサムネイルか」を OS の表示オブジェクト
   への問い合わせの繰り返しで書くと、Win32 なしで検証できない。
   レイアウト由来の矩形なら「矩形の集合 + 重なり順 → 対象」の純ロジック
   になり、単体テストで固定できる。
3. **読み戻しには測定済みの罠がある。** 除数は「走査の根の倍率」で
   なければならず、部分木から入ると黙って誤る（Phase 1 T5 実測）。型でも
   テストでも守れない前提条件で、Phase 1 handoff は「レイアウト由来の
   矩形にすればこの行ごと消える」と記録している。

**決めてほしいこと（yes / no）。** DD-002 の比較を「レイアウト時に各部品
の確定矩形（DIP）を保存し、当たり判定はそれを読む」を**基本線**として
組んでよいか。Phase 1 の合意 ②③ と同じ「この方向で判断項目を組む」で
あって結論の先取りではない — 読み戻し継続案も比較に残し、覆す場合は
理由を ADR に明記する。

## Phase 2 の主題（何を届けるフェーズか）

本フェーズは「クリックが効くようにする」フェーズではない。**M4 の主眼
そのもの — フォーカスモデルを一度だけ確定する — を実行するフェーズ**で
ある。入力欄（Phase 5）・IME（Phase 6）・複数ウィンドウ（Phase 8）・
最前面層（Phase 9）・読み上げ（Phase 11）は、すべて本フェーズが決める
モデルの消費者として後から来る。だから本フェーズの ADR は、対話面が
まだ小さいうちに書かれる — 5 つの部品面が暗黙の期待を積み上げた後では
なく（[plan.md](../../plan.md) の順序根拠）。

主題は 3 点に分解できる。

1. **配送モデルの選択は一度しかできない。** 三相（capture / target /
   bubble）か、対象のみ + 高水準シグナルか（intake 検討ケース 6）。
   これは後から足せる種類の決定ではない — ハンドラの綴り・伝播の停止・
   scrim の遮蔽・Esc の消費など、本フェーズの他の全論点がこの上に乗る。
   選択の基準は M3-Phase 7 で合意した規律のとおり製品としての価値が主軸
   であり、「Web と同じだから」も「実装が軽いから」も単独では決め手に
   しない。
2. **フォーカスモデルは M5 の消費者の分まで固める。ただし部品は作らない。**
   グループ内の矢印移動（Tab はグループを 1 停止と扱う）と、フォーカスと
   活性項目の分離（開いた一覧の中で動くのは活性項目だけ）は、M5 の公式
   部品一式が要求する意味論である。これを紙ではなく動くもの（走査中核の
   純ロジック + 機構検証 fixture）で Accepted 前に実証する。仮の
   RadioButton / ComboBox は作らない — グループの `.ui` 綴りは M5 の
   設計判断であり、既成事実化しない。
3. **モーダルなフォーカス範囲は構造非依存に定義し、本フェーズでは
   ZStack の枝で実証する。** 「最前面層に載ったものが閉じ込める」という
   層の性質にしない。A のライトボックス（ZStack + 条件表示のまま）が
   第 1 の消費者、B4（思いつきメモ）の改名ダイアログ（最前面層、
   Phase 9）が第 2 の消費者、読み上げ（Phase 11)が第 3 の消費者。
   Phase 9 が概念を変えないと使えないなら、それは本フェーズの ADR の
   supersede であり、局所の特例ではない（マイルストーン終了基準 3）。

主題の裏返しとして、**本フェーズが変えないもの**も主題の一部である:
レイアウトの計算方法と座標空間の定義（Phase 1 の契約をそのまま消費する。
当たり判定は DIP で行う）、部品の種類（1 つも足さない）、配置の意味論、
ABI の関数一覧（合意事項 ⑦）。

## 再検討しない前提（確定済み）

- **M4 はフォーカスモデルのマイルストーンであり、本フェーズがその中心**
  （[M4 framing.md](../../requirements/framing.md) F1、
  [plan.md](../../plan.md)）。
- **モーダルなフォーカス範囲は構造非依存の概念として設計し、設計は一度・
  実装は三度**（[plan.md](../../plan.md) §Cross-phase dispositions 1。
  オーナー合意済み 2026-07-28）。分割の是非は再審議しない。
- **A のライトボックスは ZStack のまま**（M4 framing §粒度の定義
  〔重ね表示〕、intake 義務 3 の解決）。最前面層への載せ替えは検討しない。
- **スパイクは ADR Accepted の前に必須。fixture は公式部品として公開
  しない**（[plan.md](../../plan.md) M4-Phase 2 行）。
- **座標空間は Phase 1 の契約に従う** — レイアウトと当たり判定は DIP、
  物理ピクセルを知るのは境界だけ、座標を運ぶ受け口は DIP の `f32`
  （[DD-M4-P1-002 / 004](../../phase-1/decisions/preamble.md)）。
- **M4-Phase 7 がマイルストーン唯一の ABI 面のフェーズ**（[plan.md](../../plan.md)）。
  本フェーズは基本線として ABI 関数を足さない（合意事項 ⑦ の手続き
  つき）。
- **比較の主軸は製品としての価値**（M3-Phase 7 合意の継承。過剰設計は
  引き続き失敗モード）。
- **文字入力とショートカットの優先順位は M4-Phase 6 が決める**
  （[plan.md](../../plan.md)。本フェーズには入力欄が無く衝突が存在
  しない）。

## 論点一覧（DD 番号の予約）

本フェーズの ADR（`decisions/preamble.md` + 判断項目ごとに 1 ファイル）が
担う問いを列挙し、**DD-M4-P2-001〜005 の番号を予約**する。各判断項目の
選択肢・比較・推奨は §3 設計判断で書く。ここでは「何を判断するか」と
「なぜ本フェーズの問いか」だけを固定する。

計画が指定した必須論点（[plan.md](../../plan.md) M4-Phase 2 行）の
割り付け: 配送モデルそのもの = DD-001、`Button.clicked` と汎用クリックの

### DD-M4-P2-001 — イベント配送モデル

**問い:** OS からの入力（マウス・キーボード・タッチ）を、どの部品のどの
ハンドラに、どの順序で届けるか。三相（capture / target / bubble）か、
対象のみ + 高水準シグナルか（intake 検討ケース 6）。

**Phase 2 の問いである理由:** 本フェーズの他の全論点（遮蔽・Esc の消費・
汎用クリックの綴り）と後続 5 フェーズの全消費者がこの上に乗る、
マイルストーンの土台の決定。

**下位の問い:** 高水準シグナルの語彙（`clicked` / `pressed` / `hovered`
のどこまでか）と、生のポインタイベント面（`pointer_down` 等）を出すか
出さないか（出さない判断も可 — intake の分類記録どおり）。キーイベントの
届け先（フォーカスされた部品か、ウィンドウ / フォーカス範囲か —
DD-003 / 004 と交差）。ハンドラの状態書き込みと同期 drain 契約の結合
（[constraints §3](./constraints.md)。M3-Phase 7 残件の発火有無の明示を
含む）。除去済み部分木への非配送の保証（条件表示の枝がハンドラ実行中に
消える場合）。pointer capture（押下したまま部品外へ出る drag）・hover の
enter / leave・pressed 状態の持ち主。タッチのメッセージ（`WM_POINTER`
系か、マウスへの昇格で足りるか）と Phase 1 の DIP 変換への載せ方。
倍率変化後のポインタ合成更新を採るか（[constraints §5](./constraints.md)）。

### DD-M4-P2-002 — 当たり判定と汎用クリック処理

**問い:** ポインタ座標から対象部品をどう解決するか（幾何の出どころ・
重なり順・遮蔽）、どの部品が当たり判定に適格か、既存の `Button.clicked`
シグナルと汎用クリック処理はどう関係するか。

**Phase 2 の問いである理由:** intake 義務 4 の着地先（必須論点）。かつ
Phase 1 handoff の前送り第 1 行（レイアウト由来の当たり矩形）が本フェーズ
を名指ししており、相殺している 2 変換が実荷重に変わる転換点
（[constraints §1](./constraints.md)）。

**下位の問い:** 幾何の出どころ — レイアウト時の確定 DIP 矩形キャッシュ
（基本線、合意事項 ②）か Visual 読み戻しの継続か。移行時の全数監査
（読み戻し箇所ゼロの確認）と、走査根の除数の前提条件の解消。ZStack
兄弟間の遮蔽 — 全面の scrim `Box` が下の兄弟へのクリックを遮る、重なり順
を考慮した判定（M4 framing §粒度の定義〔重ね表示〕の設計条件 2）。
当たり判定の適格性 — 視覚を持つ部品は全て対象か、明示の属性が要るか。
`Button.clicked` の既存意味論（最初に当たった Button 族が発火・disabled
は不発）の保存または再定義。disabled / hover / pressed / selected 状態と
の関係。項目ごとの解決（クリックがどのサムネイルかを特定し item / index
をハンドラへ渡す仕組みの実行時側）。DIP 建ての最小ヒット領域を M4 で
持つか（持たない判断も可、理由を記録）。

### DD-M4-P2-003 — フォーカスモデル（保持場所と走査）

**問い:** フォーカスをどこに保持し、何がフォーカス可能で、Tab /
Shift+Tab / 矢印キーでどう走査するか。

**Phase 2 の問いである理由:** マイルストーン主眼の中核。M5 の公式部品
一式が要求する 2 つの意味論（グループ走査、フォーカスと活性項目の分離）
まで含めて、ここで一度だけ固める（M4 framing §粒度の定義〔フォーカス
モデル〕）。

**下位の問い:** フォーカスの保持場所（`WindowState` 単位 — Phase 8 の
ウィンドウ間フォーカスを塞がない形の責務）。フォーカス可能の適格性
（部品固有か、宣言か）。走査順序の源（木の順か、レイアウトの視覚順か）。
グループ化の意味論 — 矢印はグループ内、Tab はグループを 1 停止と扱う
（綴りは fixture 限定・非規範。`.ui` の正規の綴りは M5）。フォーカスと
活性項目の分離（開いた一覧で動くのは活性項目、フォーカスは本体に留まる）。
クリックとフォーカスの関係（クリックでフォーカスが移るか）。初期
フォーカス。フォーカスされた部品の視覚表示（フォーカスリング相当）と
`sync_visuals` 単一パスとの整合（[constraints §4](./constraints.md)）。
フォーカス保持部品が条件表示で消えた場合の戻し先（intake 検討ケース 4 の
設計論点。DD-004 の復帰規則と一体で決める）。Win32 の `WM_SETFOCUS` /
`WM_KILLFOCUS` との関係（ウィンドウ活性とフォーカスの分離）。

### DD-M4-P2-004 — 構造非依存のモーダルフォーカス範囲

**問い:** 任意の部分木に付けられる「モーダルなフォーカス範囲」を何と
定義し、閉じ込め・Esc・復帰・読み上げの規則をどう固定するか。

**Phase 2 の問いである理由:** AC1 の名指しの構成要素であり、「設計は
一度、実装は三度」の**設計の一度**がここ（[plan.md](../../plan.md)
§Cross-phase dispositions 1）。Phase 9・Phase 11 は本判断項目の消費者に
なる。

**下位の問い:** 範囲の定義（何を持つ概念か: フォーカス走査の閉じ込め・
背面の入力遮断・復帰情報）。走査の閉じ込め（Tab が範囲内で巡回する）。
背面の不活性化と DD-002 の遮蔽（scrim）との役割分担 — クリックの遮断は
遮蔽か範囲か。**Esc の消費** — モーダル範囲が Esc を消費する規則（必須
論点）と、「Esc で閉じる」動作の持ち主（範囲の組み込みか、アプリの
ハンドラか）。閉じたときのフォーカスの戻し先（開いた時点の記録か、
構造からの導出か。条件表示で開閉するライトボックスでの具体形）。**読み
上げのモーダル性はフォーカス範囲に付く**（必須論点 — 規則をここで固定、
実装は Phase 11）。範囲の入れ子（M4 で必要か。B4 のダイアログ・イン・
メニューの見込みだけ確認し、不要なら理由を記録）。第 2 構造（最前面層）
が概念を変えずに消費できることの見通しと、変えるなら supersede という
手続きの明記。

### DD-M4-P2-005 — DSL の綴り（汎用ハンドラと項目ごとのハンドラ）

**問い:** Button 以外へのクリックハンドラ、`for` の中の item / index を
ハンドラ位置で参照する綴り、モーダル範囲の付与、キー操作（Esc・← →）の
ハンドラを、`.ui` にどう綴るか。IR / コンパイラ / 実行時に何が要るか。

**Phase 2 の問いである理由:** 本フェーズで唯一の規範 DSL 面。項目ごとの
ハンドラは M3 が reject し「M4 の項目ごとの対話で着地」と先読みした面の
再開（[M3 handoff](../../../milestone-3/handoff.md)）。仕様同期（フェーズ
終了基準 4）の対象を確定する判断でもある。

**下位の問い:** 汎用クリックの綴り（`Box { clicked => … }` を Button の
綴りと同形にするか）。ハンドラ位置での item / index 参照の綴りと checker
規則（束縛位置の既存規則との整合。M3 の reject 理由の解消の明示）。
モーダル範囲の付与の綴り（属性か、部品か、暗黙か — ライトボックスの
ZStack の枝にどう付くか）。キー操作の綴り — Esc / ← → をアプリの
ハンドラとして綴るか、範囲・部品の組み込み動作にするか（宣言的
ショートカット面の一般機構化は本フェーズの AC ではない — intake 分類の

要ると出た場合のみ）。IR の表現（シグナル名の語彙・ハンドラ表の拡張）と
`wasamoc` の検査・lowering。C ABI シグナル経路の語彙拡張の範囲
（合意事項 ⑦ の線内）。`docs/dsl_spec.md` のどの節を動かすか。fixture
限定綴りが規範面に漏れないことの確認。

## 検証方針

[constraints.md](./constraints.md) §7〜§9 の規律（ビルド順・複数回捕捉・
クライアント矩形・観測側の DPI 宣言・陽性対照の一致脚・fixture の前提
確立・red-test 義務）を前提に、本フェーズ固有の分担を仮確定する。

### 純ロジックの単体テスト

- **走査中核**: 木 + スコープ注釈 → 次のフォーカス先。Tab / Shift+Tab の
  順序、グループ 1 停止、グループ内矢印、フォーカスと活性項目の分離、
  モーダル範囲内の巡回、範囲が消えた時の戻し先。スパイクの (a) が
  そのまま資産になる。
- **当たり判定の解決**（レイアウト由来キャッシュ案の場合): 矩形集合 +
  重なり順 → 対象部品。縁の含否は**境界条件**なので
  [DD-V-029](../../../cross-milestone/decisions/dd-v-029-pure-logic-red-test-obligation.md)
  の red-test 義務が正面から当たる（誤実装が名指しのテストを落とすことを
  示す）。
- **コンパイラ側**: ハンドラ位置の item / index 参照の checker 規則
  （受理と reject の両側）、新しい綴りの IR 往復。M3 の共有 lexer
  ヘルパの規律（entry-flag が variant 分岐へどう効くかを reject test で
  ピン留め）を継承する。

### Windows 統合テスト（mock なし）

- 合成メッセージ（`WM_LBUTTONDOWN` / `WM_KEYDOWN` 等）を `wnd_proc` へ
  注入し、live な部品状態（フォーカス位置・ハンドラ発火・閉じ込め）を
  読み戻す。**限界の明示**: 合成は経路の正しさを示すが、実機の入力装置と
  OS の配送を証明しない — 実物の側は可視の証拠とオーナー目視が担う
  （Phase 1 R6 と同じ分担を ADR に明記）。
- fixture は前提状態（初期フォーカス・hover なし）を読み戻して確立して
  から注入する（F-47 の型）。skip 防護は `tests/common` の status 先行
  2 条件を崩さない（constraints §8）。CI では黙って skip せず落ちる。

### 可視の証拠と陽性対照

アシスタントの自動証拠は起動 + 捕捉 + 画像解析。単一フレームで済む対照は
無く、**操作の前後の対**が単位になる。各対照に「一致すべき側の脚」
（F-50）を置く:

| 対照 | 撮り方 | なぜ対照になるか / 一致すべき側の脚 |
|---|---|---|
| **A. クリック配送と項目の同一性** | サムネイル N をクリック → ライトボックス、別の実行でサムネイル M をクリック | 開くだけなら「どこかをクリックしても開く」誤実装と区別できない。N と M で**異なる内容**（束縛値の差）が出ることが項目ごとのハンドラの証拠。一致脚 = 同じ N を 2 回クリックした結果は一致する |
| **B. フォーカス走査の順序** | Tab を 1 回・2 回・3 回押した各フレーム + Shift+Tab での逆行 | 「フォーカスがどこかへ動く」ではなく**期待した次の停止**に動くことが証拠。逆行が順行の逆順であることが順序の実在を示す。一致脚 = 操作なしの 2 フレームは一致する |
| **C. モーダルの閉じ込めと遮蔽** | ライトボックス開で背面ボタンをクリック（不発）+ Tab 巡回が内側で閉じる | 「背面が反応しない」だけでは背面が空の誤実装と区別できない。**一致脚 = ライトボックス閉で同じ座標のクリックが発火する**ことを対で示す |
| **D. Esc の消費** | ライトボックス開で Esc → 閉じる。閉のとき Esc → 何も起きない | 閉じる動作と消費規則の両方を示す。一致脚 = 無関係のキーでは閉じない |

捕捉はクライアント矩形・内容が収まる幅（ツールバー重なりの写り込み
回避）・release ワークスペースビルド先行・変更の両側複数回、を
constraints §6〜§7 のとおり適用する。

### タッチ

合意事項 ⑥ の決定に従う。基準線 = 合成タッチ注入で配送経路（タッチ →
DIP 変換 → 当たり判定 → ハンドラ）の統合テスト。実機がある場合のみ
オーナー目視を足し、無い場合は「実機のタッチを証明しない」限界を記録
して AC1 のタッチの半分を閉じる。いずれの場合も
[verification-environments.md](../../../../docs/notes/verification-environments.md)
の分類への追記が要るかを実装計画で確認する。

### オーナー目視（human-visible smoke）

対話の実感 — クリック・Tab・Esc・← → が「効く」こと — は開発マシン上の
オーナー操作で確認できる（Phase 1 と違い別機体は不要の見込み。タッチ
だけが ⑥ に依存する）。手引きは実装計画で書き起こし、対象コミットとの
結合を確認してから使う。

### 仕様の同期（別種の検証）

`docs/dsl_spec.md` に汎用クリック・項目ごとのハンドラ・モーダル範囲の
綴りを、外部の実装者が再現できる水準で記述する（フェーズ終了基準 4）。
ABI は合意事項 ⑦ の線内なら `docs/abi_spec.md` の関数一覧を動かさない
（シグナル語彙の記述だけ確認）。改訂履歴は追記式。fixture の綴りは仕様に
**載せない**ことが確認項目になる。

### 判断項目と検証手段の対応（仮確定）

| 判断項目 | 主たる検証手段 |

- **呼び出し箇所の監査** — 幾何の出どころを移行する場合、`visual_rect`

  触れるか。
- **目視の陽性対照** — 上の対照 A〜D。

## リスク

### R1. 中心フェーズの過大範囲で ADR が停滞する

[plan.md](../../plan.md) の第 1 リスクそのもの。配送・当たり判定・走査・
モーダル・綴りを一度に閉じようとして停まる。

**軽減:** スパイクが最難の意味論（グループ走査・分離）を Accepted 前に
動くもので答えさせる。ADR は**後続フェーズの規則を実装せずに固定して
よい**（読み上げモーダル性がその模範例）。判断項目を 5 件に分割し、
依存の浅い順（001 → 002 → 003 → 004 → 005）で個別に閉じられる形にする。

### R2. fixture が事実上の部品になる

グループ走査の実証に使う fixture の綴りが規範面へ漏れ、M5 の部品設計を
既成事実化する。

**軽減:** fixture は spec・部品一覧に載せず、綴りは fixture 限定の
非規範と明記（計画の確定事項）。仕様同期の確認項目に「fixture 綴りが
`docs/dsl_spec.md` に無いこと」を置く。

### R3. 第 2 構造で概念が破れる

Phase 9 の最前面層が本フェーズのモーダル範囲を変えないと使えず、
マイルストーンの主張（一度だけ確定）が弱まる。

**軽減:** DD-004 の下位の問いに「第 2 構造の見通し」を明示し、top-layer
の設計空間ノート（[top-layer-overlays.md](../../../../docs/notes/top-layer-overlays.md)）
を Accepted 前に読み合わせる。破れた場合の正しい手続き（supersede、
局所特例の禁止）を ADR 本文に書いておく。

### R4. 幾何の出どころの移行が混在状態で止まる

レイアウト由来キャッシュへ移す途中で、一部の経路だけが読み戻しのまま
残ると、相殺の消えた変換が高倍率でのみ誤る — Phase 1 が閉じた種類の
欠陥の再導入になる。

**軽減:** 移行するなら全数監査（読み戻し箇所ゼロの確認）を実装ゲートの
成果物にする（constraints §1）。混在を許す中間コミットを作らない task
分割を実装計画で組む。

### R5. ← → の証拠が Phase 3 の面に依存して薄くなる

前後移動の見え方（キャプション・選択強調）が述語式待ちのため、本フェーズ
の証拠が「動いたはず」に痩せる。

**軽減:** §スコープの縫い目の注記どおり、M3 で表現可能な束縛値の変化で
対照を組む。それでも薄いと判断したら、証拠の完成を Phase 3 の消費者
スライスへ明示的に送る（黙って弱い証拠で閉じない）。

### R6. タッチの検証が環境待ちで最後に残る

Phase 1 の R3 と同型。タッチの証拠形だけが決まらず、AC1 の一部が閉じない
まま終盤に残る。

**軽減:** 合意事項 ⑥ で証拠の形を**フェーズ計画の時点で**決める。実機が
無い場合の閉じ方（合成注入 + 限界の明記）まで先に合意しておく。
