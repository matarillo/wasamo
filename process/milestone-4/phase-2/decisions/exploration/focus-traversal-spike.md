# M4-Phase 2 pre-ADR spike — 走査中核と機構検証 fixture

[framing.md](../../requirements/framing.md) 合意事項 ⑤ が要求する、ADR
Accepted **前**のスパイク。目的は判断項目の比較に実測を供給することで
あって、Phase 2 の実装を先取りすることではない。

**問いの出どころ:** [plan.md](../../../plan.md) M4-Phase 2 行の
「Pre-ADR spike (required before the ADR is Accepted)」と
[M4 framing.md](../../../requirements/framing.md)
§粒度の定義（フォーカスモデル）。M5 の公式部品一式が消費者として要求する
2 つの意味論を、**紙ではなく動くもので**実証することが趣旨である。

## 1. スパイクが答える問い

判断項目に紐づけて列挙する。各問いは「何が測れたら答えたことになるか」を
持つ。

| # | 問い | どの DD へ | 答えたと言える条件 |
|---|---|---|---|
| Q1 | 走査中核は「木 + スコープ注釈 → 次のフォーカス先」だけで表現できるか。Win32 も Composition も要らないか | DD-003 | 中核が OS 型を 1 つも参照せずコンパイルし、単体テストが通る |
| Q2 | 「Tab はグループを 1 停止と扱い、矢印はグループ内を動く」を実現するのに、グループ内の**直前のフォーカス位置の記憶**は要るか。要るならその状態は中核の内側か外側か | DD-003 | 記憶なし実装で「グループを出て戻ると先頭に戻る」再現、記憶あり実装で保持を確認 |
| Q3 | フォーカスと活性項目の分離は、フォーカス位置とは**別のポインタ**を要するか。それはスコープに属するか部品に属するか | DD-003 | 開いた一覧で矢印を押してもフォーカス位置が動かず活性項目だけ動くことを assert |
| Q4 | モーダルなフォーカス範囲は、走査の閉じ込めとして**同じ機構**（スコープ注釈）で表現できるか。専用の分岐が要るか | DD-004 | modal 注釈だけを足して Tab の巡回が部分木内で閉じることを assert（走査アルゴリズムに modal 専用分岐を書かずに） |
| Q5 | フォーカスを持つノードが条件表示で消えたとき、戻し先は中核が決められるか。何の情報が要るか | DD-003 / DD-004 | 消えた後の次のフォーカス先が決定的で、必要な入力が列挙できる |
| Q6 | 中核の入力（注釈つき木）は、実在の `WidgetNode` 木から作れるか。作るのに `WidgetData` の変更が要るか | DD-005 / DD-002 | 実 Compositor 上の木から注釈木を組み、キー入力相当を通して部品状態が変わることを headless で確認 |
| Q7 | Esc の消費は走査の問題か、別の経路か | DD-004 | 中核が Esc をどう扱うか（扱わないなら誰が扱うか）を実装で決めた形で示す |

**このスパイクが答えない問い（明示）:** 配送モデルの選択そのもの
（三相か対象のみか）は走査中核の外側にあり、スパイクでは決めない —
中核は「どのノードが次か」を答えるだけで、イベントがどう届くかを知らない。
当たり判定の幾何（DD-002 の中心）も別問題であり、本スパイクは扱わない。

## 2. Start gate（着手時の失敗モード選定）

[implementation-gates.md §1](../../../../procedures/implementation-gates.md)
に従い、**手を動かす前に**選定を記録する。

```
- [ ] #1 semantic migration   - [x] #2 side effects   - [x] #3 parallel data   - [x] #4 branch tests
- [x] #5 carry-forward        - [x] #6 root cause     - [ ] #7 GUI positive control
```

**選定した罠と、それが本スパイクで何を意味するか:**

- **#2 構造的な副作用の列挙** — フォーカスの移動は単一の代入ではない。
  1 回の移動が触りうる派生状態（グループ内の記憶、スコープの活性項目、
  以前のフォーカス保持者の状態）を**列挙してから**書く。列挙を怠ると
  「Tab は動くがグループへ戻ると位置を忘れる」型の欠陥が入り、しかも
  素朴なテストは緑のままになる。
- **#3 派生データのずれ** — グループ内の記憶（roving 位置）は
  フォーカスポインタと**並行する索引**である。フォーカスを動かす同じ
  プリミティブの中で原子的に更新しなければ、2 つの真実が生まれる。
  本スパイクの Q2 はこの罠そのものを測る問いでもある。
- **#4 書いた分岐にはそれを発火させるテスト** — 中核は縁の分岐を持つ
  （フォーカス可能ノードなし / スコープが空 / 最後の停止からの巡回 /
  フォーカス保持者の消失）。各分岐に**直接それを発火させる**テストを
  1 本ずつ置く。加えて巡回の折り返しは**境界条件の純ロジック**なので
  [DD-V-029](../../../../cross-milestone/decisions/dd-v-029-pure-logic-red-test-obligation.md)
  の red-test 義務が正面から当たる — 誤実装を実際に走らせてテストが
  落ちることを示す。
- **#5 前送り** — スパイクの発見は ADR の入力であると同時に、実装
  タスクが踏んではならない不変条件を生む。再発の合図つきで報告書 §5 に
  記録する。
- **#6 決定的な失敗を flake にしない** — 発火した場合のみ。合成入力の
  テストは環境依存が少ないが、Compositor を使う fixture 側は
  `tests/common` の skip 判定に乗る（skip は失敗ではない）。

**非該当と判断した罠と理由:**

- **#1 意味論の移行** — 本スパイクは `WidgetData` / IR / スキーマの
  variant も field も変えない。走査中核は**自前の注釈木**の上で動く
  （[CLAUDE.md §Testing rules](../../../../../CLAUDE.md) が許す
  mirror 構造の適用 — 実型に注釈を足すと Phase 2 の表現を先取りして
  しまうため、あえて分離する）。fixture 側も実 `WidgetNode` 木を
  **読む**だけで型を変えない。**再判定の条件:** スパイクの途中で
  `WidgetData` か IR に手を入れる必要が出たら、その時点で #1 を選び
  直す（[F-53](../../../phase-1/implementation/handoff.md) — 着手時の
  選定は予測であり失効する）。
- **#7 目視の陽性対照** — 本スパイクの成果物は GUI の描画ではなく、
  純ロジックの戻り値と headless で読み戻す部品状態である。フォーカスの
  **見え方**（フォーカスリング等）は Phase 2 の実装タスクが持ち、
  そこで #7 が発火する。**再判定の条件:** スパイクが画面に何かを
  描いて主張する形に変わったら選び直す。

**レビュー lane:** 本スパイクのコードは production の呼び出し側を持たない
（走査中核は呼び手ゼロで着地。[T2 の `dip_scale.rs`](../../../phase-1/implementation/log.md)
と同じ形）ため、runtime の構造変更にも schema 移行にも GUI 証拠にも
当たらない。よって **branch/test-focused review**（罠 #4 の検査）が
lane。ただし**スパイクの結論は ADR の比較に入る**ので、その結論は ADR
自身のレビュー（[design-decision-review.md](../../../../procedures/design-decision-review.md)）
で多視点にかける。「コードは軽い lane、結論は重い lane」という分割を
明示的に選んでいる。

## 3. 進め方

1. **走査中核**（`wasamo-runtime/src/focus_core.rs`）— Win32 非依存の
   純ロジック。呼び出し側を作らない。単体テストで Q1〜Q5・Q7 を固定。
2. **機構検証 fixture** — 実 `WidgetNode` 木（既存部品の合成）に対して
   注釈木を組み、キー入力相当を中核へ通し、部品状態の変化を headless で
   読み戻す。Q6 を答える。**公式部品は 1 つも作らない**（framing の
   確定事項）。
3. **報告書**（本文書 §4 以降）— 測定結果と DD 別の含意、前送り。

### 4.0 「緑」を証拠にしないための変異

単体テスト 22 本が緑になった時点で言えたのは「22 本 ok」だけである。
誤実装 8 種を実際に当て、**どのテストが赤になるか**を測った。

| # | 誤実装 | 赤になったテスト |
|---|---|---|
| M1 | Tab 前進が巡回せず飽和する | `tab_wraps_at_both_ends_of_the_stop_list`, `entering_a_modal_scope_confines_tab_to_it` |
| M2 | Tab 後退が巡回せず飽和する | `tab_wraps_at_both_ends_of_the_stop_list` |
| M3 | `set_focus` がグループの記憶を書かない | `a_group_remembers_the_member_that_was_focused` ほか 1 |
| M4 | 停止の列挙がグループの中へ降りる | `tab_treats_a_group_as_one_stop` ほか 2 |
| M5 | 未入場のモーダル範囲を普通の入れ物として列挙する | `an_unentered_modal_scope_is_not_reachable_by_tab` ほか 2 |
| M6 | 活性項目の移動がフォーカスも動かす | `arrows_move_the_active_item_without_moving_focus` |
| M7 | 除去時に復帰点を見ずに構造的な後継へ落ちる | `removing_the_entered_scope_restores_rather_than_succeeds` |
| M8 | グループの記憶を在籍確認なしで信じる | `a_group_memory_pointing_at_a_gone_member_falls_back_to_the_first` |

巡回（M1 / M2）は境界条件の純ロジックなので
[DD-V-029](../../../../cross-milestone/decisions/dd-v-029-pure-logic-red-test-obligation.md)

fixture 側も同じ扱いをした。投影が注釈を無視する誤実装を当てると、
注釈に依存する 3 本が赤になり、**注釈を渡さない 1 本
（`the_widget_kind_alone_cannot_express_the_group_or_the_scope`）は緑の
まま**である。後者が

### 4.1 各問いへの答え

| # | 答え | 根拠 |
|---|---|---|
| **Q1** | **表現できる。** 中核は `windows` 型を 1 つも参照せず、`FocusTree`（親子 + 役割 + enabled）と `FocusState`（フォーカス位置 + 3 つの派生ストア）だけで閉じる | `focus_core.rs` は `use windows` を持たず、単体テストは Compositor を要さない |
| **Q2** | **要る。しかも中核の内側。** グループ内の直前位置を覚えないと、出て戻ったとき先頭に戻る。記憶は `FocusState` が持ち、**フォーカスを書く唯一のプリミティブ `set_focus` の中で原子的に**書く | M3（記憶を書かない誤実装）が `a_group_remembers_the_member_that_was_focused` を赤にする。`focused` は private なので、記憶を書かずにフォーカスだけ書く呼び出しは書けない |
| **Q3** | **別のポインタが要る。持ち主は「部品」であり範囲ではない。** 活性項目は一覧ノードを鍵とする表に載り、フォーカスとは独立に動く | M6 が `arrows_move_the_active_item_without_moving_focus` を赤にする。範囲に載せる必要は最後まで出なかった |
| **Q4** | **同じ機構で表現できる。走査アルゴリズムにモーダル専用の分岐は 1 つも無い。** 閉じ込めは「列挙の根を変える」だけ（`traversal_root`）。ただし **2 つの機構が混在していた** — §4.2 の S-3 | `tab` / `collect_stops` に modal 分岐なし。閉じ込めは `traversal_root` の 1 行 |
| **Q5** | **決められる。ただし「除去の前」に計算しなければならない。** 加えて、**閉じるモーダルの復帰先は木から導出できない** | `focus_after_removing` は除去前の木を要する。id は再構築で作り直されるため（条件表示 / `for`）、除去後に古い id を照合できない |
| **Q6** | **作れる。ただし今の `WidgetData` は 6 役割のうち 2 つしか供給できない** | `spike_focus_role` が返せるのは `Stop`（Button 族）と `Container` だけ。`Group` / `ModalScope` / `ActiveItemList` / `ActiveItem` は表現が存在しない |
| **Q7** | **走査の問題ではない。** 中核は「どの範囲が Esc を取るか」だけを答え（`esc_target`）、**閉じるとは何かは呼び出し側**。中核は木を変えない | `esc_target` は最内の入場中の範囲を返す純粋な照会。fixture では呼び出し側が「退場」と解釈している |

### 4.2 スパイクが見つけたこと（S-1〜S-4）

- **S-1 — 「Tab が 1 停止」と「矢印が中を動く」は 1 つの注釈で足りる。**
  `Group` 役割ひとつで、列挙は自身を 1 回出して降りない・矢印は在籍
  一覧の上を巡回する、が両方出る。別々の概念を用意する必要はなかった。
- **S-2 — 私のテストが主張どおりの性質を検査していなかった。**
  「古くなったグループの記憶」のテストは、記憶を作った木とは**別の id
  配置**の木で評価していたため、記憶の引き当て自体が空振りし、在籍確認
  の分岐に一度も到達していなかった。M8（在籍確認を外す誤実装）が 1 本も
  赤にしなかったことで露見した。**id の再利用**（再構築で同じ id が別の
  ノードを指す）を再現する形に書き直した。緑のテストは、それが落ちる
  条件を示すまで、通っている理由を教えない。
- **S-3 — 閉じ込めと「閉じている間 Tab で入れない」は別機構だった。**
  閉じ込めはスタック由来（`traversal_root`）、「入れない」は役割由来
  （未入場の範囲を列挙しない）。当初 `enter_modal` は役割を検査して
  いなかったため、**注釈を完全に落とした投影でも fixture の閉じ込め
  assertion が通った**（投影の変異で検出）。役割検査を足して 1 つの概念に
  結び直し、拒否分岐にテストを置いた。ADR は「モーダル範囲」を 1 語で
  呼ぶが、実装上は 2 つの性質の合成であると知って設計する必要がある。
- **S-4 — fixture の決め打ち索引が 1 つずれており、それでも半分は緑
  だった。** `build_widget_tree` が返すのは根の `VStack` 自身で Window
  ノードは無い。グループ注釈は Button に、範囲注釈は内側の `VStack` に
  載っていたが、**内側 `VStack` を範囲として扱っても閉じ込めの assertion
  は通る**（中に Prev/Next が居るため）。注釈先を木から導出し、
  「注釈先は入れ物であること」を先に assert する形に直した。
  同型: [F-53](../../../phase-1/implementation/handoff.md)（着手時の予測が
  失効する）と、指し先が実物とずれても表面的には辻褄が合う型。

### 4.3 中核が意図的に答えていないこと

- **配送モデルの選択（DD-001 の中心）** — 中核は「次はどれか」しか答え
  ず、イベントがどう届くかを知らない。三相でも対象のみでも中核は同じ。
  つまり **DD-001 と DD-003 は独立に決められる**（スパイクの副産物と
  しての構造的な発見）。
- **当たり判定の幾何（DD-002 の中心）** — 座標を 1 つも持たない。
- **フォーカスの見え方** — 描画は一切しない。
- **走査順序が視覚順か木順か** — 現状は**木順**。視覚順が要るかは
  DD-003 の判断であり、スパイクは木順で足りる範囲しか測っていない。
- **フォーカス可能な入れ物** — `Stop` は走査上の葉として扱っている
  （降りない）。「フォーカスできる部品の中にフォーカスできる部品がある」
  形（M5 の一覧項目の中のボタン等）は測っていない。

## 5. DD 別の含意（ADR への入力）

| DD | スパイクからの入力 |
|---|---|
| **DD-001（配送モデル）** | 走査中核は配送モデルに依存しない（§4.3）。よって配送モデルの選択は「フォーカスをどう動かすか」の都合では決まらず、遮蔽・伝播停止・ハンドラの綴りの都合で決めてよい。**キー入力の届け先**は中核が答えを持つ（フォーカス位置、無ければ最内の範囲） |
| **DD-002（当たり判定）** | スパイクは幾何に触れていないため直接の入力は無い。ただし fixture が示したとおり、**部品の同定は ABI 経由の読み戻しで足りた** — 当たり判定の検証も「id ではなく実部品の観測可能な性質」で書ける |
| **DD-003（フォーカスモデル）** | 保持場所 = `FocusState` 1 個（ウィンドウ単位に置けば Phase 8 の per-window 化を塞がない）。**派生ストアは 3 つ**（グループ記憶・活性項目・モーダルスタック）で、うち 2 つはフォーカスと並行するのでフォーカスを書くプリミティブの内側で書く。走査順序は木順で足りた。`Stop` を葉として扱う簡略化は明示的な限界 |
| **DD-004（モーダル範囲）** | **2 つの性質の合成**（S-3）。閉じ込め = 列挙の根の差し替え、非到達 = 未入場の範囲を列挙しない。**復帰先は入場時に捕まえるしかない**（木から導出不能）。Esc は走査の問題ではなく、中核は「どの範囲か」だけ答える。第 2 構造（最前面層）は「範囲の注釈が付いた部分木」であれば同じ機構に載る見込み — 層であることを中核が知る必要はない |
| **DD-005（DSL 綴り）** | **注釈の面積が測れた**: 今の `.ui` は 6 役割のうち 2 つしか言えない。作者が書けなければならないのは最低限 **`Group`** と **`ModalScope`**（`ActiveItemList` / `ActiveItem` は M5 の部品一式が買い手なので M4 で綴りを開く必要は無い見込み）。加えて **`enabled` は既存**、**`Stop` は部品種から導出可能**。したがって M4 で新設が要る綴りは実質 2 つ |

## 6. 前送り（再発の合図つき）

| 項目 | 着地先 | 再発の合図 |
|---|---|---|
| **フォーカスを書く経路は 1 本にする** — `focused` は private で、`set_focus` がグループ記憶も同時に書く。並行データを別々に書ける入口を作らない | 実装タスク全体 | フォーカス位置を書く 2 本目の入口（部品側のショートカット、ABI からの設定）。作るなら記憶も同じプリミティブで書く |
| **モーダル範囲は 2 機構の合成であり、片方だけでも表面上動く** | DD-004 と Phase 9 | 「閉じ込めが効いている」ことだけを見る試験。役割検査か非到達のどちらかが消えても、閉じ込めの試験は緑のまま通る |
| **復帰先は入場時に捕まえる。木から導出しようとしない** | DD-004・Phase 9 | 範囲の開閉を条件表示に任せる実装。開いた瞬間を捕まえる場所が無くなると復帰先を失う |

- **#2 構造的な副作用の列挙** — フォーカス 1 回の移動が触る派生状態は
