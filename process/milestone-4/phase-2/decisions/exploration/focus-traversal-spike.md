# M4-Phase 2 pre-ADR spike — 走査中核と機構検証 fixture

[framing.md](../../requirements/framing.md) 合意事項 ⑤ が要求する、ADR
Accepted **前**のスパイク。目的は判断項目の比較に実測を供給することで
あって、Phase 2 の実装を先取りすることではない。

**問いの出どころ:** [plan.md](../../../plan.md) M4-Phase 2 行の
「Pre-ADR spike (required before the ADR is Accepted)」と
[M4 framing.md](../../../requirements/framing.md)
§粒度の定義（フォーカスモデル）。M5 の公式部品一式が消費者として要求する
2 つの意味論を、**紙ではなく動くもので**実証することが趣旨である。

---

## 1. スパイクが答える問い

判断項目に紐づけて列挙する。各問いは「何が測れたら答えたことになるか」を
持つ。

| # | 問い | どの DD へ | 答えたと言える条件 |
|---|---|---|---|
| Q1 | 走査中核は「木 + スコープ注釈 → 次のフォーカス先」だけで表現できるか。Win32 も Composition も要らないか | DD-003 | 中核が OS 型を 1 つも参照せずコンパイルし、単体テストが通る |
| Q2 | 「Tab はグループを 1 停止と扱い、矢印はグループ内を動く」を実現するのに、グループ内の**直前のフォーカス位置の記憶**は要るか。要るならその状態は中核の内側か外側か | DD-003 | 記憶なし実装で「グループを出て戻ると先頭に戻る」再現、記憶あり実装で保持を確認 |
| Q3 | フォーカスと活性項目の分離は、フォーカス位置とは**別のポインタ**を要するか。それはスコープに属するか部品に属するか | DD-003 | 開いた一覧で矢印を押してもフォーカス位置が動かず活性項目だけ動くことを assert |
| Q4 | モーダルなフォーカス範囲は、走査の閉じ込めとして**同じ機構**（スコープ注釈）で表現できるか。専用の分岐が要るか | DD-004 | modal 注釈だけを足して Tab の巡回が部分木内で閉じることを assert（走査アルゴリズムに modal 専用分岐を書かずに） |
| Q5 | フォーカスを持つノードが条件表示で消えたとき、戻し先は中核が決められるか。何の情報が要るか | DD-003 / DD-004 | 消えた後の次のフォーカス先が決定的で、必要な入力が列挙できる |
| Q6 | 中核の入力（注釈つき木）は、実在の `WidgetNode` 木から作れるか。作るのに `WidgetData` の変更が要るか | DD-005 / DD-002 | 実 Compositor 上の木から注釈木を組み、キー入力相当を通して部品状態が変わることを headless で確認 |
| Q7 | Esc の消費は走査の問題か、別の経路か | DD-004 | 中核が Esc をどう扱うか（扱わないなら誰が扱うか）を実装で決めた形で示す |

**このスパイクが答えない問い（明示）:** 配送モデルの選択そのもの
（三相か対象のみか）は走査中核の外側にあり、スパイクでは決めない —
中核は「どのノードが次か」を答えるだけで、イベントがどう届くかを知らない。
当たり判定の幾何（DD-002 の中心）も別問題であり、本スパイクは扱わない。

## 2. Start gate（着手時の失敗モード選定）

[implementation-gates.md §1](../../../../procedures/implementation-gates.md)
に従い、**手を動かす前に**選定を記録する。

```
- [ ] #1 semantic migration   - [x] #2 side effects   - [x] #3 parallel data   - [x] #4 branch tests
- [x] #5 carry-forward        - [x] #6 root cause     - [ ] #7 GUI positive control
```

**選定した罠と、それが本スパイクで何を意味するか:**

- **#2 構造的な副作用の列挙** — フォーカスの移動は単一の代入ではない。
  1 回の移動が触りうる派生状態（グループ内の記憶、スコープの活性項目、
  以前のフォーカス保持者の状態）を**列挙してから**書く。列挙を怠ると
  「Tab は動くがグループへ戻ると位置を忘れる」型の欠陥が入り、しかも
  素朴なテストは緑のままになる。
- **#3 派生データのずれ** — グループ内の記憶（roving 位置）は
  フォーカスポインタと**並行する索引**である。フォーカスを動かす同じ
  プリミティブの中で原子的に更新しなければ、2 つの真実が生まれる。
  本スパイクの Q2 はこの罠そのものを測る問いでもある。
- **#4 書いた分岐にはそれを発火させるテスト** — 中核は縁の分岐を持つ
  （フォーカス可能ノードなし / スコープが空 / 最後の停止からの巡回 /
  フォーカス保持者の消失）。各分岐に**直接それを発火させる**テストを
  1 本ずつ置く。加えて巡回の折り返しは**境界条件の純ロジック**なので
  [DD-V-029](../../../../cross-milestone/decisions/dd-v-029-pure-logic-red-test-obligation.md)
  の red-test 義務が正面から当たる — 誤実装を実際に走らせてテストが
  落ちることを示す。
- **#5 前送り** — スパイクの発見は ADR の入力であると同時に、実装
  タスクが踏んではならない不変条件を生む。再発の合図つきで報告書 §5 に
  記録する。
- **#6 決定的な失敗を flake にしない** — 発火した場合のみ。合成入力の
  テストは環境依存が少ないが、Compositor を使う fixture 側は
  `tests/common` の skip 判定に乗る（skip は失敗ではない）。

**非該当と判断した罠と理由:**

- **#1 意味論の移行** — 本スパイクは `WidgetData` / IR / スキーマの
  variant も field も変えない。走査中核は**自前の注釈木**の上で動く
  （[CLAUDE.md §Testing rules](../../../../../CLAUDE.md) が許す
  mirror 構造の適用 — 実型に注釈を足すと Phase 2 の表現を先取りして
  しまうため、あえて分離する）。fixture 側も実 `WidgetNode` 木を
  **読む**だけで型を変えない。**再判定の条件:** スパイクの途中で
  `WidgetData` か IR に手を入れる必要が出たら、その時点で #1 を選び
  直す（[F-53](../../../phase-1/implementation/handoff.md) — 着手時の
  選定は予測であり失効する）。
- **#7 目視の陽性対照** — 本スパイクの成果物は GUI の描画ではなく、
  純ロジックの戻り値と headless で読み戻す部品状態である。フォーカスの
  **見え方**（フォーカスリング等）は Phase 2 の実装タスクが持ち、
  そこで #7 が発火する。**再判定の条件:** スパイクが画面に何かを
  描いて主張する形に変わったら選び直す。

**レビュー lane:** 本スパイクのコードは production の呼び出し側を持たない
（走査中核は呼び手ゼロで着地。[T2 の `dip_scale.rs`](../../../phase-1/implementation/log.md)
と同じ形）ため、runtime の構造変更にも schema 移行にも GUI 証拠にも
当たらない。よって **branch/test-focused review**（罠 #4 の検査）が
lane。ただし**スパイクの結論は ADR の比較に入る**ので、その結論は ADR
自身のレビュー（[design-decision-review.md](../../../../procedures/design-decision-review.md)）
で多視点にかける。「コードは軽い lane、結論は重い lane」という分割を
明示的に選んでいる。

## 3. 進め方

1. **走査中核**（`wasamo-runtime/src/focus_core.rs`）— Win32 非依存の
   純ロジック。呼び出し側を作らない。単体テストで Q1〜Q5・Q7 を固定。
2. **機構検証 fixture** — 実 `WidgetNode` 木（既存部品の合成）に対して
   注釈木を組み、キー入力相当を中核へ通し、部品状態の変化を headless で
   読み戻す。Q6 を答える。**公式部品は 1 つも作らない**（framing の
   確定事項）。
3. **報告書**（本文書 §4 以降）— 測定結果と DD 別の含意、前送り。
